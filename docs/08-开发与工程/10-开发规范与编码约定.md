## 0. 本文档要解决的六件事

1. **让 Python 单栈的短板不成为事故来源** —— 架构 §11.1 已列出 5 条强制约束，本文把它们落成可检查的条目。
2. **让"追溯"不是事后补的** —— DRP-NFR-06/07 要求记录来源、版本、模型、工具、参数，这必须是编码期的硬约束，而不是上线前的补丁。
3. **让多卡/多机/多进程的边界永远只有一条** —— DCU 资源不可随意获取，所有计算必须经统一入口，禁止旁路。
4. **让离线构建成为第一性约束** —— 约束 C-1（离线交付）决定了任何"运行时联网拉依赖"的写法都是事故。
5. **让 Code Review 有可执行的检查表** —— 而不是"我觉得写得不好"。
6. **让新人 1 天内能提交一个合规的 PR** —— 目录结构、命名、提交信息、分支模型全部给出唯一解。

**不在本文档范围**：具体业务算法实现、模型内部代码风格（遵循各自上游开源项目）、前端视觉设计（见 `02-架构/06-UI交互与原型说明.md`）。

## 1. 总体工程原则

| 编号 | 原则 | 落地要求 | 违反后果 |
|---|---|---|---|
| E-01 | **类型即契约** | 全量类型标注，Pydantic v2 模型作为唯一数据边界，`mypy --strict` 必须零错误 | CI 阻断合并 |
| E-02 | **异步不阻塞** | API 进程内禁止任何 > 50ms 的 CPU 密集计算；重计算下沉到 Worker 或计算节点 | CI 有阻塞检测；Review 一票否决 |
| E-03 | **计算必经统一入口** | 所有模型推理/分子计算只能通过 `ComputeBackend` 提交（见 `09` §3），禁止在业务服务内 `import torch` | Review 一票否决 |
| E-04 | **一切可追溯** | 任务提交必须携带 `model_name/model_version/tool_name/tool_version/params_json/env_json` 与输入快照 | 数据库 NOT NULL 约束 + 单测 |
| E-05 | **离线可复现** | 禁止任何运行时外网依赖；依赖锁定到 lock 文件；镜像构建可离线重放 | CI 外网扫描阻断 |
| E-06 | **失败要可诊断** | 所有异常必须携带 `error_code` 与结构化上下文，禁止裸 `except: pass` | Review 一票否决 |
| E-07 | **数据层强制隔离** | 所有查询强制带 `project_id` 过滤，鉴权通过依赖注入，禁止路由内手写权限判断 | 单测 + 安全测试 |
| E-08 | **小步可回滚** | 单个 PR ≤ 400 行有效变更；数据库迁移必须可回滚 | Review 检查 |

> E-01~E-08 中的 **一票否决项**：E-02、E-03、E-04、E-06、E-07 共五项。这些项在迭代验收时若被发现，该迭代不计入完成度。

## 2. 仓库与目录结构

### 2.1 仓库划分（多仓 vs 单仓）

**决策：单仓（monorepo）+ 目录内多服务**，理由：

- 业务服务与模型 IO 契约（`task.json` / `result.json`）共享同一套 Pydantic Schema，跨仓会产生版本漂移（这正是 `07` §3 要避免的）；
- 团队规模有限（评审规模 ≤ 12 人），多仓会放大 CI 与依赖管理成本；
- 离线构建要求所有依赖源可控，单仓的 lock 文件管理更简单。

**风险与缓解**：单仓随迭代变大 → 用 `uv` workspace + 按域拆包（独立可发布 wheel），避免全量重装。

### 2.2 根目录结构

> **v1.1 补充：12 个逻辑模块 → 8 个部署单元**（见 `03` §3.2.1）。目录按**逻辑模块**划分，不等于部署进程数——目录不合并，但**镜像可以合并**。`pyproject.toml` 中每个部署单元对应一个 entry point：
>
> | 部署单元 | 目录组合 | 说明 |
> |---|---|---|
> | `drp-api` | `gateway/`（应用侧）+ `auth/` + `project/` + `asset/` + `target/` + `design/` | 合并为一个 ASGI 应用，内部用 httpx 走进程内调用 |
> | `drp-task-api` | `task/` + `workflow/` + `result/` | **必须与 `drp-scheduler` 共用库连接与事务边界**（`03` §3.2.2） |
> | `drp-scheduler` | `scheduler/` | 常驻无对外端口；单实例主备（leader-election） |
> | `drp-mol-index` | `mol_index/` | RDKit 重、CPU 密集，必须独立 |
> | `drp-model-registry` | `model_registry/` | 独立 |
> | `drp-gateway` | Nginx Ingress | 非 Python 进程 |
> | `drp-worker-cpu` | 无独立目录（复用 `task/` 的 consumer 入口） | 消费 RabbitMQ 做导入/导出/指纹预计算 |
> | `drp-compute-*` | `compute/models/*` | **模型镜像，不是服务** |
>
> 约束：标记为「强一致」的操作（`03` §3.2.2 共 4 项）**不得跨部署单元**；跨进程调用一律带 `X-Request-Id` 与幂等键。

### 2.3 单个服务的内部结构（强制）

以 `services/task/` 为例，**分层固定**，禁止跨层直调：

```
services/task/
├── pyproject.toml
├── Dockerfile
├── README.md                      # 该服务的职责边界与对外接口
├── src/drp_task/
│   ├── __init__.py
│   ├── main.py                    # FastAPI app 装配（中间件、异常处理器、路由注册）
│   ├── api/                       # ★ 仅薄适配层：解析请求 → 调 service → 组装响应
│   │   ├── deps.py                # 依赖注入（CurrentUser、DB Session、权限守卫）
│   │   └── v1/
│   │       ├── tasks.py
│   │       └── schemas.py         # Pydantic 请求/响应模型（对外契约）
│   ├── domain/                    # ★ 业务规则：纯函数/纯对象，不依赖 DB 与框架
│   │   ├── models.py              # 聚合与值对象
│   │   ├── state_machine.py       # 任务状态机（对应 03 §3.4）
│   │   └── rules.py
│   ├── service/                   # 用例编排：事务边界在这一层
│   │   └── task_service.py
│   ├── repo/                      # ★ 数据访问：唯一允许写 SQL 的地方
│   │   └── task_repo.py
│   ├── ports/                     # ★ 对外依赖的抽象（ComputeBackend、Storage、EventBus）
│   └── adapters/                  # ports 的具体实现
├── tests/
│   ├── unit/                      # 不依赖外部中间件
│   ├── integration/               # 依赖 Postgres/Redis（testcontainers 或本地 compose）
│   └── contract/                  # OpenAPI 契约测试
└── alembic/                       # 若该服务拥有独立 schema
```

**分层依赖方向（单向，违反即 Review 否决）**：

```
api → service → domain ← repo
        ↓
      ports ← adapters
```

- `domain/` **禁止** `import` `sqlalchemy` / `fastapi` / `httpx`；
- `api/` **禁止** 直接 `import repo`；
- `repo/` **禁止** 调用其他 `service/`。

> 可用 `import-linter`（`pyproject.toml` 中 `[tool.importlinter]`）机械校验上述方向，CI 执行 `lint-imports`。

## 3. Python 编码规范

### 3.1 基础工具链（全仓统一，不允许服务自行偏离）

| 工具 | 用途 | 配置位置 | 门禁 |
|---|---|---|---|
| `ruff` | 格式化 + Lint（替代 black/isort/flake8） | `pyproject.toml` | 零 error |
| `mypy` | 类型检查 | `pyproject.toml`（`strict = true`） | 零 error |
| `pytest` + `pytest-cov` | 测试 | 各服务 `pyproject.toml` | 覆盖率门槛见 §3.6 |
| `import-linter` | 分层依赖校验 | `pyproject.toml` | 零违反 |
| `uv` | 依赖与虚拟环境 | `uv.lock` | lock 必须同步 |
| `pre-commit` | 本地预检 | `.pre-commit-config.yaml` | 安装后自动执行 |

**版本**：Python 3.10（与 `07` §4.3 训练/推理环境对齐；AlphaFold 侧 3.9.18 单独环境，不进业务代码）。

### 3.2 命名约定

| 对象 | 约定 | 示例 |
|---|---|---|
| 模块/包 | 全小写，下划线 | `mol_index`、`state_machine` |
| 类 | PascalCase | `TaskStateMachine`、`ComputeBackend` |
| 函数/变量 | snake_case | `submit_task`、`project_id` |
| 常量 | UPPER_SNAKE | `MAX_BATCH_SIZE` |
| 私有 | 前缀单下划线 | `_resolve_quota` |
| 类型别名 | 后缀 `T` 或语义名 | `TaskId`、`JsonDict` |
| Pydantic 模型 | 后缀区分用途 | `TaskCreate`（入）/ `TaskOut`（出）/ `TaskPatch` |
| 枚举 | UPPER_SNAKE 值，与 `04` §4.2 完全一致 | `TaskStatus.RUNNING` |
| 布尔 | `is_` / `has_` / `can_` 前缀 | `is_primary`、`can_retry` |

**禁止**：单字符变量（循环下标 `i/j` 与推导式内部除外）、拼音命名、缩写不一致（`proj`/`prj`/`project` 混用 —— 统一 `project`，而 ID 前缀按 `04` §4.1 用 `prj_`）。

### 3.3 类型标注（E-01 落地细则）

```python
# 正确
def resolve_quota(
    repo: QuotaRepo,
    project_id: ProjectId,
    profile: ResourceProfile,
) -> QuotaDecision: ...

# 禁止：Any 逃逸
def resolve_quota(repo, project_id, profile): ...   # ✗ 无标注
def resolve_quota(repo: Any, ...) -> Any: ...       # ✗ Any 逃逸
```

| 规则 | 说明 |
|---|---|
| T-01 | 所有 `def` 必须标注参数与返回值（`-> None` 也要写） |
| T-02 | 禁止 `# type: ignore` 裸用；必须带错误码与理由：`# type: ignore[arg-type]  # 上游 SDK 未标注` |
| T-03 | `Any` 仅允许出现在第三方无类型 SDK 的适配层（`adapters/`），且需 `cast` 后立即转为内部类型 |
| T-04 | 公共函数参数禁止可变默认值（`def f(x: list = [])`） |
| T-05 | `Optional` 显式写 `X \| None`，并在函数入口收敛（早返回） |
| T-06 | TypedDict / Pydantic 二选一，**不得混用**表示同一结构 |

### 3.4 异步与并发（E-02 落地细则）

| 编号 | 规则 |
|---|---|
| A-01 | 路由函数一律 `async def`；同步 DB 调用必须经 `run_in_threadpool` 包装或直接用异步驱动 |
| A-02 | 使用 psycopg 3 异步驱动 + SQLAlchemy 2 `AsyncSession`，禁止同步 `Session` 出现在 `api/` |
| A-03 | 禁止在事件循环内调用 `time.sleep` / `requests` / 阻塞文件 IO；统一用 `asyncio.sleep`、`httpx.AsyncClient`、`anyio.to_thread` |
| A-04 | 外部调用必须设置超时（默认 5s，长调用显式覆盖），并有重试上限（≤ 3 次，指数退避 + 抖动） |
| A-05 | 禁止无界 `asyncio.gather`；并发度必须由 `Semaphore` 或队列控制，数量来自配置 |
| A-06 | 后台任务不得依赖 API 进程生命周期（禁止 `BackgroundTasks` 承载业务状态推进），一律走持久化队列 |
| A-07 | 事务边界在 `service/` 层，一个用例一个事务；禁止在 `repo/` 内 `commit` |

**CPU 密集下沉清单（必须下沉，不得在 API 进程执行）**：

| 场景 | 下沉目标 |
|---|---|
| SDF/SMILES 批量解析、指纹计算 | `drp-mol-index` Worker 进程 |
| 批量导入文件解析（CSV/SDF/FASTA/PDB） | 独立 import worker（`DATA_IMPORT` 任务） |
| 表格大数据量导出 | `DATA_EXPORT` 异步任务 |
| 任何模型推理 | `ComputeBackend`（`09` §3） |

### 3.5 错误处理（E-06 落地细则）

**统一错误模型**（与 `03-接口/05-API接口规格说明书.md` 错误码对齐）：

```python
class DrpError(Exception):
    code: str            # 与 05 §1.3 错误码表【完全一致】，如 "40001" / "40903"；不要自造 DRP-409-001 这类独立编号
    message: str         # 面向用户的中文提示
    detail: dict[str, JsonValue] | None = None
    http_status: int = 500
    trace_id: str | None = None
```

| 编号 | 规则 |
|---|---|
| ER-01 | 业务错误抛 `DrpError` 子类；**禁止**在 `service/` 及以上层抛裸 `ValueError` |
| ER-02 | 全局异常处理器（`drp_core.errors`）统一转换成 `{"code","message","detail","traceId"}` 响应 |
| ER-03 | 禁止 `except Exception: pass`；捕获必须至少 `logger.exception` 或转换为 `DrpError` |
| ER-04 | 禁止把堆栈、SQL、路径回显给前端；`detail` 仅放可公开的结构化字段 |
| ER-05 | 计算任务失败必须落 `task.error_message` + `exit_code`，并保留日志分片 `chunk_urn`（`04` §9.4） |
| ER-06 | 用户可理解性：所有 `message` 为中文，明确"发生了什么 + 下一步怎么做"（对应 DRP-NFR-12） |

### 3.6 测试代码规范与覆盖率门槛

| 层 | 覆盖对象 | 门槛 |
|---|---|---|
| `domain/` | 状态机、规则、计算逻辑 | **行覆盖 ≥ 90%**，分支 ≥ 85% |
| `service/` | 用例编排、事务、权限判定 | 行覆盖 ≥ 80% |
| `repo/` | SQL 与索引有效性 | 集成测试覆盖关键查询；≥ 70% |
| `api/` | 契约（请求校验、错误码、分页、鉴权） | ≥ 70% |
| `compute/runner` | IO 契约、进度上报、产物校验 | ≥ 80%（**强制**，因为它是全部模型的公共路径） |
| `web/` | 关键交互组件 | ≥ 60%（Vitest） |
| **全仓** | — | 行覆盖 **≥ 75%** 为合并门槛 |

**测试规范**：

- 测试文件 `test_<module>.py`，测试函数 `test_<行为>_<条件>_<期望>()`，中文 docstring 说明业务意图；
- 禁止在测试中使用真实网络、真实 DCU、真实甲方环境；外部依赖用 `respx`（HTTP）、`fakeredis`、testcontainers（Postgres）；
- 时间必须可注入（`Clock` 抽象），禁止测试直接依赖 `datetime.now()`。

## 4. 数据访问与迁移规范

### 4.1 ORM 使用规则

| 编号 | 规则 |
|---|---|
| DB-01 | SQLAlchemy **2.x 风格**（`select()` / `Mapped[]` / `mapped_column`），禁止 1.x `Query` API |
| DB-02 | 表名/字段名与 `02-架构/04-数据模型设计说明书.md` **逐字一致**；枚举值亦逐字一致（`04` §4.2） |
| DB-03 | 主键统一 `uuid` 类型 + 应用侧生成（前缀化 ULID，`04` §4.1），禁止 `BIGSERIAL` 自增作为业务主键 |
| DB-04 | 所有表必须具备 `created_at/updated_at/created_by/updated_by`，软删除表必须有 `deleted_at` |
| DB-05 | 乐观锁字段 `version` 的更新必须用 SQL 条件更新（`WHERE version = :old`），失败即冲突返回 **`40903`**（`05` §1.3 与 `04` §5.6 的唯一口径）；**禁止**另造 `DRP-409-001` 之类的独立编号 |
| DB-06 | 列表查询禁止 `SELECT *` 语义的全字段加载；大字段（结构文本、jsonb 大对象）只在详情接口加载（`03` §3.5） |
| DB-07 | 分页必须走游标或 `ORDER BY + LIMIT`，默认 20、最大 200（`03` §3.5）；禁止无 `ORDER BY` 的分页 |
| DB-08 | 禁止在应用层做 N+1；关联加载必须显式 `selectinload`/`joinedload` |
| DB-09 | 只追加表（`audit_log`、`task_input_snapshot`）**禁止** `UPDATE`/`DELETE`，并用数据库权限或触发器兜底 |
| DB-10 | 所有 `jsonb` 字段的写入必须经 Pydantic 校验后再落库，禁止直接塞原始 dict |

### 4.2 数据隔离（E-07 落地细则）

```python
# 唯一允许的查询入口形态：project_id 由注入的 CurrentUser 强制带入
async def list_tasks(
    session: AsyncSession,
    scope: ProjectScope,          # 由 deps.get_project_scope() 构造，内含已校验的 project_id 集合
    **filters: object,
) -> Page[TaskOut]: ...
```

| 编号 | 规则 |
|---|---|
| SEC-DB-01 | 路由层**不得**从 body/query 自行取 `project_id` 后直接查询；必须经 `ProjectScope` |
| SEC-DB-02 | `ProjectScope` 构造时校验当前用户对项目的 `OWNER/MEMBER/VIEWER` 权限（`04` §5.2），失败抛 **`40301`**；**`ADMIN` 直通并写 `audit_log`**（`04` §5.0 两层角色，不要对 ADMIN 也判 403） |
| SEC-DB-03 | 项目归档（`ARCHIVED`）后所有写接口拒绝：**`40901`**（`05` §1.3，`detail.reason=PROJECT_ARCHIVED`） |
| SEC-DB-04 | 审计写入（`audit_log`）由中间件统一完成，业务代码不得选择性跳过 |

### 4.3 迁移规范（Alembic）

| 编号 | 规则 |
|---|---|
| MIG-01 | 每个迁移文件必须同时提供 `upgrade()` 与可执行的 `downgrade()`；**不可逆迁移不得合入** |
| MIG-02 | 迁移文件名 `YYYYMMDDHHMM_<动词>_<对象>.py`，例：`202610201030_add_screening_result_index.py` |
| MIG-03 | 大表加索引必须使用 `CREATE INDEX CONCURRENTLY`（在 Alembic 中需 `op.execute` + autocommit block） |
| MIG-04 | 破坏性变更（删列/改类型）必须走**三步走**：加新列 → 双写+回填 → 切读 → 删旧列，跨两个迭代 |
| MIG-05 | 迁移必须与代码在同一个 PR；禁止"代码合了、迁移下次再补" |
| MIG-06 | 迁移在 CI 中对空库执行一次 `upgrade head` + `downgrade base` 验证 |
| MIG-07 | 生产迁移前必须有备份点（`03` §8.3），执行人签字记录进变更单 |

> 对外契约以 `03-接口/05-API接口规格说明书.md` 为准，本节规定**实现方式**。

| 编号 | 规则 |

## 6. 计算侧编码规范（关键）

> 这一节是"平台"与"模型"的接缝，也是最容易出事故的地方。

### 6.1 ComputeBackend 唯一入口（E-03 落地细则）

```python
# packages/drp_compute/backend.py
class ComputeBackend(Protocol):
    async def submit(self, spec: TaskSpec) -> SubmissionRef: ...
    async def status(self, ref: SubmissionRef) -> TaskRuntimeStatus: ...
    async def logs(self, ref: SubmissionRef, *, tail: int = 200) -> str: ...
    async def cancel(self, ref: SubmissionRef) -> None: ...
    async def collect(self, ref: SubmissionRef) -> list[ArtifactRef]: ...
    async def health(self) -> BackendHealth: ...
```

| 编号 | 规则 |
|---|---|
| CB-01 | 业务服务只依赖 `ComputeBackend` 协议，`ports/` 中声明，`adapters/` 中实现（`SshBackend` / `K8sBackend`） |
| CB-02 | 禁止在 `services/` 下出现 `torch` / `dgl` / `tensorflow` / `subprocess` / `paramiko` / `kubernetes` 的直接 import（CI 用 `tools/forbidden_imports.py` 扫描） |
| CB-03 | 新增后端形态只需新增 adapter + 配置，不得改动业务服务 |
| CB-04 | 后端切换（SSH ↔ K8s）通过配置项 `compute.backend` 完成，运行期不得两种后端混用同一任务 |
| CB-05 | 提交前必须完成资源准入（配额、显存、优先级），准入逻辑只在 `drp-scheduler`，adapter 不做策略 |

### 6.2 模型侧代码边界

| 编号 | 规则 |
|---|---|
| MD-01 | 模型包只实现 `entrypoint/run.py`，IO 严格遵循 **`07` §3.6（唯一真源）**：读 `DRP_TASK_FILE`（默认 `/work/task.json`），写 `DRP_RESULT_FILE`（默认 `/work/result.json`），产物只写 `DRP_OUT_DIR`（默认 `/work/out`）。**禁止**使用 `/workspace/input`、`/etc/task`、`output.json` 等任何其他路径 |
| MD-02 | 模型包**不得**自己下载数据、不得写数据库、不得访问网络；所有 IO 经 `drp-runner`（`07` §3.6 职责 2/5 + §4.3 Dockerfile） |
| MD-03 | 进度上报只能写 `DRP_PROGRESS_FILE`（`07` §3.5，`{"pct":42,"stage":"..."}`）或输出 `__DRP_PROGRESS__ {json}` 结构化行，禁止私有协议 |
| MD-04 | 随机种子必须从 `task.json.params.seed` 读取并全局设置，保证可复现 |
| MD-05 | 版本自检在容器启动时执行（`07` §4.2 的 `verify_runtime`），失败即非 0 退出 |
| MD-06 | 设备名统一从 `DRP_DEVICE` 环境变量读取，禁止硬编码 `cuda:0`（`07` §3.6 / §9 已有实测差异：MolP-PC 用 `cuda:0`，MSIGN 用 `hip:0`） |
| MD-07 | 禁止用 pip 覆盖 `torch/dgl/tensorflow`（`07` §2.2 `forbidPipOverride`），构建期校验 |

### 6.3 节点 Agent 规范（`09` §4.2）

| 编号 | 规则 |
|---|---|
| AG-01 | Agent 与控制面的所有通信走 mTLS，禁止明文 HTTP 承载任务参数 |
| AG-02 | Agent 必须做**白名单命令校验**：只接受 `docker run/stop/inspect/logs` 与固定镜像前缀，拒绝任意 shell |
| AG-03 | 任务参数不得拼接 shell 字符串，一律 `list[str]` 形式 exec |
| AG-04 | Agent 上报健康心跳 ≤ 10s，失联 ≥ 3 个周期标记节点 `DEGRADED` |
| AG-05 | Agent 日志本地环形保留 7 天，回传失败不阻塞任务执行 |

## 8. 日志、追踪与审计规范

### 8.1 结构化日志（对应 `03` §7.3、DRP-NFR-13）

**统一字段**（所有服务必须一致，便于 Loki 检索）：

| 字段 | 说明 | 必填 |
|---|---|---|
| `ts` | ISO8601 毫秒 | 是 |
| `level` | DEBUG/INFO/WARN/ERROR | 是 |
| `service` | 服务名，如 `drp-task` | 是 |
| `trace_id` | 全链路追踪 ID | 是 |
| `span_id` | 当前 span | 否 |
| `user_id` | 操作人 | 是（无则 `anonymous`） |
| `project_id` | 项目作用域 | 是（有则必填） |
| `task_id` | 任务 | 任务相关接口必填 |
| `event` | 事件名，`动词_对象` 如 `task.submit` | 是 |
| `msg` | 人类可读描述（中文） | 是 |
| `duration_ms` | 耗时 | 耗时类事件必填 |
| `error_code` / `error_stack` | 失败时 | 失败必填 |

```python
# 唯一日志入口（drp_core.logging）
log = get_logger(__name__)

log.info("task.submit", msg="提交结构预测任务", project_id=pid, task_id=tid)
log.error("task.fail", msg="任务执行失败", task_id=tid, error_code="50303",  # 503xx 内部错误，见 05 §1.3
          error_stack=traceback.format_exc())
```

| 编号 | 规则 |
|---|---|
| LOG-01 | 使用 `structlog`（JSON 输出），**禁止** `print`、禁止 `logging.basicConfig` 散落各服务 |
| LOG-02 | 禁止记录：密码、token、完整文件内容、SMILES 全量列表（>100 条只记数量与哈希） |
| LOG-03 | 采样：DEBUG 级默认关闭，生产环境 INFO；`duration_ms` 类日志 100% 保留 |
| LOG-04 | 计算侧日志由 runner 收集 → 对象存储分片 + 库内索引（`04` §9.4），与业务日志分离 |
| LOG-05 | 日志中包含 SMILES/序列时必须脱敏策略：科研数据不脱敏，但禁止进入外部日志系统（本项目为内网，允许保留） |

### 8.2 审计（`04` §5.4 `audit_log`）

| 编号 | 必须审计的动作 |
|---|---|
| AUD-01 | 登录/登出/失败登录 |
| AUD-02 | 项目创建/归档/成员变更 |
| AUD-03 | 数据导入/导出/删除 |
| AUD-04 | 任务提交/取消/重试 |
| AUD-05 | 模型/工具注册与版本发布 |
| AUD-06 | 权限授予与回收、配额调整 |

审计记录只追加，含 `actor/action/target_type/target_id/before/after/ip/ua/ts`，**不可修改**（DB-09）。

### 8.3 链路追踪

- OpenTelemetry SDK，W3C `traceparent` 透传；跨服务 `httpx` 自动注入；
- 计算任务链路：网关 → 服务 → scheduler → backend → runner（runner 内生成子 span 并回传）；
- `trace_id` 写入 `task.env_json.traceId`，保证任务详情页可直接跳到追踪面板。

## 10. 分支模型与提交规范

### 10.1 分支模型

**决策：主干开发 + 短生命周期特性分支（Trunk-based，轻量 GitFlow 变体）**

```
main ────●────●────────●────────●──────▶  始终可发布（每次合入必过全量 CI）
          \    \        \        \
           \    \        \        └── hotfix/DRP-321-cancel-race
            \    \        └── release/v1.2.0 ──▶ tag v1.2.0
             \    └── feat/DRP-102-task-cancel
              └── fix/DRP-088-quota-rounding
```

| 分支 | 命名 | 生命周期 | 说明 |
|---|---|---|---|
| `main` | — | 永久 | 受保护；禁止直推；要求 1 个 approve + CI 全绿 |
| 特性 | `feat/<需求号>-<简述>` | ≤ 5 个工作日 | 合并后即删 |
| 缺陷 | `fix/<缺陷号>-<简述>` | ≤ 3 个工作日 | |
| 紧急 | `hotfix/<缺陷号>-<简述>` | ≤ 1 个工作日 | 从 `main` 拉，双人复核后合入 |
| 发布 | `release/v<主>.<次>.<修>` | 1~2 周 | 只接受修复，不接受特性 |

**规则**：

- 分支存活超 5 个工作日必须先合入（拆小的），避免长时间分叉；
- 禁止 `git merge main` 回灌到特性分支后产生大合并；优先 `rebase`（团队约定统一 rebase，历史上保持线性）；
- 发布分支禁止直接改代码，必须 backport 修复。

### 10.2 提交信息（Conventional Commits，强校验）

```
<type>(<scope>): <subject>

<body 说明为什么，而不是做了什么>

<footer: Refs / BREAKING CHANGE>
```

| type | 含义 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(task): 支持任务取消并保留部分产物` |
| `fix` | 缺陷修复 | `fix(scheduler): 修正配额并发扣减超卖` |
| `perf` | 性能优化 | `perf(mol-index): 指纹检索改用 IVFFlat` |
| `refactor` | 重构（不改行为） | `refactor(domain): 抽出任务状态机` |
| `docs` | 文档 | `docs(dev): 补充计算侧规范` |
| `test` | 测试 | `test(task): 补状态机非法跃迁用例` |
| `build` | 构建/依赖 | `build(deps): 升级 ruff 到 0.6.x` |
| `ci` | CI 配置 | `ci: 增加外网调用扫描` |
| `chore` | 杂项 | `chore: 忽略本地 dcu 缓存` |

| 规则 | 说明 |
|---|---|
| CM-01 | `subject` 中文，≤ 50 字，不加句号 |
| CM-02 | `scope` 取服务名或包名（`task`、`mol-index`、`web`、`runner`、`deploy`） |
| CM-03 | `body` 必须回答"为什么"；纯格式化改动可省略 |
| CM-04 | `footer` 必须关联需求号或缺陷号：`Refs: AIYF-TGT-02-SRS` / `Fixes: DRP-118` |
| CM-05 | 破坏性变更必须写 `BREAKING CHANGE:` 并同步 `05` API 版本策略 |
| CM-06 | 由 `commitlint` 在 pre-commit + CI 双端校验 |

## 11. Code Review 规范

### 11.1 评审规则

| 编号 | 规则 |
|---|---|
| CR-01 | 每个 PR 至少 1 名 reviewer；涉及 `packages/drp_contracts`、`packages/drp_compute`、`migrations/`、`deploy/` 需 2 名（含架构负责人） |
| CR-02 | 提交者**自评审**：合并前必须先自己看一遍 diff 并留 note |
| CR-03 | Review SLA：普通 PR ≤ 4 小时响应；阻塞中的 PR 每日站会点名 |
| CR-04 | 单个 PR ≤ 400 行有效变更（不含快照、生成代码、lock 文件）；超过必须拆分 |
| CR-05 | 意见分三级：`[必须]`（不改不合）/`[建议]`（可讨论）/`[提问]`（求解释）；合并前 `[必须]` 必须清零 |
| CR-06 | 争议超 2 轮 → 拉到架构负责人裁决并记入 ADR，不在 PR 里反复拉扯 |

### 11.2 Code Review 检查清单（必须逐项对照）

**A. 正确性**

- [ ] 是否覆盖了需求/缺陷描述中的**全部**场景（含边界：空集、单元素、超大批量、并发提交）
- [ ] 状态机跃迁是否合法（对照 `03` §3.4）；是否存在非法跃迁被允许
- [ ] 并发安全：同一任务重复取消/重复重试、配额并发扣减、幂等键冲突是否处理
- [ ] 事务边界是否正确；是否存在"部分成功但对外声称成功"
- [ ] 失败路径：外部调用超时、节点失联、对象存储 404、迁移中断

**B. 可追溯性（E-04）**

- [ ] 任务提交路径是否写全 `model_name/version`、`tool_name/version`、`params_json`、`env_json`
- [ ] 输入快照 `task_input_snapshot` 是否落库（含 `sha256`、`data_version`）
- [ ] 新增数据实体是否有 `created_by` 与审计写入

**C. 数据与安全**

- [ ] 所有查询是否经 `ProjectScope`（DB-10 / SEC-DB-01）
