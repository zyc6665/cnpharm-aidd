# 科学计算工具管理平台：项目学习与面试指南

> 面向求职学习、项目复盘和技术面试。本文以仓库当前实现和架构文档为依据；标注“规划/路线图”的内容不能在面试中描述成已上线功能。

## 1. 一分钟介绍

这是一个面向 AI 驱动药物发现（AIDD）的科学计算工具管理平台。它把分子生成、蛋白处理、分子对接、ADMET 预测等异构工具统一接入，提供工具托管、标准化数据管理、任务调度、工作流编排、结果可视化和权限治理。

平台解决四类问题：

- **工具碎片化**：不同工具的参数、文件格式和运行方式不一致。
- **结果不可复现**：输入文件、参数、工具版本和中间产物缺少统一追踪。
- **算力使用困难**：GPU、重 CPU 任务和远程集群需要统一排队与资源准入。
- **科研协作断层**：研究人员需要在一个项目上下文中复用结果、组合工具并查看运行状态。

面试中的一句话版本：

> 我参与的是一个“控制面 + 异构计算执行面”的科学计算平台。控制面用 FastAPI 管理用户、项目、工具契约、任务和 Artifact，Celery/Redis 负责异步调度，Executor Adapter 屏蔽 Docker、Python、SSH、Remote API 等执行差异，最终把工具输出沉淀成可追溯、可复用的标准科研数据资产。

## 2. 业务主线与核心领域模型

平台围绕六个稳定对象建模：

| 对象 | 作用 | 面试解释 |
| --- | --- | --- |
| `Project` | 研发上下文、成员和权限边界 | 解决资产归属和协作问题 |
| `Tool/ToolVersion` | 工具能力、版本和发布状态 | 描述“能做什么”，不保存运行状态 |
| `Tool Contract` | 参数、标准输入输出、资源和执行器契约 | 让前端、工作流和 Agent 使用统一接口 |
| `Task` | 一次工具运行实例 | 保存状态、输入、输出、日志和调度信息 |
| `Artifact/ArtifactVersion` | 可复用的标准科研数据 | 把普通文件提升为有类型、有角色、有谱系的数据资产 |
| `WorkflowDefinition/WorkflowRun` | 工作流定义和运行状态 | 组合多个工具节点，并记录节点任务绑定 |

辅助对象包括 `ExecutionRecord`（底层执行句柄和幂等信息）、`File`（存储对象）、`AgentRun`/`Conversation`（规划和解释入口）以及研究白板。

关键边界：

- `File` 是存储对象，`Artifact` 是科研语义对象；二者不能混用。
- `Tool` 是能力定义，`Task` 是执行实例；工具不保存项目状态。
- `Workflow` 只表达节点、边和状态，不把工具私有字段写死在画布中。
- Agent 可以生成计划和解释，但仍必须经过 Tool Contract、Run Preparation 和 Task，不能绕过任务系统。

## 3. 总体架构

```text
浏览器 / API 客户端
        │ HTTPS / WebSocket
        ▼
Vue 3 + Pinia + Ant Design Vue + ECharts
        │ REST / WebSocket
        ▼
FastAPI API 层
  认证授权、项目、工具、Artifact、任务、工作流、Agent、管理后台
        │
        ▼
领域服务层
  Tool Contract
  Run Preparation + Artifact Binding
  Workflow Orchestration
  Task Command / Resource Admission
  Artifact Persistence + Lineage
        │
        ▼
执行适配层
  builtin / Python / Docker / SSH / Remote API / K8s / Slurm
        │
        ├── PostgreSQL（生产）/ SQLite（开发）
        ├── Redis（缓存、Celery Broker、结果后端）
        ├── MinIO（生产对象存储）/ 本地文件（开发）
        └── Celery Worker / GPU Worker / Heavy Worker
```

### 3.1 分层职责

1. **API 层**：请求校验、鉴权、权限检查、响应序列化，不直接拼执行命令。
2. **领域服务层**：承载稳定业务规则，如输入预检、Artifact 绑定、工作流调度和任务状态迁移。
3. **执行适配层**：把统一运行请求翻译成具体的 Docker 命令、SSH 作业、远程 API 或集群任务。
4. **基础设施层**：提供数据库、缓存、对象存储、消息队列和计算资源。

### 3.2 开发与生产模式

| 能力 | 开发模式 | 生产模式 |
| --- | --- | --- |
| 数据库 | SQLite + aiosqlite | PostgreSQL + asyncpg |
| 文件存储 | 本地文件系统 | MinIO/S3 |
| 缓存 | 内存缓存 | Redis |
| 任务执行 | direct 进程内执行，适合联调 | Celery + Redis，多 Worker |
| 部署 | 本地 Uvicorn | Docker Compose，按队列拆分 Worker |

`direct` 模式会受进程重启、热更新和单进程阻塞影响，长任务、工作流和 Agent 运行应使用生产 Celery 模式。

## 4. 一次任务执行链路

```text
用户从工具页、工作流节点或 Agent 发起运行
        │
        ▼
Run Preparation
  读取 Tool Contract 和 Run Context
  校验参数、项目权限、文件和 Artifact Slot
        │
        ▼
Artifact Binding Resolver
  绑定上传文件、已有 ArtifactVersion 或上游节点输出
  产出 readiness / missing / ambiguous / incompatible 决策
        │
        ▼
PreparedRun + ResourceProfile
  统一生成 Task 输入、资源画像、队列和执行请求
        │
        ▼
Task + ExecutionRecord
  持久化任务后提交 Celery 或 direct 执行器
        │
        ▼
Executor Adapter
  staging 输入、运行工具、采集日志和结果 manifest
        │
        ▼
状态机与资源生命周期
  queued → running → succeeded / failed / cancelled
  资源 reservation/lease 释放，必要时对账和恢复
        │
        ▼
Artifact Persistence
  校验输出、创建 ArtifactVersion、记录 lineage 和可视化信息
        │
        ▼
WebSocket / 任务详情页
  推送状态、进度、日志和结果
```

### 4.1 为什么需要 Run Preparation

工具详情页独立运行、工作流节点运行和 Agent 计划运行都会遇到相同问题：输入从哪里来、是否属于当前项目、文件角色是否匹配、是否需要转换、上游是否完成。将这些判断集中到 `Run Preparation`，可以避免多个入口各自拼装任务请求，降低行为不一致和权限绕过风险。

### 4.2 为什么需要 Standard Artifact

普通文件只有路径和大小，平台无法可靠判断它是蛋白结构、结合口袋还是评分表。Standard Artifact 由类型、版本、文件角色、元数据、校验状态和 lineage 组成，使下游工具可以按契约自动绑定输入，也使结果能够被搜索、复用和审计。

示例类型包括 `protein_structure@1`、`ligand_structure@1`、`binding_pocket@1`、`molecule_table@1` 和 `run_report@1`。

## 6. 关键设计亮点

### 6.1 契约驱动的工具接入

新工具通过 `Tool Contract` 声明身份、参数 schema、Artifact 输入输出、资源画像和执行器类型。工具不需要为每个工作流单独写适配代码，前端表单、预检、工作流节点和 Agent 都消费同一份契约。

### 6.2 Executor Adapter 屏蔽异构资源

统一接口抽象为 `submit / inspect / cancel / logs / collect`。调用方只处理平台状态和 opaque handle，不暴露 Kubernetes Pod、Slurm JobId 或 SSH 命令细节。这样可以逐步增加 K8s、Slurm 或 Remote API，而不改变任务领域模型。

### 6.3 资源准入与生命周期完整

任务在真正执行前会根据 CPU、内存、GPU、并发度和 tier 做准入；运行中保存 reservation/lease；取消、超时、Worker 丢失和重试路径会触发释放或对账。队列还支持按等待时间增加 aging boost，减少低优先级任务长期饥饿。

### 6.4 可恢复的异步任务

任务状态、ExecutionRecord、远程任务句柄和输出 manifest 持久化后，后台 reconcile loop 可以在进程或 Worker 重启后重新查询和恢复。Celery 使用 late ack 和 worker lost reject，降低任务被静默吞掉的概率。

### 6.5 结果可追溯与可视化

工具输出通过 result manifest 描述文件角色、类型、指标和 lineage，再由后端创建 ArtifactVersion。前端按 Artifact 类型选择 renderer，而不是按工具名称写死展示逻辑。

### 6.6 轻量开发体验与生产约束并存

开发者可以使用 SQLite、本地文件、内存缓存和 direct 模式快速联调；生产配置通过 `Settings` 强制校验 PostgreSQL、MinIO、Redis、Celery、HTTPS CORS 和强密钥，降低“开发配置直接上线”的风险。

## 7. 现实痛点与改进方向

这些内容适合在面试中主动说明，体现工程判断力。

| 痛点 | 原因 | 改进方向 |
| --- | --- | --- |
| 工具契约仍有 legacy 兼容逻辑 | 历史工具配置格式多，迁移需要平滑过渡 | 以 Tool Package v2 和契约校验作为唯一新入口，逐步收敛旧字段 |
| 运行入口较多 | 工具页、节点、工作流和 Agent 都能发起运行 | 继续统一 `Run Preparation → Task Command → Executor`，禁止入口自行拼 payload |
| 异构集群状态不一致 | K8s、Slurm、SSH、Remote API 的状态和错误语义不同 | 扩大 Adapter contract 测试，保留原始状态和统一平台状态 |
| direct 模式不适合长任务 | 与 API 进程共享生命周期，重启会影响连续性 | 生产强制 Celery；开发模式只用于短任务和接口联调 |
| 科研结果校验复杂 | 文件存在不代表格式、角色、元数据都正确 | 强制 Result Manifest、Artifact Registry 和发布前 smoke test |
| 资源调度策略会持续增长 | GPU、队列、配额、Worker 能力和租约互相影响 | 将 ResourceProfile、Admission、Lease、Quota 分成稳定模块，增加指标和压测 |
| 规划能力与已实现能力容易混淆 | roadmap 中有 Candidate、Assay、DMTA 等扩展对象 | 文档和面试中明确版本边界，使用 verification record 支撑上线结论 |
| 工作流恢复场景复杂 | 节点状态、任务绑定、上游 Artifact 和对账需要一致 | 使用幂等键、持久化 Node Task Binding 和 workflow reconciliation |

## 8. 面试高频问题与回答框架

### Q1：为什么不用每个工具单独写一套接口？

因为工具数量和运行方式会增长，单独适配会让前端、工作流和调度逻辑重复。平台把工具能力收敛成 Tool Contract，把运行请求收敛成 PreparedRun，把执行差异收敛成 Executor Adapter。新增工具主要增加契约和执行配置，平台公共链路保持不变。

### Q2：Artifact 和 File 有什么区别？

File 只描述存储对象；Artifact 是有标准类型、版本、文件角色、元数据、校验状态和 lineage 的科研数据。只有 Artifact 才能被工作流和下游工具按语义自动绑定。这样既保留文件存储的通用性，又保证科研结果可复现。

### Q3：一次任务如何保证输入合法？

先在 Run Preparation 阶段读取工具契约和运行上下文，再由 Artifact Binding Resolver 逐个处理 slot：检查项目权限、类型版本、文件角色、生命周期、基数和上游状态，输出 ready、missing、ambiguous、incompatible 等可解释决策。只有准备成功后才创建或提交执行任务。

### Q4：Celery 只能解决异步吗？

Celery 负责消息投递和 Worker 执行，但平台还需要自己的 Task 状态机、ExecutionRecord、资源准入和 reconcile。否则消息成功不等于科学任务成功，也无法处理 Worker 丢失、远程任务超时、取消重试和资源释放。

### Q5：如何避免重复提交和资源泄漏？

任务和执行记录使用幂等键；提交、取消、释放资源等操作设计为可重复执行。reservation/lease 有 TTL，后台任务会回收过期记录；远程执行状态定期对账，避免平台状态和实际集群状态长期漂移。

### Q6：WebSocket 断开后如何保证用户看到正确状态？

WebSocket 只负责实时体验，不作为唯一事实来源。任务状态和日志先持久化，前端重连后重新拉取任务详情，再继续订阅更新。连接管理器按用户和 task_id 维护订阅，发送失败会清理连接。

### Q7：生产环境为什么必须使用 PostgreSQL、Redis、MinIO？

SQLite 和本地文件适合单机开发，但不适合多实例并发、共享 Worker 和对象生命周期管理。生产中 PostgreSQL 保存事务数据，Redis 支撑缓存和消息队列，MinIO 保存大文件和结果；配置层会对这些依赖和密钥做强校验。

### Q8：你会如何测试这个平台？

按边界分层：服务层测试输入绑定、状态机和资源准入；API 测试权限、序列化和错误响应；执行器测试 submit/inspect/cancel/collect 契约；工作流测试节点依赖、跳过、重试和恢复；端到端测试从工具输入到 Artifact 输出。仓库已有 pytest、前端单测和 Playwright 场景，可继续补充真实 Worker 与对象存储集成测试。

## 9. 简历表述模板

### 一句话版本

负责科学计算工具管理平台的后端与任务调度建设，围绕 Tool Contract、Standard Artifact 和 Executor Adapter 统一工具接入、异步执行和科研结果追溯。

### 三条项目经历

- 基于 FastAPI、SQLAlchemy Async、PostgreSQL/SQLite 实现项目、工具、任务、Artifact 和工作流 API，使用 JWT + RBAC 完成用户与项目级权限控制。
- 设计 `Run Preparation → Artifact Binding → Task → Executor → Artifact Persistence` 执行链路，统一 Docker、Python、SSH、Remote API 等异构工具接入，减少入口间的参数和文件绑定重复。
- 基于 Celery + Redis 构建多队列任务系统，引入 ResourceProfile、资源准入、reservation/lease、取消对账和 Worker 能力路由，支持 CPU、重计算和 GPU 任务隔离。

### 面试表达注意

- 不要把设计文档中的“规划对象”说成已上线能力。
- 不要只说“用了 Celery”，要说明任务状态、幂等、资源释放和恢复如何闭环。
- 不要把 MinIO 说成数据库；它负责对象，PostgreSQL 负责元数据和关系。
- 不要只说“支持 GPU”，要说明资源画像、队列、Worker capability 和 admission 的关系。
