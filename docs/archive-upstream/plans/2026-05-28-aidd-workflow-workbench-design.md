# AIDD 流程工作台设计

## 目标

新增一个真正面向 AIDD 流程的前端工作台页面，把当前零散的单工具使用方式收敛为一条连续流程：

- 按固定五步顺序组织工具
- 在同一页面内保留每一步结果
- 自动把上一步输出带入下一步
- 支持刷新后恢复当前流程
- 先采用前端本地持久化，后续再演进为后端持久化工作流

## 背景与现状

当前系统已经具备以下基础能力：

- [frontend/src/views/tools/List.vue](/data/zhouyc/cpumodel_sciminer/frontend/src/views/tools/List.vue) 提供零散工具列表
- [frontend/src/views/tools/Detail.vue](/data/zhouyc/cpumodel_sciminer/frontend/src/views/tools/Detail.vue) 提供单个工具的动态表单与任务提交
- [frontend/src/views/tasks/Detail.vue](/data/zhouyc/cpumodel_sciminer/frontend/src/views/tasks/Detail.vue) 提供单个任务的结果查看、文件下载和可视化
- [frontend/src/stores/index.ts](/data/zhouyc/cpumodel_sciminer/frontend/src/stores/index.ts) 已启用 `pinia-plugin-persistedstate`

但当前产品层仍存在明显断层：

- 工具页面是“工具集合”，不是“研究流程”
- 用户需要自己记住步骤顺序、自己保留上一步输出、自己决定下一步去哪
- 现有工具分类是管理维度，不等于产品流程维度
- 用户刷新页面后，当前工具使用上下文不会自动恢复

## 核心设计决策

### 1. 页面形态

采用“单页流程工作台”方案，而不是多页面跳转壳层。

选择原因：

- 主人要求同一页面内连续保留步骤结果
- 自动承接上一步输出在单页状态模型中更自然
- 后续升级到后端持久化时，前端状态结构可以平移到服务端

不采用的方案：

- 不采用“左侧流程 + 右侧跳转到 `/tools/:id`”的轻壳方案，因为状态会碎片化
- 不采用通用拖拽式 pipeline builder，因为明显超过当前需求

### 2. 持久化策略

第一版使用前端本地持久化。

选择原因：

- 当前项目已具备 Pinia 持久化基础设施
- 能满足“刷新后恢复”的核心诉求
- 不需要立即改后端任务模型或新增工作流表

约束：

- 状态只在当前浏览器保存
- 不保证跨设备同步
- 用户切换账号时需要清空本地流程状态

### 3. 流程步骤与工具分类解耦

新增独立的“流程步骤映射”配置，不复用后台工具分类。

原因：

- 后台分类是管理视角
- 流程步骤是产品编排视角
- 一个分类不一定等于一个流程步骤
- 后续同一个工具可能同时出现在多个步骤场景中

因此第一版明确拆分：

- `tool_categories`：管理员维护的业务分类
- `workflow steps`：前端工作流页面的固定五步编排模型

## 流程范围

### 固定五步

沿用首页已确认的 AIDD 顺序：

1. 口袋探索
2. 分子生成或虚拟筛选
3. 分子对接及结合亲和力预测
4. 性质预测
5. 先导化合物优化

### 非目标

- 不做拖拽编排
- 不做多分支流程
- 不做跨设备同步
- 不改后端任务模型
- 不尝试自动适配所有工具

## 页面架构

新增独立路由：

- `GET /workflow` 对应前端页面路由 `/workflow`

页面采用三栏布局。

### 左栏：步骤导航栏

展示五个固定步骤。

每个步骤包含：

- 步骤序号
- 步骤名称
- 步骤状态
- 展开/收起控制
- 对应工具列表

工具列表规则：

- 由独立步骤配置驱动
- 每一步可配置多个工具
- 每一步只允许存在一个当前激活工具
- 支持推荐工具默认高亮

### 中栏：当前步骤工作区

根据当前选中步骤与工具动态展示：

- 步骤说明
- 工具说明
- 参数表单
- 自动带入的输入来源提示
- 运行按钮
- 当前任务状态
- 结果摘要
- “进入下一步”动作

表单渲染策略：

- 尽量复用当前单工具页的 schema 渲染逻辑
- 不重新发明表单协议

### 右栏：流程产物面板

集中展示当前工作流会话中的关键产物。

首批统一语义包括：

- `protein_structure`
- `pocket_structure`
- `generated_ligand`
- `virtual_screening_hits`
- `docking_pose`
- `affinity_report`
- `property_report`
- `optimized_lead`

每个产物展示：

- 名称
- 语义类型
- 来源步骤
- 来源工具
- 来源任务
- 创建时间
- 当前是否为默认绑定来源

## 前端目录与模块拆分

建议新增 `frontend/src/workflow/` 目录，集中管理工作流逻辑。

建议模块：

- `aidd-catalog.ts`
  - 固定五步定义
  - 步骤顺序
  - 步骤文案 key
  - 每一步下的工具 slug 列表
- `artifact-types.ts`
  - 标准化产物语义类型
  - 步骤状态类型
  - 会话模型类型
- `tool-bindings.ts`
  - 每个工作流工具的输入要求
  - 自动绑定字段映射
  - 输出提取规则
- `artifact-resolver.ts`
  - 根据现有产物池自动选取合适输入
  - 处理多个候选产物时的优先策略

建议新增 `frontend/src/stores/workflow.ts`，负责会话状态与持久化。

## 状态模型

### Workflow Session

建议核心状态包括：

- `sessionId`
- `activeStepKey`
- `selectedToolByStep`
- `stepFormDrafts`
- `taskByStep`
- `artifacts`
- `completedSteps`
- `invalidatedSteps`
- `lastUpdatedAt`
- `ownerUserId`

### Step State

每个步骤建议使用统一状态集：

- `idle`：未开始
- `ready`：输入已满足，可执行
- `running`：当前任务运行中
- `completed`：当前步骤已完成且结果有效
- `failed`：最近一次执行失败
- `invalidated`：曾完成，但被上游重跑导致结果失效
- `needs_tool_selection`：恢复流程时发现原工具已不可用

### Artifact

产物对象建议只保存可序列化元信息，不保存文件本体。

建议字段：

- `id`
- `semanticType`
- `name`
- `fileId`
- `url`
- `contentType`
- `toolSlug`
- `stepKey`
- `taskId`
- `createdAt`
- `isDefault`
- `metadata`

## 配置驱动模型

### 步骤配置

每个步骤配置：

- `key`
- `titleKey`
- `descriptionKey`
- `requiredInputTypes`
- `producedOutputTypes`
- `toolSlugs`
- `recommendedToolSlug`

### 工具绑定配置

只有显式接入工作流的工具才允许自动承接。

每个工具配置建议包含：

- `toolSlug`
- `acceptedInputTypes`
- `fieldBindings`
- `outputExtractors`
- `resultSummaryBuilder`

设计原则：

- 第一版不做通用“自动猜测”
- 不在配置里的工具仍可浏览，但不参与自动承接

## 任务执行与结果承接

### 执行方式

工作流页面不新增后端工作流 API，继续复用现有任务 API：

- 读取工具详情
- 渲染真实 schema
- 上传文件
- 创建普通任务
- 轮询任务详情

这意味着：

- 工作流只是前端编排层
- 后端仍然只认识单任务
- 不影响现有执行器与任务模型

### 自动带入策略

自动带入不依赖字段名猜测，而依赖工具绑定配置。

例如：

- 第 1 步口袋预测成功后，登记 `pocket_structure`
- 第 2 步如果工具声明需要 `pocket_structure`，则自动选取最新有效口袋文件并填入指定字段

若存在多个候选：

- 默认选择最新有效产物
- 在界面上明确标记“已自动选择最新结果”
- 允许用户手动切换绑定来源

### 重跑与失效传播

若用户重跑上游步骤：

- 不立即删除下游结果
- 但所有依赖该上游产物的后续步骤统一标为 `invalidated`
- 右侧产物面板保留旧产物，但标记为“基于旧输入”

原因：

- 直接清除会让用户丢失上下文
- 标记失效更符合研究过程中的比较需求

## 恢复与脏状态处理

本地持久化恢复时，需要处理以下异常情况：

### 工具失效

- 若恢复时发现原工具已下线、禁用或不存在
- 对应步骤状态标为 `needs_tool_selection`
- 页面提示用户重新选择工具

### 文件失效

- 若产物元信息存在，但 URL 已失效或文件不可访问
- 保留该产物条目
- 标记为“需重新上传/重新生成”

### 账号切换

- 工作流状态绑定 `ownerUserId`
- 若检测到当前登录用户与会话归属不一致，自动清空旧会话

## 页面入口

建议新增以下入口：

- 顶级路由 `/workflow`
- 首页 AIDD 流程区的“进入流程工作台”入口
- 工具列表页的“按流程使用工具”次级入口

这样用户既能从首页进入，也能从工具集合视角转到流程视角。

## 缺失工具的降级策略

步骤配置允许先定义完整流程，即使某些工具尚未上线。

页面行为：

- 若配置中的工具 slug 当前不存在，则显示“暂未上线”
- 若该步骤存在部分可用工具，则只展示可用项
- 若该步骤没有任何可用工具，则该步骤保持只读说明态

## 错误处理

### 自动带入失败

- 缺少所需输入语义时，明确提示缺少哪类产物
- 存在多个可用结果时，提示当前自动选择规则
- 配置字段与工具 schema 不匹配时，提示用户重新确认参数

### 任务失败

- 保留上次表单草稿
- 保留已绑定输入来源
- 允许用户在原地修改参数重试

### 恢复失败

- 若本地状态不完整或解析失败，允许用户一键重置流程

## 测试策略

### 静态表面测试

锁定以下内容：

- 存在 `/workflow` 路由
- 首页和工具页存在流程入口
- 存在 `workflow` store
- 存在 AIDD 步骤配置文件

### 纯逻辑测试

覆盖：

- 产物选择优先级
- 自动绑定规则
- 步骤状态流转
- 上游重跑导致下游失效

### 组件级测试

至少覆盖：

- 上一步成功后下一步自动变为可执行
- 恢复本地会话后正确回显当前步骤与产物
- 重跑上游后下游步骤显示失效态

### 构建验证

- `node --test`
- `npm run build`

## 风险与控制

### 风险 1：工作流配置与真实工具 schema 脱节

控制方式：

- 仅对已显式配置工具启用自动承接
- 配置异常时回退为手动填写

### 风险 2：本地持久化产生脏会话

控制方式：

- 状态中记录版本号与用户 ID
- 恢复时执行兼容检查
- 提供“新建流程”清空入口

### 风险 3：第一版范围膨胀

控制方式：

- 固定五步
- 单步骤单激活工具
- 不做多分支
- 不做拖拽

## 验收标准

- 用户可以在一个页面内按 AIDD 顺序完成多步工具使用
- 页面刷新后能够恢复当前工作流状态
- 上一步结果可以自动带入下一步
- 用户可以查看并切换每一步的输入来源
- 上游重跑后，下游结果会被明确标记为失效
- 缺失工具、缺失文件、配置失配时页面不会崩溃，并能给出可理解提示
