# 团队协作开发规范与教程

## 1. 目标

本规范面向刚组建的平台研发团队，目标是让多人并行开发时做到：

- 每个人知道自己负责哪个模块、改动边界在哪里。
- 每个需求从设计、开发、测试、评审到合并都有固定流程。
- 分支、提交、合并、发布和回滚有明确规则。
- 稳定可上线版本、beta 版本、开发版本互不污染。
- 新人可以按教程完成第一条安全开发链路。

本规范优先服务当前平台改造期。改造期内最重要的不是追求流程复杂，而是避免无序提交、交叉覆盖、线上版本不可追踪和功能半成品混入稳定分支。

## 2. 核心原则

1. **稳定分支必须随时可发布**：稳定分支只能进入验收通过的版本。
2. **所有功能从开发分支进入**：不能直接在稳定分支写功能。
3. **小步提交，小步合并**：一个 PR 只解决一个明确问题。
4. **先设计后施工**：涉及模块边界、数据结构、接口契约、工作流、执行器和 Artifact 的改动，必须先更新设计文档或实施计划。
5. **先测试后合并**：没有测试或验收记录的 PR 不允许进入 beta 或 stable。
6. **先保护用户链路**：任何改动不得破坏 Fetch PDB -> Protein Preparation -> LVpocket 和 PubChem -> Ligand Preparation -> RDKit -> ADMET 两条主链路。
7. **不在 PR 中混入无关改动**：格式化、重构、功能、修复、文档尽量拆开。

## 3. 分支模型

### 3.1 长期分支

| 分支 | 角色 | 稳定性 | 允许合并来源 | 说明 |
| --- | --- | --- | --- | --- |
| `main` | 稳定可上线版本 | 最高 | `release/*`、`hotfix/*` | 只保存已验收、可部署、可回滚版本 |
| `beta` | 预发布验收版本 | 高 | `develop`、`release/*` | 用于集成测试、产品验收和演示环境 |
| `develop` | 日常集成开发分支 | 中 | `feature/*`、`fix/*`、`refactor/*`、`docs/*` | 团队日常开发合并入口 |

当前仓库已有历史分支，例如 `v1.0-7.28`、`v1.1`、`v3` 等。后续建议统一过渡为上述三层长期分支：

- `main`：稳定生产线。
- `beta`：预发布验证线。
- `develop`：日常集成线。
- 历史版本分支保留为归档或维护分支，不再作为新功能日常开发入口。

### 3.2 临时分支

| 分支类型 | 命名格式 | 用途 | 合并目标 |
| --- | --- | --- | --- |
| 功能 | `feature/<module>-<short-topic>` | 新功能 | `develop` |
| 修复 | `fix/<module>-<short-topic>` | 普通缺陷修复 | `develop` |
| 重构 | `refactor/<module>-<short-topic>` | 不改变行为的结构改造 | `develop` |
| 文档 | `docs/<topic>` | 文档更新 | `develop` |
| 发布 | `release/v<major>.<minor>.<patch>` | 准备 beta 到 stable 的版本 | `beta` 和 `main` |
| 热修 | `hotfix/v<major>.<minor>.<patch>-<short-topic>` | 稳定版本紧急修复 | `main`，随后回合 `beta` 和 `develop` |
| 实验 | `spike/<topic>` | 技术验证，不保证合并 | 原则上不直接合并 |

示例：

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/workflow-run-preparation
```

### 3.3 分支保护规则

`main` 必须启用保护：

- 禁止直接 push。
- 必须通过 PR 合并。
- 必须至少 1 名 reviewer 通过。
- 必须通过 CI。
- 必须有版本号和发布说明。

`beta` 建议启用保护：

- 禁止直接 push。
- 必须通过 PR 合并。
- 必须通过核心自动化测试。
- 必须有验收记录。

`develop` 建议启用基本保护：

- 禁止 force push。
- 至少通过基础 CI。
- 大改动必须 reviewer 通过。

## 4. 版本与发布通道

### 4.1 版本号规则

采用语义化版本：

```text
v主版本.次版本.修订版本
```

- 主版本：架构或兼容性重大变化，例如 `v2.0.0`。
- 次版本：新增模块能力，例如 `v1.1.0`。
- 修订版本：bugfix 或小范围修复，例如 `v1.1.1`。

预发布版本：

```text
v1.1.0-beta.1
v1.1.0-rc.1
```

### 4.2 发布通道

| 通道 | 对应分支 | 适用环境 | 说明 |
| --- | --- | --- | --- |
| dev | `develop` | 开发环境 | 允许不稳定，但不能长期红灯 |
| beta | `beta` | 预发布 / 演示 / 业务验收环境 | 功能完整，允许发现验收问题 |
| stable | `main` | 生产或正式交付环境 | 必须可上线、可回滚、可审计 |

### 4.3 发布流程

1. 从 `develop` 创建 `release/vX.Y.Z`。
2. 在 release 分支只允许修复阻断问题、更新版本号、更新发布说明。
3. 合并到 `beta`，部署预发布环境。
4. 完成验收测试和回归测试。
5. 合并到 `main`。
6. 打 tag：`vX.Y.Z`。
7. 将 release 分支变更回合到 `develop`。

建议命令：

```bash
git switch develop
git pull --ff-only origin develop
git switch -c release/v1.1.0

# 验收通过后，由 PR 合并 release/v1.1.0 -> beta
# beta 验收通过后，由 PR 合并 release/v1.1.0 -> main

git tag -a v1.1.0 -m "release: v1.1.0"
git push origin v1.1.0
```

## 5. 模块分工

### 5.1 责任域划分

| 责任域 | 主要目录 | 负责人类型 | 主要职责 |
| --- | --- | --- | --- |
| 平台内核 | `backend/app/services/`、`backend/app/models/`、`backend/app/schemas/` | 后端负责人 / 架构负责人 | Tool Contract、Run Preparation、Task Command、Workflow Orchestration |
| Artifact 与文件 | `backend/app/artifact_standards/`、`backend/app/files/`、`backend/app/storage/` | 后端负责人 | ArtifactVersion、file role、metadata、下载、持久化 |
| 执行器与任务 | `backend/app/tasks/`、`backend/app/execution/`、`backend/app/worker/` | 后端 / 运维负责人 | Docker、SSH、Remote API、日志、取消、输出回收 |
| 外部数据库与药研工具 | `backend/app/external_databases/`、`backend/app/protein_preparation/`、`backend/app/chemistry/`、`backend/app/worker/tools/` | CADD / 后端协作 | Fetch PDB、PubChem、蛋白处理、配体处理、RDKit、ADMET |
| 工具注册与模板 | `backend/app/tool_packages/`、`backend/app/tool_templates/`、`backend/app/remote_tools/` | 平台工具负责人 | Tool Package、Remote API 自注册、示例工具、smoke test |
| 前端工作台 | `frontend/src/views/workflow/`、`frontend/src/components/workflow/`、`frontend/src/workflow/` | 前端负责人 | 工作流画布、节点面板、预检展示、保存加载 |
| 前端工具和任务 | `frontend/src/views/tools/`、`frontend/src/views/tasks/`、`frontend/src/domain/tools/`、`frontend/src/domain/tasks/` | 前端负责人 | 工具详情、一键示例、任务中心、Task View |
| 可视化 | `frontend/src/components/artifacts/` | 前端 / CADD 协作 | protein、ligand、pocket、table、report renderer |
| 管理后台 | `frontend/src/domain/admin/`、后台管理 API | 前后端协作 | 标签、分类、renderer、executor profile、发布治理、审计 |
| 测试和发布 | `test/`、`frontend/src/**/*.spec.ts`、`.github/workflows/`、`docs/verification/` | QA / DevOps / 模块负责人 | 自动化测试、E2E、CI、发布验证 |

### 5.2 分工规则

- 每个模块必须有一个 owner。
- owner 不一定写所有代码，但必须负责接口一致性、评审和验收。
- 跨模块改动必须提前在 PR 描述中列出影响范围。
- 改动 Architecture Kernel Interface 时，必须通知所有相关 owner。
- 新人优先从文档、测试、局部组件和非核心工具 adapter 开始，不直接修改 Run Preparation、Task Command、Workflow Scheduler 等核心路径。

## 6. 开发流程

### 6.1 标准流程

```text
需求/问题
  -> 判断模块归属
  -> 写设计或任务说明
  -> 创建分支
  -> 本地开发
  -> 本地测试
  -> 提交 PR
  -> Code Review
  -> CI 通过
  -> 合并 develop
  -> beta 验收
  -> stable 发布
```

### 6.2 需求开始前

开发前必须明确：

- 需求属于哪个模块。
- 是否影响 Tool Contract、Artifact、Task、Workflow、Executor、Renderer、Governance。
- 是否需要更新文档。
- 是否需要迁移数据。
- 是否需要 feature flag。
- 验收场景是什么。

如果影响以下内容，必须先写设计文档或更新现有架构文档：

- Standard Artifact 类型、role、metadata。
- Tool Contract 字段。
- Run Preparation、BindingDecision、PreparedRun。
- Result Manifest。
- Task、ExecutionRecord、Executor Gateway。
- WorkflowDefinition、WorkflowRun、NodeTaskBinding。
- 权限、安全、发布、部署。

### 6.3 开发中

开发者每天至少保持：

```bash
git status --short
git fetch origin
```

提交前必须确认：

- 没有误提交本地日志、数据库、缓存、模型大文件。
- 没有把无关格式化混入功能提交。
- 没有覆盖他人未合并变更。
- 没有跳过测试。

### 6.4 提交 PR 前

后端建议至少运行：

```bash
python -m pytest test/ -v
python -m flake8 backend/app --select F401
```

前端建议至少运行：

```bash
cd frontend
npm run test
npm run build
```

工作流、可视化、关键用户链路变更建议追加：

```bash
cd frontend
npm run test:e2e -- --project=chromium --reporter=list --workers=1
```

文档变更建议运行：

```bash
git diff --check
```

## 7. 提交规范

### 7.1 Commit Message

使用 Conventional Commits：

```text
<type>(<scope>): <summary>
```

常用 type：

| type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(workflow): add node task binding hydration` |
| `fix` | 缺陷修复 | `fix(tasks): preserve cancellation status` |
| `docs` | 文档 | `docs(architecture): define run preparation rollout` |
| `refactor` | 不改行为的重构 | `refactor(workflow): split scheduler planning` |
| `test` | 测试 | `test(frontend): cover workflow preflight states` |
| `chore` | 构建、配置、杂项 | `chore(ci): add backend lint job` |
| `perf` | 性能优化 | `perf(tasks): reduce task view query payload` |

scope 建议使用模块名：

```text
artifact
tool-contract
run-preparation
tasks
executor
workflow
renderer
admin
frontend
backend
docs
ci
```

### 7.2 提交粒度

一个 commit 应该满足：

- 能用一句话解释。
- 不混入无关模块。
- 不包含临时调试代码。
- 最好能独立回滚。

不推荐：

```text
fix: update all
feat: many changes
wip
```

推荐：

```text
feat(run-preparation): return binding decision for missing artifact role
test(workflow): cover saved node task binding hydration
docs(development): define branch and release policy
```

## 8. PR 规范

### 8.1 PR 标题

PR 标题使用和 commit 类似的格式：

```text
feat(workflow): hydrate saved node task bindings
```

### 8.2 PR 描述必须包含

- 背景和目标。
- 改动范围。
- 影响模块。
- 测试结果。
- 风险和回滚方式。
- 截图或录屏，适用于前端 UI 改动。
- 文档更新，适用于架构、接口、部署或流程变更。

### 8.3 PR 大小

建议：

- 小 PR：小于 300 行变更，优先。
- 中 PR：300-800 行，需要说明拆分原因。
- 大 PR：超过 800 行，必须提前拆分或写清楚不可拆原因。

不允许把以下内容混在一个 PR：

- 大范围格式化 + 功能开发。
- 后端契约改动 + 前端全量 UI 重做。
- 数据迁移 + 无关 bugfix。
- 多个无关模块的“顺手修复”。

### 8.4 Review 规则

| 改动类型 | 最低 reviewer |
| --- | --- |
| 文档、小 UI、小 bugfix | 1 人 |
| 后端核心模块、工作流、任务、执行器 | 1 名模块 owner + 1 名普通 reviewer |
| 数据库迁移、权限、安全、部署 | 1 名模块 owner + 1 名运维/负责人 |
| `main` 发布或 hotfix | 技术负责人确认 |

Review 重点：

- 是否符合模块边界。
- 是否破坏已有用户链路。
- 是否有测试或验收记录。
- 是否有回滚方式。
- 是否引入重复逻辑。
- 是否把领域逻辑写进页面或执行器 adapter。

## 9. 合并规范

### 9.1 合并到 develop

合并条件：

- PR 描述完整。
- reviewer 通过。
- CI 通过。
- 本地冲突解决完成。
- 测试结果写入 PR。

推荐使用 squash merge，保持主线历史清晰。

### 9.2 合并到 beta

合并条件：

- 从 `develop` 创建 release PR 或集成 PR。
- P0 自动化测试通过。
- 两条主链路至少完成一次验收。
- 有 beta 验收说明。

### 9.3 合并到 main

合并条件：

- beta 验收通过。
- 发布说明完成。
- 版本号确定。
- 回滚方案明确。
- 无阻断 bug。

### 9.4 禁止操作

以下操作没有明确批准不得执行：

- 直接 push 到 `main`、`beta`。
- 对共享分支执行 `git push --force`。
- 对共享分支执行 `git reset --hard` 后推送。
- 合并未通过 CI 的 PR。
- 为了绕过冲突直接覆盖他人文件。

## 10. 冲突处理教程

冲突处理流程：

1. 先确认自己分支状态：

```bash
git status --short
```

2. 拉取目标分支最新代码：

```bash
git fetch origin
```

3. 推荐使用 rebase 整理个人分支：

```bash
git rebase origin/develop
```

4. 逐个文件解决冲突。
5. 运行相关测试。
6. 继续 rebase：

```bash
git rebase --continue
```

7. 推送个人分支：

```bash
git push --force-with-lease origin feature/<module>-<topic>
```

注意：`--force-with-lease` 只允许用于自己的临时分支，不能用于 `main`、`beta`、`develop`。

如果冲突涉及以下内容，必须找模块 owner 一起处理：

- 数据库模型。
- Tool Contract。
- Artifact 标准。
- Run Preparation。
- WorkflowDefinition。
- Executor Gateway。
- 权限、安全、部署配置。

## 11. Hotfix 流程

当 stable 出现阻断问题时使用 hotfix。

流程：

```text
main
  -> hotfix/vX.Y.Z-topic
  -> main
  -> tag vX.Y.Z
  -> beta
  -> develop
```

步骤：

1. 从 `main` 创建 hotfix 分支。
2. 只修复紧急问题，不做顺手重构。
3. 运行最小必要测试和相关回归。
4. PR 合并到 `main`。
5. 打修订版本 tag。
6. 将 hotfix 回合到 `beta` 和 `develop`，避免问题回归。

## 12. 模块开发教程

### 12.1 新人第一次接任务

1. 阅读 `docs/README.md`。
2. 阅读与任务相关的模块文档。
3. 找到模块 owner。
4. 从 `develop` 创建个人分支。
5. 先跑一遍相关测试，确认本地环境可用。
6. 做最小改动。
7. 自测。
8. 提 PR。
9. 根据 review 修改。
10. 合并后观察 beta 或 develop 环境状态。

### 12.2 新工具开发

新工具必须按以下顺序：

1. 确认输入输出 Standard Artifact。
2. 编写 Tool Contract。
3. 准备 example inputs。
4. 准备 smoke test。
5. 选择 executor。
6. 输出 Result Manifest。
7. 配置 renderer mapping。
8. 在工具详情页验证一键示例。
9. 在工作流验证节点独立运行。
10. 在工作流验证自动绑定上下游。

禁止：

- 只让工具在某个页面可运行。
- 工具输出只放临时目录，不进入 Artifact。
- 为新工具写 workflow 专属适配。

### 12.3 新工作流能力开发

新工作流能力必须优先判断是否属于：

- Tool Contract。
- Run Preparation。
- Result Manifest。
- Workflow Orchestration。
- Renderer Registry。

如果能力可以在这些地基模块解决，不允许只在画布页面写特判。

### 12.4 前端 UI 开发

前端开发规则：

- `views` 负责页面组合。
- `components` 负责可复用 UI。
- `domain` 负责领域展示模型和状态转换。
- `workflow` 负责工作流纯函数和画布领域逻辑。
- 不在 Vue 页面中拼后端执行 payload。
- 不按工具 slug 硬编码 Artifact renderer。

### 12.5 后端开发

后端开发规则：

- API 层只做请求解析、鉴权和调用 application/module Interface。
- 业务决策不写在路由函数里。
- executor adapter 不决定 Artifact 语义。
- Task 创建必须走 Task Command。
- 工具运行准备必须走 Run Preparation。
- 标准输出必须走 Result Manifest Collector。

## 13. 测试规范

### 13.1 测试分层

| 测试类型 | 目标 | 触发时机 |
| --- | --- | --- |
| 单元测试 | 验证纯函数、领域规则、Interface 行为 | 每个 PR |
| 集成测试 | 验证 API、数据库、任务、Artifact、workflow 协作 | 关键模块 PR |
| E2E 测试 | 验证真实用户流程 | 工作流、任务、工具、可视化变更 |
| 手工验收 | 验证复杂科研链路 | beta 发布前 |
| 回归测试 | 验证历史 bug 不复现 | release 和 hotfix |

### 13.2 必测主链路

每次 beta 或 stable 发布前至少验证：

- Fetch PDB -> Protein Preparation -> LVpocket。
- Fetch PubChem Ligand -> Ligand Preparation -> RDKit Properties -> ADMET。
- 保存工作流、刷新页面、重新加载、恢复节点任务和产物。
- 节点独立运行。
- 工具详情页一键填入示例。
- 任务中心查看任务、日志、输出和错误。

### 13.3 测试记录

PR 中必须写明：

```text
测试：
- [x] python -m pytest test/ -v
- [x] npm run test
- [ ] npm run test:e2e -- --project=chromium --reporter=list --workers=1
- [x] 手工验证：Fetch PDB -> Protein Preparation -> LVpocket
```

如果某项测试未运行，必须说明原因。

## 14. 文档规范

以下改动必须更新文档：

- 新增功能模块。
- 修改核心领域模型。
- 修改 Tool Contract。
- 修改 Standard Artifact。
- 修改 Run Preparation 或 BindingDecision。
- 修改部署、执行器、队列、环境变量。
- 修改工作流保存格式。
- 修改团队流程、分支策略或发布流程。

文档归属：

- 产品目标和用户场景：`docs/product/`。
- 企业交付材料：`docs/delivery/`。
- 架构和模块边界：`docs/architecture/`。
- 路线图：`docs/roadmap/`。
- 团队协作和开发教程：`docs/development/`。
- 验收记录：`docs/verification/`。

## 15. 安全与配置规范

- 不提交 `.env` 中的真实密钥。
- 不提交生产数据库、SQLite 本地数据库、任务输出、模型大文件和缓存目录。
- 不在日志中打印 token、密码、私钥、外部服务凭证。
- 生产配置修改必须经过 review。
- 远端 API 注册、SSH 凭证、执行器 profile 属于管理后台治理范围。
- 涉及删除数据、批量迁移、生产操作必须单独确认。

## 16. Definition of Done

一个任务完成必须满足：

- 功能符合需求。
- 模块边界清晰。
- 相关测试通过。
- PR 描述完整。
- 文档已更新或说明无需更新。
- 风险和回滚方式明确。
- reviewer 通过。
- 没有遗留临时代码、调试日志、无关改动。

涉及平台地基的任务还必须满足：

- 不新增页面级运行特判。
- 不绕过 Run Preparation。
- 不绕过 Result Manifest。
- 不破坏 Standard Artifact lineage。
- 不让新工具接入依赖 workflow 专属代码。

## 17. 团队角色建议

刚组建团队可以先按轻量角色运作，一人可兼多职，但职责不能缺失：

| 角色 | 职责 |
| --- | --- |
| 产品负责人 | 明确需求优先级和验收场景 |
| 技术负责人 | 守住架构边界、分支策略、发布质量 |
| 模块 owner | 对负责模块的 Interface、测试和质量负责 |
| 开发者 | 按规范开发、测试、提交 PR |
| Reviewer | 检查正确性、边界、测试、风险 |
| QA / 验收负责人 | 维护验收脚本和回归记录 |
| DevOps / 运维负责人 | 管理 CI、部署、环境、回滚和资源 |

## 18. 每周协作节奏

建议节奏：

- 周一：确认本周目标、模块 owner、风险点。
- 每天：10-15 分钟同步阻塞问题，不讨论长设计。
- PR 随开随审，不堆到周五。
- 周三：检查 develop 稳定性和 beta 候选范围。
- 周五：整理已合并、未合并、阻塞问题和下周风险。
- 发布前：单独开 release checklist，不在普通站会中顺带发布。

## 19. 常见错误和处理

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 直接在稳定分支开发 | 稳定版本不可控 | 从 `develop` 拉 feature 分支 |
| PR 太大 | Review 失效，冲突变多 | 拆成设计、后端、前端、测试多个 PR |
| 页面里写运行逻辑 | 多入口行为不一致 | 放入 Run Preparation 或 domain 纯函数 |
| 工具输出不标准 | 下游无法自动绑定 | 输出 Result Manifest 并创建 ArtifactVersion |
| 不写测试 | 回归风险不可控 | 至少覆盖改动模块的单元或验收测试 |
| hotfix 不回合 develop | 下个版本问题复发 | hotfix 合并 main 后必须回合 beta/develop |
| 标签硬编码 | 新工具无法筛选 | 走 Governance Registry |

## 20. 第一阶段落地建议

团队刚开始不需要一次性把流程全部工具化。建议第一阶段先落实以下 10 条：

1. 建立 `main`、`beta`、`develop` 三层长期分支。
2. 禁止直接 push `main` 和 `beta`。
3. 所有开发从 `feature/*`、`fix/*`、`docs/*` 分支开始。
4. 所有合并走 PR。
5. PR 必须写测试结果。
6. 大改动必须先更新设计文档。
7. 每个模块指定 owner。
8. beta 发布前跑两条主链路。
9. stable 发布必须打 tag。
10. hotfix 必须回合 `beta` 和 `develop`。

只要这 10 条执行稳定，团队就能先避免最常见的协作事故，再逐步补齐自动化、权限保护、发布报告和质量看板。
