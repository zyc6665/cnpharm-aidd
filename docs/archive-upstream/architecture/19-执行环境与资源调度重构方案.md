# 执行环境与资源调度重构方案

| 文档项 | 内容 |
| --- | --- |

| 文档版本 | v1.0 |
| 文档状态 | 重构基线 |
| 修订日期 | 2026-09-28 |
| 适用范围 | Tool Contract、Tool Package、Task、Executor Gateway、资源调度和管理后台 |

## 1. 重构结论

平台生产环境只使用平台可管理的计算执行环境：

1. `k8s_job` 是生产主执行器。
2. `ssh_job` 是没有 Kubernetes 集群时的过渡执行器，也可以连接现有集群登录节点或调度入口。
3. `docker_image` 和 `python_script` 不再作为独立的生产调度器，而是运行时描述，必须映射到 `k8s_job` 或 `ssh_job`。
4. `remote_api` 只保留为外部系统兼容连接器，不作为新模型的生产部署路径，也不承担平台主资源调度。
5. 模型不运行在 FastAPI、Celery 或 WebSocket 进程中。每个重计算任务都必须落到独立 Job、远程进程或远程容器。

“模型和平台部署在一起”指平台控制面与模型计算面处于同一受控网络或同一 Kubernetes 计算域，不指把模型代码塞进 API 进程。

## 2. 为什么重构

Remote API 的真实 GPU、CPU、并发、队列和限额在平台外部，平台无法凭工具配置准确观察或控制。继续为 Remote API 增加容量租约，只能做近似限流，不能替代实际资源调度。

Kubernetes 和 SSH 执行环境可以提供可验证的边界：

- 平台可以提交、查询、取消和回收一次执行。
- Kubernetes Scheduler 或受控远程节点负责真实资源分配。
- 平台可以对用户、项目、队列和工具做逻辑准入。
- 任务、尝试、日志和结果可以用稳定的 `task_id`、`attempt_id` 关联。

## 3. 统一执行模型

```text
Tool Package
  -> Tool Contract
  -> Run Preparation
  -> Task / ExecutionAttempt
  -> Platform admission
  -> K8s Job or SSH Job
  -> Result Manifest
  -> ArtifactVersion
```

### 3.1 执行器分类

| 类型 | 生产定位 | 真实资源由谁分配 | 新工具是否允许 |
| --- | --- | --- | --- |
| `k8s_job` | 标准生产执行器 | Kubernetes Scheduler | 允许 |
| `ssh_job` | 裸机、已有服务器或过渡集群 | 受控节点、Slurm 或远程容器 | 允许 |
| `docker_image` | 容器运行时描述 | 映射到 K8s 或 SSH | 不作为独立生产入口 |
| `python_script` | 脚本运行时描述 | 映射到 K8s 或 SSH | 不作为独立生产入口 |
| `remote_api` | 外部系统兼容连接器 | 外部系统自行负责 | 仅兼容旧工具 |

### 3.2 K8s Job 主流程

```text
Task Scheduler
  -> K8s Adapter Worker
  -> 创建带 task_id/attempt_id 标签的 Job
  -> Pod Pending / Running / Succeeded / Failed
  -> 状态、日志、Events reconcile
  -> 收集 result.manifest.json
  -> 持久化 ArtifactVersion
```

K8s Adapter 不自行选择节点。它只把平台批准的 Resource Profile 映射为 Job 的 requests、limits、节点池标签、PriorityClass 和存储策略。

### 3.3 SSH Job 过渡流程

```text
Task Scheduler
  -> SSH Adapter
  -> 创建 attempt 工作目录
  -> 上传输入清单和必要文件
  -> 启动受控脚本或容器
  -> 读取进程/调度器状态和日志
  -> 取消、清理、回收结果
```

SSH 节点必须注册能力和容量。平台不能接受普通用户提交任意主机、任意命令或任意凭据；节点、认证、工作目录和可用运行时由管理员配置。

## 4. Resource Profile 重构

ToolVersion 不再自由组合一组资源字段作为生产调度依据，而是引用平台批准的资源档位：

```yaml
resource_profile: gpu-large
```

档位由管理员治理：

```yaml
profiles:
  cpu-small:
    cpu: 2
    memory_gb: 4
    gpu_count: 0
    timeout_minutes: 30
  gpu-large:
    cpu: 16
    memory_gb: 64
    gpu_count: 1
    gpu_type: H100
    timeout_minutes: 480
```

平台在任务创建时执行项目、用户、队列和并发准入；Kubernetes 或 SSH 节点在执行时完成真实资源分配。`gpu_memory_mb` 只能作为兼容元数据或资源档位辅助信息，不能被当成普通 GPU 切分承诺。

## 5. Task 生命周期

统一状态流：

```text
pending
  -> admitted
  -> submitting
  -> queued
  -> running
  -> collecting
  -> succeeded / failed / canceled
```

补充规则：

- K8s Job 已创建但 Pod Pending 时，Task 保持 `queued`，并记录 Pending 原因。
- Adapter 提交失败不得伪造成功或直接释放未确认的远程执行。
- 重试必须创建新的 `ExecutionAttempt` 和新的 Job/远程进程。
- 旧 attempt 未确认终止前，不允许复用其资源租约或覆盖新 attempt 结果。
- Job、Pod、SSH 进程和 Artifact 输出都必须带 `task_id`、`attempt_id`、`tool_version_id`。

## 6. Tool Package 与管理员流程

模型交付包只负责声明代码、不可变镜像 digest、权重、adapter、Artifact 契约和运行入口；发布交付包后，平台将其绑定到受控执行环境。Namespace、ServiceAccount、集群凭据和节点池属于平台执行环境配置，不进入 ToolVersion。

管理员上线新模型的标准流程：

1. 登记 Tool Package。
2. 通过签名、digest 和 manifest 校验。
3. 选择 `Kubernetes` 或 `SSH` 执行环境。
4. 选择批准的 Resource Profile。
5. 配置镜像 digest、入口、权重挂载和输入输出目录；选择已批准的 Resource Profile。
6. 创建 smoke test Job。
7. 检查日志、结果 Manifest 和 Artifact 输出。
8. 发布 ToolVersion。

管理后台不再把 Docker、Python、Remote API 作为与 Kubernetes、SSH 同等级的生产部署选项。

### 6.1 K8s 模型注册契约

Tool Package v2 只声明运行时能力和不可变镜像，管理员在注册 ToolVersion 时选择变体和平台资源档位。最小绑定结果如下：

```yaml
type: k8s_job
variant: nvidia-cuda
runtime:
  image: registry.example/model:1.0.0@sha256:<64-hex-digest>
  entrypoint:
    - runner/platform_run_v2.sh
resource_profile: gpu-large
```

注册规则：

- `runtime.executor_support` 必须包含 `k8s_job`。
- 主运行时必须是带 `sha256` digest 的 container；不得使用 `latest` 或可变 tag 作为执行镜像。
- `resource_profile` 必须来自平台 Resource Profile Registry；Tool Package 不得自行覆盖 CPU、内存、GPU、超时和并发字段。
- `cluster_alias`、`namespace`、`credential_ref`、`service_account`、镜像拉取 Secret 和节点选择策略由执行环境配置提供，不进入 Tool Package 或 ToolVersion 的用户可编辑配置。
- 变体的输入输出契约保持不变，CPU/GPU 变体只能改变运行时和资源要求，不能改变 Standard Artifact 语义。

K8s Job 的结果使用平台绑定的对象存储前缀，不通过 Pod 文件系统回收。平台为 Job 注入以下受控环境变量；对象存储访问 Secret 只存在于 `sciminer-model-jobs`，不得使用 Tool Package 内的明文凭据：

```text
SCIMINER_OBJECT_STORAGE_ENDPOINT
SCIMINER_OBJECT_STORAGE_BUCKET
SCIMINER_OBJECT_STORAGE_ACCESS_KEY
SCIMINER_OBJECT_STORAGE_SECRET_KEY
SCIMINER_EXECUTION_OUTPUT_PREFIX=executions/<namespace>/<job-name>
SCIMINER_RESULT_OBJECT=executions/<namespace>/<job-name>/result.json
```

模型运行时必须先上传 `SCIMINER_EXECUTION_OUTPUT_PREFIX` 下的全部输出文件，再上传 `result.json`。`result.json` 必须是 `aidd.sciminer/result.v2`，其中每个文件引用的路径只能是相对路径，且 SHA-256 必须匹配对象内容。Worker 下载并校验结果后，才将文件复制到平台 File 记录并创建标准 ArtifactVersion；缺失结果、路径越界或校验失败都必须使任务失败，不能以“Job 成功”代替产物成功。

输入由 Worker 在创建 Job 前上传到 `inputs/<task-id>/<attempt-id>/<input-name>/<filename>`，并通过 `SCIMINER_INPUTS_JSON` 传递 `name`、对象 `uri`、`artifact_version_id` 和 SHA-256。模型 runner 必须下载并验证这些对象，不能把用户本地路径或后端数据库路径直接放进 Job。

## 7. Adapter 最小接口

```text
submit(request) -> ExecutionHandle
inspect(handle) -> ExecutionStatus
cancel(handle) -> CancelResult
logs(handle, cursor?) -> ExecutionLogs
collect(handle) -> CollectedOutputs
reconcile(handle) -> ExecutionStatus
```

`ExecutionHandle` 保存 namespace/job_name、SSH host/job id、日志游标和外部状态等私有字段。Task、Workflow 和 Artifact 层只依赖统一接口，不读取 K8s 或 SSH 私有字段。

Worker 通过进程级 `ExecutionService` 注册适配器。任务执行器只取得 Gateway，不自行创建 Kubernetes SDK、kubeconfig 或 SSH 凭据；未配置的 adapter 必须明确失败，不能回退到 Docker/Python 或 Remote API。

## 8. 迁移边界

### 8.1 立即冻结

- 不再为新工具增加 Remote API 资源能力。
- 不再新增独立 Docker/Python 生产队列。
- 暂时保留已有 `remote_api`、`docker_image`、`python_script` 配置用于兼容和迁移。

### 8.2 第一阶段

- 增加 `k8s_job` Tool Contract 类型和 K8s Adapter 接口。
- 将 Docker/Python 运行字段映射到 K8s Job runtime。
- 建立 Resource Profile Registry。
- 统一 Job 创建、状态 reconcile、日志、取消和结果回收。

### 8.3 第二阶段

- AlphaFold 3、OpenDDE、分子生成、虚拟筛选等模型优先迁移到 K8s Job。
- SSH 作为无集群部署和历史工具的兼容路径。
- 为旧 Remote API 工具增加 legacy 标记和迁移提示。

### 8.4 第三阶段

- 关闭新建 Remote API 入口。
- 旧 Docker/Python 工具全部转换为 K8s/SSH runtime 配置。
- 删除远程容量租约作为主调度机制的产品入口，仅保留兼容读取和迁移逻辑。

## 9. 非目标

- 平台不替代 Kubernetes Scheduler。
- 平台不自行选择具体计算节点。
- 平台不把常驻模型服务作为默认部署形态。
- 平台不允许用户提交任意镜像、Shell、Namespace、节点名称或长期凭据。
- 平台不把一次 smoke test 当作科学验证结论。
