# 部署与计算资源架构

> 本文按 [执行环境与资源调度重构方案](./19-执行环境与资源调度重构方案.md) 执行。Kubernetes Job 是生产主路径，SSH Job 是过渡路径；Remote API、独立 Docker 和独立 Python worker 不再作为新模型生产执行方式。

## 1. 部署目标

平台需要同时支持本地研发调试、小规模单机部署、私有服务器部署和重计算集群部署。部署架构应让工具开发者不需要关心平台内部表结构，让平台管理员能按资源类型管理执行环境。

## 2. 环境分层

| 环境 | 用途 | 数据库 | 存储 | 队列 | 执行方式 |
| --- | --- | --- | --- | --- | --- |
| 本地开发 | 快速联调 | SQLite | local | direct / memory | builtin、python、少量 ssh |
| 单机演示 | 小团队试用 | SQLite/PostgreSQL | local/MinIO | Celery + Redis | builtin、python、docker |
| 私有服务器 | 实验室部署 | PostgreSQL | MinIO | Celery + Redis | ssh_job，必要时使用 K8s |
| 集群生产 | 多用户重计算 | PostgreSQL HA | MinIO/S3 | Redis/RabbitMQ | k8s_job，ssh_job 作为过渡 |

## 3. 逻辑部署架构

```text
用户浏览器
  │
  ▼
Nginx / Gateway
  │
  ├─ Frontend Static / Vite Dev
  └─ FastAPI Backend
       │
       ├─ PostgreSQL / SQLite
       ├─ Redis / Memory Cache
       ├─ MinIO / Local Storage
       ├─ Celery / Adapter Workers
       │    ├─ task admission worker
       │    ├─ k8s job adapter
       │    └─ ssh job adapter
       └─ Realtime / WebSocket / Polling
```

## 4. 执行器分类

### 4.1 平台轻量兼容能力

用于平台内嵌轻量能力，例如：

- Fetch PDB。
- Fetch PubChem ligand。
- RDKit 基础性质。
- 文件格式轻量转换。
- 简单蛋白结构检查。

特点：

- 启动快。
- 与平台同进程或 worker 进程运行。
- 适合 CPU 轻任务。
- 不适合长时重计算。

### 4.2 Python Runtime（非独立生产执行器）

用于平台托管 Python 脚本或包。

特点：

- 适合内部工具原型。
- 依赖管理容易膨胀。
- 生产环境应逐步迁移到 Tool Package 或 Docker。

### 4.3 Docker Runtime（非独立生产执行器）

用于镜像化工具。

特点：

- 隔离依赖。
- 适合开源 CADD 工具。
- 可映射输入目录、输出目录和权重目录。
- 需要限制 CPU、内存、GPU 和运行时长。

### 4.4 SSH Job Executor

用于提交到已有远端服务器或集群登录节点。

特点：

- 适合复用已有 GPU/CPU 服务器。
- 可对接手工管理的 conda 环境和脚本。
- 需要严格处理上传、运行目录、日志、取消和清理。
- 后续应作为 Slurm/K8s 之前的过渡执行器。

### 4.5 Remote API 兼容连接器

用于远端服务自托管模型。

特点：

- 远端服务暴露平台标准 manifest。
- 平台只注册 URL 即可拉取契约、样例和异步任务接口。
- 适合模型团队自行部署服务。
- 必须支持提交、查询、取消、结果 manifest。

### 4.6 Tool Package 交付格式

用于长期标准化交付，不是单独的计算资源类型。

特点：

- 声明标准 Artifact 输入输出。
- 声明运行环境、镜像、权重和资源需求。
- 通过 request.v1 / result.v2 与平台交互。
- 推荐作为新模型交付主路径。

平台应先把 Tool Package 转换为 Tool Contract，再根据 `executor.type` 和批准的 Resource Profile 选择 K8s Job 或 SSH Job。Docker/Python 只作为 Job 内的 runtime 描述，Remote API 只用于旧工具兼容。

### 4.7 K8s Job Executor

用于容器化重计算任务和可弹性扩展的生产部署。

特点：

- 每个任务提交为独立 K8s Job。
- 适合 Docker 化 CADD 工具、批量筛选和 GPU 推理。
- 可通过 node selector、priority class、namespace 和资源限额做调度治理。
- 必须支持 Job 状态同步、日志读取、取消和输出回收。

### 4.8 Slurm 接入（后续可选）

Slurm 不属于当前一级执行器。已有 HPC 环境优先通过 SSH Job 接入登录节点；只有需要直接读取 Slurm 队列状态时，才实现专用 Adapter。

特点：

- 每个任务提交为 sbatch 作业。
- 适合 MD、长时对接、大规模虚拟筛选和 GPU 集群任务。
- 可映射分区、QoS、CPU、内存、GPU 和时间限制。
- 必须支持 squeue/sacct 状态同步、scancel 取消和共享文件系统或对象存储回收。

## 5. 重计算资源调度

### 5.1 重计算工具范围

- 分子对接。
- MD 模拟。
- 深度学习分子生成。
- 大规模 ADMET / 毒性预测。
- 虚拟筛选和批量重排。
- 大模型辅助分析。

### 5.2 资源画像

每个工具版本应声明资源画像：

```yaml
resource_profile: gpu-medium
```

`gpu-medium` 必须是管理员预先批准的档位。CPU、内存、GPU、超时和并发上限由 Resource Profile Registry 管理，工具版本不能自行覆盖。

资源画像用于：

- 前端预检展示。
- 队列选择。
- 受控 K8s/SSH 执行环境按 Resource Profile 分配资源；Slurm 映射仅供后续专用 Adapter 参考。
- 管理员容量规划。
- 任务失败诊断。

### 5.3 K8s 调度方向

K8s 适合容器化工具和可弹性扩展服务。

```text
Task
  ▼
Celery worker
  ▼
K8s Job Adapter
  ▼
K8s Job / Pod
  ▼
Object Storage output
  ▼
TaskOutput + Artifact
```

要求：

- 每个任务独立 Job。
- 输入通过对象存储或 PVC staging。
- 输出回传对象存储。
- 日志可流式拉取。
- 支持取消任务时删除 Job。

### 5.4 Slurm 调度方向（后续可选）

当前优先通过 SSH Job 连接已有 HPC 的登录节点。下图仅描述未来需要直接管理 Slurm 队列时的可选实现。

```text
Task
  ▼
Celery worker
  ▼
Slurm Adapter
  ▼
sbatch / squeue / scancel
  ▼
shared filesystem or staged object storage
  ▼
TaskOutput + Artifact
```

要求：

- 生成 sbatch 脚本。
- 支持队列、分区、GPU、CPU、内存、时间限制。
- 支持日志和状态同步。
- 支持取消。

## 6. 文件和 Artifact 存储

### 6.1 开发模式

- local filesystem。
- SQLite。
- direct task execution。

### 6.2 生产模式

- PostgreSQL 保存结构化数据。
- MinIO/S3 保存文件和结果。
- Redis/RabbitMQ 作为任务队列和缓存。
- Worker 使用对象存储传递输入输出。

### 6.3 存储原则

- 输入文件和输出文件都必须可追踪。
- 标准 Artifact 的每个文件角色都应关联 File。
- 下载必须走权限校验。
- 大文件不应通过 Web API 内存转发。

## 7. 网络和安全

### 7.1 网络边界

- 用户只访问前端和 API Gateway。
- Worker 可以访问对象存储、数据库和执行目标。
- SSH/K8s/Slurm 凭据只存在后端安全配置中。
- Remote API 服务可以部署在内网。

### 7.2 凭据原则

- 工具契约不保存明文凭据。
- 用户上传文件不暴露真实存储路径。
- SSH key、API token、K8s kubeconfig 应由平台安全配置管理。

## 8. 监控和运维

需要监控：

- API 健康。
- 数据库连接。
- Redis/队列长度。
- Worker 存活。
- 任务状态分布。
- 执行器错误率。
- 存储容量。
- GPU/CPU 使用率。
- K8s/SSH Job 等待时间；启用专用 Slurm Adapter 后再增加 Slurm 队列等待指标。

## 9. 部署演进路线

### 阶段 1：受控 Job 执行基线

- 保留本地开发 direct 模式。
- 生产使用 Celery + Redis。
- V1 至少验收一条 K8s Job 或 SSH Job 路径；SSH 可用于没有 Kubernetes 的部署。
- 工具契约统一。

### 阶段 2：Job runtime 标准化

- CADD 工具逐步容器化，并作为 K8s/SSH Job 内部 runtime。
- 标准输入输出目录。
- 统一镜像 digest、资源画像和日志收集。

### 阶段 3：K8s 生产化与可选 Slurm Adapter

- 抽象 ClusterJobAdapter。
- 支持 K8s Job。
- 有明确客户需求时再支持 Slurm sbatch 专用 Adapter。
- 支持任务取消、状态同步和输出回收。

### 阶段 4：多租户生产治理

- 队列优先级。
- 配额和资源限制。
- 审计和成本统计。
- 高可用数据库和对象存储。
