**P4 的验证路径成立**：8×4090 全部可见、Docker + nvidia-container-toolkit 就绪、k3s 与 GPU device plugin 在跑，单卡容器隔离被实测证明可行。

## 3. 阻塞项 D-34：节点 DiskPressure 导致 Pod 无法调度（🔴 需运维处理）

### 3.1 现象

```
kubectl get node 4090 -o jsonpath='{.status.conditions}'
→ MemoryPressure=False DiskPressure=True PIDPressure=False Ready=True

kubectl describe pod → Warning FailedScheduling:
  0/1 nodes are available: 1 node(s) had untolerated taint(s)
```

节点被自动打上污点 `node.kubernetes.io/disk-pressure:NoSchedule`（`timeAdded 2026-10-22`），**任何 Pod 都无法调度**；加 `tolerations: [{operator: Exists}]` 强行调度后 Pod 被 **`Evicted`**。

### 3.2 根因（2026-10-25 第二次复检后定位到具体元凶）

`/data` 使用率 **95%**（66T / 73T，剩 3.8T）。kubelet 的 `nodefs`/`imagefs` 阈值触发 `DiskPressure`。

第一次记录只写了「镜像/容器垃圾量已经很大」，属于没查清就下结论。第二次复检把它量化了：

| 项 | 实测 | 说明 |
|---|---|---|
| Docker Root Dir | **`/data/docker`** | 所以 Docker 镜像直接吃 `/data` 的空间，而不是系统盘 |
| k3s 数据目录 | `/data/k3s` = **253 MB** | **k3s 本身几乎不占空间**，不是元凶 |
| 镜像总数 / 总体积 | **157 个 / 约 3054 GB** | 平均每个镜像 19 GB，这是典型的多用户共用 GPU 机器的形态 |
| 其中**无任何容器引用**的镜像 | **77 个 / 约 1592 GB** | 这一半是「拉下来但容器已经删了」的历史遗留 |
| dangling 镜像 | 4 个 / **101 GB** | 构建中间层，无 tag |
| 容器总数 | **146 个，其中 102 个已停止** | 已停止容器的可写层也在占空间 |

**结论：真正吃满 `/data` 的是 Docker 镜像与已停止容器（约 3 TB 镜像 + 写层），k3s 只占 253 MB。** 因此「清 k3s」没有意义，必须清 Docker。

> 一个容易被忽略的点：`/data` 上的 `docker` 目录属主是 `root` 且权限 `drwx--x---`，普通用户读不到子目录大小；`sudo` 在本机**需要密码**（`sudo -n true` 返回 `a password is required`），所以按目录 `du` 拿不到明细。上面的数字全部由 `docker images` / `docker ps -a` / `df` 直接得出，**不依赖 sudo**，是可以在无 root 情况下复现的。

## 4. 发现并修正的缺陷：`CUDA_VISIBLE_DEVICES` 双重过滤（🔴 静默失败）

### 4.1 缺陷

`09` §5.6 与 `13` §6.5 原文（v1.3）写：NVIDIA 卡位的可见性变量是

```
NVIDIA_VISIBLE_DEVICES=6 + CUDA_VISIBLE_DEVICES=6
```

**这是错的。** 两者叠加时是**串联过滤**：`NVIDIA_VISIBLE_DEVICES=6` 先把容器可见卡限制为「宿主第 6 张」，在容器内它变成**列表的第 0 个**；紧接着 `CUDA_VISIBLE_DEVICES=6` 再从这个**只有 1 个元素**的列表里取下标 6 → **空集**。

### 4.2 实测矩阵（同一镜像 `pytorch/pytorch:2.6.0-cuda12.4-cudnn9-runtime`）

| # | 启动方式 | `torch.cuda.device_count()` | 判定 |
|---|---|---|---|
| A | `--gpus '"device=3"'` + `CUDA_VISIBLE_DEVICES=3` | **0** | ❌ **文档原写法，静默失败** |
| B | `--gpus '"device=3"'` + `CUDA_VISIBLE_DEVICES=0` | **1** | ✅ 正确 |
| C | `--gpus '"device=3"'`，**不设** `CUDA_VISIBLE_DEVICES` | **1** | ✅ 也可（此时 0~7 被整体映射为单卡） |
| D | `--gpus all` + `CUDA_VISIBLE_DEVICES=6` | **1** | ✅ 不同机制：`--gpus all` 给全 8 张，由 `CUDA_VISIBLE_DEVICES` 做选择 |
| E | `--runtime=nvidia` + `NVIDIA_VISIBLE_DEVICES=6` + `CUDA_VISIBLE_DEVICES=0` | **1** | ✅ 正确（不用 `--gpus` 的等价写法） |
| F | `--runtime=nvidia` + `NVIDIA_VISIBLE_DEVICES=6` + `CUDA_VISIBLE_DEVICES=6` | **0** | ❌ **同 A，另一条错误路径** |

**规律**：

> 只要用了「只暴露 1 张卡」的机制（`--gpus '"device=N"'` 或 `NVIDIA_VISIBLE_DEVICES=N`），容器内就**只剩 1 张卡**，它的编号必然是 `0`。此时 `CUDA_VISIBLE_DEVICES` 只能填 **`0`**（或干脆不填），**绝不能填宿主卡号**。
>
> 填宿主卡号会让程序看到的卡数变成 0，而**报错方式取决于模型实现**：有的抛 `RuntimeError: No CUDA GPUs are available`（PyTorch 直接初始化会抛），有的（多数推理脚本包了 try/except 或 `torch.cuda.is_available()` 判断）**静默 fallback 到 CPU**。

### 4.3 为什么这条特别危险

1. **容器不报错、退出码 0、日志无异常**——监控看不到。
2. **NVIDIA 侧与 DCU 侧不对称**：DCU 的 `ROCR_VISIBLE_DEVICES=6` + `HIP_VISIBLE_DEVICES=0` 恰好是「宿主卡号 + 容器内 0」的**正确**组合（`09` §4.3 一次性容器示例就是这么写的），所以照着 DCU 习惯往 NVIDIA 上套 `CUDA_VISIBLE_DEVICES=6` 会**刚好踩中**。
3. **性能差别是数量级**：Boltz-2 在 DCU 上 9.5s/件，落到 CPU 上是小时级；MD 直接跑不动。用户只会觉得「这台机器好慢」，不会怀疑配置。

### 4.4 修正（已落入文档）

| 文档 | 修改 |
|---|---|
| `09` §5.6 差异表 | NVIDIA 行改为 **`NVIDIA_VISIBLE_DEVICES=N`，且 `CUDA_VISIBLE_DEVICES` 必须为 `0` 或省略**；补一行「⚠ 常见错误」说明 |
| `09` §5.6 YAML 示例 | 示例卡位由 **A0 改为 A6**（`deviceIds: [6]`、`NVIDIA_VISIBLE_DEVICES: "6"`、`CUDA_VISIBLE_DEVICES: "0"`、`--gpus '"device=6"'`）——**原示例用卡 0 时两个值都是 `"0"`，恰好把语义差异完全掩盖了**，这是本轮最值得记住的一条 |

| 卡位模型与硬件无关，差异只在 `env{}` / `dockerArgs[]` / 镜像基座 | 把 DCU 的 `--device=/dev/kfd…` 换成 `--gpus`，其余流程不变即可达到同等隔离 | ✅ **成立**（但 `env{}` 的具体值必须按 §4 修正，不能想当然） |
| 平台侧零改动 | 本次未涉及平台代码 | ⏳ 待 P4-6 |
| 适配成本压到「镜像基座 + 逐模型 fallback」两层 | 单卡隔离、GPU 可见性、Docker 运行时均已就绪，无额外适配层需求 | ✅ **成立** |
| 不能外推：耗时基线、显存、复现等级 | 显存 24GB vs 64GB 已确认是硬差异；耗时基线未测 | ✅ 论断正确，**必须坚持** |

**一条新增的提醒**：`D-33` 说「卡位设计不绑定 DCU」是对的，但**「不绑定」不等于「配置可以直接照搬」**。DCU 的 `ROCR+HIP` 双变量组合在 NVIDIA 上要换成 `--gpus` 单机制，**变量语义（宿主卡号 vs 容器内序号）必须逐个确认**。这一条已作为第 5 条迁移纪律写进 `09` §5.6。
