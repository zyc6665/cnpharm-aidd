# 数据库索引与查询规范

| 项 | 值 |
|---|---|
| 文档编号 | DRP-DB-IDX-001 |
| 版本 | v1.0（2026-10-30） |
| 适用范围 | `backend/app/models/`（索引声明）、`backend/app/services/`、`backend/app/api/v1/`、`backend/alembic/versions/` |
| 生产库 | PostgreSQL 16；开发与测试用 SQLite（同一套模型） |

## 0. 一句话结论

**索引不是"给每个 WHERE 列建一个"**，而是"给一条具体的 `WHERE … ORDER BY … LIMIT` 建一棵能一次扫完的树"。
本仓库原有 168 个索引、58 张表，问题不在数量少，而在**每个高频分页查询都缺"等值列 + 排序列"的组合索引**——
表现为查询计划里稳定出现的 `USE TEMP B-TREE FOR ORDER BY`：先把过滤结果全取出来、全排序、再切前 20 行。

## 1. 实测基线（本机 SQLite，30,000 `tasks` / 120,000 `audit_logs`）

| 查询 | 加索引前 | 加索引后 | 提升 |
|---|---|---|---|
| 结果中心：`project_id + 终态 + ORDER BY finished_at DESC` | 6.26 ms | 1.10 ms | 5.7× |
| 任务列表：`user_id + status + ORDER BY created_at DESC` | 3.83 ms | 1.03 ms | 3.7× |
| 审计日志：`action + 时间范围 + ORDER BY created_at DESC` | **51.07 ms** | **0.69 ms** | **74×** |
| 审计计数：`count(*)` + 时间范围 | 18.87 ms | 8.50 ms | 已走 covering index，无需再加 |

### 1.1 真 PostgreSQL 复核（20 万 `tasks` / 12 万 `audit_logs`）

SQLite 与 PostgreSQL 的优化器不是一回事，索引写法在两边也不是一一对应，所以上面这组
SQLite 数字只能当"量级示意"。本机起 PostgreSQL 16 灌 20 万任务复核（`EXPLAIN ANALYZE`）：

| 查询 | 改前 | 改后 | 说明 |
|---|---|---|---|
| 结果中心 `project_id + 终态 + ORDER BY finished_at DESC NULLS LAST` | 4.52 ms（普通升序索引 + `top-N heapsort`） | **2.53 ms** | 索引改成 `DESC NULLS LAST` 后仍有一次 top-N sort：`status IN (三个值)` 要求跨三段有序区间归并，规划器选择排序反而更便宜 |
| 任务列表 `user_id + status + ORDER BY created_at DESC` | — | **2.95 ms** | `ix_tasks_user_status_created` + `top-N heapsort` |
| 审计 `action + 时间范围 + 倒序 50` | — | **0.099 ms** | `Index Scan Backward using ix_audit_logs_created_at` |
| 游标翻页 `(created_at, id) < (?, ?)`（页深 5 万） | 21.15 ms（`Parallel Seq Scan`） | **0.079 ms** | 加 `ix_tasks_created_at_id` 后走 `Index Only Scan Backward`，**267×** |
| 同上但写成 `created_at < ? OR (created_at = ? AND id < ?)` | 23.00 ms（Seq Scan） | 4.13 ms | 上了索引也仍要扫更多区间；**行值比较才是对的写法** |
| 对照 `OFFSET 150000 LIMIT 20` | 64.21 ms | 64.21 ms | `Seq Scan` + `external merge` 落盘 5 MB |

真库复核抓到两个只在 PostgreSQL 上出现的缺口，都已修（迁移 `20261031_03`）：

1. **`DESC NULLS LAST` 在空库上根本没生效**。`20261031_01` 里写了 `DESC NULLS LAST`，
   但基线 `20260624_01` 的 `Base.metadata.create_all()` 先按**模型**（普通升序）建了
   同名索引，`20261031_01` 见索引已存在就跳过。→ 迁移 `20261031_03` 在 PG 上
   `DROP/CREATE INDEX CONCURRENTLY` 重建。**这是"模型声明 vs 迁移建表"双真源
   第三次咬人**（前两次见 §6）。
2. **游标翻页缺索引**。`tasks` 上没有以 `created_at` 打头的索引，**不带筛选**的
   游标翻页退化成 `Parallel Seq Scan`（21 ms，和 `OR` 展开式一样慢）。→ 补
   `ix_tasks_created_at_id (created_at, id)`。**上了游标但没上索引，等于白上。**

> 这组数字的意义不是绝对值（SQLite 单机、数据在页缓存里），而是**差距的量级**：
> `TEMP B-TREE` 的代价与"命中行数 × 行宽"成正比，数据量翻十倍，51 ms 会变成 500 ms 以上；
> 而索引区间扫描的代价只与"要返回的 20 行"有关，基本不随表增长。

## 2. 复合索引的列顺序规则

只有一条规则，但要严格执行：

> **等值条件的列在前，范围/排序的列在后；排序方向与索引方向必须一致。**

推演一次就明白：

- `WHERE project_id = ? AND status IN (...) ORDER BY finished_at DESC LIMIT 20`
  - 建 `(project_id, status, finished_at)`：`project_id`、`status` 是等值（`IN` 在单列上等价于若干等值），
    前两列把扫描范围收敛到一个连续区间；第三列已按需要的顺序排好 → 顺序扫描取前 20 行即可 **提前终止**。
  - 若建成 `(finished_at, project_id, status)`：树的顺序是"时间优先"，要凑齐 20 条满足 project 的
    行就得从最新往里翻，直到翻够 20 条符合的——`LIMIT` 完全失效。
- `ORDER BY finished_at DESC NULLS LAST, created_at DESC`
  - PostgreSQL 默认把 NULL 视作比任何值都大，**ASC 索引反向扫描得到的是 `NULLS FIRST`**，
    与 `NULLS LAST` 不匹配 → 必须显式建 `(... , finished_at DESC NULLS LAST, created_at DESC)`。
  - SQLite 相反（NULL 最小），DESC 扫描天然把 NULL 放最后，所以同一份索引声明在 SQLite 侧
    写成普通 `(…, finished_at, created_at)` 即可。**这是本仓库唯一需要方言分叉的索引**。

## 3. 什么时候**不要**加索引

索引不是免费的：每次 `INSERT` 要维护每一棵 B 树，`UPDATE` 改到索引列还要移动位置。
`audit_logs` 就是反面教材——13 列上挂了 10 个索引，而它是只追加表，**写入放大是确定的、读放大是概率的**。

不加索引的四种情形：

| 情形 | 例子 | 原因 |
|---|---|---|
| 低基数（< 10 个不同值） | `audit_logs.result`（4 个值）、`users.role` | 选择性太差，优化器多半直接忽略；就算用了也不比顺序扫快 |
| 真前缀已被更长索引覆盖 | `project_members.project_id` ⊂ `(project_id, user_id)` | 完全冗余，只是多一棵树要维护 |
| 表本身就小（< 1 万行且不会长） | `projects`、`users`、`pockets`、`protein_structures` | 顺序扫几十页就完，索引反而增加计划开销 |
| 过滤发生在应用层 | `molecule_fingerprints` 的相似性检索 | SQL 只做 `fp_ecfp4 IS NOT NULL`，Tanimoto 在 Python 里算（2 万条 × 2048 bit ≈ 5 MB，全扫 < 200 ms）。**加索引无效**，> 2 万条时应换外部向量检索，不是加索引 |

## 5. 查询规范（12 条硬规则）

每条都给出**本仓库的真实反例**，方便对号入座。

### 5.1 禁止前导通配 `LIKE '%x%'`

`task_views.py` 原来的关键字搜索是 8 列 `ilike('%kw%')` 的 `OR`，其中两列是 `Text`
（`error_message`、`progress_message`）。前导通配无法走任何 B 树索引，且长文本把每行要扫的字节放大一个量级。
**规则**：关键字搜索只覆盖"标识类短字段"；长文本检索走专用表（`task_logs`）或后续引入全文检索。

### 5.2 禁止把 JSON 提取写进 `WHERE` / `JOIN` 条件

真实反例：`execution/records.py` 曾经是
`.outerjoin(Task, Task.id == ExecutionRecord.request_snapshot["task_id"].as_string())`。
JSON 提取是函数调用，优化器无法把它与 `tasks.id` 的索引对上，只能退化成哈希连接 + 全扫。
**规则**：被查询/排序/连接的 JSON 字段要**升为真列**（`tasks.project_id`、`execution_records.task_id`
都是这样处理的），保留 JSON 一个版本周期做双读即可。

### 5.3 禁止函数包裹列

`func.lower(col) == x`、`cast(col as ...)`、`func.date(col)` 一律让索引失效。
需要大小写不敏感查询时，存一份规范化列并建索引，而不是在查询里套函数。
（现状核查：全库没有这类写法，保持。）

### 5.4 列表接口必须分页，且必须给 `ORDER BY`

没有 `ORDER BY` 的分页在数据量上来后是随机结果 + 全表扫。
**规则**：`ORDER BY` 的列组合必须与某个索引的前缀一致，否则就是 `TEMP B-TREE`。

### 5.5 `count(*)` 与列表查询用同一个过滤条件、但不要包整个查询

现有写法 `select(func.count()).select_from(query.subquery())` 会在子查询里保留
`selectinload`/`order_by` 等无用部分。**规则**：计数时单独构造 `select(func.count()).select_from(Model).where(同条件)`，
去掉排序与 eager load。

### 5.6 列表查询必须显式指定列或确认需要整行

`select(Model)` 会把所有列拉回来（含 `Text`/`JSON` 大列）。分页列表只要 id/name/status/时间时，
用 `select(Model.id, Model.name, ...)`；需要整行时说明理由。

### 5.7 `offset` 深分页要换成游标（已落地）

`OFFSET 100000 LIMIT 20` 不是「跳过 10 万行」，而是让数据库**逐行产出再丢掉** 10 万行。
20 万行表实测：`OFFSET 1000` 3.0 ms、`OFFSET 100000` 3.0 ms、`OFFSET 199000` **9.4 ms**，
随页深线性增长。

**必须写成行值比较**，不能展开成 `OR`：

| 条件写法 | 执行计划 | 页深 10 万 | 页深 19.9 万 |
|---|---|---|---|
| `ts < ? OR (ts = ? AND id < ?)` | `SCAN tasks USING COVERING INDEX` | 10.2 ms | 21.2 ms |
| `(ts, id) < (?, ?)` | `SEARCH tasks USING COVERING INDEX ((ts,id)<(?,?))` | **0.16 ms** | **0.14 ms** |

同一份数据、同一个索引，**写法差 60 倍**——`OR` 形式让 SQLite 与 PostgreSQL 都用不上
索引区间，退化成整段索引全扫。

实现：`backend/app/common/keyset.py`（`encode_cursor` / `decode_cursor` /
`apply_desc_keyset` / `next_cursor`）；已接入 `GET /api/v1/tasks` 与
`GET /api/v1/admin/audit-logs` 的 `cursor` 参数。契约：

* 不传 `cursor`：`page` / `page_size` / `total` 行为完全不变；
* 传 `cursor`：**不再计算 total**（算总数与深分页同代价），用 `nextCursor` / `hasMore`
  翻页，`total` 返回 `null`、`totalKnown` 返回 `false`；
* 偏移模式**也**返回 `nextCursor`，客户端可以从第 N 页平滑切到游标翻页，不需要额外接口。

排序键必须全序：游标里除时间戳还带主键（`id DESC`），否则同毫秒的多行在翻页时会
漏行或重复（`test/test_keyset_pagination.py::test_cursor_walk_covers_every_row_exactly_once`
就是拿 25 行、其中 4 行同毫秒来卡这一点的）。

### 5.8 一个请求内只 `commit` 一次

真实反例：`api/v1/tasks.py` 与 `api/v1/artifacts.py` 有请求内多次 `commit()` 的路径。
多次提交会让"部分成功"成为可能状态，且拉长事务持锁窗口。

### 5.9 不要在持有行锁时调用外部服务

真实反例：`api/v1/tasks.py` 在 `with_for_update` 区间里发起 HTTP 调用。
**规则**：锁内只做数据库操作，外部调用移到锁外。

### 5.10 `SELECT … FOR UPDATE` 必须带 `skip_locked`（批量扫描场景）

巡检类查询（`records.py`、`workflow_reconciliation.py`）已正确使用 `skip_locked=True`。保持。

### 5.11 严禁 `max(col) + 1` 取号

真实反例（已修）：`services/artifacts.py` 早期用 `max(version) + 1` 取版本号，并发下撞唯一约束报 500。
现在的做法（`artifact_writer.py`）是：`begin_nested` + 行锁 + `IntegrityError` 重试 + 数据库唯一约束兜底。
**规则**：任何序号/版本号都由数据库约束保证唯一，应用层只负责重试。

### 5.12 `COUNT`、聚合与 `GROUP BY` 不要拉回 Python 做

真实反例：`workspace.py` 用 `func.lower(...)` 分组；`project_stage.py` 的 counters 逐项查。
**规则**：能在 SQL 里 `count/count(distinct)/group by` 的就不要在 Python 里 `len([...])`。

## 6. 模型 / 迁移一致性（本次修掉的四处）

根因：基线迁移 `20260624_01` 用 `Base.metadata.create_all()` 建表，**fresh 库的索引集等于模型声明**；
而预存库（逐迁移升级上来的生产库）只有迁移里显式写过的索引。**两套来源必然漂移。**

| 问题 | 影响 | 修法 |
|---|---|---|
| `datasets.uq_datasets_project_name_type` 模型有、迁移从未建 | 生产库同名同类型数据集可重复插入（去重只靠应用层，并发下失效） | 迁移补建唯一约束 |
| `compounds.inchikey` 唯一约束 + 非唯一索引同名双份 | 多维护一棵树，且容易被误认为"还有一条非唯一索引" | 删非唯一那条 |
| `ix_candidates_attrs_gin` 迁移有、模型无 | fresh 库（开发/测试）缺 GIN，JSON 过滤在测试环境与生产行为不同 | 补进模型 `__table_args__` |
| `ix_upload_sessions_idempotency_key` 迁移有、模型无 | 同上前提，且已被联合唯一约束覆盖 | 删 |

| `ix_tasks_project_status_finished` 迁移写 `DESC NULLS LAST`、模型写普通升序 | **空库上拿到普通升序索引，`NULLS LAST` 从未生效**（SQLite 看不出） | 迁移 `20261031_03` 在 PG 上重建；模型注释点明两端差异 |
| `ix_tasks_created_at_id` 两边都缺 | 无筛选的游标翻页在 PG 上退化成 `Parallel Seq Scan` | 模型 + 迁移 `20261031_03` 同时补 |
| `candidates.attrs` 用 `sa.JSON`（PG `json`）却建 GIN | **空库迁移直接失败**：`data type json has no default operator class for access method "gin"` | 模型与建表迁移都改 `JSON().with_variant(JSONB, "postgresql")` |
| `request_snapshot ? 'task_id'`（`?` 是 jsonb 运算符） | **空库迁移直接失败**：`operator does not exist: json ? unknown` | 迁移里改成 `(request_snapshot::jsonb) ? 'task_id'` |

**新增规则（写进评审清单）**：任何新表/新索引，必须同时出现在**模型**与**迁移**里；
`test/test_index_governance.py` 会用元数据做静态断言，任何单边声明都会让 CI 红。
**另加一条**：涉及 PG 专有语法（`GIN`、`DESC NULLS LAST`、`jsonb` 运算符）的索引与回填，
必须在**真 PostgreSQL** 上跑一遍 `upgrade head` + `downgrade base`——SQLite 全绿不代表
空库能建起来。CI 已有 `migrations-pg` 门禁（`.github/workflows/ci.yml`）。

## 7. 生产执行注意事项

1. **大表必须 `CREATE INDEX CONCURRENTLY`**（在 Alembic 里用 `op.get_context().autocommit_block()` 包住），
   否则会持有 `SHARE` 锁阻塞写入；`DROP INDEX CONCURRENTLY` 同理。
2. **一次性不要建太多**：`tasks` 上本次新增 5 个索引，建议生产按 `project_status_created` →
   `user_status_created` → `project_status_finished` → 其余 的顺序分批发布，每批观察写入延迟。

## 9. 附：本次核查的 join 与 N+1 事实清单

核查范围：`backend/app` 全量。`grep "\.join(" ` 命中 173 行，其中 **SQLAlchemy join 43 条**、
其余 130 条是 `os.path.join` / `str.join` 之类的字符串拼接——**"多表 join" 的真实规模是 43 条，不是 173 条**，
按后者去"优化"会白改 130 处路径拼接。

### 9.1 单查询涉及 ≥3 张表的只有 3 条

| 位置 | 链路 | 性质 | 处置 |

### 9.4 一条容易误判的"好实践"

`services/workflow_reconciliation.py:70-84` 是 `while` + 每轮
`with_for_update(skip_locked=True) ... limit(1)`，看起来像 N+1，实际是**刻意单条领取**：
它要保证多个 worker 副本并发时不会重复领同一个 run，而 `id NOT IN (已处理)` 会随轮次单调增长。
这类"逐条领取"是锁语义要求，不是性能缺陷——**评审时不要按 N+1 改掉它**。
