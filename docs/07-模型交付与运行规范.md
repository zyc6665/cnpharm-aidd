## 2. 模型交付包规范（Model Package）

### 2.1 目录结构（强制）

```
{model}-{version}-dcu.tar.gz                 # 交付包，命名强制
├── manifest.yaml                            # ★ 必填：唯一元信息源
├── README.md                                # ★ 必填：构建/运行/排障说明
├── code/                                    # ★ 必填：模型源码（含编译产物）
├── entrypoint/
│   ├── run.sh                               # ★ 必填：批处理统一入口
│   ├── adapter.py                           # RESIDENT 形态必填
│   └── run_smoke_test.sh                    # ★ 必填：冒烟自测
├── io/
│   ├── input.schema.json                    # ★ 必填：输入契约
│   └── output.schema.json                   # ★ 必填：输出契约
├── weights/                                 # 可选：<5GB 权重随包；否则仅放索引
│   └── ...
├── weights.checksums.txt                    # 权重 SHA-256 清单
├── env/
│   ├── requirements.lock.txt                # ★ 必填：精确锁版本
│   └── dtk-notes.md                         # DTK/HYHAL/libuv 等特殊依赖说明
├── sample/
│   ├── input/                               # ★ 必填：最小可跑样例
│   └── expected/                            # ★ 必填：期望输出（用于回归）
└── tests/
    └── verify_dcu.sh                        # 复现验证脚本
```

**规则**
1. `manifest.yaml` 是**唯一元信息源**，平台只认它，不解析 README。
2. 权重 > 5GB 时**不得**放进交付包，改为在 manifest 中声明 `weights.urnPrefix`，由平台侧导入。
3. `code/` 中禁止出现绝对路径硬编码（`/workspace/...`），一律改为读取环境变量或相对路径。
4. 禁止在包内自带完整 `.venv`（STD-Diff 实测 3.9G）；改为声明 `runtime.baseImage`。
5. `sample/` 必须能在**不联网**的情况下跑通，这是离线验收的第一道关。

### 2.2 manifest.yaml 完整规范

```yaml
apiVersion: drp/v1
kind: ModelPackage

metadata:
  name: boltz2                       # 全局唯一，小写，无下划线
  version: 2.0.1                     # 语义化版本
  displayName: Boltz-2 结构与亲和力预测
  vendor: 内部/开源
  license: MIT                       # ★ 必填，用于合规审查
  description: 蛋白-配体复合物结构预测与亲和力预测，DTK/HIP PyTorch fallback 路径

spec:
  # ---- 能力声明：决定平台把这个模型挂到哪些任务类型上 ----
  capabilities:
    - taskType: STRUCTURE_PREDICTION
      priority: 1                    # 同能力多模型时的默认优先级
    - taskType: AFFINITY_PREDICTION
      priority: 1

  # ---- 运行时：决定镜像与容器环境 ----
  runtime:
    baseImage: harbor.drp/library/runtime-torch-dtk26.04-py3.10:1.2.0
    pythonEnv: /opt/venv              # 或 micromamba 环境名
    pythonVersion: "3.10"
    frameworks:
      torch: "2.7.1"                 # 必须与版本矩阵一致
      hip: "6.3.26045"
      dgl: null
      tensorflow: null
    forbidPipOverride: [torch, dgl, tensorflow]   # ★ 禁止运行时覆盖

  # ---- 设备与资源 ----
  device:
    type: DCU                          # DCU | CPU
    count: 1
    memoryGB: 40
    selector: "cuda:0"                 # 容器内逻辑设备名（PyTorch/TF 兼容层）；同时作为 DRP_DEVICE 的取值
    deviceEnvVar: DEVICE               # 模型私有环境变量名（每个模型可能不同，如 MSIGN 用 DEVICE）
    deviceValue: "cuda:0"              # ★ v1.2 新增：该变量注入的值；DGL 系模型填 "hip:0"
    timeSlicing: false                 # 是否允许与其他容器共享一卡
  resources:
    cpu: 8
    memGB: 32
    coldBootSeconds: 110               # ★ 从实测推算：wall 123s - loop 9s
    steadyStateSecondsPerItem: 9.5     # ★ v1.1 新增：稳定态单件成本（不含冷启）
    expectedSecondsPerItem: 127        # 单件任务的墙钟时长 = coldBoot + steady（仅供单件预估）
    maxMinutes: 60

  # ---- 服务形态 ----
  serving:
    mode: BATCH                        # BATCH | RESIDENT | HYBRID
    batchMaxSize: 8                    # 一次 Job 最多处理几个样本（摊薄冷启动）
    maxConcurrency: 16                 # 常驻模式下单副本并发
    replicas: 0                        # RESIDENT 形态的默认副本数

  # ---- 环境变量（平台注入，容器不得硬编码）----
  env:
    - name: DGLBACKEND
      value: pytorch
    - name: TF_FORCE_GPU_ALLOW_GROWTH
      value: "true"
    - name: POCKET2MOL_ALLOW_PYG_FALLBACK
      value: "1"
  libraryPathAdditions:                # 追加到 LD_LIBRARY_PATH
    - /opt/hyhal/lib
    - /opt/dtk-26.04/lib
    - /opt/dtk-26.04/opencl/lib

  # ---- 入口 ----
  entrypoint:
    batchCommand: ["bash", "/opt/model/entrypoint/run.sh"]
    adapterModule: null                # RESIDENT 时填 adapter:DrpModelAdapter

  # ---- 输入输出契约 ----
  io:
    inputs:
      - role: SEQUENCE
        kind: FASTA
        required: true
        maxItems: 8
      - role: LIGAND
        kind: SDF
        required: false
    outputs:
      - role: STRUCTURE
        format: CIF
        primary: true
      - role: METRIC
        key: confidence_score
        unit: score
      - role: METRIC
        key: affinity
        unit: pIC50

  # ---- 权重 ----
  weights:
    source: MINIO                      # MINIO | NODE_LOCAL | IN_IMAGE | NONE
    urnPrefix: drp-models/boltz2/2.0.1/
    sizeGB: 3.2
    checksumsPath: weights.checksums.txt
    mountPath: /opt/model/weights
    loadStrategy: INIT_CONTAINER       # INIT_CONTAINER | NODE_CACHE | MOUNT

  # ---- 冒烟与验证 ----
  smoke:
    command: ["bash", "/opt/model/entrypoint/run_smoke_test.sh"]
    inputDir: /opt/model/sample/input
    timeoutSeconds: 900
    expectedExitCode: 0
    expectedOutputs: [result.json]
  validation:
    status: PASSED                     # PASSED | PARTIAL | FAILED
    reportRef: 模型海光兼容测试报告(3)
    testedOn: 浪潮CS5468H3 / K100-AI ×8 / DTK 26.04
    testedAt: "2026-08-20"
    notes: "8卡并发3轮24/24成功；使用 PyTorch fallback kernels；MSA 为 empty"

  # ---- 可复现性声明（v1.2 新增，必填）----
  reproducibility:
    level: D2                          # D1 | D2 | D3 | D4（定义见 03 §7.4.1）
    toleranceRef: null                 # D2 必填：指向 08 实测报告的回填条目，未标定为 null
    seedParam: "params.seed"           # D1/D2 必填：随机种子参数路径；D4 写 null
    fixedEnv: ["MSA_MODE", "NUM_RECYCLES", "FALLBACK_FLAGS"]
    nondeterminism:                    # D3/D4 必填：已知不确定来源
      - "cuEquivariance fallback 可能随卡数变化"
    note: "D2：容差待 08 实测回填；不同卡数视为不同复现基线"
```

### 2.3 交付包校验清单（DoD）

- [ ] `manifest.yaml` 通过平台 JSON Schema 校验
- [ ] `sample/input` 可在**断网**环境跑通，产物与 `sample/expected` 一致
- [ ] 权重 SHA-256 与 `weights.checksums.txt` 一致
- [ ] 镜像内 `torch.cuda.is_available() == True`，`torch.version.hip == 6.3.26045`
- [ ] 无硬编码绝对路径
- [ ] **（v1.1 新增）** `resources.coldBootSeconds` 与 `resources.steadyStateSecondsPerItem` 分别填写，不得只给 `expectedSecondsPerItem`——后者是「冷启 + 单件」的墙钟和，**用它乘批量数会把总耗时高估一个数量级**（`03` §5.2.1 与 §5.6.2 的核算就靠这两个值分开算）
- [ ] （**v1.2 新增**）`reproducibility.level` 已如实填写（`D1`/`D2`/`D3`/`D4`，定义见 `03` §7.4.1）：**扩散/采样类（STD-Diff、Pocket2Mol、TheraPainter）必须填 `D4`，不得为了「好看」填 D2**；填 `D2` 则 `toleranceRef` 必须指向 `08` 实测回填条目，未标定前保持 `null`
- [ ] `license` 已登记并通过合规审查
- [ ] 冷启动耗时、单样本耗时已实测并回填 manifest

## 3. 统一输入输出契约（IO Contract）

### 3.1 运行期目录约定（平台注入，模型不得更改）

```
/work/
├── in/                     # 输入目录（DRP_IN_DIR）：Runner 按 inputs[].urn 下载到此
│   ├── RECEPTOR/receptor.pdb
│   └── LIGAND/ligands.sdf
├── out/                    # 输出目录（DRP_OUT_DIR）：模型只往这里写产物
│   └── ...                 # 具体文件名由 result.json 的 artifacts[].path 声明
├── tmp/                    # 临时文件（DRP_TMP_DIR）
├── task.json               # 输入：平台下发的任务描述（DRP_TASK_FILE）
└── result.json             # ★ 输出：结果清单（DRP_RESULT_FILE）
```

> **v1.2 修订（三号审核 B-4）**：`result.json` 的位置此前在本树中被画在 `out/` 下，与 §3.6 环境变量表 `DRP_RESULT_FILE=/work/result.json` **冲突**。现统一为**`/work` 根下**：`result.json` 是「**结果清单**」，声明产物文件（`artifacts[].path` 指向 `out/` 内的实际文件）。两者不是同一类东西——清单在根、产物在 `out/`。以 §3.6 为唯一真源。

环境变量：

> **运行期环境变量的唯一定义在 §3.6**（含 10 个变量、取值与默认值）。本节**不再重复列变量表**，避免出现「§3.1 有、§3.6 没有」的游离变量（v1.2 已删除原表中的 `DRP_WEIGHTS_DIR`——权重目录固定只读挂载到 `/opt/model/weights`，不经环境变量下发）。

### 3.2 输入 `task.json`

```json
{
  "taskId": "tsk_01J...",
  "taskType": "STRUCTURE_PREDICTION",
  "projectId": "prj_...",
  "model": { "name": "boltz2", "version": "2.0.1" },
  "bizRef": { "targetId": "tar_...", "candidateIds": [] },
  "device": "cuda:0",
  "params": {
    "recycling_steps": 3,
    "sampling_steps": 200,
    "diffusion_samples": 1,
    "seed": 20260101
  },
  "inputs": [
    { "role": "SEQUENCE", "kind": "FASTA", "path": "/work/in/SEQUENCE/seq.fasta",
      "urn": "oss://drp-assets/.../seq.fasta", "sha256": "..." },
    { "role": "LIGAND", "kind": "SDF", "path": "/work/in/LIGAND/lig.sdf",
      "urn": "oss://...", "sha256": "..." }
  ],
  "limits": { "maxMinutes": 60, "maxItems": 8 }
}
```

**设计要点**：模型**不感知对象存储**。平台 Runner 在容器启动后先把 `inputs[].urn` 下载到 `inputs[].path`，模型只读本地路径。这样模型包不需要集成任何 SDK。

### 3.3 输出 `result.json`（强制）

```json
{
  "status": "SUCCESS",
  "model": { "name": "boltz2", "version": "2.0.1" },
  "device": "cuda:0",
  "metrics": [
    { "key": "confidence_score", "label": "置信度", "value": 0.433, "unit": "score", "subjectRole": "COMPLEX" },
    { "key": "plddt_mean",       "label": "平均pLDDT", "value": 0.512, "unit": "score" },
    { "key": "affinity",         "label": "亲和力",   "value": 7.31, "unit": "pIC50" }
  ],
  "artifacts": [
    { "role": "STRUCTURE", "name": "complex.cif", "path": "/work/out/complex.cif",
      "format": "CIF", "primary": true, "sha256": "..." },
    { "role": "CONFIDENCE", "name": "confidence.json", "path": "/work/out/confidence.json", "format": "JSON" }
  ],
  "tables": [
    { "role": "PREDICTIONS", "name": "predictions.csv", "path": "/work/out/predictions.csv",
      "rowCount": 2, "columns": ["id", "predicted_affinity", "..."] }
  ],
  "warnings": [
    { "code": "OPENBABEL_MOL2_WARNING", "count": 12, "message": "Mol2 原子类型非标准，不影响结果" }
  ],
  "timing": { "loadSeconds": 108.2, "inferSeconds": 9.4, "totalSeconds": 123.6 }
}
```

**强制字段**：`status`、`metrics` 或 `artifacts` 至少一个、`timing`。
**禁止**：输出中出现绝对主机路径；输出中出现未声明的文件。

### 3.4 各能力的标准输出映射

| 能力 | primary artifact | 关键 metric key |
|---|---|---|
| STRUCTURE_PREDICTION | `*.cif` / `*.pdb` | `plddt_mean`、`confidence_score` |
| POCKET_PREDICTION | `pockets.json`（含中心/体积/评分）+ `*.cmap` | `pocket_count`、`top_score` |
| MOLECULE_GENERATION | `molecules.sdf` | `generated_count`、`valid_count` |
| PEPTIDE_DESIGN | `peptides.fasta` | `generated_count`、`reward_score` |
| ADMET_PREDICTION | `predictions.csv` | 按指标族展开（`logS`、`hERG`…） |
| AFFINITY_PREDICTION | `predictions.csv` | `predicted_affinity`、`pocket_atom_count` |
| DOCKING | `poses.sdf` | `docking_score`（kcal/mol）、`rmsd_lb` |
| MD_SIMULATION | `md.xtc` | `rmsd_final`、`duration_ns` |
| FREE_ENERGY | `report.csv` | `delta_g`（kcal/mol） |

> **MolP-PC 的 56 列**必须在 `io/output.schema.json` 中逐列声明 `column → metric_key → 中文名 → 单位 → 方向（越大越好/越小越好）`，平台据此自动渲染指标矩阵。

### 3.5 进度与日志协议

- **进度**：模型周期性写 `/work/out/progress.json`：`{"pct": 35, "stage": "分片 7/20"}`
  - 若模型无法改造（如 GROMACS），则 Runner 解析 stdout 中的约定行：`__DRP_PROGRESS__ {"pct":35,...}`
- **日志**：直接写 stdout/stderr，由 Runner 采集分片上传；禁止写本地文件后不输出
- **退出码**：`0` 成功；`10` 输入非法；`11` 权重缺失；`12` 显存不足；`13` 超时；`1` 其他失败
  - 非 0 时仍需写 `result.json`，`status=FAILED` 且带 `error`

### 3.6 `drp-runner` 接口规范（**v1.2 新增，唯一入口契约**）

> **为什么单列一节**：`drp-runner` 是全部 9 个模型镜像的公共 ENTRYPOINT（§3.1 / §4.3 Dockerfile `ENTRYPOINT ["/opt/drp-runner/bin/drp-runner"]`），它的参数与环境变量此前**在文档中没有正式定义**——只在 §6.3 的 `docker run` 示例里零星出现过 `DRP_TASK_FILE` / `DRP_RESULT_FILE`。Runner 契约不明确，等于模型包与平台之间没有契约。本节为**唯一真源**，`03` §6.5 与 `10` §6.2 均只作引用，不得再各自书写路径。

**调用方式：镜像 ENTRYPOINT 无参数启动，全部通过环境变量注入。**（Runner 不依赖 CLI 参数，避免各模型 `run.sh` 与命令行解析打架。）

```bash
# 由 drp-node-agent 组装，模型镜像 ENTRYPOINT 即 drp-runner
docker run --rm --name drp-<taskId> \
  -e DRP_TASK_FILE=/work/task.json \
  -e DRP_RESULT_FILE=/work/result.json \
  -e DRP_IN_DIR=/work/in \
  -e DRP_OUT_DIR=/work/out \
  -e DRP_PROGRESS_FILE=/work/out/progress.json \
  -e DRP_WORK_DIR=/work \
  -e DRP_MODEL_ENTRY=/opt/model/entrypoint/run.sh \
  -e DRP_DEVICE=cuda:0 \
  -e DRP_HEARTBEAT_SEC=15 \
  -e DRP_MAX_MINUTES=60 \
  -v /data/drp/work/<taskId>:/work \
  -v /data/drp/model-cache:/opt/model/weights:ro \
  --stop-timeout 60 \
  harbor.drp.local/drp/compute-boltz2:2.0.1-dtk26.04-py3.10-r3
```

**环境变量（全部由 Agent 注入，模型侧只读）**

| 变量 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `DRP_TASK_FILE` | ✅ | `/work/task.json` | 任务描述，结构见 §3.2 |
| `DRP_RESULT_FILE` | ✅ | `/work/result.json` | 结果输出，结构见 §3.3（**注意不是 `output.json`**） |
| `DRP_IN_DIR` | | `/work/in` | 输入目录；Runner 按 `task.json.inputs[].urn` 下载到此目录下的 `{role}/` 子目录 |
| `DRP_OUT_DIR` | | `/work/out` | 输出目录；模型只写这里 |
| `DRP_PROGRESS_FILE` | | `/work/out/progress.json` | 进度文件（§3.5） |
| `DRP_WORK_DIR` | | `/work` | 工作根目录（Agent 挂载点，与 `09` §4.3 的 `-v ...:/work` 一致） |
| `DRP_MODEL_ENTRY` | ✅ | — | 模型实际入口，来自 `manifest.entrypoint.batchCommand`（§2.2）。Runner 以 `list[str]` 形式 exec，**不经 shell** |
| `DRP_DEVICE` | | `cuda:0` | 逻辑设备名（MD-06 要求模型从此读取，禁止硬编码） |
| `DRP_HEARTBEAT_SEC` | | `10` | **Runner→Agent** 的进度心跳周期。⚠ 与 `10` §6.3 **AG-04（Agent→平台的健康心跳，≤10s / 失联 ≥3 周期即 30s 判 DEGRADED）是两条不同链路**，不要设成同一个值也不用互相满足大小关系。本参数的约束是：< `09` §4.5 的「卡位 > 90s 无进度 → 判 FAULT」窗口（即 10s 留 9 次重试余量） |
| `DRP_MAX_MINUTES` | | 取 `manifest.resources.maxMinutes`（**首次启动时的全量值**） | 墙上超时上限。**计时权威是 Agent，不是 Runner**：Agent 记录容器启动时刻并按 `maxMinutes` 计时，**到点先发 `SIGTERM`**（`--stop-timeout 60` 给 Runner 收尾窗口），Runner 收到 `SIGTERM` 后应尽快写部分产物并以退出码 `13` 退出；若 60s 内未退出，Agent `SIGKILL` 并置 `TIMEOUT`。**本变量只是 Runner 侧的「自觉上限」，用于提前优雅收尾，不构成强制**——因此不存在「两个计时器谁先到」的竞争：只有 Agent 会 kill |

**Runner 职责（模型不需要实现）**

1. 读 `DRP_TASK_FILE` → 校验 Pydantic Schema（`packages/drp_contracts`，与 `10` §2.2 同源）；
2. 按 `inputs[].urn` 从对象存储下载到 `DRP_IN_DIR/{role}/`，校验 `sha256` 不符则退出码 `10`；
3. 启动 `DRP_MODEL_ENTRY`，转发日志到 stdout，每 `DRP_HEARTBEAT_SEC` 上报进度；
4. 模型退出后**校验 `DRP_RESULT_FILE` 存在且 `artifacts[].path` 均落在 `DRP_OUT_DIR` 内**（越界即判失败，防模型写宿主路径）；
5. 上传 `DRP_OUT_DIR` 到对象存储，回填 `sha256` 与 `size`；**上传发生在容器退出前（`SIGTERM` 分支亦必须执行）**，容器被 `SIGKILL` 时由 Agent 在节点目录兜底上传并标注 `partial=true`（见下方「与 Agent 的分工」）；
6. 把退出码映射到 §3.5 的语义，非 0 时保证 `result.json` 存在且 `status=FAILED`。

**与 Agent 的分工（最容易写错的一处，务必遵守）**

| 动作 | 唯一负责方 | 另一方 |
|---|---|---|
| 挂载 `/work`、注入 `DRP_*` 环境变量、计时与终止 | `drp-node-agent` | Runner 不感知宿主机 |
| 按 `inputs[].urn` 下载输入到 `DRP_IN_DIR` | **Runner（容器内）** | Agent **不得**下载，否则会下两遍 |
| 读 `progress.json` 上报进度 | **Runner（容器内）** | Agent 只做**只读观测**兜底 |
| 上传 `DRP_OUT_DIR` 产物、回填 `sha256` | **Runner（容器内）** | Agent **不得**上传，否则产生两份 `artifact` 与两份哈希 |

> **为什么必须这样切**：`/work` 是**容器独占目录**（挂载 `-v /data/drp/work/<taskId>:/work`）。若 Agent 也下载输入，容器内会拿到两份同名文件；若 Agent 也在退出后扫描 `/work/out` 上传，`03` §3.2.2 的「对象存储写入先于事务提交、失败由对账回收孤儿对象」会同时收到两条产物记录，追溯链直接错乱。**Agent 的唯一兜底场景是容器被 `SIGKILL`**——那时 Runner 已无法执行，只能由 Agent 抢救并标 `partial=true`。

**幂等要求**：同一 `taskId` + 同一 `DRP_TASK_FILE` 内容哈希，重复启动必须产出语义一致的结果（D1 任务要求比特一致，D2/D3 按 `03` §7.4.2 容差）。Runner 不得在 `DRP_IN_DIR` / `DRP_OUT_DIR` 之外写文件。

**禁止事项**

- 禁止模型自行下载数据或访问对象存储（MD-02）——所有 IO 经 Runner；
- 禁止模型写 `/etc`、`/opt/model/weights`、`/work` 根目录；
- 禁止镜像覆盖 `ENTRYPOINT`（若确需自定义，须在 manifest 中声明并走评审，`07` §4.5 检查清单项）。

## 4. 镜像构建规范

### 4.1 三层镜像体系（关键：避免每个模型都带一份环境）

```
L0  base      OS + DTK 26.04 runtime + HYHAL + 驱动库 + libuv        ← 海光/甲方提供，极少变更
     ↓
L1  runtime   按「运行时族」建，全平台只维护 3~4 个：
              ├ runtime-torch-dtk26.04-py3.10   （PyTorch 2.7.1 + RDKit）
              ├ runtime-dgl-dtk26.04-py3.10     （+ DGL 1.1.3 patched）
              ├ runtime-tf-dtk26.04-py3.10      （+ TF 2.13.1 ROCm）
              └ runtime-hpc-dtk26.04            （GROMACS OpenCL + Vina + Meeko）
     ↓
L2  model     FROM L1 + code/ + entrypoint/ + manifest（薄层，通常 < 2GB）
```

**为什么必须这样**：STD-Diff 的 `.venv-dcu` 实测约 **3.9G**。若 9 个模型各自打包，Harbor 将承担 ~35GB 且每层无法复用；按运行时族收敛后，L1 只需维护 4 个，L2 各几十 MB~数百 MB。

### 4.2 runtime 镜像构建要点（L1）

```dockerfile
# L1 示例：runtime-dgl-dtk26.04-py3.10
ARG DTK_VERSION=26.04
FROM harbor.drp/library/base-dtk:${DTK_VERSION}

ENV DEBIAN_FRONTEND=noninteractive \
    LD_LIBRARY_PATH=/opt/hyhal/lib:/opt/dtk-${DTK_VERSION}/lib:/opt/dtk-${DTK_VERSION}/opencl/lib:$LD_LIBRARY_PATH \
    DGLBACKEND=pytorch \
    DGL_SKIP_GRAPHBOLT=1

# 1) Python 环境：micromamba 或 venv，锁文件安装，禁止浮动版本
COPY requirements/requirements.torch.lock.txt /tmp/
RUN /opt/conda/bin/micromamba create -y -n drp -f /tmp/requirements.torch.lock.txt

# 2) DGL 必须从 DTK CUDA shim 源码编译，不能用 pip wheel
COPY build/dgl-1.1.3-patched /tmp/dgl
RUN /opt/conda/envs/drp/bin/python /tmp/dgl/build_dgl_dtk.sh

# 3) 固化版本自检（构建期即失败，不放过到运行期）
COPY build/verify_runtime.py /opt/verify_runtime.py
RUN /opt/conda/envs/drp/bin/python /opt/verify_runtime.py   # 断言 torch/torch.version.hip/dgl/cuda 可用

ENV PATH=/opt/conda/envs/drp/bin:$PATH
```

**构建期强制自检 `verify_runtime.py`**：

```python
import torch, sys
assert torch.__version__ == "2.7.1", torch.__version__
assert torch.version.hip == "6.3.26045", torch.version.hip
assert torch.cuda.is_available(), "DCU 不可用"
assert torch.cuda.device_count() >= 1
# DGL runtime 镜像额外断言
# import dgl; g = dgl.graph(([0,1],[1,2])).to('cuda:0'); ...
```

> 注：构建机若无 DCU，`torch.cuda.is_available()` 断言会失败。DCU 不进 K8s（`09` / `13`），因此**没有「Kaniko Pod 申请 1 张 DCU」这条路**。两个可行方案：① 在 **DCU 机器上用 `docker build` 构建**（`13` §6.4，镜像层与 `--cache-from` 走本地 registry）；② 把 DCU 断言**下沉为运行期 smoke**，构建期只做 `pip check` 与导入测试。**推荐 ②**：L1 基座镜像构建频次低、可一次性在 DCU 机器上完成，日常 L2 构建不需要 DCU。

### 4.3 model 镜像构建要点（L2）

```dockerfile
FROM harbor.drp/library/runtime-dgl-dtk26.04-py3.10:1.2.0

# 代码与入口固定路径
COPY code/       /opt/model/code/
COPY entrypoint/ /opt/model/entrypoint/
COPY io/         /opt/model/io/
COPY sample/     /opt/model/sample/
COPY manifest.yaml /opt/model/manifest.yaml

# 平台通用执行器（下载输入/上传产物/上报进度）——模型不必实现
COPY --from=harbor.drp/library/drp-runner:1.0.0 /opt/drp-runner /opt/drp-runner

# 权重不进镜像（默认）；若 <200MB 且确需内嵌，需评审
# COPY weights/ /opt/model/weights/

RUN chmod +x /opt/model/entrypoint/*.sh
ENTRYPOINT ["/opt/drp-runner/bin/drp-runner"]
```

**模型自带 Python 环境的处理原则**

| 情况 | 处理方式 |
|---|---|
| 依赖为标准 pip 包 | 写入 `requirements.lock.txt`，并入 L1 |
| 需要 patched 库（DGL 1.1.3、torch_scatter HIP 版） | 在 L1 源码编译，禁止在 L2 覆盖 |
| 确实无法并入（版本冲突） | 允许 L2 自建 `/opt/model/.venv`，但需在 manifest 中标注 `pythonEnv`，且**单镜像体积需评审** |
| Cython/编译产物（STD-Diff） | 在 L2 构建期编译，产物进镜像 |

### 4.4 构建流水线（离线）

1. 源码仓库（内网 Git）提交 → 触发 CI
2. **构建方式分两类**：L1 基座镜像在 **DCU 机器上用 `docker build`** 构建（需真实 DCU 做 `verify_runtime.py` 断言）；L2 模型镜像在 **K8s 内用 Kaniko** 构建（无需 Docker daemon、无 DCU）
3. 构建期从**内网 PyPI 镜像**拉依赖（锁文件 + `--no-index`）
4. 推送到内网 Harbor，tag 规范：`{model}-{version}-dtk{26.04}-py{3.10}-r{buildN}`
5. 触发**冒烟流水线**：在 DCU 卡位跑 `run_smoke_test.sh`（一次性容器），产物与 `sample/expected` 比对
6. 通过后写入模型注册中心，状态 `PUBLISHED`

### 4.5 镜像构建检查清单

- [ ] 基础镜像 tag 锁定，不用 `latest`
- [ ] 依赖全部锁版本，构建可复现（同一 tag 两次构建产物一致）
- [ ] 容器内非 root 用户运行（安全基线）
- [ ] 无 `pip install torch/dgl/tensorflow`（防覆盖）
- [ ] 镜像内无源码明文泄漏（STD-Diff 实测要求「.venv 之外无项目明文 .py」）
- [ ] 体积评审通过（L2 建议 < 2GB）

## 5. 权重与大模型资产存放

### 5.1 存放分层策略

| 体积 | 存放位置 | 加载方式 | 适用 |
|---|---|---|---|
| < 200MB | 镜像内 `/opt/model/weights` | 无需加载 | 小权重（需评审） |
| 200MB ~ 5GB | MinIO `drp-models/{name}/{version}/` | Agent 拉取 + 校验 → 节点缓存（`/data/drp/model-cache`） | Boltz-2、Pocket2Mol 等 |
| 5GB ~ 50GB | 节点本地盘预置 + 节点标签 | 宿主机预置 + 校验 + 只读挂入容器 | 大模型权重 |
| > 50GB | 专属节点本地盘常驻 | 只读直接挂入容器 | AlphaFold reduced_dbs（610GB，如引入） |

### 5.2 命名与路径规范

```
对象存储： oss://drp-models/{model}/{version}/{file}
节点缓存： /data/drp/model-cache/{model}/{version}/       # 宿主机本地盘（DCU 机器）
容器内：   /opt/model/weights                              # 与 manifest.weights.mountPath 一致
校验清单： weights.checksums.txt（每行：sha256  相对路径）
```

### 5.3 加载流程（Agent 预拉 + 容器只读挂载）

> **v1.1 修订**：原为 K8s `InitContainer` 拉取权重。DCU 不进 K8s，改为 **`drp-node-agent` 预拉 + 宿主机只读挂载**（`13` §6.3）。K8s 侧的 CPU 任务仍可用 InitContainer。

```bash
# Agent 侧：任务开始前确保权重就位（幂等）
drp-agent weights ensure \
  --urn oss://drp-models/boltz2/2.0.1/ \
  --target /data/drp/model-cache/boltz2/2.0.1 \
  --checksums /data/drp/model-cache/boltz2/2.0.1/weights.checksums.txt
# 行为：命中缓存则跳过下载；未命中则从 MinIO 拉取；逐文件校验 SHA-256；失败即失败，不静默
```

容器侧只需一个只读挂载：

```bash
-v /data/drp/model-cache/boltz2/2.0.1:/opt/model/weights:ro
```

**要点**
- 节点缓存命中时不重复下载 → 第二个同类任务冷启动大幅缩短
- 校验失败直接失败，**不允许「先跑再说」**
- 缓存目录由宿主机本地盘承载，`drp-cache-gc.timer` 按 LRU 清理（DCU 侧）；K8s 侧（仅 CPU 任务）仍用 `ReadOnlyMany` PVC + CronJob

### 5.4 离线导入流程

```
1) 供应商/我方在外网环境下载权重 → 打包 {model}-{version}-weights.tar.gz + checksums.txt
2) 介质拷入内网（符合甲方安全流程）
3) 执行 drpctl weights import --bundle xxx.tar.gz --target drp-models/boltz2/2.0.1
   - 校验 SHA-256
   - 写入模型注册中心（weightsUrn、sizeGB、checksums）
   - 记录导入人、时间、来源介质
4) 可选：drpctl weights preseed --model boltz2 --nodes dcu-node-01,dcu-node-02  # 预置到节点本地盘
```

### 5.5 特殊资产处理

| 资产 | 体积 | 方案 |
|---|---|---|
| AlphaFold reduced_dbs | ≈610GB | **默认不引入**；若因 MSA 精度需要引入，则部署在专用节点本地盘，宿主机路径直接挂入容器，禁止走网络 |
| STD-Diff `.venv-dcu` | 3.9G | **不入镜像**；按 §4.1 收敛到 L1 运行时族，L2 只放代码 |
| MD 轨迹产物 | 单任务 GB 级 | 生成即写 `drp-bulk`，边算边传，容器本地只保留最近分片 |

## 6. 算力节点上的运行形态（DCU 不进 K8s）

> **v1.1 修订**：本章原名「K8s 调度推理方案」。按 `09` / `13`，DCU 机器以裸机 + `drp-node-agent` 方式交付，K8s 只承载业务服务与 CPU 型任务。本章的**形态划分**（BATCH / RESIDENT / HYBRID）是模型自身特征，与承载方式无关，故保留；具体的承载实现已改为 Docker 容器 + `slots.yaml`。

### 6.1 三种运行形态

```
                       ┌─────────────────────────────────────────┐
   用户提交任务 ─────▶ │ drp-task：参数校验 → 配额 → 入队         │
                       └───────────────┬─────────────────────────┘
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                             ▼
            mode = BATCH                     mode = RESIDENT
        ┌───────────────────────┐      ┌────────────────────────────┐
        │ drp-workflow 自研 DAG  │      │ 常驻 Docker 容器（卡位绑定）│
        │  └ 算力侧一次性容器    │      │  ├ 模型常驻显存             │
        │    ├ init: 权重        │      │  ├ 进程内排队消费           │
        │    ├ run.sh            │      │  └ 由 slots.yaml 声明副本   │
        │    └ 结束即回收        │      └────────────────────────────┘
        └───────────────────────┘
```

> **v1.1 修订**：原图与表把 DCU 形态写成 `Deployment` / `Job` / `HPA`，与 `09`、`13` 的「DCU 不进 K8s」矛盾。现改为：DCU 侧统一由 `drp-node-agent` 在裸机上拉起容器（一次性或常驻），K8s 仅承载 CPU 型任务。

| 形态 | 判据 | 承载形态 | 组件 |
|---|---|---|---|
| **BATCH** | 单次 > 60s，或冷启动占比 > 50% | DCU：`drp-node-agent` 拉起的一次性容器；CPU：K8s `Job` | Boltz-2、STD-Diff、Pocket2Mol、TheraPainter、GROMACS、Vina |
| **RESIDENT** | 单次 < 60s 且显存占用 < 20% | DCU 机器上的**常驻 Docker 容器**（`slots.yaml` 声明、卡位独占），进程内排队；副本数由卡位而非 HPA 决定 | LVpocket、MolP-PC、MSIGN、PEARL |
| **HYBRID** | 交互场景要低延迟，批量场景要吞吐 | 两者并存，按 `priority` 路由 | Boltz-2（交互走常驻、批量走一次性容器） |

### 6.2 设备映射与环境变量（实测约束）

**设备名**：DCU 在 PyTorch/TensorFlow 兼容层表现为 `cuda:N`；DGL 侧可见 `hip:N`。
**容器化约定**：每个容器 **只占用 1 张卡**，容器内统一视作 `cuda:0`。DCU 侧由**卡位静态独占**（`slots.yaml` 中 `ROCR_VISIBLE_DEVICES` 固定绑卡）完成物理隔离，不依赖 device plugin；K8s 侧只有 CPU 任务，不涉及 DCU 设备插件。详见 `09` §4.3 与 `13` §6。

```yaml
# 容器环境变量（由 manifest.env 生成，Agent 以 docker run -e 注入）
env:
  - name: DEVICE                     # manifest.device.deviceEnvVar
    value: "cuda:0"
  - name: LD_LIBRARY_PATH
    value: "/opt/hyhal/lib:/opt/dtk-26.04/lib:/opt/dtk-26.04/opencl/lib"
  # 按模型注入（来自 manifest.env）：
  - name: DGLBACKEND
    value: pytorch                   # MSIGN / MolP-PC / PEARL
  - name: DGL_SKIP_GRAPHBOLT
    value: "1"
  - name: TF_FORCE_GPU_ALLOW_GROWTH
    value: "true"                    # LVpocket
  - name: TF_CPP_MIN_LOG_LEVEL
    value: "1"
  - name: POCKET2MOL_ALLOW_PYG_FALLBACK
    value: "1"                       # Pocket2Mol
  - name: OMP_NUM_THREADS
    value: "16"                      # GROMACS / CPU 类
  - name: GMX_GPU_DISABLE_COMPATIBILITY_CHECK
    value: "1"                       # GROMACS
  # ⚠️ OCL_ICD_VENDORS 必须保持【未设置】（GROMACS 实测结论）
```

> **v1.1 修订**：原示例在本代码块末尾带有 `resources.limits.hygon.com/dcu`、`nodeSelector: dcu-compute` 与 `tolerations` 三行——那是 DCU 进 K8s 的写法，与 `09` / `13` 矛盾，已删除。DCU 侧的卡隔离由 `slots.yaml` 的 `ROCR_VISIBLE_DEVICES` 完成；只有 CPU 型任务才使用 K8s 的 `resources` / `nodeSelector`（见 §6.3 末的 CPU 侧说明）。

> **GROMACS 专项**：必须 `source $HOME/gromacs-opencl/bin/GMXRC`，`OCL_ICD_VENDORS` 未设置，运行参数固定 `-nb gpu -pme cpu -gpu_id 0`。这些必须写进模型镜像的 `run.sh`，不能依赖 K8s 注入。

### 6.3 BATCH 模式：一次性容器（DCU 侧）

> **v1.1 修订**：原示例为 K8s `Job` 清单。按 `09` / `13`，DCU 不进 K8s，BATCH 任务由 `drp-node-agent` 在裸机上以 `docker run --rm` 拉起一次性容器。下例是 Agent 实际执行的等价命令与容器参数（`task.json` 契约不变）。

```bash
# drp-node-agent 在卡位 A3（物理卡 3）上拉起一次性容器
docker run --rm --name drp-tsk-01J... \
  --gpus all \
  -e ROCR_VISIBLE_DEVICES=3 \
  -e DRP_TASK_FILE=/work/task.json \
  -e DRP_RESULT_FILE=/work/result.json \
  -e DRP_IN_DIR=/work/in \
  -e DRP_OUT_DIR=/work/out \
  -e DRP_PROGRESS_FILE=/work/out/progress.json \
  -e DRP_WORK_DIR=/work \
  -e DRP_MODEL_ENTRY=/opt/model/entrypoint/run.sh \
  -e DRP_DEVICE=cuda:0 \
  -e DRP_HEARTBEAT_SEC=15 \
  -e DRP_MAX_MINUTES=60 \
  -e DEVICE=cuda:0 \
  -v /data/drp/work/tsk_01J...:/work \
  -v /data/drp/model-cache/boltz2/2.0.1:/opt/model/weights:ro \
  --cpus 8 --memory 32g --shm-size 2g \
  --stop-timeout 60 \
  harbor.drp.local/drp/compute-boltz2:2.0.1-dtk26.04-py3.10-r3
```

| 参数 | 说明 |
|---|---|
| `ROCR_VISIBLE_DEVICES` | **卡位固定绑卡**，由 `slots.yaml` 声明；容器内只看得到 1 张卡 |
| `DRP_DEVICE=cuda:0` | **平台级逻辑设备名**，恒为容器内编号；Runner 与平台读它（`10` MD-06） |
| `DEVICE=cuda:0` | **模型私有变量**，名字与取值由 `manifest.device.deviceEnvVar` + `manifest.device.deviceValue` 声明（MSIGN 为 `hip:0`）。Agent 按 manifest 注入，**与 `DRP_DEVICE` 不同源、不互为默认值** |
| 其余 `DRP_*` | 完整 10 个变量的含义与默认值见 **§3.6 表**，本节不重复 |
| `--stop-timeout 60` | 与状态机取消语义对齐：SIGTERM → 宽限 60s → SIGKILL（`03` §3.4） |
| 权重挂载 | 宿主机 `/data/drp/model-cache/<model>/<version>` 只读挂入 `/opt/model/weights`；**不经环境变量下发路径** |
| 超时 | Agent 按 `manifest.resources.maxMinutes` 计时（同时以 `DRP_MAX_MINUTES` 告知 Runner），到时 SIGTERM |
| 重试 | 由平台状态机控制，Agent **不自动重启**（等价于 `backoffLimit: 0`） |

> **v1.2 修订（B-5）**：原示例只注入 2 个变量，缺 §3.6 标为「必填无默认」的 `DRP_MODEL_ENTRY`，照此命令拉起镜像 Runner 第 3 步无从执行；同时 `DEVICE` 与 `DRP_DEVICE` 两套机制并存却无优先级，开发无法判断 MSIGN 该读哪个。现已补全 10 个变量并把两者关系写进参数表。

**冷启动治理（关键）**

Boltz-2 实测：wall 123s = 加载/编译 ~110s + 推理 ~9s。对策：

| 手段 | 说明 |
|---|---|
| **批量合并** | 一个容器内处理 `batchMaxSize` 个样本，摊薄冷启动（Boltz-2 设 8） |
| **权重节点缓存** | 宿主机只读挂载，省去下载 |
| **常驻池预热** | 交互类（单分子）走 RESIDENT，模型常驻显存 |
| **容器复用（可选）** | 对高频 BATCH 模型保留「热容器」，任务来了直接 `docker exec` 投递 |

### 6.4 RESIDENT 模式规范

> **v1.1 修订**：原示例为 K8s `Deployment`。按 `09` / `13`，常驻形态由 **systemd unit + `slots.yaml` 声明**管理（`13` §6.3），不用 Deployment、不用 HPA。

```yaml
# /etc/drp/slots.yaml（宿主机，由 drp-node-agent 收敛）
slots:
  - slot: A5
    card: 5
    model: lvpocket
    version: 2.0.0
    image: harbor.drp.local/drp/compute-lvpocket:2.0.0-dtk26.04-py3.10-r2
    mode: RESIDENT
    queue: capability.POCKET_PREDICTION
    replicas: 1                 # 1 卡 1 副本
    healthCheck: http://127.0.0.1:18080/healthz
```

对应 systemd unit（由 `13` §6.2 下发）：

```ini
[Unit]
Description=DRP slot A5 (lvpocket RESIDENT)
After=docker.service
Requires=docker.service

[Service]
Restart=always
RestartSec=10
ExecStartPre=-/usr/bin/docker rm -f drp-slot-A5
ExecStart=/usr/bin/docker run --rm --name drp-slot-A5 \
  --gpus all -e ROCR_VISIBLE_DEVICES=5 -e DEVICE=cuda:0 \
  -e TF_FORCE_GPU_ALLOW_GROWTH=true \
  -e DRP_QUEUE=capability.POCKET_PREDICTION \
  -v /data/drp/model-cache:/opt/model/weights:ro \
  -v /data/drp/work:/work \
  -p 127.0.0.1:18080:8080 \
  harbor.drp.local/drp/compute-lvpocket:2.0.0-dtk26.04-py3.10-r2
ExecStop=/usr/bin/docker stop -t 60 drp-slot-A5

[Install]
WantedBy=multi-user.target
```

**规则**
- 不对外暴露；只监听 `127.0.0.1`，消费者从 RabbitMQ 拉任务（或 Agent 投递）
- **一卡一副本**：显存足够小（LVpocket 4%）时可开启 time-slicing 让多模型共享一卡
- 常驻副本数由 `slots.yaml` 的卡位声明决定，**不用 HPA**（DCU 侧无 K8s 控制器）；扩缩 = 改 `slots.yaml` + Agent 收敛（`13` §6.3）
- 优雅退出：收到 SIGTERM 后处理完当前批次再退出（宽限 60s）

### 6.4.1 运行后端抽象（与具体后端解耦）

| 后端 | 承载任务 | 承载形态 |
|---|---|---|
| `K8sBackend` | CPU 密集任务（Vina 对接、构象、药效团、导入导出） | K8s `Job` |
| `SSHBackend`（**当前主用**） | DCU 模型推理 | DCU 机器上的一次性 / 常驻 Docker 容器，由 `drp-node-agent` 管理 |

### 6.5 调度、排队与配额

| 机制 | 设计 |
|---|---|
| 队列 | 按 `capability` 分队列（如 `capability.STRUCTURE_PREDICTION`），RESIDENT 消费者按能力订阅 |
| 准入 | `drp-scheduler` 校验项目配额 → 写 `queue_position` → 按 优先级 + FIFO 放行 |
| 优先级 | `HIGH`（交互） / `NORMAL` / `BULK`（批量，夜间优先） |
| 卡位预留 | 16 卡中：交互类预留 4、批量 10、冗余 2（见架构 §5.1） |
| 超时 | 按 manifest `maxMinutes` 设置（DCU 侧由 Agent 计时后 SIGTERM；K8s 侧用 `activeDeadlineSeconds`） |
| 长时任务 | GROMACS MD 走长时队列（DCU 侧专用卡位；K8s 侧 `priorityClassName: drp-compute-long`），配 checkpoint 续跑 |

## 9. 附录：环境变量速查（**模型私有变量**）

> `DRP_*` 平台注入变量见 **§3.6**，本表不重复。本表只列**各模型自身**读的环境变量——它们**名字各不相同、取值可能不同**，由 `manifest.device.deviceEnvVar` / `deviceValue` 逐模型声明，Agent 按 manifest 注入。
>
> **与 `DRP_DEVICE` 的关系**：`DRP_DEVICE` 是平台级逻辑设备名，恒为容器内编号（`cuda:0`）；`DEVICE` / `POCKET2MOL_DEVICE` 等是模型私有变量。**两者不同源、不互为默认值**——Runner 与平台读 `DRP_DEVICE`，模型代码只读自己的私有变量。

| 变量 | 适用模型 | 值 | 来源 |
|---|---|---|---|
| `DEVICE` | MolP-PC | `cuda:0` | 实测 |
| `DEVICE` | MSIGN | `hip:0` | 实测 |
| `POCKET2MOL_DEVICE` | Pocket2Mol | `cuda:0` | 实测 |
| `POCKET2MOL_ALLOW_PYG_FALLBACK` | Pocket2Mol | `1` | 实测 |
| `DGLBACKEND` | MSIGN/MolP-PC/PEARL | `pytorch` | 实测 |
| `DGL_SKIP_GRAPHBOLT` | 同上 | `1` | 实测 |
| `TF_FORCE_GPU_ALLOW_GROWTH` | LVpocket | `true` | 实测 |
| `TF_CPP_MIN_LOG_LEVEL` | LVpocket | `1` | 实测 |
| `LD_LIBRARY_PATH` | 全部 DCU 模型 | `/opt/hyhal/lib:/opt/dtk-26.04/lib:...` | 实测 |
| `OCL_ICD_VENDORS` | GROMACS | **必须未设置** | 实测 |
| `GMX_GPU_DISABLE_COMPATIBILITY_CHECK` | GROMACS | `1` | 实测 |
| `OMP_NUM_THREADS` | GROMACS / CPU 类 | `16` | 实测 |
| `HOME` | MSIGN/MolP-PC | `/tmp/{model}-dcu-home` | 实测 |
| `MODEL_PYTHON` | TheraPainter/MSIGN | 解释器绝对路径 | 实测 |
| `CUDA_VISIBLE_DEVICES` | 单卡隔离场景 | **`0`（容器内序号，不是宿主卡号）** | ⚠️ v1.4 实测修正 |

> **v1.4 修正（2026-10-25 实测，见 `08A` §4）**：`CUDA_VISIBLE_DEVICES` 的值是**容器内可见列表的序号**，不是宿主卡号。当卡位已用 `--gpus '"device=N"'` 或 `NVIDIA_VISIBLE_DEVICES=N` 把可见范围限制为 1 张卡时，容器内只剩 1 个元素，其序号必然是 `0`；此时填宿主卡号 `N` 会得到**空集**，`torch.cuda.device_count()` 返回 `0`，且容器**正常退出、无报错**，模型静默走 CPU。
>
> 对照：DCU 侧的 `ROCR_VISIBLE_DEVICES=6` + `HIP_VISIBLE_DEVICES=0` 恰好就是「宿主卡号 + 容器内 0」的正确组合，所以从 DCU 习惯照搬 `CUDA_VISIBLE_DEVICES=6` 会刚好踩中——**这是本题最容易漏的地方**。
