# 工具分类独立化与管理员收口设计

## 目标

将当前工具分类从 `tools.category` 自由字符串升级为可管理的独立资源，并把工具生命周期完全收口到管理员侧：

- 管理员可新增、编辑、删除、排序、启用/停用分类
- 工具只能从分类表中选择分类
- 工具只能由管理员创建、编辑、删除
- 下线普通用户创建工具、社区工具、审核流相关能力

## 背景与现状

当前项目中的分类能力存在以下问题：

- 后端 [backend/app/models/tools.py](/data/zhouyc/cpumodel_sciminer/backend/app/models/tools.py:60) 中 `Tool.category` 只是普通字符串字段，没有主数据约束
- [backend/app/api/v1/tools.py](/data/zhouyc/cpumodel_sciminer/backend/app/api/v1/tools.py:196) 的 `/tools/categories` 只是对已发布工具的分类字符串做聚合，不支持管理
- 前端管理员工具页 [frontend/src/views/admin/Tools.vue](/data/zhouyc/cpumodel_sciminer/frontend/src/views/admin/Tools.vue:21) 使用硬编码分类和模拟工具数据
- 当前系统仍保留“用户创建工具 + 官方/社区工具 + 审核状态”的旧支线，权限模型复杂且与新的产品决策冲突

## 设计决策

采用“独立分类表 + 工具权限管理员化 + 接口兼容过渡”的方案。

### 选择原因

- 直接建立分类主数据，才能真正实现“管理员管理分类、工具只能从分类表选择”
- 一次性去掉用户工具和审核流，可以显著简化后端查询条件和前端状态分支
- 后端响应在迁移期暂时保留 `category` 展示字段，可控制前端改动节奏，降低回归风险

## 范围

### 包含

- 新增 `tool_categories` 数据表与模型
- 工具改为使用 `category_id` 外键
- 新增管理员分类管理接口
- 管理员后台新增分类管理页面
- 工具创建/编辑改为管理员专用，并使用分类下拉
- 下线普通用户创建工具入口和审核流相关能力

### 不包含

- 不调整收藏能力
- 不修改任务执行、工具版本管理底层逻辑
- 不在本次同步清理数据库中所有历史兼容字段，兼容字段可以延后删除

## 数据模型设计

### 新表：`tool_categories`

建议字段：

- `id`: UUID 主键
- `name`: 分类名称，唯一
- `slug`: 分类标识，唯一，用于稳定引用和排序展示
- `description`: 分类描述，可选
- `sort_order`: 排序值，默认 0
- `is_enabled`: 是否启用，默认 `true`
- `created_at`
- `updated_at`

### 工具表调整

- `tools` 新增 `category_id` 字段，外键指向 `tool_categories.id`
- 业务逻辑改为只认 `category_id`
- 原 `tools.category` 字符串列在迁移期保留只读兼容，不再作为写入源

### 历史数据迁移

- 扫描现有 `tools.category` 去重值，批量生成分类记录
- 将每个工具回填到对应 `category_id`
- 如历史工具存在空分类，创建一个兜底分类，例如 `uncategorized`
- 兜底分类默认可设置为停用，避免新工具继续使用

## 权限模型

### 普通用户

- 可查看工具列表和工具详情
- 可按分类筛选工具
- 可收藏/取消收藏工具
- 不可创建、编辑、删除工具
- 不再拥有“我的工具”“提交审核”“待审核”“社区工具”等能力

### 管理员

- 可管理分类
- 可创建、编辑、删除工具
- 可在后台查看和维护分类顺序与启用状态

## API 设计

### 公开分类读取接口

- `GET /api/v1/tools/categories`
- 返回启用中的分类列表
- 按 `sort_order` 升序返回
- 用于工具列表筛选和管理员工具表单下拉

建议响应字段：

- `id`
- `name`
- `slug`
- `description`
- `sort_order`

如列表页仍需数量统计，可由后端附带 `tool_count`，但不强制要求。

### 管理员分类管理接口

- `GET /api/v1/admin/tool-categories`
- `POST /api/v1/admin/tool-categories`
- `PUT /api/v1/admin/tool-categories/{id}`
- `PATCH /api/v1/admin/tool-categories/{id}/status`
- `POST /api/v1/admin/tool-categories/reorder`
- `DELETE /api/v1/admin/tool-categories/{id}`

约束规则：

- 删除时若分类下仍有关联工具，返回明确业务错误，禁止删除
- 停用分类不出现在公开分类列表中
- 停用分类不可用于工具新建或编辑

### 工具接口调整

- `POST /api/v1/tools` 改为仅管理员可用
- `PUT /api/v1/tools/{id}` 改为仅管理员可用
- `DELETE /api/v1/tools/{id}` 改为仅管理员可用
- 创建和更新工具时使用 `category_id` 作为输入字段

迁移期响应兼容：

- 保留 `category_id`
- 保留 `category` 展示字段，值为分类名称
- 可选增加 `category_detail`

## 下线能力

以下能力和接口整体下线：

- 用户创建工具
- 用户“我的工具”视图
- 工具审核提交
- 工具待审核列表
- 审核通过/拒绝
- 平台官方工具/社区工具切换
- 与 `provider_type`、`review_status` 相关的前后端显示与筛选

涉及的典型路径包括：

- `/tools/create`
- `/tools/my`
- `/tools/{id}/submit-review`
- `/tools/admin/pending-reviews`
- `/tools/admin/{id}/review`
- `/tools/admin/{id}/set-platform`

## 前端改造

### 管理后台

- 在管理员侧边栏新增“分类管理”入口
- 新增独立页面用于分类增删改查、启停、排序
- 管理员工具页改为真实接入后端，而不是使用模拟数据和硬编码分类

### 工具创建/编辑

- 只保留管理员入口
- 分类选择使用 `category_id`
- 只展示启用中的分类
- 当编辑中的工具落在停用分类下时，可在表单中回显但不可继续提交到非法状态，或要求管理员先变更分类

### 普通用户侧

- 删除创建工具按钮和对应路由
- 删除“我的工具”以及审核状态相关 UI
- 保留工具分类筛选和收藏能力

## 错误处理

- 非管理员访问分类管理接口返回 `403`
- 非管理员调用工具写接口返回 `403`
- 使用不存在或停用分类创建/编辑工具返回 `422` 或明确业务错误
- 删除仍被引用的分类返回 `409`
- 分类名称或 `slug` 冲突返回 `409`

## 测试与验证

### 后端

- 管理员分类接口权限测试
- 分类增删改查、启停、排序测试
- 引用中分类删除失败测试
- 工具写接口管理员权限测试
- 工具创建/编辑时 `category_id` 合法性测试
- 迁移脚本测试

### 前端

- 管理员分类管理页基本交互
- 管理员工具创建/编辑页分类下拉
- 普通用户不再看到创建工具和审核流入口
- 工具列表按分类筛选仍可用

### 数据校验

- 迁移后 `tools.category_id` 无空值
- 分类表条目与历史分类去重结果一致
- 工具详情和列表中的分类展示正确

## 风险控制

- SQLite 迁移前必须备份数据库
- 先新增 `category_id` 并回填，再切业务代码，最后考虑移除旧字符串列
- 通过兼容响应字段降低前端一次性修改风险
- 审核流先下线业务入口，再清理残留字段和类型，避免一步到位造成大面积回归

## 实施顺序

1. 新增 `tool_categories` 表、模型和迁移脚本
2. 回填工具分类外键并完成数据校验
3. 新增分类管理 API，收紧工具写权限
4. 改前端类型、管理员分类管理页和管理员工具页
5. 下线普通用户创建工具与审核流前后端入口
6. 完成测试、构建和迁移校验

## 验证标准

- 管理员可以完整管理分类
- 非管理员无法创建、编辑、删除工具
- 工具只能绑定已存在且可用的分类
- 普通用户界面不再出现创建工具和审核流入口
- 工具列表与详情中的分类显示正常
- 迁移后历史工具未丢失分类信息
