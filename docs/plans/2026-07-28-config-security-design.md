# 配置安全加固设计

## 目标

完成技术债清单 P0 1.1.2 与 1.1.3：为生产与预发布环境建立独立、可验证的密钥边界，并消除示例配置中的宽泛 CORS 默认值。

## 决策

采用兼容策略。开发环境允许 `SETTINGS_ENCRYPTION_KEY` 为空，此时加密模块回退使用 `JWT_SECRET_KEY`，从而保持已有本地密文在重启后的可解密性。该回退会发出一次警告，提示开发者配置独立密钥。

`staging` 和 `production` 必须提供独立的 `SETTINGS_ENCRYPTION_KEY`：长度不少于 32 个字符，且不得与 `JWT_SECRET_KEY` 相同。原有的 JWT 长度、生产环境 `DEBUG=False` 与禁止通配 CORS 规则保持不变。

`CORS_ORIGINS` 的默认值从通配符改为本地 Vite 开发地址。示例环境文件使用相同的安全默认值，并明确说明部署时必须替换为受控域名。

## 数据流与错误处理

`Settings` 在 Pydantic 的 model validator 中根据环境验证密钥与 CORS。生产或预发布配置不合规时，应用构造设置对象即失败，避免以弱配置启动。

`secret_crypto._fernet()` 始终优先使用独立设置密钥；仅在开发环境缺失该密钥时回退 JWT 密钥并记录去重警告。它不生成临时密钥，因此不会破坏已保存配置的解密能力。

## 测试策略

先写失败测试，再实现最小代码。覆盖开发回退、预发布/生产缺失独立密钥、过短密钥、复用 JWT 密钥、有效独立密钥以及新的 CORS 默认值。现有加解密往返测试确保兼容路径不回归。
