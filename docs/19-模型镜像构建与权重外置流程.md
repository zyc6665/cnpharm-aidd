| 状态 | 已验证（`lvpocket` 在 4090 GPU 上跑通；2026-10-31 另验证 MolP-PC / MSIGN / Pocket2Mol，见 §12） |
|---|---|

| 适用 | 所有以容器形式交付的计算模型（`docs/07` §1.1 的 10 个模型） |

## 1. 为什么要单独定义这套流程

`docs/03` §10 规定离线交付形态是「镜像 + 权重包 + 内网 registry」。但
「镜像」到底该装什么、权重到底放哪里，在代码层没有可执行的约束，导致：

- 有人把 19 GB 权重打进镜像，镜像仓库被撑爆；
- 有人把权重留在宿主机某个目录，换节点就找不到；
- 有人让模型自己在容器里下权重，违反 `docs/07` §3.6 的 MD-02（禁止模型访问对象存储）；
- 有人用 `tag` 引用镜像，追溯包里的镜像名过两个月指向另一个镜像。

本流程把上述四件事固化成可检查的约定，并给出一个**已验证的参照实现**
（`deploy/model-images/lvpocket/`）。

## 2. L1 / L2 两层验证

| 层 | 权重 | 验证什么 | 状态 |
|---|---|---|---|
| **L1** | 无（mock 包） | `manifest → 提交 → 排队 → K8s Job → 产物 → Artifact → 页面` 全链路 | ✅ 已完成（6 个 mock 包 + 40 页） |
| **L2** | 真权重 | **算得对不对**（数值与参考实现一致） | 🟡 `lvpocket` 已跑通推理，v1/v2 一致性比对待做 |

L1 与 L2 用的是**同一套镜像骨架与同一份 runner 契约**，差别只在于 `model/` 里放的是
mock runner 还是真模型代码。

## 3. 镜像分两层

```
base-cu121:py3.10-r3                     CUDA / cuDNN / PyTorch 通用栈，全平台只存一份
  └─ compute-lvpocket:2.0.0-cu122        只叠加该模型的代码与专属依赖
```

规则：

- **base 必须显式冻结版本**（tag 里带 `py3.10-r3` 这类后缀）。否则各模型镜像
  `pip install` 时装出不同版本的 torch，迁移到 DCU 时无法定位差异来源。
- **模型镜像只装"这个模型特有"的东西**。`lvpocket` 的例子：`tensorflow[and-cuda]`
  自带 CUDA 12.2 运行时，因此连 `nvidia/cuda` 基础镜像都不需要，`python:3.11-slim`
  就够，最终 6.31 GB。
- **不要把虚拟环境整目录拷进镜像**。`lvpocket` 源目录的 `env/` 是 5.8 GB，
  容器里按 `requirements.txt` 重装后只有必要依赖。

## 4. 权重不进镜像

`lvpocket` 实测：权重 19 GB，占原 26 GB 的 **73%**。

权重用 `runtime.weights[]` 声明（示例 `deploy/model-images/lvpocket/weights.json`）：

```json
{
  "name": "lvpocket-new-best",
  "mountPath": "/opt/sciminer/model/new_best",
  "readOnly": true,
  "source": { "kind": "object-store", "urn": "oss://drp-models/lvpocket/2.0.0.tar.zst", "sha256": "...", "sizeBytes": 0 },
  "cache":  { "kind": "host-path", "path": "/data/model-cache/lvpocket/2.0.0" }
}
```

平台生成 Job 时两条路径：

1. **节点缓存命中且 sha256 一致** → 直接 `hostPath` 只读挂载，零下载；
2. **未命中** → 注入 downloader **initContainer**：从对象存储拉取 → 校验 sha256 →
   解压到 `cache.path` → 再挂给主容器。

两条路径都**不由模型自己下载**，守住 MD-02。

镜像里只需留一个空目录作为挂载点：

```dockerfile
RUN mkdir -p /opt/sciminer/model/new_best
```

若运行时忘记挂权重，模型入口会因为找不到 `.hdf` 立刻失败（fail fast），
不会静默跑出错误结果。

## 5. 平台注入的运行时契约（以代码为准）

> ⚠️ **文档偏差**：`docs/07` §3.6 写的是 `DRP_TASK_FILE` / `DRP_RESULT_FILE` /
> `DRP_IN_DIR` / `DRP_OUT_DIR` 一套；代码实现用的是 `SCIMINER_*` 一套。以**代码**为准，
> 本偏差已登记到 `docs/18`。

`backend/app/execution/adapters/kubernetes_manifest.py` 注入、由
`deploy/kubernetes/model-image-template/platform_adaptor/object_storage.py` 读取：

| 环境变量 | 含义 |
|---|---|
| `SCIMINER_INPUTS_JSON` | 输入清单（含每个输入的 `urn` 与 `sha256`） |
| `SCIMINER_INPUT_MANIFEST` | 落盘后的清单路径，默认 `/workspace/input/manifest.json` |
| `SCIMINER_OBJECT_STORAGE_ENDPOINT` / `_BUCKET` / `_ACCESS_KEY` / `_SECRET_KEY` | 对象存储凭据 |
| `SCIMINER_EXECUTION_OUTPUT_PREFIX` | 产物上传前缀 |
| `SCIMINER_RESULT_OBJECT` | `result.json` 的目标对象键 |

执行链：

```
tini → entrypoint.sh → platform_run_v2.sh
      ├─ object_storage.py prepare    下载输入 + 校验 sha256
      ├─ model/platform_run.sh        模型推理
      └─ object_storage.py upload     上传产物 + 回填 sha256
```

`platform_run_v2.sh` 负责把 `--task-id/--input-dir/--output-dir/--params-json/--work-dir/--device`
转给 `model/platform_run.sh`。

**注意 `--model-root` 的兼容性**：早期模板无条件给模型入口传 `--model-root`，
而部分遗留模型的入口脚本不认这个参数（它们从脚本自身所在目录解析模型根），
会以 `Unknown argument: --model-root`、退出码 2 失败。模板已改为**先探测**
（`grep -q -- '--model-root)'`）再决定是否传，`test/test_model_image_template.py`
守着这条行为。

## 6. 构建流程

```bash
cd deploy/model-images/lvpocket
export MODEL_SRC=/data/zhouyc/kaiwu/LVpocket-2
export WEIGHTS_DIR=/data/zhouyc/model-cache/lvpocket/v2/new_best

./build.sh prepare    # 从源目录准备 model/ 与 platform_adaptor/（跟软链、排除 env/ 与权重）
./build.sh build      # docker build
./build.sh smoke      # 挂权重跑一次真实推理，打印 result.json 摘要
./build.sh push       # push + 打印 @sha256 digest
```

`prepare` 的三个易错点：

1. **必须跟软链**（`rsync -aL`）。源目录的 `new_best` 是指向 `new_best_1` 的软链，
   不跟软链会得到一个断链目录。
2. **排除 `env/`**（Python 虚拟环境）与 `new_best*/`（权重）。
3. **`requirements.txt` 以实际 `pip list` 为准**，不要抄 `env_v100.yml`——两者常常不一致
   （`lvpocket` 的 `env_v100.yml` 有 `scikit-image` 但 `pip list` 里没有显式体现，
   结果是推理时才 `ModuleNotFoundError`）。

## 7. 十个实测踩过的坑（`lvpocket` 从零构建）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `docker build` 超时被 Canceled | pypi.org 直连仅 1~3 MB/s，CUDA wheels 1.3 GB | `pip -i https://pypi.tuna.tsinghua.edu.cn/simple` |
| 2 | `OSError: Read-only file system: /workspace/input/manifest.json` | `prepare` 会往 input 目录写 `manifest.json` | input 目录不能只读挂载 |
| 3 | `Unknown argument: --model-root` | 模板无条件传该参数，遗留模型入口不认 | 模板改为探测（见 §5） |
| 4 | `LVpocket environment python not found: .../env/bin/python` | 模型入口硬编码 `model_root/env/bin/python` | 镜像里 `ln -s /usr/local/bin/python model/env/bin/python` |
| 5 | `Unable to open file: model1.hdf5` | `SCOP_Classifier/predict.py` 用相对路径加载权重，依赖 cwd | 适配层先 `cd "${MODEL_PACKAGE_ROOT}"` |
| 6 | `No module named 'pybel'` | `scripts/predict.py` 在子目录，`sys.path[0]` 是脚本目录 | `ENV PYTHONPATH=/opt/sciminer/model` |
| 7 | `ValueError: not enough values to unpack (expected 2, got 1)` @ `openbabel/pybel.py:69` | `openbabel-wheel 3.1.1.23` 的格式表解析 bug，崩在 import 阶段 | `shared/patch_openbabel.py` 在构建期修库 |
| 8 | `libXrender.so.1: cannot open shared object file` | OpenBabel 的 dmol 插件需要 X 库 | apt `libxrender1 libxext6`（仅告警，但会刷屏） |
| 9 | `No module named 'seaborn'` | `tfbio/net.py` 隐式依赖 | requirements 显式加 |
| 10 | `No module named 'skimage'` | `model/LV_former.py` 用 `skimage.segmentation.clear_border` | requirements 显式加 `scikit-image` |

## 8. 排查方法论

**先让子进程的 stderr 可见。** 平台入口脚本把模型跑在 `subprocess` 里并捕获输出，
一旦失败只报 `CalledProcessError: ... returned non-zero exit status 1`，看不到真正原因。
排查时应当绕过平台入口，直接执行模型自己的入口：

```bash
docker run --rm --gpus '"device=2"' \
  -v <weights>:/opt/sciminer/model/new_best:ro \
  -v <input>:/in:ro -v <out>:/out \
  --entrypoint /opt/sciminer/model/env/bin/python <IMAGE> \
  /opt/sciminer/model/scripts/predict.py --input /in/protein.pdb --output /out/raw \
  --model /opt/sciminer/model/new_best/a+b.hdf --format pdb
```

这样才能看到 `ModuleNotFoundError: No module named 'seaborn'` 这类真正的首因。
第 7~10 号坑都是这样一层层剥出来的（每修一个暴露下一个）。

**判定"跑通"的标准**（不要只看 exit code）：

- `result.json` 里 `success: true`；
- `outputs.device` 是 `gpu` 而不是 `cpu`（否则是静默 fallback，比失败更危险）；
- `metrics.model_duration_sec` 在合理量级（`lvpocket` 4090 上 17.35s）；
- `artifacts` 数量与预期一致（`lvpocket` 是 10 个）。

## 9. 迁移到 DCU 要改什么

框架、契约、输入输出、文件管理、Artifact 绑定、追溯**全部不变**，只改四处：

| 项 | NVIDIA 侧 | DCU 侧 |
|---|---|---|
| 基础镜像 | `base-cu121:py3.10-r3` | `base-dtk26.04:py3.10-r3` |
| torch/tf 包 | `tensorflow[and-cuda]` | 海光适配版（`docs/08` 的 L1 runtime 镜像） |
| 设备声明 | `--gpus device=N` + `CUDA_VISIBLE_DEVICES=0` | `--device=/dev/kfd --device=/dev/dri` + `ROCR_VISIBLE_DEVICES` |
| 算子 fallback | 无 | `docs/07` §1.2 的禁用项（如 `AlphaFold 2.3.2`、原生 `cuEquivariance`） |

**纪律**：只在 `docs/07` §1.1 那 10 个「DCU 实测通过」的模型里选；
**绝不用 AlphaFold 3 验证管道**（它在 DCU 上输出 NaN，会给出错误的安全感）。

## 10. 离线交付清单

一个模型要交付到甲方内网，需要四样：

1. **镜像**：`docker save` 成 tar（`docs/13` §5 的 `build-offline-package.sh`）；
2. **权重包**：`*.tar.zst` + `SHA256SUMS`；
3. **manifest**：`tool-package.v2` 的 `tool.yaml`（含 `runtime.weights[]` 与 `image@sha256`）；
4. **示例输入**：`examples/protein.pdb` + `params.json`（供部署验收复跑）。

四样齐了，在任何一台装好驱动的节点上 `docker load` + `kubectl apply` 就能跑起来。

## 13. 坑十一：CPU 轮子的 torch 会让 GPU 任务静默跑在 CPU 上（2026-11-01）

MolP-PC 的 `1.0.0` 镜像是从 4090 上的 conda 环境 `conda-pack` 出来的，而那个环境里装的是
**`torch==2.0.1+cpu`**。后果不是报错，而是：

| 观察项 | 现象 |
|---|---|
| Pod 资源 | `limits: {nvidia.com/gpu: "1"}` 正常下发，调度到 `4090` 节点 |
| `torch.cuda.is_available()` | **False** |
| 模型行为 | 静默退回 CPU 推理，日志无任何告警 |
| 单任务耗时 | 47 s（GPU 版 **23 s**；三个分子的 SMILES 表） |

也就是说「申请了 GPU」和「用上 GPU」之间没有任何保证，平台侧也看不出来——任务
`succeeded`、产物齐全，只是慢一倍多。这类问题在只跑一两个分子时几乎不可察觉。

**修法（`1.1.0`，digest `sha256:c7e5dfdc8ce1f4669aa00faef71a21a9d61c4ab78449293d9dab81c993a5f516`，13.1 GB）**：

1. 在宿主环境把 CPU 轮子整体换成 CUDA 轮子（`torch/torchvision/torchaudio +cu118`、
   `torch-scatter==2.1.2+pt20cu118`、`dgl==1.1.2+cu118`），连同 cuDNN 8.9 / cuBLAS 11.11
   的用户态库一起进 env，再 `conda-pack`；
2. `Dockerfile` 里显式设 `LD_LIBRARY_PATH` 指向 `site-packages/nvidia/*/lib`——cu118 轮子
   把这些库放在包内而不是 `/usr/local/cuda`，不设就会 `libcublas.so.11: cannot open`；
3. **打包前自检**：宿主上先跑 `python -c "import torch,dgl;assert torch.cuda.is_available()"`，
   容器内再跑一次 `torch.cuda.is_available()` 与 `dgl.graph(...).to("cuda").device`。

**沉淀到流程的两条硬规则**：

- 任何「GPU 计算镜像」构建完必须验证 `torch.cuda.is_available() == True` 且
  `torch.version.cuda` 非空，验证不通过不允许注册工具版本；
- 注册工具版本时 `tool_versions.config.image` 用 digest 引用（`@sha256:`），
  并用迁移同步 `runtime.cuda` 字段——本次即 `backend/alembic/versions/20261101_01_molp_pc_gpu_image.py`，
  把 `cuda` 从 `11.3` 更正为 `11.8`、把三处 `image`/`image_digest` 一起换掉。

顺带记一个 `conda-pack` 的坑：`torch 2.0` 已移除 `caffe2`，但旧环境的
`conda-meta/pytorch-1.10.1-*.json` 仍记录着那些文件，`conda-pack` 会因文件缺失中止；
删掉这类过期 `conda-meta` 记录后用 `ignore_missing_files=True` 打包即可。本次还因为
手工清理 `*.egg-info` 时误删了 `site-packages/dgl`，导致第一版镜像 `import dgl` 失败——
**清理 site-packages 目录时不要把包本体和元数据一起删**。
