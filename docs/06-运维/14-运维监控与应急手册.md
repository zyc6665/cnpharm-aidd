## 0. 本文档要解决的六个问题

1. **"出问题了谁先知道"** —— 平台必须在用户报障之前发现异常，需要一份**可落地的告警清单**，而不是"接个 Prometheus 就完了"（§3）。
2. **"算力节点不在 K8s 里，怎么监控"** —— DCU 机器由 `drp-node-agent` 独立管理，监控体系必须覆盖 cluster 外的物理机与 16 个卡位（§4）。
3. **"任务卡住了算谁的"** —— 任务卡在 `QUEUED` 是排队正常还是调度器死了？必须能从现象直接定位到责任环节（§6 诊断决策树）。
4. **"凌晨三点怎么办"** —— 值班人员不一定是架构师，需要有**按症状索引**的操作卡（§7），一步步照着做。
5. **"怎么证明可用率 99.5%"** —— 需要明确的可用性统计口径与月度报告模板，避免验收时口径争议（§9）。
6. **"什么该记进变更单"** —— 运维最怕"随手改了一个参数"，必须定义变更分级与审批（§10）。

**不在本文档范围**：安装与升级步骤（见 `13`）、备份恢复操作细节（见 `15`）、开发期日志规范（见 `10` §8）。

## 1. 监控架构与数据来源

### 1.1 观测栈（沿用 `03` §11.3）

| 层 | 组件 | 部署位置 | 说明 |
|---|---|---|---|
| 指标采集 | Prometheus | `drp-observability` | 主 + 长时存储（`--storage.tsdb.retention.time=90d`） |
| 指标暴露 | 业务服务 `/metrics` | 各 Pod | OpenTelemetry SDK → Prometheus exporter |
| 算力指标 | `drp-node-agent` `/metrics` | DCU 物理机 :8780 | 由 `hy-smi` 采集，格式兼容 Prometheus |
| 日志 | Loki + Promtail | `drp-observability` | 只收结构化 JSON 日志（`10` §8） |
| 面板 | Grafana | `drp-observability` | 面板 JSON 随交付包下发（`13` §5.1） |
| 告警 | Alertmanager | `drp-observability` | 邮件 + 企业微信/钉钉 Webhook |
| 链路 | Jaeger（可选） | `drp-observability` | 采样率 1%，仅排障期临时调高 |

### 1.2 采集拓扑

```
业务 Pod ──/metrics──┐
drp-node-agent ──────┼──▶ Prometheus ──▶ Alertmanager ──▶ 值班渠道
中间件 exporters ────┘        │
                              └──▶ Grafana（面板 + 排障查询）
业务 Pod ──JSON 日志──▶ Promtail ──▶ Loki ──▶ Grafana（检索）
```

### 1.3 采集频率与保留

| 数据类型 | 间隔 | 保留 | 说明 |
|---|---|---|---|
| 业务指标 | 15s | 90 天（降采样后 1 年） | 可用率统计依赖 90 天原始数据 |
| DCU 指标（温度/功耗/显存/HCU 利用率） | 30s | 90 天 | `hy-smi` 本身有一定开销，不宜过频 |
| 卡位状态 | 30s | 90 天 | 用于"卡位可用率"统计 |
| 应用日志 | 实时 | 180 天 | DRP-NFR-13 / `03` §4.5 |
| 审计日志 | 实时 | ≥ 1 年 | 等保要求（`03` §9） |
| 任务日志 | 任务结束归档 | 与结果同周期 | 见 `15` |

> **纪律**：**审计日志不可与业务日志混在同一 Loki 租户**，审计需独立保留策略与访问控制。

## 2. 指标字典（必须落地的最小集）

### 2.1 业务层指标

| 指标名 | 类型 | 含义 | 用途 |
|---|---|---|---|
| `drp_http_requests_total{route,method,status}` | Counter | HTTP 请求数 | 错误率、QPS |
| `drp_http_request_duration_seconds{route}` | Histogram | 请求耗时 | P50/P95/P99（DRP-NFR-02/03） |
| `drp_db_pool_in_use` / `_size` | Gauge | 连接池占用 | 连接耗尽预警 |
| `drp_db_query_duration_seconds{operation}` | Histogram | SQL 耗时 | 慢查询 |
| `drp_task_submitted_total{task_type,priority,scale}` | Counter | 提交量 | 容量规划 |
| `drp_task_status_total{task_type,status,scale}` | Counter | 各状态计数 | 失败率 |
| `drp_task_queue_depth{task_type,scale}` | Gauge | 队列深度 | 排队告警 |
| `drp_task_queue_wait_seconds{task_type,scale}` | Histogram | 排队等待时长 | 用户体验 |
| `drp_task_duration_seconds{task_type,scale}` | Histogram | 执行时长 | 超时判定基线 |
| `drp_task_cost_dcu_seconds{task_type,model}` | Counter | 实际消耗 DCU 秒 | 配额核销与成本核算（`03` §5.6.3 ③） |
| `drp_task_cost_cpu_seconds{task_type}` | Counter | 实际消耗 CPU 秒 | 同上 |
| `drp_scheduler_leader` | Gauge | 是否为 leader（0/1） | 调度器单活检查 |
| `drp_scheduler_cycle_duration_seconds` | Histogram | 调度循环耗时 | 调度器健康 |
| `drp_quota_usage_ratio{project_id}` | Gauge | 项目配额占用率 | 配额告警 |
| `drp_login_failed_total{remote_ip,username}` | Counter | 登录失败次数 | 撞库检测（AL-24） |
| `drp_user_locked_total` | Counter | 账号因连续失败被锁定的次数 | 账号锁定（AL-25） |
| `drp_idempotent_replay_total{route}` | Counter | 幂等键命中重放的次数 | 诊断「用户重复提交」（`04` §5.5） |

> **v1.1 强制要求（`scale` 标签不可省）**：`scale` 取值为 `S` / `M` / `L` / `XL` / `T`，由 `drp-scheduler` 按 `task.scale.itemCount` 自动判定后写入标签（`03` §5.2.2）。
>
> **为什么必须带**：同类型任务的规模可差 5 个数量级（1 个分子对接 vs 10 万条批量筛选）。若只按 `task_type` 聚合，P95 会被 S 层的毫秒级样本拉低，**算出的「预估完成时间」会系统性偏乐观**，直接违反 `03` §5.6.3 ③。任何告警规则与看板只要涉及排队/时长，**必须按 `scale` 分组**，不得混算。
>
> 同理，`drp_task_cost_*` 是**配额以算力分钟计量**（而非任务个数）的数据底座，缺了它配额核销就只能退回按个数算。

### 2.2 算力层指标（来自 `drp-node-agent`）

| 指标名 | 类型 | 含义 | 告警阈值参考 |
|---|---|---|---|
| `drp_node_up{node}` | Gauge | 节点心跳（1/0） | 3 分钟无心跳 → P1 |
| `drp_slot_state{node,slot}` | Gauge | 卡位状态（0=FREE,1=BUSY,2=FAULT,3=BORROWED） | FAULT → P2 |
| `drp_slot_busy_seconds{node,slot}` | Counter | 累计占用时长 | — |
| `dcu_hbm_used_bytes{node,slot}` | Gauge | 显存占用 | > 95% 持续 5min → P2 |
| `dcu_hbm_total_bytes{node,slot}` | Gauge | 显存总量 | 偏离 64GB → P2（丢卡） |
| `dcu_temperature_celsius{node,slot}` | Gauge | 温度 | > 85℃ 持续 3min → P2 |
| `dcu_power_watts{node,slot}` | Gauge | 功耗 | > 额定 110% → P3 |
| `dcu_utilization_ratio{node,slot}` | Gauge | HCU 利用率 | < 5% 且 BUSY → P3（空转） |
| `drp_container_restarts_total{node,container}` | Counter | 容器重启次数 | 1h 内 > 3 → P2 |
| `drp_agent_task_active{node}` | Gauge | 执行中任务数 | — |
| `drp_node_disk_free_bytes{mount}` | Gauge | 磁盘剩余 | < 200GB → P2 |

### 2.3 中间件指标

| 组件 | 关键指标 | 告警线 |
|---|---|---|
| PostgreSQL | 复制延迟、连接数、长事务、WAL 增长、慢查询 | 延迟 > 10s（P1）、连接 > 80%（P2）、长事务 > 30min（P2） |
| Redis | 内存使用率、命中率、evicted_keys、连接数 | 内存 > 85%（P2）、evicted > 0（P2） |
| RabbitMQ | 队列积压、unacked、消费者数、死信 | 积压 > 1000（P2）、消费者 = 0 且积压 > 0（P1） |
| MinIO | 存储使用率、请求错误率、集群健康 | 使用率 > 85%（P2）、错误率 > 1%（P2） |

## 3. 告警分级与规则

### 3.1 分级定义

| 级别 | 定义 | 响应时限 | 通知方式 | 负责人 |
|---|---|---|---|---|
| **P1 严重** | 平台不可用、数据面临丢失、核心能力全断 | **15 分钟内**响应 | 电话 + 群 + 邮件 | 值班 + 技术负责人 |
| **P2 高** | 单项核心能力不可用 / 性能显著劣化 / 有数据风险隐患 | 1 小时内 | 群 + 邮件 | 值班 |
| **P3 中** | 非核心能力异常、资源接近阈值、可自愈的抖动 | 1 个工作日内 | 群 | 值班 → 转工单 |
| **P4 低** | 提示类、容量趋势 | 每周巡查 | 仅面板/日报 | 值班 |

### 3.2 告警规则清单（必须配置的最小集）

| 编号 | 规则 | 表达式（示意） | 级别 | 处置指引 |
|---|---|---|---|---|
| AL-01 | 平台入口不可用 | `probe_success{job="gateway"} == 0` 持续 2min | P1 | §7 C-01 |
| AL-02 | 核心服务无就绪副本 | `kube_deployment_status_replicas_available{deployment=~"drp-.*"} == 0` | P1 | §7 C-02 |
| AL-03 | 调度器无 leader | `max(drp_scheduler_leader) == 0` 持续 3min | P1 | §7 C-03 |
| AL-04 | 任务失败率突增 | `rate(drp_task_status_total{status="FAILED"}[10m]) / rate(drp_task_status_total[10m]) > 0.3` | P1 | §7 C-05 |
| AL-05 | 队列积压且无消费 | `drp_task_queue_depth > 20 and absent(rate(drp_task_status_total{status="RUNNING"}[10m]))` | P1 | §7 C-03/C-04 |
| AL-06 | 节点心跳丢失 | `drp_node_up == 0` 持续 3min | P1 | §7 C-06 |
| AL-07 | 数据库主库不可达 | `pg_up == 0` 持续 1min | P1 | §7 C-07 |
| AL-08 | 复制延迟超限 | `pg_replication_lag_seconds > 10` 持续 2min | P1 | §7 C-07 |
| AL-09 | WAL 归档失败 | `pg_stat_archiver_failed_total` 增加 | P1 | §7 C-08 |
| AL-10 | 磁盘剩余不足 | `drp_node_disk_free_bytes < 200e9` | P2 | §7 C-09 |
| AL-11 | 显存占用近满 | `dcu_hbm_used_bytes / dcu_hbm_total_bytes > 0.95` 持续 5min | P2 | §7 C-10 |
| AL-12 | DCU 温度过高 | `dcu_temperature_celsius > 85` 持续 3min | P2 | §7 C-11 |
| AL-13 | 卡位 FAULT | `count(drp_slot_state == 2) > 0` | P2 | §7 C-12 |
| AL-14 | 容器反复重启 | `increase(drp_container_restarts_total[1h]) > 3` | P2 | §7 C-13 |
| AL-15 | HTTP 错误率 | `sum(rate(drp_http_requests_total{status=~"5.."}[5m])) / sum(rate(drp_http_requests_total[5m])) > 0.01` | P2 | §7 C-02 |
| AL-16 | P95 响应超时 | `histogram_quantile(0.95, drp_http_request_duration_seconds) > 3` 持续 10min | P2 | §7 C-14 |
| AL-17 | 备份失败 | 备份 Job 状态非 Success | P2 | §15 §5 |
| AL-18 | 长事务 | `pg_stat_activity` 中 `xact_start` 超过 30min | P2 | §7 C-15 |
| AL-19 | 卡位空转 | `drp_slot_state == 1 and dcu_utilization_ratio < 0.05` 持续 15min | P3 | §7 C-16 |
| AL-20 | 证书 30 天内到期 | `probe_ssl_earliest_cert_expiry - time() < 30*86400` | P3 | §7 C-17 |
| AL-21 | **交互卡被大任务侵占** | `drp_slot_reserved{node,slot} == 1 and drp_slot_task_scale{node,slot} =~ "L\|XL\|T"` 持续 5min | **P1** | §7 C-18 |
| AL-22 | **任务预估耗时严重偏差** | `drp_task_duration_seconds / drp_task_estimated_seconds > 3` 且 `scale=~"XL\|T"` | P2 | §7 C-19 |
| AL-23 | **配额超额** | `drp_quota_usage_ratio > 1.0` | P2 | §7 C-20 |
| AL-24 | **登录失败暴增**（疑似撞库） | `sum(rate(drp_login_failed_total[5m])) > 0.2` 持续 10min，或同一来源 IP 10 分钟内失败 > 20 次 | **P1** | §7 C-21 |
| AL-25 | **账号被锁定** | `increase(drp_user_locked_total[10m]) > 0` | P2 | §7 C-22 |

> **AL-21 为什么是 P1**：`03` §5.3 v1.1 新增了一条**硬规则**——预留的 4 张交互卡**仅接受 S/M 层**，BULK/XL/T 永远不得占用。这不是性能建议，而是保证「用户点一下能在分钟级拿到结果」的产品红线。一旦被长任务占住，交互体验直接崩坏且**用户无法自助恢复**（抢占未启用），所以按 P1 处理。
>
> 若持续出现 AL-21，说明调度器的规模层判定或卡位分配逻辑有缺陷，**不要靠人工杀任务解决**，应回查 `drp-scheduler` 的准入日志。
>
> **AL-22 的用途**：XL/T 层的「预估完成时间」是向用户承诺的（`03` §5.6.3 ③），偏差 3 倍以上说明单件成本基线失准，需回填 `03` §5.2.1 并更新 `07` manifest 的 `steadyStateSecondsPerItem`（稳定态）与 `coldBootSeconds`（冷启）——**先分清是稳定态变慢还是冷启变长，两者的处置完全不同**（前者查降频/模型变慢，后者查权重加载与镜像层）。

### 3.3 不告警的"噪声"（预先声明，避免疲劳）

| 现象 | 为什么不告警 | 说明 |
|---|---|---|
| 任务 `CANCELLED` 增多 | 用户主动行为 | 只在日报统计，不实时告警 |
| 排队深度 > 0 | 16 卡下排队是常态 | 只在深度 > 20 且无消费时告警（AL-05） |
| 单卡利用率短期 < 5% | 任务间隙正常 | 持续 15min 才算空转 |
| 日志中出现 `Retry` 字样 | 模型侧重试机制正常 | 仅统计而不触发 |

## 4. 算力节点监控（K8s 之外）

### 4.1 为什么必须单独设计

DCU 机器**不在 K8s 集群内**（`09` §7），kubelet/Node Exporter 体系覆盖不到。因此：

| 能力 | K8s 内 | DCU 物理机 | 实现 |
|---|---|---|---|
| 存活探测 | kubelet | ❌ | Agent 心跳 → 平台 |
| 资源指标 | cAdvisor | ❌ | Agent 采集 + `/metrics` |
| 日志 | Loki | ⚠️ 部分 | Agent 转发容器日志到 Loki（带节点标签） |
| 自我修复 | 原生 | ❌ | systemd `Restart=always` |

### 4.2 Agent 心跳与节点健康模型

| 状态 | 判定 | 平台动作 |
|---|---|---|
| `READY` | 心跳 ≤ 30s，8 卡位可读 | 正常调度 |
| `DEGRADED` | 心跳正常，但存在 FAULT 卡位 | 从可用池移除 FAULT 卡，继续调度其余卡 |
| `UNREACHABLE` | 心跳 30s~3min 缺失 | 暂停向该节点派新任务，保留运行中任务 |
| `DOWN` | 心跳 > 3min 缺失 | 该机所有卡位置 FAULT，任务入队重调度（`09` §4.6） |
| `MAINTENANCE` | 人工置位 | 拒绝新任务，等待腾空后进行变更 |

> **平滑过渡纪律**：`UNREACHABLE` 阶段**不要**立刻杀任务。实测中网络抖动 40s 恢复的情况很常见，过早重调度会造成重复计算与产物冲突。

### 4.3 卡位监控面板要素（Grafana）

| 面板 | 内容 |
|---|---|
| 16 卡位总览 | 每卡位一宫格：状态色块 + 承载模型 + 占用时长 + 显存条 |
| 卡位可用率 | `FREE+BUSY` 占比的 7 日趋势 |
| 排队与吞吐 | 各任务类型队列深度 + 完成速率 |
| 温度与功耗 | 16 卡温度热力图、总功耗曲线 |
| 节点心跳 | 2 台节点心跳时序与最近事件 |
| 任务瀑布 | 最近 50 个任务的排队/执行时长分布 |

## 5. 日志规范与检索

### 5.1 日志分层（延续 `10` §8）

| 来源 | 格式 | 关键字段 | 去向 |
|---|---|---|---|
| 业务服务 | JSON | `ts, level, service, trace_id, project_id, user_id, task_id, route, msg` | Loki `drp-app` |
| 调度器 | JSON | 同上 + `node, slot, decision` | Loki `drp-app` |
| Agent | JSON | `ts, node, slot, container, event, exit_code` | Loki `drp-node` |
| 计算容器输出 | 文本 + 结构化打点 | `task_id, stage, progress` | Loki `drp-compute` + 任务日志归档 |
| 审计 | JSON（独立租户） | `actor, action, target, before, after, ip` | Loki `drp-audit`（不可删改） |
| 系统 | journald | 节点级 | 本地 + Loki `drp-host` |

### 5.2 常用检索（LogQL 速查）

```logql
# 某任务的完整链路（跨应用、调度、Agent、容器）
{namespace="drp-app"} |= "tsk_01JABC..." 

# 某项目近 1 小时的所有错误
{namespace="drp-app"} | json | level="ERROR" | project_id="prj_01J..." 

# 某卡位今天的容器事件
{job="drp-node"} | json | node="a" | slot="A3"

# 调度决策序列（用于排查"为什么没派卡"）
{namespace="drp-app"} | json | service="drp-scheduler" | line_format "{{.msg}}"

# 审计：某用户的所有导出操作
{job="drp-audit"} | json | actor="zhangsan" | action=~"EXPORT|DOWNLOAD"
```

### 5.3 排障时的时间对齐

> **实战提醒**：跨节点排障最大的坑是**时钟不一致**。所有节点必须 NTP 同步（`13` §10.1），日志时间戳统一 UTC 写入、界面按本地时区展示。若发现事件时序矛盾，第一件事是查 `chronyc tracking` 的 offset。

## 6. 诊断决策树

### 6.1 "任务一直排队不执行"

```
任务长时间 QUEUED
├─ 查 drp_scheduler_leader
│   ├─ == 0  → 调度器缺失活。查 Pod 状态与 advisory lock（C-03）
│   └─ == 1  → 继续
├─ 查 drp_node_up
│   ├─ 有节点 == 0 → 节点失联（C-06），任务无法派到该机
│   └─ 全部 == 1 → 继续
├─ 查 drp_slot_state{承载该模型的卡位}
│   ├─ 全为 BUSY → 正常排队（容量不足）。看队列深度与预计等待，考虑弹性借用（09 §5.3）
│   ├─ 有 FAULT → 卡故障（C-12）
│   └─ 有 FREE → 调度器未选中 → 检查配额（drp_quota_usage_ratio）、优先级、任务参数合法性
├─ 查项目配额
│   └─ 已达上限 → 平台拒绝派发，需管理员调额
└─ 查任务准入日志（drp-scheduler 的 decision 字段）
    └─ 若准入失败 → 看 error_code，常见为 CONCURRENCY_LIMIT / QUOTA_EXCEEDED
```

### 6.2 "任务 RUNNING 但一直没有进度"

```
├─ Agent 是否在跑该任务？查已派发任务与容器
│   ├─ 容器不存在 → Agent 已丢任务（C-13），任务置失败并重试
│   └─ 容器在跑 → 继续
├─ 查 progress.json 是否更新
│   ├─ 不更新 → 模型卡住（可能是显存不足或数据异常）
│   │   ├─ 看 dcu_hbm_used_bytes 是否接近 100% → C-10
│   │   └─ 看容器日志尾部 → 定位到具体阶段
│   └─ 在更新但 hbm_utilization 低 → CPU 瓶颈（数据供给），检查节点 CPU/磁盘 IO
└─ 是否超过 maxMinutes？→ 平台将置 TIMEOUT，Agent 执行 kill
```

### 6.3 "某模型的容器反复重启"

```
├─ 查 docker logs <container> 最近 50 行
│   ├─ "RuntimeError: HIP error" / "No device found"
│   │   └─ 驱动/设备挂载问题：确认 /dev/kfd、/dev/dri、HIP_VISIBLE_DEVICES（09 §4.3）
│   ├─ "out of memory" → 显存分配超限：查该卡是否有其他实例（C-10）
│   ├─ "ImportError" → 镜像内依赖被覆盖（禁止 pip 覆盖 torch/dgl）→ 回退镜像版本
│   └─ 秒退无报错 → 检查 entrypoint 与权限（挂载目录属主）
└─ 检查宿主 hy-smi 是否正常
    └─ 单卡失联 → 硬件问题，置 FAULT 并联系厂商
```

### 6.4 "页面很慢（> 3 秒）"

```
├─ 查 drp_http_request_duration_seconds P95 按 route 分组，定位具体接口
├─ 针对该接口：
│   ├─ 数据库慢查询（pg_stat_statements）→ 索引缺失或全表扫描（C-15）
│   ├─ 连接池耗尽（drp_db_pool_in_use == size）→ 见 C-02
│   ├─ 外部调用超时（MinIO/Agent）→ 查对应服务错误率
│   └─ 同步计算未下沉 → 代码缺陷（违反 E-02），记工单
└─ 若为列表页 → 检查分页参数是否被绕过（默认 20，最大 200）
```

### 6.5 "追溯导出内容缺失"

```
├─ 查 task 表 model_name/model_version/tool_name/tool_version 是否 NULL
│   ├─ 有 NULL → 数据缺陷（违反 E-04），需补数据并追查提交流程
├─ 查 task_input_snapshot 是否有记录
│   ├─ 缺失 → 提交时未做快照（严重），影响 DRP-NFR-07 验收
└─ 查产物哈希是否与存储一致（MinIO ETag / sha256 清单）
```

## 7. 应急操作卡（按症状索引）

> 每张卡结构一致：**现象 → 立即动作 → 验证 → 升级条件**。值班人员按卡执行，不要跳过"验证"。

### C-01 平台入口不可用（AL-01，P1）

**立即**：1）`kubectl -n drp-system get pods`；2）查 Ingress Controller 副本；3）查证书是否过期；4）若 Pod 正常，检查上游 LB/防火墙。
**验证**：`curl -k https://<域名>/healthz` 返回 200，浏览器可登录。
**升级**：10 分钟内未恢复 → 通知技术负责人，启动 `13` §8.4 回退评估。

### C-02 服务无就绪副本 / 5xx 突增（AL-02/AL-15，P1）

**立即**：`kubectl -n drp-app describe pod <pod>` 看事件；`kubectl logs --previous` 看崩溃原因；检查 DB/Redis 连通性。
**验证**：Pod `Ready` 数恢复至期望值，5xx 率 < 1%。
**升级**：若为近期发布引起 → 立即 `helm rollback`（`13` §8.1）。

### C-03 调度器无 leader（AL-03，P1）

**立即**：1）查 `drp-scheduler` Pod 是否 Running；2）查 `pg_locks` 中 advisory lock 持有者；3）若旧 leader 僵死（Pod 在但锁未释放且无循环），**杀掉旧 Pod** 让待命副本接管。
**验证**：`max(drp_scheduler_leader) == 1`，调度循环 `cycle_duration` 恢复 < 1s。
**升级**：连续两次接管失败 → 手工 `kubectl rollout restart`，并排查 DB 连接问题。

### C-04 队列积压无消费（AL-05，P1）

**立即**：确认是"无消费"还是"容量不足"。看 `rate(drp_task_status_total{status="RUNNING"})`，为 0 则是消费侧问题。
**验证**：RUNNING 速率恢复，积压下降。
**升级**：若为节点心跳丢失导致 → 按 C-06。

### C-05 任务失败率突增（AL-04，P1）

**立即**：按 `task_type` 与 `error_code` 分组统计（面板已内置），找出集中在哪类任务；下载 1~2 个失败任务的日志与 `result.json`。
**验证**：失败率 < 5%。
**升级**：若集中在单模型 → 按 `07` §7 回退该模型版本；若全类型失败 → 按 C-02。

### C-06 节点心跳丢失（AL-06，P1）

**立即**：1）`ping` 节点；2）SSH 登录（应急通道）查 `systemctl status drp-node-agent`；3）查 `hy-smi`；4）查系统日志（是否 OOM、磁盘满）。
**验证**：平台侧 `drp_node_up == 1`，卡位状态回 `FREE`/`BUSY` 一致。
**升级**：硬件故障（丢卡、宕机）→ 联系厂商，同时按 §8 演练流程处理重调度。

> **注意**：若节点 `UNREACHABLE` 但任务仍在跑，**先恢复网络**，不要立即重调度。重调度会造成双跑与产物冲突（§4.2）。

### C-07 数据库主库不可达 / 复制延迟（AL-07/08，P1）

**立即**：1）查 PG Pod 或主机；2）查磁盘是否满（最常见）；3）若主库不可恢复 → 触发主备切换（按甲方 DBA 流程或 Patroni/Patroni-like 自动切换）。
**验证**：`pg_up == 1`，应用可写，复制延迟 < 10s。
**升级**：切换失败或数据不一致风险 → **停止写入**（把服务降级为只读），评估是否需要 PITR（`15` §4）。

### C-08 WAL 归档失败（AL-09，P1）

**立即**：查归档目标（MinIO/本地归档盘）空间与凭据；执行 `pg_switch_wal()` 后观察 `pg_stat_archiver`。
**验证**：`failed_count` 不再增长，`last_archived_time` 接近当前。
**升级**：归档持续失败会撑爆 pg_wal 并导致主库只读 —— 6 小时内未修复必须扩容或暂停非核心写入。

### C-09 磁盘空间不足（AL-10，P2）

**立即**：`du -sh /var/drp/work/* | sort -h | tail` 找出大户；清理已完成任务的 `work` 目录（产物已上传 MinIO）；检查日志轮转。
**验证**：剩余 > 300GB。
**升级**：若为轨迹类产物堆积 → 触发 `15` 的归档/清理策略。

### C-10 显存占用近满（AL-11，P2）

**立即**：`hy-smi --showpids` 找出占用进程；确认该卡是否多实例共享（A5/B5 卡位）导致超卖；必要时 `docker restart` 该卡位容器。
**验证**：显存降到阈值以下，卡位恢复可用。
**升级**：若为显存泄漏（随运行时长单调增长）→ 记录模型版本，报厂商/算法团队，并在调度侧降低并发实例数。

### C-11 DCU 温度过高（AL-12，P2）

**立即**：检查机房温度与风扇；`hy-smi` 看是否单卡异常；暂停向该卡派新任务（平台侧置卡位 `MAINTENANCE`）。
**验证**：温度回落至 75℃ 以下。
**升级**：持续高温或单卡异常 → 摘卡（置 FAULT），联系厂商。

### C-12 卡位 FAULT（AL-13，P2）

**立即**：`hy-smi` 确认该物理卡是否可见；若不可见 → 硬件问题，置 FAULT 并摘除；若可见 → 重启该卡位容器并重探。
**验证**：卡位恢复 `FREE` 且可承载任务。
**升级**：同机 ≥ 2 卡不可见 → 整机置 `MAINTENANCE`，走 C-06 流程。

### C-13 容器反复重启（AL-14，P2）

按 §6.3 决策树处理。**最常见根因**：镜像内依赖被 pip 覆盖、设备挂载参数与驱动版本不匹配、挂载目录权限。
**验证**：1 小时内重启次数 = 0。

### C-14 接口 P95 超 3 秒（AL-16，P2）

按 §6.4 决策树定位到具体 route。若是新版本引入 → 回滚。
**验证**：P95 < 3s 持续 30 分钟。

### C-15 长事务（AL-18，P2）

**立即**：`SELECT pid, now()-xact_start, query FROM pg_stat_activity WHERE state='active'`；确认是否为备份/统计任务；必要时 `pg_cancel_backend`（**不要直接 terminate**，先取消）。
**验证**：无 > 30min 的活跃事务。

### C-16 卡位空转（AL-19，P3）

**立即**：确认该卡是否为"常驻但无任务"的正常状态（专卡空转是设计而非故障）；若为借用实例长时间空转 → 触发归还（`09` §5.3 冷却 30min）。
**验证**：空转下降到阈值或实例被回收。

### C-17 证书即将到期（AL-20，P3）

**立即**：按 §4.3 轮换清单执行；**内部 CA 签发的证书需同步平台与 Agent 两侧**。
**验证**：`probe_ssl_earliest_cert_expiry` 大于 90 天。

### C-18 交互卡被大任务侵占（AL-21，P1）

**背景**：`03` §5.3 v1.1 硬规则——预留 4 张交互卡仅接受 S/M 层。这 4 张卡是「用户点一下能分钟级拿结果」的唯一保障，**且抢占未启用**，一旦被占用户无法自助恢复。

**立即**：
1. 确认 `drp_slot_reserved` 标记与 `slots.yaml` 的 `reserved: true` 一致——若不一致，是 `slots.yaml` 被改坏了，先修声明；
2. 查该任务的 `task.scale.itemCount` 与实际准入日志（`drp-scheduler` 的 `decision` 字段）：是**判定错**（itemCount 小但实际跑得久）还是**分配错**（判定对了但分到交互卡）；
3. **判定错** → 调 `03` §5.2.2 的规模层阈值；**分配错** → 查卡位选择的筛选条件是否漏了 `reserved` 约束。

**不要做的事**：不要靠人工 `docker stop` 杀任务——会留下孤儿产物与不一致的任务状态，且下次还会发生。

**验证**：`drp_slot_task_scale` 中 reserved 卡位上不再出现 L/XL/T，且 `drp_task_queue_wait_seconds{scale="S"}` 的 P95 回到分钟级。

### C-19 任务预估耗时严重偏差（AL-22，P2）

**背景**：XL/T 层的「预估完成时间」是向用户**明确承诺**的（`03` §5.6.3 ③）。偏差 > 3 倍说明单件成本基线失准。

**立即**：
1. 按 `scale` 分组取 `drp_task_duration_seconds` 的实际 P50/P95，与 `03` §5.2.1 表中值对比；
2. 差异大时区分是**模型侧变慢**（镜像/权重/驱动变更）还是**硬件侧变慢**（`dcu_utilization_ratio` 下降、温度降频）还是**规模估算错**（每件成本随批量变化，如批量对接的并行度下降）；
3. 回填 `03` §5.2.1，并同步更新 `07` manifest 中的 `steadyStateSecondsPerItem` / `coldBootSeconds` / `maxMinutes`。

**验证**：一周内偏差回到 3 倍以内。

### C-20 配额超额（AL-23，P2）

**背景**：`03` §5.6.3 ③ 要求配额以「算力分钟」计量、按实际消耗核销，而非按任务个数。

**立即**：
1. 查 `drp_quota_usage_ratio > 1` 的项目，确认是**核销延迟**（任务结束未回写）还是**真超额**；
2. 核销延迟 → 查 `drp-task-api` 的产物入库事务（`03` §3.2.2 强一致第 2 项：任务结束 + artifact + status 同事务），最常见原因是对象存储写成功但提交失败留下的孤儿对象；
3. 真超额 → 按 `04` §5.3 `project_quota` 的规则处理，**不要静默放宽**，需留 `audit_log`。

**验证**：`drp_quota_usage_ratio` 回落到 1.0 以下，或已补审批记录。

---

### C-21 登录失败暴增（AL-24，P1）

**背景**：`04` §5.0 `sys_user` 有 `failed_login_count` 与 `locked_until`，失败 5 次置 `LOCKED`。短时间内大量失败通常是两类事：**撞库/口令喷洒**（外部攻击）或**某个客户端的凭据过期后疯狂重试**（内部误配，常见于 CI 脚本或浏览器缓存的旧 token）。

**立即**：
1. 先分清是**同一 IP 多账号**（撞库）还是**多 IP 同一账号**（针对某人）还是**单 IP 单账号**（脚本重试）；
2. 撞库 → 立即在网关层对该 IP/网段限流封禁，**不要改应用配置**；同时查 `audit_log` 中 `action=LOGIN_FAILED` 是否已有成功登录紧随其后（若有，按账号入侵处置，强制改密并吊销会话）；
3. 脚本重试 → 找出 User-Agent 与来源主机，通知对应团队更新凭据；
4. **不要为了止住告警而调大 `failed_login_count` 阈值**，那等于降低了暴力破解的成本。

**验证**：`rate(drp_login_failed_total[5m])` 回落，且无「失败后紧跟成功」的账号。

**注意**：本手册只负责发现与止血，**不做取证分析**——需要保留现场时先打快照再封禁。

---

### C-22 账号被锁定（AL-25，P2）

**背景**：`04` §5.0 定义 `failed_login_count ≥ 5` 置 `LOCKED`，`locked_until` 到期自动解锁。AL-25 是「10 分钟内有账号被锁」的温和提醒，多数情况是用户自己记错口令，**不需要立即处置**。

**立即**：
1. 查是哪个账号、来自哪里。若是**普通用户自助**导致，无需操作，告诉他等 `locked_until` 到期或找管理员解锁；
2. 若是**同一账号反复被锁**（一天内多次），大概率是该用户在多个设备/浏览器留有旧口令，或被 C-21 的撞库命中，转 C-21 流程；
3. 管理员解锁：`PUT /api/v1/users/{id}/status` 置 `ACTIVE` 并清零 `failed_login_count`，**必须留 `audit_log`**（人工解锁是可审计的敏感操作）；
4. 若被锁的是 `ADMIN` 且系统内只剩这一个管理员，走 `15` 的数据恢复或直接改库，**并立即补充第二个管理员**——单管理员是配置缺陷，不是偶发事故。

**验证**：`drp_user_locked_total` 不再增长；人工解锁均有审计记录。

## 8. 高可用演练剧本

> 演练是硬要求：每季度 1 次，且上线前必须在 `staging` 完成一次。演练结果作为 `13` §12 与验收报告的附件。

### 8.1 演练一：业务服务滚动更新不中断

| 项 | 内容 |
|---|---|
| 目标 | 验证 `maxUnavailable=0` 滚动更新期间页面无 5xx |

|---|---|

| 判据 | 能力不中断（仍有成功任务），无重复产物，无数据不一致 |

### 8.3 演练三：断电自愈

| 项 | 内容 |
|---|---|
| 目标 | 验证 §6.4 链路的自愈（`13` §6.4） |

### 8.4 演练四：数据库 PITR 恢复

| 项 | 内容 |
|---|---|
| 目标 | 验证数据回滚能力（`13` §8.3、`15` §4） |
| 步骤 | 在 staging 记录基线 → 执行若干写操作 → 模拟误删 → 按 `15` 恢复到误删前时点 |
| 判据 | RTO ≤ 4h（目标 ≤ 2h），数据丢失 ≤ 5min，对象存储产物与 DB 记录一致 |
| 失败处置 | 检查 WAL 归档连续性、恢复脚本、MinIO 版本化 |

### 8.5 演练五：应用回滚

| 项 | 内容 |
|---|---|
| 目标 | 验证 `helm rollback` 分钟级可用 |
| 步骤 | 发布一个新版本 → 人工注入一个 5xx 缺陷 → 执行回滚 |
| 判据 | ≤ 10 分钟回到上一版本，业务恢复，DB 迁移无需回退（向后兼容） |
| 失败处置 | 检查迁移是否破坏性、镜像是否本地可拉取 |

## 9. 可用性统计口径（99.5% 怎么算）

### 9.1 定义

| 项 | 定义 |
|---|---|
| **可用性计算单元** | 平台 Web 入口 + 核心 API（登录、项目、任务提交、结果查看） |
| **不可用判定** | 任一计算单元在 1 分钟内出现以下之一：入口探针失败 2 次以上；核心 API 5xx 率 > 5%；P95 > 10s |
| **排除项** | 已提前 3 个工作日报备的计划停机（如升级窗口）；甲方网络/电力故障；甲方要求的外部变更 |
| **统计周期** | 自然月；年度为 12 个月加权平均 |

公式：`可用率 = 1 - 不可用分钟数 / (总分钟数 - 计划停机分钟数)`

99.5% 对应每月允许不可用 **约 3.6 小时**（按 30 天计）。

### 9.2 月度运维报告模板

| 章节 | 内容 |
|---|---|
| 1 概览 | 可用率、请求量、任务量、平均排队时长 |
| 2 事件 | 本月事件列表（时间、级别、影响、处理人、MTTR） |
| 3 容量 | 卡位利用率、存储使用率、趋势与预测 |
| 4 备份 | 备份成功率、恢复演练结果 |
| 5 变更 | 本月变更清单（对齐 `11` 发布记录） |
| 6 风险与建议 | 需甲方决策事项 |

## 10. 变更管理与值班交接

### 10.1 变更分级

| 级别 | 定义 | 审批 | 窗口 |
|---|---|---|---|
| 标准变更 | 预定义、低风险（扩副本、调阈值、清理日志） | 值班自行执行 + 记录 | 任意 |

| 重大变更 | 数据库迁移、中间件升级、驱动/DTK 升级、卡位重排 | 技术负责人 + 甲方 | 提前 3 天报备，含回退预案 |

### 10.2 绝对不能在生产做（黑名单）

| 禁止动作 | 原因 |
|---|---|
| 直接 `docker run` 手工起模型容器 | 绕过 `slots.yaml`，Agent 会判定漂移并重建，造成任务中断 |
| 手工改数据库业务数据 | 破坏追溯与审计链（DRP-NFR-07/08） |
| `pip install` 覆盖 torch/dgl/tensorflow | 直接导致 DCU 路径失效（`07` §6.1） |
| 删除 MinIO 中的产物对象 | 破坏结果与追溯完整性 |
| 关闭审计日志"临时提性能" | 合规红线 |
| `kubectl delete pod --grace-period=0 --force` 常态使用 | 跳过优雅退出，产生部分产物与锁残留 |
