## 0. 一句话结论

**在同一个仓库里开一条 `cnpharm/*` 的独立长跑交付线，产品线 `develop`/`beta`/`main` 原样不动，双方只通过 `cnpharm-base-*` 标签与偶发的 cherry-pick 单向交换成果。**

这样做的理由：中国医药要 3 个月硬交付，产品线要慢慢完善——两条线的节奏差一个数量级，任何双向同步机制都会在交付冲刺期变成负担，而单向 cherry-pick 的成本是可选的、按需支付的。

## 2. 分支结构

```
                    ┌── cnpharm-base-ce9a521 (tag, 分叉点)
                    │
ce9a521 ────────────┼── cnpharm/v1            ← 中国医药交付主干（保护，禁止直推）
  (develop 头部)    │      ├── cnpharm/feat/<topic>   ← 功能
                    │      ├── cnpharm/fix/<topic>    ← 缺陷
                    │      ├── cnpharm/refactor/<topic> ← 结构改造
                    │      └── cnpharm/docs/<topic>   ← 文档
                    │
                    └── (product) develop/beta/main  ← 产品线，不动
```

| 分支 | 角色 | 保护 | 合并来源 | 生命周期 |
|---|---|---|---|---|
| `cnpharm/v1` | 中国医药一期交付主干 | 禁止直推、必须 PR、CI 通过 | `cnpharm/feat|fix|refactor|docs/*` | 一期全程 |
| `cnpharm/feat/<topic>` | 新功能（如靶点实体、口袋持久化） | 无 | — | ≤ 5 工作日 |
| `cnpharm/fix/<topic>` | 缺陷修复 | 无 | — | ≤ 2 工作日 |
| `cnpharm/refactor/<topic>` | 不改变行为的重构（如 agents 拆包） | 无 | — | ≤ 5 工作日 |
| `cnpharm/docs/<topic>` | 文档 | 无 | — | ≤ 3 工作日 |
| `cnpharm/release/v1.x.0` | 一期发布（对应验收/离线包） | 禁止直推 | `cnpharm/v1` | 发布期 |
| `cnpharm/hotfix/<topic>` | 交付后紧急修复 | 无 | — | ≤ 1 工作日 |

**命名理由**：与仓库既有规范（`docs/development/01-团队协作开发规范与教程.md` §3.2 的 `feature|fix|refactor|docs`）保持一致，只加 `cnpharm/` 前缀做命名空间隔离——这样既复用团队习惯，又能用 `git branch -a --list 'cnpharm/*'` 一键看清交付线全貌，且不会与产品线的 `feature/*` 冲突。

## 3. 与产品线的关系：单向、可选、有记录

### 3.1 默认不同步

产品线 `develop` 继续自由演进，**不需要**照顾中国医药交付线的兼容性；交付线也不向产品线回灌。理由：交付期任何"顺手把改动合回 develop"的动作都会引入"这笔改动到底有没有被验证过"的歧义，而交付期最贵的就是这个歧义。

### 3.2 产品线 → 交付线：cherry-pick（按需，逐笔）

当产品线修了一个交付线也存在的缺陷（如 K8s adapter 的 bug、状态机的竞态），按单笔 cherry-pick：

```bash
cd _upstream_CPUmodel_V2
git switch cnpharm/v1
git fetch origin develop
# 先看这笔改动碰了哪些文件
git show --stat <product-sha>
# 只 pick 修复提交，不 pick 功能提交
git cherry-pick -x <product-sha>     # -x 会在 message 里留下原提交号，便于追溯
```

`-x` 是硬要求：交付期要能回答"这个文件为什么和产品线不一样"，`-x` 留下的 `(cherry picked from commit ...)` 就是答案。

### 3.3 交付线 → 产品线：摘取（交付后，人工判断）

交付线里做出来的**通用**能力（例如更完整的 `audit_log` 表、`upload_session` 分片上传、任务 SSE），交付结束后由产品负责人评估是否回收。方式是从 `cnpharm/v1` 摘出独立 commit 用 PR 合回 `develop`，**禁止整分支合并**——交付线里有大量中国医药专属内容（靶点/口袋/候选物领域模型、LDAP、离线约束），整分支合并会污染产品线。

判断标准（三条全中才回收）：

1. 不含中国医药专有内容（无客户名、无内网地址、无专属枚举值）；
2. 不依赖交付线新增的领域表；
3. 产品线现有测试能覆盖，或能补齐测试。

### 3.4 分叉点的维护

每做一次大规模上游同步（例如产品线交付了一个重要的执行层重构），打一个新标签：

```bash
git tag -a cnpharm-base-<short-sha> <short-sha> -m "第 N 次上游同步基线"
git push origin cnpharm-base-<short-sha>
```

这样任何时候都能用 `git log cnpharm-base-ce9a521..cnpharm/v1` 精确回答"我们相对产品线改了什么"，这是验收和交接时最常被问的问题。

## 6. 提交规范（交付线专用）

沿用仓库既有 commit 规范，但**每条提交必须带交付上下文**，便于验收追溯：

```
<type>(<scope>): <subject>

<body>

Refs: <PRD 编号 / 决策编号>
```

`type` 取 `feat|fix|refactor|docs|test|chore|perf`；`Refs` 填中国医药需求编号（如 `M2-FR-06`）或决策编号（如 `D-25`）。示例：

```
feat(target): add target entity with protein and structure relations

新增 target / protein / protein_structure 三张表与迁移，
支撑 M2 结构预测任务的归属关系追溯。

Refs: M2-FR-02, 04-数据模型 §6.1~§6.3
```

这条规则的用途：验收时要能按 `git log --grep="M2-FR-06"` 直接列出某个需求条款的全部实现提交。

## 8. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 产品线大改导致 cherry-pick 冲突 | 执行层重构后 `tasks/*` 全线冲突 | 分叉点标签 + 只在必要时 pick；冲突严重时改为"读产品线代码、在交付线重写"而非硬 pick |
| 交付线长期不回灌，产品线重复踩坑 | 两边都写了 audit_log | 每季度做一次「交付线通用能力回收评估」（§3.3 三条标准） |
| 分支命名与产品线冲突 | 出现两个 `feature/*` 语义 | `cnpharm/` 前缀强制隔离（已定） |
| CI 只在 `main`/`develop` 触发 | 交付线 PR 无自动化门禁 | 第 1 步 PR 中把 `.github/workflows/ci.yml` 的 `branches` 加 `cnpharm/**` |
| 交付期忘了自己在哪条线 | 误提交到 `develop` | 本地工作目录 `_upstream_CPUmodel_V2` 只 checkout `cnpharm/*`；产品线同步用 `git fetch` + cherry-pick，不 switch 到 `develop` 改代码 |
