# 团队协作开发指南

本文面向即将参与 CPUModel / SciTool 平台协作开发的成员，说明当前前后端架构、前端页面分布与排版模式，以及团队开发流程和规范。

## 1. 项目定位

本仓库是一个科学计算工具管理平台，核心能力包括工具托管、任务提交、任务执行、文件管理、AIDD 工作流、用户体系和管理后台。

技术栈：

- 后端：FastAPI、SQLAlchemy Async、Pydantic、SQLite/PostgreSQL、Celery、Redis、MinIO、本地文件存储。
- 前端：Vue 3、Vite、TypeScript、Pinia、Vue Router、Ant Design Vue、Less、ECharts、MolStar。
- 测试：后端使用 `pytest`；前端测试文件使用 Node.js `node:test` 风格。

## 2. 后端架构

后端入口位于 `backend/app/main.py`。应用启动时会初始化数据库，注册后台循环任务，并挂载 `/api/v1` 路由。

主要目录职责：

| 路径 | 职责 |
| --- | --- |
| `backend/app/api/v1/` | API 路由层，负责参数接收、鉴权依赖、响应组装 |
| `backend/app/models/` | SQLAlchemy ORM 模型 |
| `backend/app/schemas/` | Pydantic 请求与响应结构 |
| `backend/app/services/` | 业务服务，如模型服务、验证码、邮件 |
| `backend/app/tasks/` | 任务执行、状态机、直接执行器、SSH 传输 |
| `backend/app/worker/` | Celery 应用和 Worker 任务 |
| `backend/app/storage/` | 本地存储与 MinIO 存储适配 |
| `backend/app/cache/` | 内存缓存与 Redis 缓存适配 |
| `backend/app/auth/` | JWT、密码、游客和权限依赖 |
| `backend/app/agents/aidd/` | AIDD 智能体编排、规划、后台同步 |
| `backend/storage/` | 本地数据库、上传文件和运行产物 |

核心路由分布：

- `/api/v1/auth`：注册、登录、刷新 Token、退出。
- `/api/v1/users`：当前用户、用户管理、收藏等。
- `/api/v1/tools`：工具列表、详情、导入配置、发布、收藏、版本、分类和工作台分组。
- `/api/v1/tasks`：任务列表、详情、创建、取消、重试、日志、删除。
- `/api/v1/files`：上传、文件列表、产物查询、下载、格式转换、删除。
- `/api/v1/system`：健康检查、系统统计、模型服务配置。
- `/api/v1/agents`：AIDD run 创建、查询、取消、删除、同步。
- `/ws` 相关接口：任务状态和统计推送。

配置集中在 `backend/app/config.py`。开发环境默认使用 SQLite、本地文件、内存缓存；生产或集成环境可切换 PostgreSQL、MinIO、Redis 和 Celery。

## 3. 前端架构

前端入口为 `frontend/src/main.ts`，挂载 Vue 应用并注册 Pinia、Router、i18n 和 Ant Design Vue。

主要目录职责：

| 路径 | 职责 |
| --- | --- |
| `frontend/src/router/` | 路由表、页面标题、登录与管理员守卫 |
| `frontend/src/api/` | Axios 实例、Token 刷新、各业务 API 封装 |
| `frontend/src/stores/` | Pinia 状态管理，包含用户、工具、任务、工作流、智能体等 |
| `frontend/src/views/` | 页面级组件 |
| `frontend/src/components/` | 可复用组件，按 layout、common、tasks、tools、workflow 分类 |
| `frontend/src/workflow/` | AIDD 工作流状态、工具绑定、产物解析逻辑 |
| `frontend/src/types/` | TypeScript 类型定义 |
| `frontend/src/locales/` | 中英文国际化文案 |
| `frontend/src/assets/styles/` | 全局 Less 变量、基础样式和 Ant Design 覆盖 |

请求层位于 `frontend/src/api/request.ts`，负责：

- 使用 `VITE_API_BASE_URL` 作为 API 根地址。
- 自动附加 Bearer Token。
- 401 时尝试刷新 Token。
- 统一弹出错误提示。
- 提供 `get/post/put/patch/del/upload` 封装。

## 4. 前端页面分布

路由配置在 `frontend/src/router/index.ts`。

| 页面组 | 路由 | 组件 |
| --- | --- | --- |
| 首页 | `/` | `views/home/index.vue` |
| 认证 | `/login`、`/register`、`/forgot-password` | `views/auth/` |
| 工具市场 | `/tools`、`/tools/:id` | `views/tools/List.vue`、`Detail.vue` |
| AIDD 工作流 | `/workflow` | `views/workflow/index.vue` |
| 任务中心 | `/tasks`、`/tasks/:id` | `views/tasks/List.vue`、`Detail.vue` |
| 用户中心 | `/user`、`/user/settings`、`/user/favorites` | `views/user/` |
| 管理后台 | `/admin/*` | `views/admin/index.vue` 及子页面 |
| 错误页 | `/403`、`/404` | `views/error/` |

权限规则：

- `meta.requiresAuth`：需要登录，如任务中心和用户中心。
- `meta.requiresAdmin`：需要管理员，如管理后台。
- `meta.guest`：登录后不应访问，如登录和注册页。

## 5. 前端排版模式

### 5.1 全局布局

`frontend/src/App.vue` 按路由选择布局：

- 普通页面使用 `components/layout/DefaultLayout.vue`。
- 管理后台、认证页、错误页使用页面自身布局。

`DefaultLayout.vue` 包含：

- 顶部导航：Logo、首页、工具、CPU PDB 外链、任务、管理入口。
- 右侧操作：语言切换、登录注册或用户菜单。
- 移动端抽屉导航。
- 主内容区 `router-view`。
- 页脚链接。

### 5.2 管理后台布局

实际路由使用 `frontend/src/views/admin/index.vue` 作为后台壳：

- 左侧固定导航：Dashboard、用户、工具、分类、工作台分组、任务、系统。
- 顶部栏：折叠按钮、面包屑、用户菜单。
- 内容区：子路由页面。

`components/layout/AdminLayout.vue` 也存在，但当前路由未直接使用。新增后台页面时优先接入 `views/admin/index.vue` 的子路由。

### 5.3 主要页面排版

- 首页：`hero-section` 加工作流展示区，偏产品展示和入口引导。
- 工具列表：搜索、分类筛选、排序、卡片网格、分页。
- 工具详情：主栏展示工具信息和参数表单，侧栏展示标签、状态和元信息。
- 任务列表：Tab 区分全部、运行中、历史；任务卡片展示状态、进度和操作。
- 任务详情：状态卡、进度条、时间线、输入参数、文件、结果可视化和日志。
- 工作流页：`workflow-shell workflow-deck` 容器，按模式 Tab 展示 AIDD 工作台。
- 用户中心：左侧用户卡和菜单，右侧子页面内容。
- 管理页：以 `AppPageHeader`、筛选条、统计卡片、表格、抽屉或弹窗为主。

排版原则：

- 新页面优先复用 `AppPageHeader`、`AppFilterBar`、`AppErrorState`。
- 前台内容页使用 `.container` 控制宽度。
- 后台页面保持“标题操作区 + 筛选区 + 表格/卡片区”的结构。
- 任务和工具相关产物优先复用 `components/tasks/`、`components/tools/`。

## 6. 本地开发教程

### 6.1 首次准备

后端：

```bash
cd backend
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

前端：

```bash
cd frontend
npm install
```

### 6.2 启动开发环境

推荐使用仓库脚本：

```bash
./start-dev.sh
```

脚本默认启动：

- 后端：http://localhost:8000
- 前端：http://localhost:8585
- API 文档：http://localhost:8000/docs

也可以单独启动：

```bash
cd backend
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

```bash
cd frontend
npm run dev -- --host 0.0.0.0 --port 8585
```

注意：`frontend/vite.config.ts` 中 Vite 默认端口是 `3000`，但 `start-dev.sh` 会显式使用 `8585`。Docker Compose 中后端也可能映射到 `9501`，以实际启动方式为准。

### 6.3 Celery 与 Redis

任务队列相关开发可使用：

```bash
./start-celery.sh
```

或：

```bash
docker-compose -f docker-compose.celery.yml up -d
docker-compose -f docker-compose.celery.yml logs -f celery-worker
```

Flower 监控地址通常为 `http://localhost:9555` 或脚本提示的端口。

### 6.4 数据库迁移

当前数据库迁移使用 Alembic。模型变更后，必须同时提交迁移文件：

```bash
cd backend
alembic -c ../alembic.ini revision --autogenerate -m "describe change"
alembic -c ../alembic.ini upgrade head
alembic -c ../alembic.ini downgrade -1
```

说明：

- `backend/app/database/session.py` 仅在开发环境保留 `create_all()` 兜底。
- 生产和预发布环境必须先执行 `alembic upgrade head`，再启动服务。
- 已存在的旧数据库如需接入新迁移，先校验表结构，再使用 `alembic stamp head` 对齐版本。

## 7. 功能开发流程

### 7.1 后端功能

常规顺序：

1. 在 `models/` 确认是否需要新增或调整数据模型。
2. 在 `schemas/` 定义请求和响应结构。
3. 在 `services/` 或 `tasks/` 写业务逻辑，避免把复杂逻辑塞进路由。
4. 在 `api/v1/` 增加路由，使用依赖注入获取数据库和当前用户。
5. 在 `test/` 添加或更新 `pytest` 测试。
6. 更新文档或示例配置。

约束：

- 路由层只做协议适配、鉴权和简单编排。
- 数据库写操作应通过 `get_db()` 管理事务。
- 文件、缓存、任务队列必须通过适配层调用，不要在业务代码里硬编码具体后端。
- 新增配置项放入 `Settings`，并同步 `.env.example`。

### 7.2 前端功能

常规顺序：

1. 在 `types/` 定义或复用类型。
2. 在 `api/` 封装请求函数。
3. 若跨页面共享状态，放入 `stores/`。
4. 页面级入口放 `views/`，复用能力放 `components/`。
5. 新增文案同步 `locales/zh-CN` 与 `locales/en-US`。
6. 添加 `frontend/test/*.test.ts`，覆盖路由、文案、数据转换或页面结构约束。

约束：

- 不在组件中散落 API URL，统一走 `src/api/`。
- 不在页面中重复复杂转换逻辑，抽到 `utils/`、`workflow/` 或组件旁的 `.ts` 文件。
- 前台页面保持响应式；后台页面优先保证表格、筛选、批量操作和详情查看效率。
- Less 变量优先使用 `assets/styles/variables.less`。

## 8. 测试与验证

后端：

```bash
pytest test
pytest test/test_tasks_api.py -q
```

前端构建：

```bash
cd frontend
npm run build
```

前端测试示例：

```bash
cd frontend
node --test test/tool-list-i18n.test.ts
```

当前 `package.json` 尚未定义统一 `npm test` 脚本。团队协作时建议补齐脚本，例如把常用 `node --test test/*.test.ts` 封装为 `npm test`，再写入 CI。

提交前最低检查：

- 后端改动：运行相关 `pytest`，风险较高时运行 `pytest test`。
- 前端改动：运行相关 `node --test` 文件和 `npm run build`。
- API 改动：打开 `/docs` 检查接口结构，必要时补充前端 API 类型。
- UI 改动：检查桌面和移动端主要宽度，确认文字不溢出、操作按钮不遮挡。

## 9. 分支、提交与 PR 规范

分支命名建议：

- `feature/<short-name>`：新功能。
- `fix/<short-name>`：缺陷修复。
- `docs/<short-name>`：文档。
- `refactor/<short-name>`：重构。
- `test/<short-name>`：测试补充。

提交信息使用 Conventional Commits 风格：

```text
feat(frontend): add workflow artifact picker
fix(api): handle missing task output files
docs: add team development guide
test(frontend): cover task result renderer
```

PR 必须包含：

- 背景和目标。
- 主要改动清单。
- 测试命令和结果。
- 影响范围：后端、前端、数据库、任务队列、配置、文档。
- UI 改动需附截图或录屏。
- 有破坏性变更时写清迁移步骤和回滚方式。

评审重点：

- 是否符合现有目录边界。
- 是否引入重复逻辑。
- 是否有测试覆盖核心行为。
- 是否处理权限、空状态、异常、加载态。
- 是否影响已有工具配置和任务产物。

## 10. 配置与安全规范

- 不提交真实密钥、访问令牌、生产数据库地址和生产对象存储凭据。
- 本地配置从 `backend/.env.example` 派生。
- 生产环境必须修改 `JWT_SECRET_KEY`。
- `backend/storage/`、`storage/`、上传产物、SQLite 数据库和日志不应作为业务代码提交。
- 涉及远程 SSH、Docker Socket、模型服务密钥的改动必须在 PR 中明确风险。

## 11. 数据库与迁移约定

当前项目使用 Alembic 管理数据库迁移，SQL 脚本仍保留在 `docs/sql/` 作为补充说明。涉及表结构调整时：

1. 先确认 `models/` 的字段和关系。
2. 更新相关 `schemas/`、API 和测试。
3. 新增 Alembic migration 文件，并在需要时补充 `docs/sql/` 说明脚本。
4. 在 PR 中说明老数据兼容策略、升级顺序和回滚方式。
5. 不允许只改模型不补迁移。

## 12. 团队协作建议

- 每个任务保持小粒度，优先拆成后端接口、前端页面、测试、文档四类子任务。
- 公共组件、类型和接口改动要提前同步，避免多人在页面内各自复制实现。
- 修改工具执行、任务状态、文件产物、AIDD 工作流时，必须先梳理数据流再动手。
- 对已有用户数据、任务产物和工具配置保持兼容；不能兼容时必须写迁移说明。
- 新成员第一天建议按顺序阅读：`README.md`、本文档、`AGENTS.md`、`docs/guides/工具添加指南.md`、`docs/design/03-接口规格说明书.md`。
