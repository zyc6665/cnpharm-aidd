## 0. 本文档要解决的四个问题

1. **评审到底发现了什么** —— 不是笼统地说「设计不错」，而是指出**哪一处会导致项目失败**。
2. **改了哪些地方** —— 每一条改动都要能定位到文档与章节，评审会上可以逐条勾。
3. **为什么这么改** —— 保留决策理由，避免下一个人重复讨论同一个问题。
4. **哪些没改、为什么不改** —— 被否决的方案必须留痕，否则三个月后会被重新提出。

**不在本文档范围**：新功能的详细设计（见各文档正文）、未决策事项的推进（见 §5）。

## 2. P0 致命问题（3 项）

### P0-1 耗时估算挂在「任务类型」上，导致算力可行性完全失真

**原状**：`03` v1.0 §5.2 的资源画像表用「典型时长」列描述每类任务，例如 DOCKING 写「秒~5 min」、VIRTUAL_SCREENING 写「10~60 min」。

**问题**：同一任务类型的**规模**可相差 5 个数量级。1 个配体对接 1~5 分钟是对的；但 `01` DRP-M5-FR-04 承诺的「10 万条批量筛选」是同一任务类型，实际需要 **278~1667 CPU·h**（按 Vina 10~60s/配体、单核）。按单机 8 核算是 26 天。原表对此完全无感知。

连带失效：`03` §5.3 的「基于历史均值估算等待时间」在数学上不成立——10 万条任务与 10 条任务的均值混在一起算，估出来的数字毫无意义。

**修订**（已落入 `03`）：
- §5.2 拆为 **§5.2.1 单件成本**（与规模无关，12 行，实测值加粗）+ **§5.2.2 规模分层**（S 交互 1~10 / M 常规 10~500 / L 大批量 500~10000 / XL 超大批量 10000~100000 / T 长时单体 >1h）。
- 硬性规则：规模层由 `drp-scheduler` 按 `task.scale.itemCount` **自动判定**，不依赖用户自报；XL 提交时必须返回预估完成时间，用户确认后才入队；T 层不计入普通并发配额。
- 新增 **§5.6 算力可行性核算**：按 16 卡（交互 4 / 批量 10 / 冗余 2）+ 64 核 CPU 池核算，逐条比对 5 条 ★ 条款。
- 新增约束 **C-7**：任务规模跨度极大，须按规模而非按任务类型估算耗时与资源。

**核算结论（这是本次评审最重要的输出）**：

| ★ 能力 | 规范书规模 | 总成本 | 结论 |
|---|---|---|---|
| S-01 结构预测 | 单序列 ≤400aa | 约 2 分钟·卡 | ✅ 毫无压力 |
| S-02 口袋预测 | 单结构 | 约 0.4 分钟·卡 | ✅ 毫无压力 |
| S-03 分子/多肽设计 | 单次一批 | 1000 分子 ≈ 3.3 DCU·h | ✅ 可行 |
| S-04 批量 ADMET | 500 条 | 约 8 CPU·min | ✅ 可行 |
| **S-05 批量虚拟筛选** | **10 万条** | **278~1667 CPU·h**（v1.1 按 64 核估算 = 2~11 个 64 核日；**v1.2 实测 128 核后 ≈3.1~18.5 小时，典型 9.3 小时**） | ⚠️ **可行，但是「天级」不是「小时级」**（v1.2 起风险已降级） |
| MD | 100 ns | 5×10⁷ 步（实测 500000 步≈1ns） | ⚠️ 单复合物数小时~1 天 |

**由此产生的强制产品约束**（已写入 `03` §5.6.3）：
1. XL 层任务必须返回预估完成时间，并**默认启用漏斗前置**（药效团 / ADMET 先筛掉约 90% 再对接），否则不得放行。
2. 长时任务运行时交互卡可被临时占用，但必须保证**至少 2 卡对 S 层可用**。
3. 配额以「**算力分钟**」而非任务个数计量，按实际消耗核销。
4. 所有单件成本在 `08` 复现完成后必须回填实测值，否则核算不成立。

**遗留风险**：CPU 池实际核数未定（`D-03-11`）。若甲方只给 16~32 核，10 万条筛选从「天级」恶化为「周级」，**必须在需求基线阶段就与甲方重谈规模预期**，不能拖到验收。

> **✅ v1.2 更新（2026-10-23 甲方书面确认）**：计算节点 **128 核**、平台部署机 **32 核**，`D-03-11` 已关闭。上述遗留风险**不成立**——`03` §5.6 已按 128 核全表重算（预估分母取 **90 有效核** = 128 × 0.7）：10 万条筛选典型 **9.3 小时**、乐观 3.1 小时、保守 18.5 小时，仍是「天级」但不再是「2~11 个 64 核日」的悬崖。同时新增两条约束：① 预估**不得用 128 理论核数**，必须打 0.7 折扣（SMT 收益有限 + 内存带宽争抢 + 给 S 层留余量）；② **32 核部署机不参与任何计算**（`03` §5.6.4），`drp-worker-cpu` 的 Job 必须调度到 CPU 计算池。本次核算详见 `03` §5.6.1~§5.6.4。

### P0-2 业务架构缺一条研发主线，「决策」这个核心动作无处安放

**原状**：`01` 的 M1~M7 是按能力域**横向切分**的（这是规范书的写法，便于逐条验收），`04` 的 `project_status` 是 `ACTIVE/PAUSED/ARCHIVED`——**行政状态，不是研发阶段**。

**问题**（三条，都是产品级缺陷）：
1. **用户看不出项目走到哪一步了**。页面能显示「靶点 3 / 候选 1.2k / 任务 86」，但这不等于「当前处于结构与口袋阶段，还差选定口袋」。
2. **平台不承载「选哪个候选往下走」**。药物研发的核心动作是决策，不是跑计算。用户看完表格后把结论记在 Excel，平台的追溯链在这里断掉。
3. **决策依据不沉淀，就谈不上「研发资产」**。`01` 术语表对研发资产的定义是泛指，没有可复用对象。

**修订**（已落入 `03` / `01` / `04` / `05` / `06` / `12`）：

| 新增概念 | 定义 | 落在哪 |
|---|---|---|
| **研发阶段 S0~S6** | 立项与数据归集 → 靶点确立 → 结构与口袋就绪 → 候选生成 → 性质评估 → 计算验证 → 决策归档 | `03` §3.6.1、`01` §4.1、`06` §5.1 |
| **决策点 DP1~DP5** | 每个阶段过渡时「选定哪些对象往下走」并留依据 | `03` §3.6.2、`04` §9.5、`05` §3.3 |
| **研发资产（收敛为三类）** | 工作流模板 / 带评分候选集 / 决策记录 + 报告 | `03` §3.6.3 |

**三个关键设计决定**：
1. **阶段是纯推导，不落库**。`GET /projects/{id}/stage` 由数据实时计算（`05` §3.2），**不引入 `project.stage` 字段**。理由：落库就要双写，双写必然不一致，而阶段只是导航提示，不值得为它承担一致性风险。
2. **阶段允许回退，且不阻塞操作**。回退不是错误，是研发的常态（新增靶点后从 S3 回到 S2）。它只是导航与提示，**不是门禁**。
3. **决策记录必须存成员快照，不能只存引用**。候选集合后续会被修改，若不快照，半年后回看决策记录会看到一组与当时完全不同的数据，追溯链断裂。此语义与 `04` 已有的 `candidate_set_item.snapshot_score` 一致。

**边界声明（写进 `01` §4.1，防止范围蔓延）**：
- 不新增任何功能点编号，62 个功能点与 P0/P1 分布不变。
- 不新增验收条款；仅作为 DRP-NFR-12 界面易用性的加分项，不参与 ★ 条款演示。
- 若甲方认为超出规范书范围，**可整体回退**，不影响 M1~M7 任何一条需求。

### P0-3 「复算结果一致」未定义「一致」，验收必然争议

**原状**：`01` §16 验收方式写「随机抽取 3 个历史任务，还原其输入/参数/环境并**复算，结果一致**」；`03` §7.1 的追溯六要素只解决了「**记录**」，没有解决「**可复算**」。

**问题**：至少三条计算路径**本质上不具备比特级确定性**——
- **Boltz-2 使用 empty MSA**（`03` AR-09）：没有 MSA 时结构预测对序列微小差异敏感，且无法通过事后补跑 MSA 还原历史结果。
- **GROMACS `-nb gpu` 浮点非确定性**：同一输入两次跑出的轨迹字节不同（GPU 并行归约顺序不固定）。
- **cuEquivariance fallback 路径**：不同卡数 / 批次可能触发不同 kernel 路径。

若不在设计阶段定义「一致」，验收现场要么被判定不合格，要么靠现场谈判。

**修订**（已落入 `03` §7.4 与 `01` §16）：

| 级别 | 定义 | 适用任务 | 验收方法 |
|---|---|---|---|
| **D1 比特级** | 同输入 + 同参数 + 同镜像 ⇒ 产物 SHA-256 完全一致 | 结构准备、构象生成（固定种子）、药效团、格式转换、指纹 | 直接比对 `artifact.sha256` |
| **D2 数值容差** | 结果在约定容差内一致，字节不必相同 | 结构预测、口袋、ADMET/亲和力、对接 | 按 `03` §7.4.2 逐模型容差表比对 |
| **D3 统计等价** | 统计分布一致，单次结果不要求相同 | MD、自由能 | 重复 ≥3 次，比较 RMSD/RMSF 与能量均值方差 |
| **D4 不可复现**（v1.2 新增） | 每次运行结果都不同，且无稳定统计口径 | **STD-Diff 扩散生成、Pocket2Mol（VAE 采样）、TheraPainter 多肽设计** | **不比对结果**，只核对参数/种子是否完整记录、manifest 与详情页是否如实标注 D4 |

> **为什么 v1.2 要加 D4**：甲方 2026-10-23 明确「**复现容差看模型，我们不确保能复现**」。v1.1 曾把「分子生成」放进 D2 并给「有效分子率偏差 ≤ 5%」——**这个承诺物理上给不出**：扩散/VAE 采样本随机，固定种子只在同一环境下可重放，换卡数或批大小结果就完全不同。把它硬塞进 D2，验收现场失败的会是甲方验收，而不是模型能力。分级后承诺变成三条：**平台侧 100% 可复现**（能原样重跑）、**模型侧按模型分级承诺**（容差逐模型声明、经 `08` 标定才算数）、**不做超出等级的承诺**（达不到就如实标 D4）。

**D2 容差表**（`03` §7.4.2，**逐模型**、**需甲方书面确认** `D-03-12`，**最终值由 `08` 实测回填**）：Boltz-2 主链 RMSD ≤ 0.5 Å、pLDDT 偏差 ≤ 1.0；LVpocket 中心偏差 ≤ 2.0 Å、Top-1 命中一致；AutoDock Vina 评分偏差 ≤ 0.5 kcal/mol、姿势 RMSD ≤ 2.0 Å（固定种子 + 固定 exhaustiveness）；MSIGN / MolP-PC 相对偏差 ≤ 5% 或绝对 ≤ 0.2 log。**未标定的模型一律标 `PENDING`，不得声称「可复现」。**

**验收口径修正**：由「随机抽 3 个」改为「**D1 / D2 / D3 各抽 1 个，D4 不抽**」——D4 改为核对声明。原因：随机抽 3 个可能全抽到 D3（或全抽到 D1），抽样不具代表性；而对 D4 抽检「结果是否一致」在物理上必然失败。同时补充「复算前置检查」——镜像是否仍在 Harbor、权重 SHA-256 是否匹配、输入产物是否仍在对象存储、**卡位是否仍可用**，任一缺失则该任务不具备复算条件，需换样重抽并当场记录原因。**报告格式由五列改为七列**（模型 / 复现等级 / 原结果 / 复算结果 / 偏差 / 判据 / 结论）。

## 3. P1 / P2 / P3 问题与修订

### P1-1 服务划分与事务边界矛盾（12 个服务 = 12 个进程？）

**原状**：`03` §3.2 列了 12 个服务，§3.2 末尾只说「进程内 httpx / 跨服务 REST」，**没有回答原子性**。

**问题**：`task` / `workflow` / `result` / `scheduler` 之间存在**强事务耦合**——
- 任务失败回滚配额：跨 `task` ↔ `project`
- 产物入库 + 更新任务状态：跨 `result` ↔ `task`
- 工作流节点状态与任务状态：跨 `workflow` ↔ `task`

按 12 个独立进程部署，上述操作全部变成分布式事务。在 Python 技术栈下，这是最容易写出脏数据的地方。

**修订**（已落入 `03` §3.2.1 / §3.2.2）：

| 部署单元 | 包含逻辑模块 | 副本 |
|---|---|---|
| `drp-api` | gateway(应用侧) + auth + project + asset + target + design | 2~3 |
| `drp-task-api` | task + workflow + result（**必须与 `drp-scheduler` 共用库连接与事务**） | 2 |
| `drp-scheduler` | scheduler（常驻，无对外端口） | 1 主备（K8s leader-election 防双主） |
| `drp-mol-index` | mol-index（RDKit 重、CPU 密集，独立） | 1~2 |
| `drp-model-registry` | model-registry | 1 |
| `drp-gateway` | Nginx Ingress | — |

### P1-2 调度系统全自研，但三个难点未被论证

**原状**：`drp-scheduler` 是自研的（`03` §3.2），`13` §12.1 又建议不引入 Argo，等于**整套调度系统全自研**。原文档没有讨论这意味着什么。

**三个必须写对的点**（已在 `03` §3.2.2 / §5.3 / §5.4 / §5.6 补齐）：

| 难点 | 后果 | 修订后的约束 |
|---|---|---|
| 配额核销与排队放行必须**原子** | 并发提交 100 个任务时超发配额 | 两者同在 `drp-scheduler`，用行锁 `SELECT ... FOR UPDATE` 串行化（`03` §3.2.2） |
| 不启用抢占 + 长任务 + 4 卡交互预留 | 交互任务被长 MD 占住，体验崩塔 | 新增**交互卡保护**：预留 4 卡仅接受 S/M 层，BULK/XL 永远不得占用（`03` §5.3） |
| `13` 的 `slots.yaml` 是静态声明，`03` 要动态排队 | 两套机制没对齐 | 明确分工：`slots.yaml` 声明**有哪些卡位**（静态），`drp-scheduler` 决定**卡位给谁**（动态），两者通过 Agent 的卡位占用状态对齐（`13` §6.3） |

**工作流引擎的处置**：原 `03` §11.3 列 Argo，`13` §12.1 建议不引入，两处冲突。经三方案对比（完全引入 / 仅管 CPU 侧 / 不引入），**采信 `13`：v1.0 不引入 Argo**，`drp-workflow` 用自研轻量 DAG（`workflow_template.dag_json` + `drp-scheduler` 5s 轮询 + `(workflow_instance_id, node_key)` 幂等键），保留 `WorkflowEngine` 接口（`start/cancel/status`）待将来替换。

理由：① 工作流节点规模小（预置模板最多 7 节点）；② Argo 需额外维护 CRD + 控制器 + artifact 仓库，离线环境运维成本高于收益；③ **DCU 不在 K8s 内，Argo「每节点一个 Pod」的核心优势在本项目失效**；④ 自研可与 `ComputeBackend` 直接对接，同时调度 DCU（Agent）与 CPU（K8s Job）两类异构节点。

#### P6 的三个系统性教训（比这 21 条本身更重要）

1. **「唯一真源」必须可执行，不能只是声明。** `07` §3.6 声明「不得再各自书写路径」之后，`10` 与 `07` 自己在别处仍在写默认值——于是 B-4 / B-5 / B-14 全都出在这里。可执行的做法是：**别处一旦出现具体路径就视为缺陷**，而不是「以某文档为准」的口头约定。
2. **数字是最容易全库一起错的东西。** 「33 张表」一路沿用了三个版本没人验算，审核方指出后一算就是：清单 38 个表名 = 系统表 3 + 业务表 35。同理「38 页 → 40 页」「AL-01~23 → AL-01~25」都是改了一处忘了另一处。**结论：任何计数型断言都必须在 CI 里可校验**（本轮已建立「交叉引用 + 表列数 + 计数一致性」三段检查脚本）。
3. **改章节号必须扫全库引用，改完必须跑检查。** 这不是「建议」而是「必须」——本轮 `03` 拆分 §5.2、新增 §3.6 / §5.6 / §7.4 之后，立刻出现了 25 处指向不存在章节的引用（P4），而 P5 / P6 又各制造了一批新的。**每轮修复后强制执行「交叉引用存在性 + 列名存在性 + 计数一致性」三查**，已写进 `10` §6 的提交前检查项。

## 4. 未采纳的建议及理由

> 这一节与修订清单同等重要。被否决的方案必须留痕，否则会在三个月后被重新提出。

| 建议 | 为何不采纳 |
|---|---|
| **新增 `project_stage_event` 表，记录阶段变迁历史** | 阶段是**纯推导**的导航提示，落库就要双写，双写必然不一致。若将来确有「阶段停留时长分析」需求，再从任务与产物时间戳离线计算，不引入在线双写 |
| **把 12 个服务真的拆成 12 个进程，用 Saga 保证一致性** | 强事务耦合的四块（task/workflow/result/scheduler）拆开后，每个操作都要 Saga + 幂等补偿。在 24 周工期、Python 技术栈、无成熟分布式事务中间件的条件下，风险远大于收益 |
| **引入 Argo Workflows 做工作流** | 见 P1-2：节点 ≤7、离线运维成本高、DCU 不在 K8s 内使核心优势失效。仅当甲方明确要求「使用 K8s 原生工作流引擎」（`D-13-04`）时回退方案 B |
| **启用任务抢占（preemption）解决交互饥饿** | 长任务（MD 数小时~数天）被中断的代价过高，且断点续算不总是可行。改用**交互卡硬隔离**（4 卡仅接受 S/M 层）从源头避免争抢 |
| **把「10 万条筛选」承诺为小时级** | 数学上不成立（278~1667 CPU·h）。诚实告知为「天级」+ 强制漏斗前置 + 预估单，比验收时被现场打脸要好 |
| **让用户手动推进研发阶段** | 手动推进等于增加一个需要维护的状态字段，且用户会忘记推。改为数据自动推导 + 缺口提示，用户只需看「下一步」 |
| **用 `pg_dump` 每日全备替代 WAL 归档** | RPO 会退化到 24 小时，与 `15` 的 RPO ≤ 5min 目标不符。见 `15` §3 |
| **把 DCU 强行纳入 K8s 以统一运维** | 需先验证 device plugin，且已验证的 9 个模型全部是「常驻 Docker + 静态卡位」形态，改造等于把 `08` 的复现工作推倒重来 |

## 8. 评审结论与下一步

### 8.1 结论

修订后的 v1.1 在**技术可实现性**上已具备开发条件：耗时估算改为「单件成本 × 规模层」，服务划分与事务边界明确，DCU 承载方式与工作流引擎选型统一，复现判据可验收。

但**两项待确认事项仍是阻塞级**（`D-03-12` / `D-03-13`）。其中 `D-03-12` 在 2026-10-23 已被甲方答复改写：**「复现容差看模型，我们不确保能复现」**——据此 `03` §7.4.1 改为**按模型分级 D1/D2/D3/D4**，新增 **D4 不可复现**（STD-Diff / Pocket2Mol / TheraPainter 不做复现承诺），`01` §16 第 3 条验收口径同步改为「查平台可复现能力 + 查声明是否诚实」。这意味着 `D-03-12` 的签字对象从「一张 D2 容差表」变成「**一份逐模型复现能力清单 + 这张表的最终值**」，且**必须等 `08` 实测回填后才能签**——阻塞形态从「等甲方」变为「等实测」。

`D-03-11`（CPU 池核数，**128 核 + 32 核**）与 `D-03-14`（内存容量，「肯定够」）已于 2026-10-23 由甲方确认关闭；`D-03-14` 关闭后留下的只是分配口径（🟡 `D-03-15`），不构成阻塞。
