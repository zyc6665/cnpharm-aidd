### 2.3 一个必须知道的结构性事实

**D3 / D4 / D5 在后端没有独立模块。** 预测类功能（生成、亲和力、性质、对接）共享同一套后端：

- `backend/app/api/v1/tasks.py`（任务提交）
- `backend/app/api/v1/results.py`（结果读取）
- `backend/app/tools/` + `backend/app/tool_templates/drug_discovery/*.yaml`（工具定义）

含义有两条：

1. **前端按域切，后端按模块切。** D4 的 owner 拥有 `frontend/src/views/predict/` 与对应 `tool_templates`，但不拥有 `tasks.py` / `results.py`。
2. **`tasks.py` / `results.py` 属于契约层**（见 §4），改动要按契约流程走，不能谁顺手谁改。

这条也是「按 AIDD 功能全栈切域」会打架的根因——AIDD 的域边界是**页面 + 工具定义**，不是后端模块。

## 3. 角色（槽位）

> P2–P4 的人选**待分配**，此处只定职责边界。分配时只改本表的「负责人」列与 `.github/CODEOWNERS`，不改域的定义。

| 角色 | 主责 | 次责 | 量级 |
|---|---|---|---|
| **P1** | L1 执行调度 + L2 部署算力 + 契约层（alembic / CI / 镜像 / `docs/05`） | L4 性能压测；D8 系统与算力页 | ~34k |
| **P2** | D1 数据底座 + D2 靶点结构 + L3 前端平台（公共组件/国际化/路由） | D8 用户与权限 | ~16k |
| **P3** | D3 分子设计 + D4 亲和/ADMET + D5 筛选/MD + 结果中心（`results.py`、`views/results`） | 结果解读口径 | ~16k |
| **P4** | D6 工作流与任务（画布 + 任务中心）+ D7 产物与谱系（`artifacts.py`、`services/artifact*`） | 工具接入 | ~19k |

**为什么这样配**：

- **D1 + D2 同人**：结构挂在靶点下，同一批表。
- **D3 + D4 + D5 同人**：三个域共用 `tasks`/`results` 读路径与同一套结果详情组件，拆开就会天天改同一批文件。
- **`results.py`（结果中心）给 P3，`artifacts.py`（产物谱系）给 P4**：两者是两个独立文件、两套语义。P3 是「结论的出口」，P4 是「物料的账本」。
- **L3 给 P2 而不是单开一人**：公共层没有交付物，只有约束。单开一人会让所有业务 PR 排队等它 review。
- **P1 不做业务**：执行层一改，D2–D7 全部受影响；P1 一旦接业务域，执行层出问题就没人兜。

**分配原则**：主责 ≠ 独占。主责是「第一责任人 + review 义务」，不是「只有他能改」。

## 5. 冲突治理

冲突分两类，处理方式完全不同：

| 类型 | git 会报吗 | 成本 | 对策 |
|---|---|---|---|
| 文本冲突（同行） | 会 | 低 | 小步提交 + 每日 rebase |
| 语义冲突（无冲突但互相破坏） | **不会** | **高** | 契约 + 测试 + 域边界 |

**5 个汇聚点 → 扩展点。** 近 300 次提交中改动最频繁的文件：

| 文件 | 改动次数 | 现状 | 目标形态 |
|---|---|---|---|
| `frontend/src/locales/zh-CN/index.ts` | 72 | 3340 行单体 | 每域一个文件，`index.ts` 用 `import.meta.glob` 合并 |
| `frontend/src/locales/en-US/index.ts` | 72 | 同上 | 同上 |
| `backend/app/config.py` | 26 | 单体 Settings | 按域拆子 Settings 组合 |
| `frontend/src/router/index.ts` | 17 | 476 行单体 | `router/modules/<域>.ts` |
| `frontend/src/types/models.d.ts` | 15 | 共享类型 | 按域拆 `.d.ts` |

**这一步是投入产出比最高的改动**：做完之后，四人日常开发的物理冲突基本归零。它本身就是一个 PR，谁做谁受益。

**其余三条规则**：

1. **迁移取号**：文件名 `YYYYMMDD_NN_主题`。取号前在群里报一声，同一天两人抢同一个 `NN` 必撞。
2. **谁后合谁 rebase**：先合的人不改语义，后合的人负责对齐。写死，避免「你先合吧」。
3. **分支活不过 3 天**：超时说明任务该拆了。

## 7. 进度同步

### 7.1 Issue 是唯一工作单元

- **粒度 ≤ 2 天**，超了就拆。这是防住巨型 PR 的唯一机制：#97 那种 101 文件的改动，拆成 8 个 Issue 自然就散了。
- **必填三项**：需求编号（如 `M3-FR-02`）、验收标准、影响域。
- 阻塞当天开 `blocker` Issue 并同步 `docs/03B`，**不要只在聊天里说**。

### 7.2 看板

GitHub Projects，一个看板，5 列：

```
Backlog → Ready → In Progress → In Review → Done
```

**硬性 WIP 上限：In Progress 每人最多 1 个。** 4 个人同时开 12 个分支，冲突量按平方涨，不是线性。

自动化：PR 打开 → 移到 In Review；PR 合并 → 移到 Done。

### 7.3 节奏

| 频率 | 形式 | 内容 | 时长 |
|---|---|---|---|
| 每日 | 固定 Discussion 下发 3 行 | 昨天合了什么 / 今天做什么 / 卡在哪 | 5 分钟 |
| 每周一 | 视频或当面 | **只过 blocker 与下周排期**，不汇报进度（进度看板上） | 30 分钟 |
| 每 2 周 | 更新 milestone | milestone 按交付节点设，不按功能设 | 10 分钟 |

### 7.4 只看三个指标

1. 每周**合并**的 PR 数（不是提交数）
2. 看板上 In Progress 的条数（> 4 说明有人在偷偷并行）
3. `blocker` 标签的 Issue 数，超过 2 天没动即升级

## 8. 开发环境

**数据集中，应用各本地。**（2026-11-12 已迁移完成）

- **数据服务**（PostgreSQL / Redis / MinIO）跑在 4090 的 k3s 上，命名空间 `cnpharm-aidd`，通过 NodePort 暴露，全队共用同一份。
- **应用进程**（backend / celery worker / celery beat / 前端）**每人本地各跑一份**，只把数据连接指向 4090。

理由：数据必须唯一，否则两个人调试时看到的不是同一份库，"改完口头说应该好了"就没法验证；但应用进程没必要集中，各本地改代码即时生效，也不用抢部署。

| 组件 | 位置 | 地址 |
|---|---|---|
| PostgreSQL 16 | 4090 k3s | `10.202.2.228:30432` |
| Redis 7 | 4090 k3s | `10.202.2.228:30379` |
| MinIO | 4090 k3s | `10.202.2.228:30900`（S3）/ `30901`（Console）|
| backend | 每人本地 | `127.0.0.1:8000` |
| celery worker / beat | 每人本地 | — |
| 前端 vite | 每人本地 | `127.0.0.1:5173` |

`backend/.env` 里要改的是这 6 行（其余不动）：

```dotenv
DATABASE_URL=postgresql+asyncpg://scitool:<密码>@10.202.2.228:30432/scitool
MINIO_ENDPOINT=10.202.2.228:30900
REDIS_HOST=10.202.2.228
CELERY_BROKER_URL=redis://:<密码>@10.202.2.228:30379/0
CELERY_RESULT_BACKEND=redis://:<密码>@10.202.2.228:30379/1
K8S_ADAPTER_OBJECT_STORAGE_ENDPOINT=http://10.202.2.228:30900
```

**最后一行最要紧**：它决定 4090 上跑的工具 Pod 从哪儿读文件。迁移前它指向 `http://10.4.3.19:30900`，也就是某个人的工作站——那个人关机，所有正在跑的工具任务全部失败。

部署清单在 `deploy/k8s-dev/cnpharm-aidd/`，按顺序 apply：

```bash
kubectl apply -f 00-namespace.yaml
kubectl apply -f 10-data-services.yaml
kubectl apply -f 11-image-4090.yaml    # 只覆盖 minio 镜像地址，见下
```

凭据走 Secret `cnpharm-aidd-credentials`（4 个键），不入库。

**两个坑，踩过了**：

1. **4090 节点拉不到 Docker Hub 的 minio 镜像**。节点的镜像加速 `docker.1panel.live` 对 `minio/minio` 返回 `403 Forbidden`，`postgres`/`redis` 却正常。镜像已推到集群内 registry（`10.202.2.228:30500/aidd/minio`），所以 `11-image-4090.yaml` 这个覆盖文件不能省；只 apply 前两个，MinIO 会一直 `ImagePullBackOff`。
2. **NodePort 对整个内网开放**。开发期可以接受，但别往这套共享环境里放真实患者数据或未公开分子结构。

工具 Pod 用的 Secret `sciminer-minio-client` 与新 MinIO 的根凭据一致，无需改动。`K8S_ADAPTER_API_SERVER` 仍是每人本地的 SSH 隧道（`127.0.0.1:16443`），只有真正往 4090 投递任务时才需要它通。
