### 2.3 一个必须知道的结构性事实

**D3 / D4 / D5 在后端没有独立模块。** 预测类功能（生成、亲和力、性质、对接）共享同一套后端：

- `backend/app/api/v1/tasks.py`（任务提交）
- `backend/app/api/v1/results.py`（结果读取）
- `backend/app/tools/` + `backend/app/tool_templates/drug_discovery/*.yaml`（工具定义）

含义有两条：

1. **前端按域切，后端按模块切。** D3/D4/D5 的前端页面归 P3；对应的 `tool_templates` YAML 归 P4（P1 复核）；业务域后端不拥有 `tasks.py` / `results.py`（这两个归 P1 的 L1 调度与结果契约）。
2. **`tasks.py` / `results.py` 属于契约层**（见 §3），改动要按契约流程走，不能谁顺手谁改。

## 4. 前后端契约同步（OpenAPI 为唯一真源）

**接口以 FastAPI 自动生成的 OpenAPI Schema 为唯一真源**，不再靠人工维护字段级接口文档：

1. 后端改完接口（Schema / 路由）后导出 OpenAPI：

   ```bash
   cd backend && python -c "import json; from app.main import app; print(json.dumps(app.openapi()))" > openapi.json
   ```

2. 前端用 `openapi-typescript` 从该 schema 生成类型（只读生成，不手改）：

   ```bash
   cd frontend && npx openapi-typescript ../openapi.json -o src/types/api-schema.d.ts
   ```

3. 改动后端接口 Schema 的 PR，**必须同步通知 P3** 更新前端类型定义。PR 模板已加勾选项：「若改动后端接口 Schema，已同步通知前端更新类型定义 / OpenAPI 契约」。
4. 人工接口文档（`docs/03-接口/05`）保留为**面向验收的叙述**；字段级真源仍是 OpenAPI。
5. `openapi-typescript` 通过 `npx` 内网镜像安装；离线环境需提前把该包与 `openapi.json` 产物打入离线依赖，运行时不得联网。

## 5. 分支模型：「标准版 → 完整版」一次性交付

```
main（唯一长期主干）
 ├─ Feature Flag 控制「完整版」未就绪能力（默认关，标准版可见面收窄）
 ├─ release/standard-v1.0   ← 标准版一次性交付分支（短命）
 └─ release/full-v2.0       ← 完整版一次性交付分支（短命）
```

- **单主干 `main`**：所有功能先合 `main`；完整版未完成的能力用 **Feature Flag** 包起来（默认关），保证 `main` 任何时点都能出「标准版」。
- **短命发版分支**：`release/standard-v1.0`、`release/full-v2.0` 仅用于冻结交付；现场 bugfix 在发版分支修好后 **`cherry-pick` 回 `main`**，避免修复丢失。
- **产品线 `upstream`（`CPUmodel_V2`）同步**：**仅 `@zyc6665`（P1）拥有 `upstream` 的 cherry-pick 权限**；新人克隆仓库**只配置 `origin`**，不要自行添加 `upstream` 远端。
- **分支命名**：`{type}/{role}-{issue号}-{简述}`（`type` ∈ feature/fix/refactor/docs/chore，`role` ∈ fe/be/ops/arch），例 `feature/fe-123-tool-form`。

```bash
# 新人：只配 origin
git clone git@github.com:zyc6665/cnpharm-aidd.git

# 发版分支（发布经理）
git switch -c release/standard-v1.0 main

# 现场 bugfix 修回主干（upstream 侧 cherry-pick 仅 P1 操作）
git cherry-pick -x <fix-commit>
```

## 6. 冲突治理（高冲突汇聚点）

冲突分两类，处理方式完全不同：

| 类型 | git 会报吗 | 成本 | 对策 |
|---|---|---|---|
| 文本冲突（同行） | 会 | 低 | 小步提交 + 每日 rebase |
| 语义冲突（无冲突但互相破坏） | **不会** | **高** | 契约 + 测试 + 域边界 |

**优先治理顺序：前端归 P3 独占后，前端汇聚点不再需要跨人拆分；因此优先拆解后端 2 个高频冲突点。**

| 优先级 | 文件 | 现状 | 目标形态 | 主责 |
|---|---|---|---|---|
| **1** | `backend/app/config.py` | 单体 `Settings`，改动频繁 | 按域拆子 Settings 组合 | P1 |
| **2** | `backend/app/api/v1/__init__.py` | 路由注册表，单体 | 按域拆 `router` 聚合 | P1 |
| 3 | `frontend/src/locales/{zh-CN,en-US}/index.ts` | 中英双语单体 | P3 独占，按域拆文件后用 `import.meta.glob` 合并 | P3（内部治理） |
| 4 | `frontend/src/router/index.ts` | 单体路由表 | P3 独占，按域拆 `router/modules/<域>.ts` | P3 |
| 5 | `frontend/src/types/models.d.ts` | 共享类型 | 由 OpenAPI 生成 + 按域拆 `.d.ts` | P3 |

**其余三条规则**：

1. **迁移取号**：文件名 `YYYYMMDD_NN_主题`。取号前在群里报一声，同一天两人抢同一个 `NN` 必撞；**`main` 上必须保持单头**（CI 已强制 `alembic heads` 单头校验）。
2. **谁后合谁 rebase**：先合的人不改语义，后合的人负责对齐。
3. **分支活不过 3 天**：超时说明任务该拆了。

## 8. 开发环境

**日常开发走本机独立数据栈；4090 是团队共享联调 / P4 GPU 真实模型调试环境。**

- **日常开发（默认）**：本机 `deploy/compose/docker-compose.dev.yml` 起 PG / Redis / MinIO，连接串指向 `127.0.0.1`，随起随停，可随便造数据。
- **团队联调 / 集成验证**：4090 服务器（`10.202.2.228`）上的 k3s（namespace `cnpharm-aidd`，NodePort 暴露），**只做短期联调，改数据前先在群里打招呼**。
- **P4 真实模型 / GPU 调试**：4090 上做真实模型镜像与 GPU 卡位调试，**切勿用来跑日常 CRUD**。
- **应用进程**（backend / celery worker / beat / 前端）每人本地各跑一份。

> **禁止把 4090 当普通日常开发的直连数据库**：多人并发写同一个库会互相踩数据，「改完口头说应该好了」就没法验证。

| 组件 | 日常开发（本机） | 共享联调（4090） |
|---|---|---|
| PostgreSQL 16 | `127.0.0.1:5432`（compose） | `10.202.2.228:30432` |
| Redis 7 | `127.0.0.1:6379`（compose） | `10.202.2.228:30379` |
| MinIO | `127.0.0.1:9000`（compose） | `10.202.2.228:30900`（S3）/ `30901`（Console） |
| backend | `127.0.0.1:8000` | — |
| 前端 vite | `127.0.0.1:5173` | — |

`backend/.env` 里按所选数据源二选一配置这 6 行（其余不动），口径见 `AGENTS.md` §4：

```dotenv
DATABASE_URL=postgresql+asyncpg://<用户>:<密码>@127.0.0.1:5432/<库>          # 联调改 10.202.2.228:30432
MINIO_ENDPOINT=127.0.0.1:9000                                              # 联调改 10.202.2.228:30900
REDIS_HOST=127.0.0.1                                                       # 联调改 10.202.2.228
CELERY_BROKER_URL=redis://127.0.0.1:6379/0                                 # 联调 redis://:<密码>@10.202.2.228:30379/0
CELERY_RESULT_BACKEND=redis://127.0.0.1:6379/1
K8S_ADAPTER_OBJECT_STORAGE_ENDPOINT=http://127.0.0.1:9000                  # 联调必须写 http://10.202.2.228:30900
```

> `K8S_ADAPTER_OBJECT_STORAGE_ENDPOINT` 最要紧：它决定 4090 上跑的工具 Pod 从哪儿读文件。联调时必须是 `http://10.202.2.228:30900`，不要指向某个人本机——那个人关机，所有正在跑的工具任务都会失败。

`DB_POOL_MODE` 不需要手工设：默认 `auto`，worker / beat 自动切 `NullPool`（见 `backend/app/database/session.py` 的 `celery_runtime()`）。手写 `pooled` 会让 beat 的维护任务每轮报 `got Future ... attached to a different loop`，表现为「取消超时不清、GPU 租约不回收」却看不出错。

部署与离线包见 `deploy/` 与 `scripts/build-offline-package.sh`（P4 主责）。
