## 0. 一句话结论

**交付线独立成仓 `cnpharm-aidd`，从产品线 `develop@ce9a521` 分叉，此后单主干 `main` 开发，与产品线只保留单向、按需的 cherry-pick 关系。**

v1.0 设想的是「同一仓库里开 `cnpharm/*` 分支」，被本版取代的原因有两条：

1. **多人协作需要独立的权限与保护规则**。交付仓库要拉入甲方之外的实施、测试、前端多人，产品线仓库不该为交付人员开写权限。
2. **交付线要做的是减法，不是增量**。要在产品线里删掉约 8,900 行专属代码、改 38 个测试文件；留在同一仓库就等于每次产品线演进都要在交付分支上重新解一遍删除冲突，而交付期只有 3 个月。

1. **绝不能以产品线 `main` 为基线**——落后 700 个提交，是 2026-01 的旧线。
2. **基线 CI 本来就红**，已在新仓库首个提交 `80a7b9f` 修复；否则分支保护会让所有 PR 永远无法合入。

## 2. 仓库关系

```
zyc6665/CPUmodel_V2  (产品线，私有)
  develop ──●──●──●──▶  持续演进，节奏放缓、慢慢完善
             │
             │ ce9a521  (标签 cnpharm-base-ce9a521，只存在于本仓库)
             ▼
zyc6665/cnpharm-aidd  (交付线，私有，独立仓库)
  main ──●──●──●──▶  单主干，3 个月冲刺交付
```

| 方向 | 是否允许 | 方式 |
|---|---|---|
| 产品线 → 交付线 | ✅ 允许，按需 | `git fetch upstream` + `git cherry-pick -x <sha>`，**必须带 `-x`** 记录来源 |
| 交付线 → 产品线 | ⚠️ 仅通用能力，逐条评估 | 从交付线摘独立 commit，用 PR 合回产品线 `develop`；**禁止整分支合并** |
| 双向自动同步 | ❌ 禁止 | 节奏差一个数量级，同步机制会在冲刺期变成负担 |

**交付线 → 产品线回收的三个准入条件**（同时满足才评估）：

1. 不含任何中国医药专属内容（靶点/口袋/候选物领域模型、甲方参数、LDAP 配置、离线路径）；
2. 不依赖交付线新增的领域表；
3. 有独立测试覆盖，脱离交付线上下文也能跑。

典型可回收项：`audit_log` 表、`upload_session` 分片上传、任务 SSE、`TaskStatus` 的 `QUEUED`/`TIMEOUT` 补充。

### 2.1 分叉点锚点

标签 `cnpharm-base-ce9a521` 打在 `ce9a521` 上，由仓库 ruleset `protect-base-tags` 保护（禁止删除、禁止移动）。

用途：任何时候都能精确回答「我们相对产品线改了什么」——

```bash
git log --oneline cnpharm-base-ce9a521..main      # 交付线相对产品线的全部改动
git diff --stat cnpharm-base-ce9a521..main        # 改了多少
```

这是验收和交接时最常被问的问题，别让这个标签丢掉。

## 3. 分支模型（交付仓库内部）

```
main ──●──●──●──●──▶        交付主干，受保护，随时可出包
        ╲   ╲
         ╲   ●── feature/target-entity-crud      功能
         ●────── fix/task-cancel-race            缺陷
```

| 分支 | 用途 | 从哪切 | 合到哪 | 保护 | 生命周期 |
|---|---|---|---|---|---|
| `main` | 交付主干 | — | — | 禁直推 + PR + CI 绿 | 全程 |
| `feature/<模块>-<主题>` | 新功能 | `main` | `main` | 无 | ≤ 5 工作日 |
| `fix/<模块>-<主题>` | 缺陷 | `main` | `main` | 无 | ≤ 2 工作日 |
| `refactor/<模块>-<主题>` | 不改行为的重构 | `main` | `main` | 无 | ≤ 5 工作日 |
| `docs/<主题>` | 文档 | `main` | `main` | 无 | ≤ 2 工作日 |
| `release/v1.x.y` | 交付候选 | `main` | `main` + tag | 禁直推 | 交付周期 |
| `spike/<主题>` | 技术验证 | `main` | **不合** | 无 | ≤ 3 工作日 |

**为什么主干叫 `main` 而不是 `develop`**：`docs/11-CICD与制品管理方案.md` 的 GitLab 流水线按 `main` 为主干设计（`feat/fix ──MR──▶ main`），交付线要能直接对应这份验收文档。产品线那套 `develop + beta` 双长期分支模型是为持续演进的产品节奏设计的，3 个月交付用不上——多一层集成分支只会让回滚变麻烦。

详细流程与提交规范见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 4. 提交规范

沿用产品线既有 commit 规范，但**每条提交必须带交付上下文**：

```
<type>(<scope>): <subject>

<body>

Refs: <PRD 编号 / 决策编号>
```

`type` 取 `feat|fix|refactor|docs|test|chore|perf|ci`；`Refs` 填中国医药需求编号（`M2-FR-06`）或决策编号（`D-25`）。

验收时按需求条款反查实现：

```bash
git log --grep="M2-FR-06" --oneline     # 该条款的全部实现提交
git log --grep="D-25" --oneline         # 该决策涉及的全部改动
```

四条设计决策：

1. **`compounds` 没有 `project_id`**——化合物是全平台去重主数据（`inchikey` 唯一），项目视图 `GET /projects/{id}/compounds` 只列被本项目候选物引用的分子。若把 `project_id` 写进化合物表，同一个分子在 A/B 两个项目就会各存一行，跨项目去重与相似性检索立刻失效（docs/04 §7.1 的 InChIKey 唯一约束正是为此）。
2. **指纹在化合物写入时就算好，不留待查询时补**——相似性检索是全表扫描 + `WHERE fp_ecfp4 IS NOT NULL`，缺指纹的分子会直接从结果里消失。`upsert_compound` 里直接调 `ensure_fingerprint`，`backfill_fingerprints` 只作为「升级 RDKit 后刷新历史数据」的运维入口。
3. **`candidates` 的形态约束写进数据库**——`ck_candidates_payload_matches_type` 要求 `SMALL_MOLECULE → compound_id NOT NULL`、`PEPTIDE → peptide_sequence NOT NULL`；否则「有多肽类型但既无序列也无分子」的脏行会一路传到生成与预测任务里，报错点会离现场很远。
4. **`candidate_set.version` 做乐观锁，冲突返 409 并带 `currentVersion`**——候选集是多人在同一项目里并发改的对象（docs/04 §5.6）。实现上注意 `UPDATE ... WHERE id=? AND version=?` 的 `rowcount == 0` 分支必须先 `rollback()` 再重查；**重查要用提前取出的主键字符串，不能用 ORM 实例的属性**，否则 rollback 使实例过期，取属性会触发隐式 IO 并抛 `MissingGreenlet`。

另有两处反向改动：项目总览 `GET /projects/{id}/overview` 的 `counts` 新增 `candidates`/`candidate_sets`（配套前端 `ProjectOverviewCounts` 与统计卡由 6 张扩到 8 张）；项目删除 `DELETE /projects/{id}` 增加 `delete_project_compound_rows` 级联清理候选集项、候选集与候选物，**但保留化合物本身**（全局主数据，不随项目消失）。

### 5.8 步骤 11 的时区口径统一（2026-10-25）

一个跨全仓的隐性缺陷：后端所有时间列都是**不带时区的 UTC**（`backend/app/common/time.py` 的 `utcnow()` 会 `replace(tzinfo=None)`），序列化时用裸 `isoformat()`，得到 `2026-10-25T13:00:00` 这种没有 `Z` 的字符串。前端 `new Date('2026-10-25T13:00:00')` 会**按本地时区解释**它——东八区用户看到的每个时间都晚 8 小时。这不是显示格式问题，是错误的时间。

| 层 | 改动 |
|---|---|

### 5.11 步骤 14 的排队超时巡检（2026-10-26）

验收报告 `18` §6.4 的 **B-2b** 是「状态机有 `QUEUED → TIMEOUT` 边，但没有任何东西去用它」。这个缺口的性质值得单独说：**它不是功能缺失，而是失败模式没被覆盖**。

队列一旦停止消费——调度器漏消息、卡位全占、配额被占死、集群掉卡——任务会永远停在 `QUEUED`：页面显示「排队中」而实际永远不会开始，用户看不到失败也就不会重试，运维看队列深度还正常。**「安静地卡住」比直接失败更难排查**，因为它不产生任何告警面。

| 决策 | 选择 | 理由 |
|---|---|---|
| 锚点取哪个时间 | `extra_data["queued_at"]`（入队时写入） | 用 `created_at` 会把 PENDING 停留的时间算进排队——任务可能先等上传物化、等前置校验，那段时间队列根本没接手，计入会误判。历史行没有该键时退回 `updated_at`，在本场景等价且不漏判 |
| 离开 `QUEUED` 时 | 清掉锚点 | 不清则重排的任务带着旧时间，下一轮巡检立刻又判超时，形成「重试即超时」死循环 |
| 超时窗口 | 默认 6 小时 | 比最长单任务执行时长（k8s/ssh 3600s）留足余量——只兜「排不进来」，不兜「跑得慢」；跑得慢由执行器层的 `timeout_sec` 负责 |
| 转 TIMEOUT 的方式 | 走 `TaskStateMachine.mark_timeout` | `docs/04` §9.1 要求状态迁移一律 CAS；`test_worker_state_machine.py` 有 AST 守卫禁止直接赋 `task.status`；`mark_timeout` 顺带写 `finished_at`/`error_message`/`execution_time_sec`，少写一次就会在追溯包里缺字段 |
| 扫描节奏 | 5 分钟一轮、每轮 200 条、`with_for_update(skip_locked=True)` | 巡检是兜底不是主链路，慢一点没关系；`skip_locked` 让多副本同时扫不会互相阻塞 |

配套动作：写 `WARNING` 级 `TaskLog`（用户与运维都该看到这条）、调用 `release_task_resource_reservation(task, reason="task_queue_timeout")` 释放可能已占的资源预约、通过 `task_event_hub` 推一条 `status` 事件让 SSE 订阅方立刻刷新（否则页面要等下一次轮询才发现状态变了）。

实测：`test/test_queue_timeout.py` 20 个用例（锚点 6 / 巡检 8 / 循环 4 + 2 个配置项），其中**变异验证**两条——把锚点改成 `created_at` 则 `test_anchor_uses_enqueue_moment_not_created_at` 红；把离开队列的清理去掉则 `test_leaving_queue_clears_anchor` 与 `test_timeout_task_can_be_retried` 红。全量后端 `1526 passed`（含新增 20 个），仅余 6 个已知 Windows 环境差异。

#### 5.11.1 由本步骤暴露的一次 CI 挂死（2026-10-26）

首次推送后 CI 的「后端测试」卡在 `运行 pytest` **45 分钟不返回**，取消重跑再一次卡在同一处，而本机 Windows 全量 3 分钟通过。用 `python:3.11-slim` 容器在真 Linux 上复现，`faulthandler` 堆栈显示进程停在 `selectors.select`——**不是 IO 等待，是事件循环被占满**。

根因是巡检循环的退出条件写错：`_run()` 用 `while True`，只靠 `stop()` 里的 `cancel()` 退出；而 `stop()` 是**先** `self._stop_event.set()` **再** `cancel()`，事件置位后 `asyncio.wait_for(event.wait(), timeout)` 立即返回、循环马上进入下一轮，当 `sweep` 是纯计算（测试桩、或无待处理数据的真实巡检）时这一轮没有任何挂起点，`CancelledError` 拿不到投递窗口，`await self._task` 永不返回。Windows 上只是时序侥幸。

| 项 | 内容 |
|---|---|
| 同源缺陷 | `IdempotencySweepLoop`（`backend/app/services/idempotency_maintenance.py`）是同一份代码结构、同一处 `while True`，一并修正；它此前没有任何循环启停的测试覆盖 |
| 正确写法 | 两处改为 `while not self._stop_event.is_set():`——**退出条件写在 `while` 上，不能只靠 `cancel()`** |
| 为什么测试挡不住 | 回归测试里给 `stop()` 套了 `asyncio.wait_for(timeout=5)`，但红测证明：事件循环被占满时**连超时定时器也没有机会执行**，测试不是失败而是永久挂起。所以测试内的超时是必要的（能挡住普通死锁），但不足以兜住这一类 |
| CI 层兜底 | `.github/workflows/ci.yml` 的「运行 pytest」加 `timeout-minutes: 20` + `timeout 900`。这不是优化：全量正常约 3 分钟，硬时限让作业**变红而不是无声空转**——这次空的 45 分钟 × 2 次完全是可避免的 |
| 复现方式 | 本机没有 Linux/3.11 时，`docker run python:3.11-slim` + `pip install -r backend/requirements-dev.txt` 即可；注意 Windows 下要 `MSYS_NO_PATHCONV=1` 才能正确挂载路径 |

回归测试 4 条（`test_queue_timeout.py` 2 条、`test_idempotency.py` 2 条），含 1 条专门针对「纯计算 sweep 下 `stop()` 必须有限时间内返回」。修复后容器内全量 `1544 passed / 3 failed / 167s`（3 个失败是 slim 镜像缺 git 与 `/etc/mime.types` 的容器差异），CI 上八项全绿、后端测试 **2m1s**。

**这一条给后续所有后台循环的规矩**：写 `while True` + 只靠 `cancel()` 退出的循环，只要循环体里可能没有挂起点，就一定会挂死——这不是"偶发"，是必然，只是 Windows 的调度时序把它掩盖了。

### 5.12 步骤 15 的幂等补挂与装饰器注解缺陷（2026-10-26）

`docs/05` §12 要求「任务提交必须幂等」，步骤 13（PR #24）落地了 `idempotency_keys` 表与 `@idempotent_route` 装饰器，但只启用了 `POST /api/v1/tasks`。本步骤补挂 `POST /api/v1/workflows/{workflow_id}/runs`——选它是因为**副作用最贵**：一次运行会按节点展开成多个任务并各自入队，重复提交等于把整条链路跑两遍。

| 项 | 内容 |
|---|---|
| `path_template` | `/api/v1/workflows/{workflow_id}/runs`（**模板**而非真实路径）。scope 由「用户 + 方法 + 模板」组成，客户端在**不同工作流**上误用同一个键时才会被 40905 拦住；若把真实 `workflow_id` 拼进 scope，两个工作流变成两个互不相干的作用域，键误用永远发现不了 |
| 让键可重试 | 4xx/5xx 一律释放键（PR #24 已定的语义）。「失败也算完成」会让客户端永远无法用同键重试，而那正是幂等键最需要工作的场景 |

#### 5.12.1 挂上装饰器后端点直接 422：一个只在特定条件下才正确的机制

补挂后该端点立刻返回 `422 {"detail":[{"type":"missing","loc":["query","data"],"msg":"Field required"}]}`——`data: WorkflowRunCreate` 被当成了 **query** 参数，请求体不再解析，但 OpenAPI 文档看起来一切正常。

根因：`functools.wraps` 把 `__wrapped__` 指向原函数，FastAPI 用 `inspect.unwrap` 拿到的是**原函数**的参数表；但它 eval 注解时用的 `globalns` 是 `getattr(call, "__globals__")`，即**中间件模块**的名字空间。`backend/app/api/v1/workflows.py` 有 `from __future__ import annotations`，注解在它自己的作用域里已经是字符串，`WorkflowRunCreate` 在中间件里不存在，eval 失败后 FastAPI **静默降级**成 query 参数。

`backend/app/api/v1/tasks.py` 没有 future import，所以 PR #24 里完全没暴露。**这意味着当时的幂等机制其实只在「被包装模块没有 future import」这个未言明的前提下才正确**——不是实现写得糙，而是这个前提从未被写下来，也没人测过。

| 项 | 内容 |
|---|---|
| 修法 | 装饰期 `inspect.signature(func, eval_str=True)` 在**原函数自己的作用域**里解析注解，结果挂到 `wrapper.__signature__`。字符串注解不存在了，「用谁的 globals 去 eval」这个问题也就不存在 |
| 元数据 | `functools.wraps` 的 `__name__` / `__doc__` / `__wrapped__` 全部保留（`test_wrapper_keeps_metadata_of_the_original_function` 守着） |
| 影响面 | 对没有 future import 的模块，`eval_str=True` 的结果与原来完全一致（`POST /api/v1/tasks` 的 36 个原有用例全过即为证） |

**规矩**：任何用 `functools.wraps` 包裹路由函数的装饰器，只要被包装的模块可能写 `from __future__ import annotations`，就必须自己解析注解并挂 `__signature__`。这类缺陷的可怕之处是**静默**——端点还能注册、OpenAPI 还能出文档、只是参数位置错了。

守护测试两条（`test/test_idempotency.py::TestDecoratorSignatures`）刻意**不依赖任何具体端点**：直接断言「包装后的签名注解必须是解析后的真实类型而不是字符串」，将来在别的模块上挂装饰器也能拦住。另有 `test/test_workflow_idempotency.py` 10 例覆盖该端点的幂等语义，其中 `test_scope_uses_path_template_so_cross_workflow_reuse_conflicts` 直接盯 `path_template` 的选择。

**这一条给后续所有注册类装饰器的规矩**：只要装饰器改变了函数的签名可见性（`wraps` / `partial` / 自造 wrapper），就要么不碰注解，要么自己 `eval_str=True` 解析后挂 `__signature__`；靠「框架会自己处理」的想法在两种注解形态并存时必然出错，而且错得无声无息。

### 5.13 步骤 16 的数据版本账本（2026-10-26）

`docs/04` §8.3 规划了 `data_version` 表与「按版本查历史、按版本做 diff」，但仓库里只有实体表的**当前态**——`compounds.canonical_smiles`、`proteins.sequence`、`datasets.file_urn` 每个实体一行、原地覆盖。于是出现一个自相矛盾的现场：`proteins.current_version` 会说「这是第 3 版」，而查历史只有第 1 条。

| 项 | 内容 |
|---|---|
| 表 | `data_versions`：`entity_type`（COMPOUND/PROTEIN/DATASET）、`entity_id`、`version`、`source_type`（IMPORT/COMPUTE/MANUAL）、`source_file_urn`、`change_summary`、`content_hash`、`operator`；唯一索引 `(entity_type, entity_id, version)` |
| 只追加 | 与 `audit_logs` 同级（`docs/10` DB-09）。可被改写的历史不是历史——若运维能编辑第 3 行，第 3 行与第 4 行的 diff 就不再描述流水线实际产出了什么。更正一律表达为**新版本** |
| `operator` 存用户名 | 存快照而不是外键，理由同 `AuditLog.actor`（`docs/04` §3 注 1）：账户被改名/停用后历史仍可读。刻意不建 `operator_id`——这张表要回答的是「谁把实体改成了这样」，join 到 `users` 会让答案随账户编辑而变 |
| 并发 | `record_version` 用 `begin_nested()` 把新行放进 SAVEPOINT，唯一约束冲突时只回滚该 SAVEPOINT（外层事务与已写入的实体行不受影响），重算版本号后重试一次；重试仍冲突就抛 `IntegrityError` 而不是静默吞掉——吞掉会让版本序列出现空洞 |
| 提交边界 | `record_version` 自己**不 commit**，由调用方与实体写入在同一次事务里提交。这样「改了实体却没记版本」在事务层面就不可能发生 |

四处写入路径（全部是「先写实体行 → flush → 记版本 → 一次 commit」）：

| 路径 | 位置 | 说明 |
|---|---|---|
| 化合物新建 | `backend/app/services/domain_compounds.py:235` | `change_summary="首次导入"` |
| 化合物复用 | `backend/app/services/domain_compounds.py:208` | **加内容哈希判据**：同一份文件导两次不产生重复版本 |
| 蛋白新建 | `backend/app/api/v1/targets.py:320` | `source_type` 由请求里的 `data.source` 决定 |
| 蛋白更新 | `backend/app/api/v1/targets.py:390` | 本次补的第四处，见下 |
| 数据集登记 | `backend/app/services/datasets.py:88` | |

#### 5.13.1 为什么必须补第四处：一个自相矛盾的版本号

`update_protein`（`backend/app/api/v1/targets.py:350`）原本会**无条件** `current_version += 1`，却不在账本里留任何痕迹。于是「这是第 3 版」这句话没有任何一条历史记录能支撑——版本号是真的在涨，历史里却只有第 1 版。

补法把「递增」与「记账」绑成一对，判据是**与上一版比**而不是「与历史任意版去重」：

| 场景 | 行为 | 理由 |
|---|---|---|
| 改序列 | `current_version += 1` 且记一版 | 结构预测的输入变了 |
| 只改 name | 不递增、不记版 | `name` 不进任何结构输入；若改名也算版本，`current_version` 表示的就变成「保存过几次」而不是「序列被改过几次」 |
| 原样重存 | 不递增、不记版 | 用户连点两次保存不该跳号 |
| 改走再改回 | 递增、记版（版本号不同、`content_hash` 相同） | 判据是「与上一版比」；若按历史去重，撤销操作会在历史里变成空白，恰好抹掉最需要追溯的那一步 |

快照函数 `_protein_version_content()`（`backend/app/api/v1/targets.py:129`）只含 `target_id` + `sequence`：`name` 不进快照，`seq_length` 是派生量不重复计入。`create_protein` 也改用同一函数，两处口径统一。

**组合路径的守护**：`test_updating_sequence_and_name_in_one_request` 覆盖「同一请求既改 sequence 又改 name」——这是唯一此前只存在于注释推理里的路径。它断言一次请求只产生一个版本（`[1, 2]` 而不是 `[1, 2, 3]`）、快照只含结构输入（`content_hash` 与 `{"target_id", "sequence"}` 的哈希相等）、`change_summary` 里不出现 `name` 的内容。变异「在 name 分支也递增+记版」会让这条与 `test_protein_rename_does_not_bump_version` 双双变红。

#### 5.13.2 顺带修掉一个偶发失败：排序平局

`test_upload_file_returns_existing_record_when_duplicate_rows_exist` 长期随机失败（实测连跑 10 次 pass=4~6）。根因不在被测代码：`backend/app/api/v1/files.py:127-135` 的排序是 `case(source_type==UPLOAD ? 0 : 1), created_at DESC, updated_at DESC, id DESC`，而测试里三行在**同一事务的同一刻**写入，Windows 时钟粒度把 `created_at`/`updated_at` 压成完全相同的值（实测连调 12 次 `utcnow()` 只得到 1 个不同 `microsecond`），排序最终退化到 `id DESC`（UUID 字典序）——随机。

| 项 | 判断 |
|---|---|
| 为什么不改生产代码 | 排序链是**全序**（`id` 是主键唯一），结果确定、不会 500；时间戳完全相同时几条候选的 `sha256` 相同（内容相同），取哪条语义等价。要让「时间相同取后插入那条」真正有意义，需要给 `files` 加自增序列列并回填，代价远大于收益 |
| 改法 | 只改测试：fixture 三行用显式递进时间戳（`base` / `+5min` / `+10min`），让用例测的是**排序逻辑**而不是 UUID 的运气 |
| 守护 | 变异（删掉 `created_at.desc(), updated_at.desc(),`）会让该用例立刻变红；不删则连跑 10 次全 pass |

**这一条的一般化教训**：凡是「同一事务里插多行再按时间排序」的用例，都在暗暗依赖时钟分辨率；Windows 上 15.6ms 的粒度会让它们变成抛硬币。时间相关的断言要显式给值，不要依赖默认 `utcnow()`。

### 5.14 步骤 17 的项目配额与算力分钟核销（2026-10-26）

`docs/01` M6-BR-1 要求「DCU 按项目配额 + 优先级排队」，`docs/05` §5.3 规划了 `project_quota` 表，但仓库里一直没有——`backend/app/tasks/resource_quota.py` 的 `ResourceQuotaManager` 只是 worker 侧的 cache 租约限流，回答的是「这台机器此刻还塞不塞得下」，不是「这个项目这个周期还该不该给」。

| 项 | 内容 |
|---|---|
| 表 | `project_quotas`：`max_concurrent_dcu`（默认 2）、`max_concurrent_cpu_tasks`（10）、`daily_quota_minutes`（0 = 不限）、`max_single_task_minutes`（1440）、`quota_period`（DAILY/MONTHLY/NONE）、`overdraft_ratio`（默认 1.00） |
| 折算 | `docs/03` §5.6：DCU·分钟 `1.0`、CPU 核·分钟 `1/64`、内存 GB·分钟 `0`。**不因甲方确认 128 核而变**——这是口径不是容量 |
| 核销时机 | 终态一次性核销（`SUCCESS`/`FAILURE`/`TIMEOUT`/`CANCELED` 都核销，`REJECTED` 不核销）。失败与取消同样核销：算力已经被占用了，不因为结果不好就退回去 |
| 准入 | 只阻塞**新提交**，已入队任务不受影响。三条维度：DCU 并发、CPU 任务并发、周期算力分钟 |

#### 5.14.1 核销为什么挂在 `state_machine.transition()` 而不是 worker

走终态的路不止一条：

| 路径 | 触发方 |
|---|---|
| 执行成功/失败 | worker |
| 排队超时 | `backend/app/services/queue_timeout.py` 的巡检 |
| 用户取消 | `backend/app/tasks/cancellation.py` |
| 远端结果补回 | 远端工具回调 |
| direct runner 兜底 | `backend/app/tasks/direct_recovery.py` |

每处各写一遍核销，**漏一条就给那条路径留下白嫖算力的口子**。`transition()` 是所有终态的必经之路（`if to_status in cls.TERMINAL_STATES: _set_cost_metadata(task)`），写一次就全覆盖，worker 一行不用改。

**不漏扣**靠「纯内存改 `extra_data` + 与状态变更同一个 commit 落库」，外加 `settle_finished_tasks` 巡检兜底扫「终态但无 cost」的行（含升级前的老任务）。
**不重扣**靠 `(task.id, retry_count)` 幂等键 + `history` 累加。为什么按轮次而不是「只记一次」：一个失败三次才成功的任务，只记最后那次会让配额账**系统性偏小**。

#### 5.14.2 `GET` 不得建记录：一个「看页面就改变了行为」的缺陷

初版实现里 `GET /projects/{id}/quota` 会调 `get_or_create_project_quota` 顺手落一条默认记录，而准入检查是「无记录 = 不限」。

**于是「有没有人点开过配额页」改变了这个项目能不能提交任务。** 前端一旦在项目总览挂个配额卡片，所有存量项目打开首页那一刻就被静默套上「并发 2 张 DCU」的限制——而且没人知道为什么提交被拦。

| 项 | 改法 |
|---|---|
| `GET` | 走 `load_project_quota`；`None` 时用 `serialize_default_quota` 返回默认值 + `configured: false` + `updatedAt: null` |
| `GET` 与 `PUT` 共用 | 一层 `_build_quota_payload`，字段名与换算只有一处，避免两条路径漂移 |
| `get_or_create_project_quota` | 保留但**只给 `PUT` 用** |
| 写入入口唯一 | 要让默认值生效必须显式 `PUT` 一次。前端「使用默认配额」按钮 = 把默认值 PUT 上来 |

守护测试三条：`test_get_quota_does_not_create_a_row`（用**独立 session** 复核行数为 0，排除 identity map 假阴性）、`test_get_quota_reports_default_values_as_unconfigured`、`test_get_quota_does_not_change_submission_behaviour`（GET 前后各调一次准入检查，都不该抛）。把 `_quota_payload` 改回 `get_or_create` 会让这四条一起变红。

**这一条的一般化教训**：任何「读接口顺手补齐默认值」的设计，都要先问「补齐之后会不会改变别处的判定」。当「缺记录」与「有记录」在别处语义不同时，补齐默认值等于**在用户不知情的情况下改了配置**。

PR #37 的只读评审报了 6 条阻塞，其中三条不是风格问题，而是**配额机制根本没闭合**：

### 5.15 步骤 18 的一处测试缺陷：断言全过但进程不退出（2026-10-26）

步骤 17 合入后，`test/test_project_quotas.py` 在本机表现为 **`41 passed` 之后进程不退出**——pytest 已经把汇总打出来了，命令却一直挂着，被 `timeout 90` 杀掉时退出码是 `124`。CI 上同一提交是 `pass / 2m39s`，完全没暴露。

#### 5.15.1 根因

`test_task_without_any_project_stays_unrestricted` 是本文件里**唯一**真的走到 `dispatch_tool_task` 却不被配额拦下的用例：

| 用例 | 是否走到分发 | 原因 |
|---|---|---|
| `test_create_task_blocked_by_quota_leaves_no_task_row` | 否 | 停在 `QuotaExceededException` |
| `test_structure_prediction_is_blocked_by_quota` | 否 | 同上（领域入口） |
| `test_task_attached_to_migration_project_is_blocked_by_quota` | 否 | 同上（迁移项目） |
| `test_task_without_any_project_stays_unrestricted` | **是** | 无项目 → 不适用配额 |

它没传 `direct_runner`，于是落到 `backend/app/tasks/service.py` 里**绑定在函数定义上**的 `default_direct_task_runner`。后者用 `asyncio.create_task` 起真任务，测试返回后那个 task 仍挂在事件循环上。

**为什么 `direct_runner_stub` fixture 救不了**（我实际试过，仍然 exit 124）：该 fixture monkeypatch 的是 `tasks_api.direct_task_runner`，只影响 HTTP 路由；本用例直接调 service，Python 的默认参数在函数定义时就已绑定，改模块属性对它无效。

#### 5.15.2 修法与为什么不是「改绿就算」

改为显式把 stub 传进 `create_and_schedule_tool_task(direct_runner=direct_runner_stub)`，**并补一条断言确认任务确实被分发**（`scheduled == [(task_id, version_id)]`）。

第二条断言是必要的：否则为了让测试变绿，很自然会顺手把分发也短路掉，那这条用例对 B-2 的覆盖就只剩「不抛异常」——保护了性能、削掉了覆盖面。

#### 5.15.3 两条一般化教训

1. **「测试通过」不等于「测试干净退出」。** 本次 CI 八项全绿，缺陷却真实存在——因为 CI 只检查 pytest 的退出码，而泄漏的后台 task 在 Linux runner 上恰好没让进程卡住。凡是测试里会调 `asyncio.create_task` 的路径，都应显式注入 stub，而不是依赖「跑得快所以看不出来」。
2. **默认参数是隐式全局。** `direct_runner=default_direct_task_runner` 写在函数签名里，测试改模块属性改不动它；这类「参数默认值指向模块级单例」的写法在多处复用时要特别标注，否则 monkeypatch 会静默失效。

#### 5.16.2 一条实现时踩到的坑：跨方言的 try/except 重试不成立

缺陷 3 最初写成「逐表 `try: op.drop_table(); except: continue`，反复重试直到收敛」。在 SQLite 上成立，在 PG 上永远收敛不了：**PG 里一条语句失败会让整个事务进入 aborted 状态，后续语句一律报 `current transaction is aborted`**，`except: continue` 之后没有任何一条语句能成功。

所以最终按方言分流：PG 直接 `DROP ... CASCADE`（由数据库处理依赖，一次删干净且不会失败），SQLite 不支持 `CASCADE` 才逐轮尝试。**凡是「失败后继续试」的迁移逻辑，都要先问一句这个方言失败后事务还能不能用。**

### 5.17 步骤 20 的 K8s Job 消失缺陷（2026-10-27）

在本地 kind 集群上按 `docs/18` §6.2 复验 K8s 执行链路时，用平台自己的 `KubernetesJobExecutionAdapter` + `KubernetesHttpTransport`（不 mock）跑四个场景，发现**任务在 Job 从集群消失后必然被判失败**。

#### 5.17.1 四场景取证（修复前）

| 场景 | 修复前 | 是否合理 |
|---|---|---|
| A 任务完成、Job 仍在 | `succeeded` | ✅ |
| B `ttlSecondsAfterFinished` 到点，Job 被回收 | `KubernetesTransportError: HTTP 404` | ❌ |
| C 取消运行中任务后查状态 | `KubernetesTransportError: HTTP 404` | ❌ |
| D 完全不存在的外部 ID | `KubernetesTransportError: HTTP 404` | ❌ |

三处「不合理」是同一个机制：`backend/app/execution/transports/kubernetes_http.py` 的 `_get_job()` 对任何 404 都直接 `_raise_for_status`，适配器**无法区分**「取消后已删除」「TTL 回收」「从未存在」。而 `backend/app/tasks/executors/kubernetes_job.py` 的轮询 `while state in {QUEUED, RUNNING}` 没有 try/except，404 冒泡到 worker 的 `except Exception` 就落 FAILURE。

放大因素：`job_ttl_seconds` 默认 **86400 秒**且 `backend/app/config.py` 里**没有这一项配置**，运维无法调。也就是说**任何超过 24 小时才回读状态的任务都会失败**，而这正是 MD 与自由能计算（小时~天级）的常态。

#### 5.17.2 「Job 消失」不等于「任务失败」

最初把修复写成「捕获 404，直接抛 `TaskExecutionError`（消失即失败）」。读 `backend/app/execution/transports/kubernetes_artifacts.py` 后推翻了这个判断：**结果产物在对象存储里，不依赖 Job 是否存在**（按 `prefix = _object_prefix(namespace, job_name)` 下 `result.json` 与各 artifact，并校验 sha256）。

于是改为**结果优先**：

1. `ExecutionHandleGone`（新增，刻意**不**继承 `KubernetesTransportError`）——消失是已知终态，不是可重试的传输失败，两者必须能分开；
2. `KubernetesHttpTransport._get_job()` 遇 404 抛 `ExecutionHandleGone`，并新增 `job_exists()` 用同一路径给出布尔答案；
3. 适配器补 `exists()`、`ExecutionService` 补 `execution_exists()`（transport 不支持时返回 `True`，即保持旧行为，不凭空造终态）；
4. 执行器捕获 `ExecutionHandleGone` 后**先试 `collect_result`**：取到结果就按 `SUCCEEDED` 走，取不到才抛可操作的错误。

第 4 步还要处理一个细节：恢复路径收集过一次结果，外层正常路径会再收集一次。为此把 `_recover_result_after_job_gone()` 的返回类型从 `bool` 改成「collection 或 `None`」，外层用 `if collection is None:` 兜底，避免同一份 manifest 下载两遍。

#### 5.17.3 顺带保留的行为（不能顺手改掉）

- **取消仍然有效**：worker 在失败分支里会重读任务状态，已是 CANCELED 就转 CANCELLED；所以「消失 → 抛错」这条路是取消场景所依赖的，不能改成静默成功。
- **真实传输失败必须继续冒泡**：`connection reset by peer` 之类不能被当成「Job 消失」，否则重试策略失效。测试里专门有一条锁住这点。

#### 5.17.4 验证

- 新增 `test/test_kubernetes_job_gone.py`（8 例）：transport 抛 `ExecutionHandleGone` 且**不是** `KubernetesTransportError`、`job_exists` 不抛异常、适配器在 transport 无该能力时返回 `True`、service 对普通适配器返回 `True`、执行器在结果可读时按成功返回且 `collect_result` 只被调一次、结果不可读时给出含「消失」且不含「404」的可操作消息、取消场景仍抛错且已记录 `external_id`、真实传输失败不触发恢复。
- **变异验证两次**：删掉 transport 的 404 分支 → 传输层 2 例红；删掉执行器的恢复分支 → 恢复用例红。恢复后 8 例全绿。
- 关联套件 `test_kubernetes_job_executor.py` / `test_kubernetes_execution_adapter.py` / `test_kubernetes_http_transport.py` / `test_kubernetes_cancellation.py` / `test_kubernetes_artifacts.py` / `test_executor_module_layout.py` → 23 passed。
- 真 kind 集群复验（3 节点 v1.36.1）：四场景 9/9 PASS，B/C/D 全部抛 `ExecutionHandleGone`、`job_exists` 全部返回 `False`，A 场景 `succeeded` 且 `job_exists` 为 `True`。
- 全量 `pytest test/` → **5 failed / 1637 passed / 4 skipped**，5 个仍是既有 Windows 差异清单，无新增。

**一般化结论：「外部资源不存在」不是错误，是一种状态。** 基础设施类适配器遇到 404/410 时，第一反应不该是抛传输异常，而是先把「资源真的消失了」这件事表达出来，再由业务层判断它意味着成功、失败还是取消——这三者在这条链路上都真实存在。

### 5.18 步骤 21 的对象存储生命周期（2026-10-27）

`docs/15` §4.1 把「对象存储生命周期规则没配」列为**运维最常漏的一条**（对应 `docs/14` C-13）。平台侧的清理（`backend/app/services/upload_maintenance.py` 的巡检 + 三个业务入口校验 `expires_at`）全跑在 backend 进程里：进程停摆或开关关掉，暂存分片就无声长期占盘。MinIO 侧的生命周期由存储服务自己执行，与平台进程存活无关——这是**第二道保险**。

#### 5.18.1 单桶 + 前缀，不是文档里的多桶

`docs/03` §4.5 描述的是目标态多桶（`drp-assets` / `drp-results` / `drp-bulk` / `drp-logs` / `drp-temp` / `drp-models`），而本仓库只有 **`settings.MINIO_BUCKET` 一个桶**，靠前缀区分：

| 文档的桶 | 本仓库前缀 | 写入方 |
|---|---|---|
| `drp-temp` | `_uploads/` | `backend/app/files/part_staging.py` |
| `drp-assets` | `inputs/files/` | `backend/app/files/writer.py` |
| `drp-results` | `organizations/…/artifacts/`、`executions/` | `services/artifacts.py`、`execution/transports/kubernetes_artifacts.py` |
| `drp-logs` | （尚未落对象存储） | — |

规则因此按前缀配：`aidd-temp-scratch` 有 `Expiration`，其余三条**只配 `NoncurrentVersionExpiration`、绝不配 `expiration`**（业务数据被 lifecycle 删掉是不可恢复的事故）。

#### 5.18.2 三个被真实服务端推翻的判断

单元测试替身全部通过（21 例），接上真 MinIO 后暴露三个缺陷：

1. **参数顺序写反，静默互换**：`set_bucket_lifecycle(self, config, bucket=None)` 而调用方按 SDK 习惯写 `(target, config)`，SDK 拿 `LifecycleConfig` 当桶名 → `TypeError: expected string or bytes-like object`。改为 `(self, bucket, config)` 并注明「刻意与 minio SDK 一致」。
2. **`ExpiredObjectDeleteMarker` 与 `Days` 互斥**：`S3Error: Delete marker cannot be specified with Days or Date`。
3. **空规则集必须删除配置，不能写空配置**：`S3Error: Lifecycle configuration should have at least one rule`。新增 `delete_bucket_lifecycle()` 走删除路径。

#### 5.18.3 实测推翻的那条需求

`AbortIncompleteMultipartUpload`（`docs/04` §5.8 要求）在本机 MinIO **写不进去**：只带 abort 的规则 400 `InvalidArgument`；abort + `Expiration` 同写则 PUT 200 但**读回来 abort 被静默丢弃**（用自签 SigV4 的 `requests` 直接 `GET ?lifecycle` 确认是服务端行为，不是 SDK 解析丢的）。

更根本的原因：本仓库的分片是**对象级暂存**（`_uploads/<session_id>/00001.part`），从头到尾没用 S3 原生 Multipart Upload，**压根不存在「未完成的分片上传」可中止**。这条规则是从文档照抄的，既不适用也写不进去。故 temp 规则收敛为「30 天 `Expiration`」。

#### 5.18.4 CI 全红的教训：SDK 位置参数顺序会变

首次 CI 13 条同挂：`TypeError: Rule.__init__() got multiple values for argument 'abort_incomplete_multipart_upload'`。

根因是 minio SDK 两个版本的 `Rule.__init__` 签名不同——7.2.3 的第二个位置参数是 `abort_incomplete_multipart_upload`，7.2.20 是 `rule_filter`。本机装 7.2.20、`backend/requirements.txt` pin 7.2.3，于是**本机全绿、CI 全红**。另有第二处：7.2.3 的 `LifecycleConfig([])` 抛 `ValueError("rules must be provided")`，7.2.20 允许空列表——用本地 `_EmptyLifecycleConfig` 绕开。

> **教训**：凡调用第三方 SDK 的构造函数，位置参数顺序都要当成会变的。pin 版本号只保证「同一个版本」，不保证「升级后顺序不变」，而升级恰恰是最容易漏测的时机（本机装了更新版本时）。

### 5.20 步骤 23 的 traceId 全链路（2026-10-27）

#### 5.20.1 一个 ID，四个落点

`traceId` 同时充当 `X-Request-Id` / 响应体 `requestId` / 日志 `trace_id` / 任务 `extra_data["traceId"]`。**刻意不拆成两个 ID**——两个 ID 会把链路断成两段，跨服务排查时反而要先查「哪个 ID 属于哪一段」。

生成器是 `req_` + Crockford base32（48 位毫秒 + 80 位随机，总长 30），如 `req_01M5XST75H5PVKQYGKB02APNMP`。入站 ID 走白名单（`^[A-Za-z0-9._:\-]{1,64}$`），防换行注入日志、防超 64 字符撞 `audit_logs.request_id String(64)`；非法时继续尝试 `traceparent` 再生成。

#### 5.20.2 为什么是纯 ASGI 不是 `BaseHTTPMiddleware`

`BaseHTTPMiddleware` 把 `send` 收进 anyio 内存流，下游发完首帧后若阻塞，帧会压在缓冲里——`/api/v1/tasks/{task_id}/events` 的 **SSE 会被拖到流结束才见首帧**。纯 ASGI 中间件直接包 `send`，不引入缓冲。

#### 5.20.3 信封从 3 字段变 5 字段

`success_response` / `paginated_response` / `error_response` 全部转调新的 `_envelope()`，返回值多了 `requestId` 与 `timestamp`。**`requestId` 无请求上下文时为 `None`**（降级不抛错）——30+ 模块调这些 helper，任何一个在无请求上下文时炸掉都不值得。

#### 5.20.4 变异验证暴露的一个真实漏洞

第一轮变异「去掉 `finally: reset_trace_id(token)`」→ **33 passed、0 failed**。原因是原有用例都在 `asyncio.gather` 的子 task 里跑，context 是复制的，泄漏在子 task 结束后自然消失。据此补 `test_contextvar_is_reset_after_request_finishes`（在调用方自己的 task 里 await 后断言 `get_trace_id() is None`），重跑变异 → 1 failed。

真实后果：中间件是进程级单例，uvicorn 同一连接 keep-alive 的第二个请求会**继承**第一个的 traceId——日志里两个不相干的请求挂同一个 ID，比没有 ID 更难查。

#### 5.20.5 明确未做

未引入 OpenTelemetry SDK。`docs/10` §8.3 要求的 OTel 需要 collector 整套基础设施；本步骤只做**可 grep、可透传、可跳面板**的 ID 串联，不产生 span。`parse_traceparent` 已能取 parent-id，可作后续接入点。

### 5.21 步骤 24 的化合物版本与 diff（2026-10-27）

#### 5.21.1 评审抓出的第一条：哈希与 diff 判等互相矛盾

`record_version` 用 normalize **之前**的原对象算哈希，却用 normalize **之后**的值落库；diff 判等又走 `_same_leaf` 的 `==`。三条可复现矛盾：

| 输入 | 哈希 | diff | 矛盾 |
|---|---|---|---|
| `0` vs `0.0` | 不同（"变了"） | 相等（"没变"） | 同一响应两个答案 |
| `{'props': {}}` vs `{}` | 相同 | 两侧都漏报 | 空容器摊平后整体消失 |
| `NaN` vs `NaN` | 相同 | `nan != nan` → "变了" | 同上 |

修法：哈希只对规范化后的快照计算（`record_version` 复用同一个 `snapshot` 变量）；`_same_leaf` 增加 int/float 类型判等与 NaN 特判；`flatten_content` 把非顶层空容器作为叶子保留。

#### 5.21.2 比评审更严重的发现：`jsonb` 拒收 NaN

`docker exec compose-postgres-1 psql -c "SELECT '{\"x\": NaN}'::jsonb"` → `DETAIL: Token "NaN" is invalid.`。**PostgreSQL 的 `jsonb` 直接拒收 NaN，而 SQLite 静默存下**——同一份内容在测试里存得下、在生产报错。

修法不是在写入后捕获数据库异常，而是在写入**前**拒绝非法 JSON（`allow_nan=False` + `ValidationException`）。把报错挡在调用方看得懂的层，而不是等 ORM flush 抛一个「数据库返回的错」。

#### 5.21.3 鉴权收紧零覆盖

把 `require_compound_read_access` 的角色判据改成无条件返回，**此前 70 个用例全绿、零用例杀死**。补 `test_low_privilege_role_cannot_read_compound_versions` 后，同样的变异 → 2 failed。

顺带修掉一个真实缺陷：原实现「取前 50 个引用项目再逐个查成员」，**超过 50 个项目引用同一化合物时误判 404**；换成一条 EXISTS 子查询。

#### 5.21.4 三条刻意的语义选择

1. **`content` 可空、历史行不回填** —— 用当前态回填等于伪造历史。
2. **无快照时给 `warning` 而不是 409** —— 历史不可改，报错只会把「我们记漏了」说成「你查错了」。两侧都无快照时 `contentHashChanged` 是 `null` 而不是 `false`：把「未知」说成「没变」是更危险的错误（用户会据此跳过复核）。
3. **`from > to` 按请求方向比对，不排序不 422** —— diff 有向；排序会让响应里的 `from` 与请求参数不一致，前端标签就错了。

#### 5.21.5 验证

- `pytest test/test_compound_versions_diff.py` → 19 passed；关联套件 82 passed。
- 三个变异全部被捕获：角色判据（2 failed）、`_same_leaf` 的 float 判等（1 failed）、空容器分支（1 failed）。
- **真 PostgreSQL**：迁移链升起、`content` 为 `json` 可空、`downgrade` 真删列；端到端导入→改版→diff、越界（`page=999` 返空列表不夹取）、鉴权（外部用户 404 而非 403）逐项核对。

### 5.22 这一轮的一般化结论

五个 PR（#45~#48 与 #46 的 pypdf 补丁）里有四个是「按文档写完、测试全绿、然后被真环境或变异验证推翻」：

| 缺陷 | 只在什么条件下现形 |
|---|---|
| `jsonb` 拒收 NaN | 真 PostgreSQL（SQLite 静默接受） |
| SDK 位置参数顺序 | 版本差异（本机 7.2.20 vs pin 7.2.3） |
| `AbortIncompleteMultipartUpload` 写不进去 | 真 MinIO（替身照我的错误实现写，两边一起错） |

> **结论**：验收报告里的 ✅ 必须挂在「在真环境跑过」或「变异能被杀死」上，不能挂在「单元测试通过」上。凡「写配置」类功能，**测试替身必须比真实服务端更严格**，否则两边一起错就互相抵消。

### 5.23 步骤 25 的 `REJECTED` 第 8 态（2026-10-27）

`docs/04` §4.2 定义了八态，实现只有七态。补 `REJECTED`（准入拒绝）看起来是「加一个枚举值」，实际牵动了 6 个层面：

| 层面 | 改动 | 不看清楚会怎样 |
|---|---|---|
| 状态机 | `TRANSITIONS[PENDING]` 加 `REJECTED`；`TRANSITIONS[REJECTED] = set()`；新增 `reject()` | 给了出边就等于给了「被拒后重试」的路 |
| 核销判定 | **把 `TERMINAL_STATES` 与 `_SETTLED_STATUSES` 拆成两个集合**，`REJECTED` 只进前者 | 加一个终态就自动多一条白嫖算力的口子（`03` §7.3 要求 REJECTED 不核销） |
| 配额落库 | `_record_quota_rejection`：建 `Task(status=PENDING)` → 写 `TaskInput` → 记 `extra_data["rejection"]` → `reject()` → commit | 继续「一条都不留」就无法回答「用户说提交失败过，但没有任务记录」 |
| 视图口径 | 「历史」加 `REJECTED`；「需关注」刻意不加；结果中心刻意排除 | 漏在历史里 = 这行只在 `view=all` 可见，而被找到正是它存在的唯一理由；漏在结果中心 = 点进去看到空产物 |
| 事件流 | `task_event_stream.TERMINAL_STATUSES` 加 `REJECTED` | 订阅方会等一个永不到来的状态变化，挂到 30 分钟上限才断 |
| 工作流三处 | `workflow_waiting_task` / `workflow_loop_scheduler` / `workflow_map_scheduler` 的失败判定集合各加 | 节点任务被配额拦下时留 REJECTED 行而不执行，不算失败则工作流一直等一个永不开始的任务直到整体超时 |

**三处非显然的取舍**：

1. **`REJECTED` 不核销算力**。把「终态」与「要核销」拆成两个集合，是为了让「以后再加一个终态」这个动作**不会自动**获得核销语义。语义相近的两个概念一旦共用同一个集合，未来加成员时就会有人踩坑。
2. **不可重试**。`retry_task` 这条路**不做配额准入**（配额只在 `create_and_schedule_tool_task` 里查），允许重试等于给「提交被拒 → 点重试」开一条绕过配额的路。正确做法是重新提交走完整准入。这是实现到一半**自我推翻**的地方：初版让它可重试（状态机给边 + `can_retry` 放行 + 前端 `retryableStatuses` 加值 + 接口白名单加值，四处都改了），想清楚 `retry_task` 不做配额准入之后全部回滚。
3. **422/429 响应体不变**。用户看到的仍是「配额不足」，只是库里同时多一行可追溯记录。改响应体会破坏已有前端与文档契约，而这次要解决的是「事后无从追溯」，不是「提示不够明显」。

**迁移是空操作**（`20261028_07` 的 `upgrade`/`downgrade` 均为 `pass`）。两点理由：①`schema` 无变更——`tasks.status` 是 `String(20)`，全仓唯一的 `CheckConstraint` 在 `candidates` 表上，与任务状态无关；加约束反而让以后再加状态多一次迁移 ②数据不迁移——改动前配额拒绝直接抛 429 不落库，历史库中根本没有可回填的记录，**凭空造一批 REJECTED 行等于伪造审计证据**。

**一次未被杀死的变异（如实记录）**：把 `if to_status in cls._SETTLED_STATUSES` 改回 `cls.TERMINAL_STATES`，16 条用例**仍全绿**——因为 `reject()` 分支里没写 `started_at`，`cost_from_task` 算出的成本本就是 0，没有可断言的差异化结果。也就是说这一行目前靠 `test_rejected_is_terminal_but_not_settled` 守护**集合本身**，而不是靠行为差异。这类「集合正确但行为等价」的变异只能靠读代码发现，变异验证并不万能。

> **一般化结论**：「加一个枚举值」从来不只是加一个枚举值。**同一份语义散落在多处判断里时，名单越短的那处越容易被漏**（本次漏在「工作流三处失败判定」和「SSE 终态集合」——两处都是 3~4 个元素的短名单，而 `TERMINAL_STATES` 有 5 个）。

### 5.24 步骤 26 的 `retry_of` 字段（2026-10-28）

`04` §9.1 的 `task` 表列了 `retry_of`（重试来源任务）。落字段本身很小，**但落完之后发现它和测试用例的期望不是一回事**，这一点必须写清楚而不是含糊过去。

`12` TC-M6-06 的原文是：「重提生成**新任务**（`retry_of` 指向原任务）；失败任务的日志与已产出文件仍保留；新任务不重复占用配额两次」。而本仓库的重提是**就地重试**——`TaskStateMachine.retry()` 只改同一行的 `status` 与 `retry_count`，**不新建任务行**。

于是 `retry_of` 只能记「这条重试链的起点任务 id」：首次重试时链起点就是本行自身，之后永不覆盖。**非 NULL 等价于「这一行被重提过」**，并不存在「新行的 `retry_of` 指向旧行」。

| 选项 | 代价 | 判断 |
|---|---|---|
| 只落字段（本次做法） | 语义与 TC-M6-06 有差距；`retry_of` 与 `retry_count` 信息重叠 | 最小、无风险；但**不能标 TC-M6-06 ✅** |
| 改成「重提新建任务行」 | 牵动配额核销（同一行还要求「新任务不重复占用配额两次」）、工作流节点绑定、取消逻辑、列表口径、15 个既有重试测试 | 另一种重提模型，属独立改造 |

选了前者，并在 `18` 里把 TC-M6-06 保持 ⚠️、把 G-4 只划「部分」。**验收报告不能把「字段存在」写成「规格满足」**——这是本轮最值得记住的一条。

**顺带修掉的迁移缺陷**：`20261028_08` 首版 `_column_names()` 直接 `sa.inspect(bind).get_columns("tasks")`，在**没有 `tasks` 表**的库上抛 `NoSuchTableError`。`test_alembic_migration_dry_run.py` 里那个「stamp 在 `20260730_02`、无 tasks 表」的 legacy 库正好命中。已按同目录 `20261028_06` 的既有模式补表存在性护栏。

> **一般化结论**：字段落地与语义对齐是两件事。凡是「文档里写了一个字段」的实现，都要回去读**用例**（而不只是读字段表），否则很容易做出一个「有字段、但表述与规格不同」的东西，然后在验收报告里把它写成已关闭。

### 5.25 步骤 27 的 `DataFile` 写入与不可用文件拦截（2026-10-28）

`04` §8.2 的 `data_files` 表建了很久，**没有任何代码往里写过一行**——数据集登记时 `file_urn` 只存成字符串，`serialize_dataset` 的 `files` 恒为 `[]`。这次补上写入路径，顺带把 G-13 的 `DOCUMENT` 类型补齐。

三条契约边界（按「拒绝 / 放行」分）：

| 情形 | 行为 | 为什么 |
|---|---|---|
| 非 `file:` urn（`oss://` 等） | 不落 `DataFile`，仍可登记 | 外部系统的 urn 不能让整个登记失败 |
| 文件存在但属于别的项目 | 422 | 入口拦住，否则一个项目的资产清单能列出别人的文件 |
| 已软删除 / 已损坏 / 已过期 | 422 | **复核时补的**：这类记录仍留在 `files` 表里（软删除等物理清理、损坏只置标记），只校验「存在」会让用户拿到指向已删文件的数据集，直到下载才 404 |

**关键取舍：可用性判定复用 `is_file_usable`，不另立一套。** 「能不能被新任务绑定」与「能不能被登记进数据集」是同一个问题；另立一套只会让两处口径慢慢分开，而分开的那天不会有人在同一个 PR 里发现。`_unusable_reason()` 只负责把原因说清楚（已被删除 / 已损坏 / 已过期），**不是第二道闸门**——闸门仍然只有 `is_file_usable` 一处。

**`attributes` 与 `summary` 的合并顺序**：`attributes` 铺底、`summary` 覆盖。`summary` 是既有契约字段且有测试守「显式给出的 summary 键必须原样回读」；`attributes` 只是为无结构文件补键的附加面，不能反向覆盖调用方明确给出的摘要。

三种新类型**只登记不解析**：解析是重活且已有唯一入口（`POST /projects/{id}/compounds:import`），数据集登记再解析一遍会让同一份文件被解析两次、产生两套行数口径，追溯链立刻断裂。

**四处非显然的取舍**：

### §5.29 产物写入单点化与来源血缘（步骤 33，Task 3a）

产物系统此前只支撑了「资产」和半个「追溯」：`ArtifactVersion` 没有来源列，`link_artifact_lineage` 全仓零调用，于是「输入结构+口袋 → 产出的口袋」这条边根本不存在——追溯包靠 `task_input_snapshots` 钉住了输入，但谱系图画不出来。

**这一档做了什么**

| 项 | 改前 | 改后 |
|---|---|---|
| 版本来源 | 只有 `Artifact.source_task_id` 单值，版本粒度无来源 | `artifact_versions` 加 `source_task_id` / `source_attempt_id` / `source_tool_version_id` / `storage_tier` |
| 版本取号 | `max(version)+1` 在应用层算，并发撞 `uq_artifact_versions_artifact_version` 返 500 | `artifact_writer._create_version_with_retry` 持锁取号 + `IntegrityError` 重试（`MAX_VERSION_RETRIES`） |
| 血缘 | 非工作流单任务无「输入→产出」边 | 由 `task_input_snapshots` 派生 `ArtifactLineage`，`INSERT ... ON CONFLICT DO NOTHING` 幂等 |
| 写入入口 | `artifacts.py` / `standard_artifacts.py` / `standard_input_uploads.py` 三处各写一套 | `ArtifactWriter` 独占这三张表；角色文件统一走 `attach_version_files` |

**四条设计裁决（都有理由，不是随手定）**

1. **删掉 partial 唯一索引 `uq_artifact_versions_artifact_sha256`**。「内容在版本维度唯一」与「每一次生产都留痕」不可兼得；对只追加的生产记录表必须选后者（`04` §9、`12` TC-M7）。它想省的存储本来就不存在——同内容的不同版本指向**同一个 `File` 行**（`storage_key` 相同），只多一行元数据。保留 `(artifact_id, version)` 唯一约束，那是并发正确性。
2. **幂等判据只认「同一个生产任务」**。跨任务同字节必须各建一版：我们的 mock 模型打分是 `seed + 输入 sha256` 的确定性合成，同输入必然同字节；若按内容复用，第二个任务会拿到 `created=False`、不写自己的血缘、`source_task_id` 还留着第一个任务的 id——**追溯包里它看不到自己的产出**，正好打在本步骤要修的病上。
3. **上传路径（`source=None`）保留按 sha 去重**。那是既有语义，不能被新逻辑挤掉；复用版本时**不重复存 File**，并删掉刚上传的重复对象，`deduplicated` 如实置 `true`。
4. **角色文件写入必须幂等**。`artifact_version_files` 有 `uq_artifact_version_files_version_role`，而两个调用方原先都在 `upsert_version` 之后无条件写角色行并把 `created` 丢掉——同任务重放（`standard_artifacts`）和上传同内容二次（`artifacts`）都会 `IntegrityError` 500。`attach_version_files` 按 `(version, role)` 跳过已存在者，成为唯一入口；这条纪律写进了它的 docstring：**写入侧自己收敛，不靠调用方「小心别重放」**。

**验证（`main@23ac83b`，本机）**：flake8 `F401,F821,E9` 零输出；后端 `pytest test/` **1866 passed / 5 failed（均为已知 Windows 差异）/ 4 skipped**；四个目标文件 23 passed；迁移单 head `20261030_05`，空库 `upgrade head` + `downgrade base` 双向 rc=0。**先红后绿做了两次变异**：去掉 `attach_version_files` 的跳过判断 → 幂等用例红；把 `if not created:` 改成 `if False:` → 上传复用用例红；还原后均绿。

**未完成**：`standard_input_uploads` 仍是裸构造 `Artifact`/`ArtifactVersion`（本次能跑只因「每次新建 artifact」，一旦同槽重复物化就撞 `uq_artifact_versions_artifact_version`），属 Task 3b 收编范围；上传/下载改预签名 URL 与列表分页属 Task 3c。计划书 §5.1 里「保留内容唯一索引、靠复用避免重复存储」的判断已被本步骤第 1 条裁决取代。

### §5.36 游标分页（步骤 40，2026-10-30）

`docs/20` §5.7 留的那条「offset 深分页换成游标」在这一步落地。

**为什么 offset 深分页要改**：`LIMIT 20 OFFSET 100000` 不是「跳过 10 万行」，
而是让数据库**逐行产出再丢掉** 10 万行。20 万行表实测：`OFFSET 1000` 3.0 ms、
`OFFSET 100000` 3.0 ms、`OFFSET 199000` **9.4 ms**，随页深线性增长；游标恒定 0.14~0.18 ms。

**这一步踩出的最大教训：同样的索引，写法差 60 倍**

首版把游标条件写成展开式 `ts < ? OR (ts = ? AND id < ?)`，实测（20 万行 SQLite）：

| 条件写法 | 执行计划 | 页深 10 万 | 页深 19.9 万 |
|---|---|---|---|
| `ts < ? OR (ts = ? AND id < ?)` | `SCAN tasks USING COVERING INDEX` | 10.2 ms | 21.2 ms |
| `(ts, id) < (?, ?)` | `SEARCH tasks USING COVERING INDEX ((ts,id)<(?,?))` | **0.16 ms** | **0.14 ms** |

`OR` 形式让 SQLite 与 PostgreSQL 都用不上索引区间，退化成整段索引全扫。
所以 `apply_desc_keyset` 只用 `tuple_(...) < tuple_(...)`，并加了
`test_keyset_compiles_to_row_value_comparison` 这条守护（编译 SQL 里不得出现 ` OR `）。

**做了什么**

| 项 | 内容 |
|---|---|
| 新模块 | `backend/app/common/keyset.py`：`encode_cursor` / `decode_cursor`（`~` + base64url，坏游标 → 422）/ `apply_desc_keyset` / `next_cursor` |
| 任务列表 | `services/task_views.query_task_page(...)` 加 `cursor`；`TaskQueryPage` 加 `total: int \| None` / `next_cursor` / `has_more` |
| 审计日志 | `api/v1/admin_audit.list_audit_logs` 加 `cursor`，游标分支不跑 `count(*)` |
| 契约 | 不传 `cursor` 行为完全不变；传了不算 total，用 `nextCursor`/`hasMore`，`total=null`、`totalKnown=false`；偏移模式**也**返回 `nextCursor` |
| 测试 | `test/test_keyset_pagination.py` 9 条，含「25 行里 4 行同毫秒」的逐页覆盖断言 |

**排序键必须全序**（时间戳 + 主键）：只按时间戳翻页时，同一毫秒的多行会漏行或重复。
那条「4 行同毫秒」的用例就是为了钉死这一点，普通数据造不出来。

**未做**：结果中心、产物、工作流三个列表仍是 offset——它们有项目维度上界，深页概率低；
触发条件是「单项目结果数 > 10 万」或「该列表翻页 P95 > 500 ms」，已记入 `docs/20` §8。

**验证**：`flake8 F401,F821,E9` 零输出；`test/test_keyset_pagination.py` 9 passed；
后端全量 `pytest test/` 结果见提交说明；`docs/20` §5.7 与 §8 已同步为「已落地」。

### 5.38 步骤 42：执行后端去 direct 化（Celery + Worker，本地即生产形态）

**为什么必须做**：本地验证一直靠 `TASK_EXECUTION_BACKEND=celery` + `CELERY_BROKER_URL`
为空的组合，`use_direct_task_execution()` 在这种组合下返回 `True`，任务由 API 进程内
`asyncio.create_task` 执行。这让「模拟真实部署」失真：生产是 API 与 Worker 两个进程、
消息走 Redis，而本地是单进程内存直跑，跨进程才会暴露的问题（事件广播、连接池、
acks_late 重投、Worker 与队列订阅）全都被绕过。

**做了什么**

| 项 | 内容 |
|---|---|
| 运行形态 | `.env` 显式写 `TASK_EXECUTION_BACKEND=celery` + `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`（Redis 分库 0/1） |
| Worker | `celery -A app.worker.celery_app worker --pool=threads --concurrency=4 -Q high_priority,gpu_queue,heavy_compute,cpu_queue,default,tool_tasks,maintenance,monitoring` |
| Beat | `celery -A app.worker.celery_app beat`（`reclaim-*`、`cleanup-expired-files`、`heartbeat-worker-capability`、`reconcile-execution-records` 全在 beat 里） |
| 可观测性 | 新增 `backend/app/worker/health.py`：`probe_workers()` / `worker_availability()`（默认 10s 缓存）/ `WorkerAvailability.describe()`；`_check_celery()` 改为复用；派发前探测结论写入 `extra_data.dispatch.worker_available` |

**两条必须记住的坑（都实测过）**

1. **`--pool=solo` 会让健康检查误报**。单线程 Worker 在执行长任务时占满线程，控制通道
   （`inspect.ping`）无人应答，`/system/health` 于是把「正在干活」报成「没有 Worker」。
   本地 Windows 用 `--pool=threads`（任务主要是等 K8s Job，I/O 密集，线程池正合适），
   Linux 生产用默认 `prefork`。**不要用 solo**。
2. **队列名不匹配等于没起 Worker**。平台把任务路由到 `high_priority` / `gpu_queue` /
   `heavy_compute` / `cpu_queue` / `default`（`app/tasks/queue_manager.py` 的
   `TaskQueue`），而 Celery 的 `task_routes` 又把维护类任务送到 `maintenance`/`monitoring`/
   `tool_tasks`。Worker 的 `-Q` 少写任何一个，落到那个队列的任务就**静默排队**。
   实测：`-Q tool_tasks,default,...` 漏了 `high_priority`，任务 4 分钟不动、日志零报错；
   补上队列重启 Worker 后，**同一条消息立刻被消费**（Broker 里的消息不会丢）。

3. **Worker 必须用 `DB_POOL_MODE=null`（每会话新建连接）**。asyncpg 的异步连接
   **绑定创建它的事件循环**，而 `threads`/`prefork` 池里并发的两个任务各跑在自己的
   循环上。共享进程级连接池时，第二个任务会拿到「绑在别人循环上」的连接，
   报 `Future attached to a different loop` / `interface error: another operation is in progress`。
   实测症状具有欺骗性：**不是任务失败，而是 beat 周期任务（`reclaim-stale-gpu-leases`、
   `reconcile-execution-records` 等）每轮丢一行异常、任务本身照常跑**，所以容易一直
   当成噪音忽略。API 进程保持 `pooled`（`DB_POOL_MODE` 默认值），只有 Worker 容器/
   进程设 `null`；`deploy/compose/docker-compose.prod.yml` 的三个 worker 服务已显式写死，
   `test/test_db_pool_mode.py` 守着这条不被删。

4. **`threads`/`solo` 池不会触发 `worker_process_init`**，执行器网关必须在 `worker_ready` 上也注册一次。
   只挂 `worker_process_init` 时，Worker 的执行器表是空的，任务提交后立刻报
   **「不支持的执行器类型: k8s_job」**——这个报错发生在 Worker 里、不在 API 里，看接口日志一无所获。
   `test/test_worker_health.py` 已用信号接收器断言守住两个信号都挂着。
5. **执行句柄只存在 `ExecutionRecord` 上时，日志归档会静默失效**。`harvest_task_runtime_logs`
   原实现只读 `task.extra_data["external_id"]`，而 Celery 直接派发的任务根本没有
   `ExecutionRecord`（`task_execution_record_id(task)` 返回 None），句柄也随失败事务回滚掉了。
   线上表现：**任务失败、`task_logs` 里只有两行平台状态、没有任何容器输出**。
   修法两条：`harvest_task_runtime_logs` 回退到 `task_execution_record_external_id()`；
   k8s 执行器在没有执行记录时用**独立事务**把句柄写进 `task.extra_data`。

**边界**：`direct` 执行路径保留不删（单元测试与无 Broker 的开发环境仍用它，`conftest` 里 `TASK_EXECUTION_BACKEND` 未显式设置时也走它），但不再作为「模拟部署」的形态。

**验证**：真实任务 `boltz2-structure-prediction` 经 API 提交 →
`dispatch={'mode':'celery','queue':'high_priority'}` → Worker 消费 → `QUEUED→RUNNING` →
K8s Job `sciminer-…` 完成 → `SUCCESS 100%`；`task_logs` 出现 `log_data.source="runtime"`
的容器日志行（`adapter_type=k8s_job`，`external_id=sciminer-model-jobs/sciminer-9912646000a9`）。
`/api/v1/system/health` 的 `celery` 项随 Worker 在线/离线在 `healthy`/`degraded` 之间变化。

#### 真 PostgreSQL 复核（同日补充）

游标在 SQLite 上做好之后，本机起 PostgreSQL 16 灌 20 万任务复核，抓到两个**只在 PG 上
出现**的缺口——都在这一步一并收口（迁移 `backend/alembic/versions/20261031_03_keyset_and_nulls_last_index.py`）：

1. **`DESC NULLS LAST` 在空库上从未生效**。`20261031_01` 写了 `finished_at DESC NULLS LAST`，
   但基线 `20260624_01` 用 `Base.metadata.create_all()` 先按模型（普通升序）建了同名索引，
   `20261031_01` 见索引已存在即跳过。→ `20261031_03` 在 PG 上 `DROP/CREATE INDEX CONCURRENTLY`
   重建。这是「模型声明 vs 迁移建表」双真源**第三次**咬人。
2. **游标翻页缺索引**。`tasks` 上没有以 `created_at` 打头的索引，**不带筛选**的游标翻页
   退化成 `Parallel Seq Scan`：21.15 ms，和 `OR` 展开式 23.00 ms 一样慢。→ 补
   `ix_tasks_created_at_id (created_at, id)`，同一查询降到 **0.079 ms**（`Index Only Scan
   Backward`，**267×**）。

同批复核还暴露出两个「空库迁移直接失败」的 PG 专有缺陷，也一并修掉：
`candidates.attrs` 用 `sa.JSON`（PG `json`）却建 `GIN`（`data type json has no default
operator class for access method "gin"`）→ 改 `JSON().with_variant(JSONB, "postgresql")`；
`20261031_01` 回填里的 `request_snapshot ? 'task_id'`（`?` 是 jsonb 运算符，json 上没有）→
改 `(request_snapshot::jsonb) ? 'task_id'`。

修完后空库 `alembic upgrade head` 51 个迁移全通过、`alembic downgrade base` rc=0。
**教训**：`INSERT`/索引/回填里凡是用了方言专有语法，SQLite 全绿不能证明空库能建起来。
CI 的 `migrations-pg` 门禁就是为了不再靠人肉复核。

### 7.1 `main` 分支保护

不手敲 JSON——规则是交付纪律的一部分，必须可复核、可重放：


### §5.30 直传输入物化收编与死代码清理（步骤 34，Task 3b）

§5.29 把「产物的写入口」收敛成 `artifact_writer.py` 一处，但当时只覆盖了 worker 与工作流两条路。剩下的漏网者是**直传输入**：`backend/app/services/standard_input_uploads.py` 仍在自己的代码里 `Artifact(...)` + `ArtifactVersion(version=1)`。

3. 删掉因此失去调用者的 `_create_input_artifact` / `_create_input_artifact_version` / `_link_role_files`。

**顺手删的真死代码**：`backend/app/files/deduplication.py`。`FileDeduplicator` 从加入那天起就没有任何生产调用方（只有 `files/__init__.py` 的再导出和它自己的单测），而且 `_find_by_hash` 的查询**没有 project 过滤**——它现在无害只是因为没人用；一旦有人把它接进上传路径，就是一个跨项目文件泄露。删这类代码不是洁癖，是把「暂时无害」变成「结构上不可能」。

### §5.31 产物单份存储、流式下载与生命周期回收（步骤 35，Task 3c）

§5.29 解决了「产物只有一个写入口」，§5.30 把直传输入也接了进来。本节解决第三层：**存取不浪费、删得干净**。

三件事，共同点是「都只能从代码里看出来，跑功能测试不会报错」：

1. **同一份产物存两份**。上传路径先 `storage.upload`、再 `store_file_bytes`，两边都往对象存储写一遍。功能上完全正常——只是每份产物占两倍空间。改法是把 `ArtifactVersion.storage_key` 直接指向 `File.storage_path`，只写一次。
2. **下载全量进内存**。`api/v1/artifacts.py` 原来 `await storage.download()` 后塞进 `Response`；一个 2GB 的轨迹文件就是 2GB 常驻内存，并发几个就 OOM。`StorageBackend` 增加 `open_stream` 抽象（Local 用 `asyncio.to_thread` 读块，MinIO 用 `to_thread(get_object/read)` 并在 `finally` 里 `close + release_conn`——不关会逐个占满连接池）。同时给 >100MB 和 `.dcd/.xtc/.trr` 加预签名 302 分流：让对象存储直接对着浏览器发流量，应用进程只发一个 302。
3. **删了行、留了对象**。项目删除只删数据库行，对象存储里留下永久孤儿——没人能再枚举到它们。现在先枚举 `ArtifactVersion.storage_key` 逐个删对象再删行。

**GC 的危险点在「什么算无引用」**。最直觉的写法是「没有 `artifact_version_files` 指向它就算无引用」，但 `artifact_version_files` 只在产物写入路径创建；用户通过 `POST /files/upload` 上传的 File 从来不出现在那张表，它的真实引用是 `TaskInput.file_ids`——一个 JSON 数组，没有外键，数据库层拦不住。按那个写法，30 天前上传、此刻仍被任务引用的输入文件会被删掉。所以最终条件是四条同时成立：`source_type='tool_output'` + 超 30 天 + 无 `artifact_version_files` 引用 + 未被 `TaskInput/TaskOutput.file_ids` 引用（用 `CAST(... AS TEXT) LIKE '%"<id>"%'` 判定，SQLite 与 PostgreSQL 通用）。

顺带修掉一个同类隐患：逐条事务里如果直接复用刚查出来的 ORM 实例，一次 `rollback()` 会 expire 整批对象，下一条 `record.id` 就抛 `DetachedInstanceError`，整批中断——而「单条失败不阻塞整批」正是这个函数存在的理由。现在先取 id 列表，再逐条 `db.get`。

**验证**：GC 三条保护用例（upload / TaskInput 引用 / TaskOutput 引用）与流式两条（Local、MinIO 假 response）均先红后绿；全量 `1874 passed / 5 failed / 4 skipped`，5 个失败与基线完全一致。

### §5.32 执行链路硬化（步骤 36，Task 4）

五项问题都不报错，但会让「卡住」看起来像「通过」：

- `blocked` 不在 `workflow_scheduler` 的收口集合里 → 含 blocked 节点的 run 永远显示运行中；
- 更要命的是 `workflow_skip._NON_SKIPPABLE_STATUSES` 也没有 `blocked`，不可达分支传播会把 blocked 覆盖成 skipped，**run 被判成功**。这两处必须一起改，只改编排器等于没修。
- run 没有超时；K8s 大产物整块读进内存（峰值 = 文件大小）；产物写入异常被 `except: pass` 吞掉（产物丢了任务却显示成功）。
- `platform_run_v2.sh` 没有 `trap TERM`，被 SIGTERM 时已产出的结果全废。

**迁移回填的顺序是这里最容易写错的地方**：lookup 带 `status IN (PENDING,QUEUED,RUNNING,SUCCESS)` 过滤，若把唯一键回填给一条已 FAILURE/TIMEOUT 的更早行，就会出现「lookup 查不到 → 建新任务 → 撞唯一索引 → 回查终结行 → 节点永远等不到结果」。所以顺序是「非终态中最早 → 全部中最早 → 其余留 NULL」，并且对留 NULL 的行做自愈认领（`UPDATE ... WHERE workflow_run_id IS NULL`，保证单写入者）。

### §5.34 三路只读审计与两批缺陷收口（步骤 38，2026-10-30）

Task 1~5 完成后按要求派出三路只读审计（任务/执行/状态机、API 契约/前端一致性、
产物/资产/存储）。归并原则是**按病根而不按报告的路径**：同一个「集合在多处各写
一份」的病根，无论在哪个文件表现都算一处。

| 批次 | 病根 | 项数 | 代表性问题 |
|---|---|---|---|
| 产物与文件完整性（`0fde8b9`） | 产物身份判据不一致；删除与引用顺序不清 | 5 | 标准产物按 `(artifact_id, sha256)` 判重，而 mock 模型打分是「seed + 输入 sha256」的确定性合成值，跨任务同字节会复用他人版本；项目删除只删行不删对象，且硬删被跨项目引用的 `File` 会让删除事务回滚 |
| 任务状态八态扩散（`7ac5588`） | 八态引入后「算已提交/算失败/算终态」散落十余处 | 10 | 结果接口直出大写状态；项目阶段把排队的任务算作「没提交过」；`/system/stats` 有 4 个状态不属于任何桶；排队超时无条件 UPDATE 覆盖 RUNNING |

三条通用结论：

1. **同一外键，处理方式取决于它是「共享引用」还是「从属记录」**。跨项目的
   `artifact_version_files.file_id` 必须跳过（否则硬删打挂事务），而同为
   无 ondelete 的 `file_access_logs.file_id` 是从属日志、必须陪着删（否则只要
   被访问过的文件永远删不掉并留下 `project_id` 孤儿）。
2. **写回终态要用条件更新（CAS）**：`mark_timeout` 只算字段 → `expunge` 防脏实例
   绕过 → `WHERE status='QUEUED'` → rowcount 不为 1 只告警；资源租约只在
   CAS 命中后归还。
3. **计数器语义不能混用**：资源重排与用户重试必须分开计数，且 `resource_retry_count`
   不能留在 `RESOURCE_WAIT_METADATA_KEYS`（`start()` 会每轮清空）。

验证：后端全量 1959 passed / 5 failed（均既有 Windows 差异）、flake8 零告警、
前端 220 文件 938 用例全通 + `vue-tsc` 退出 0。

### §5.35 索引与查询硬化（步骤 39，2026-10-30）

用户提出「检查一下我们的数据库设计，预留索引。复合索引，防止后期数据量变大，
查询太慢了，注意查询规范，规避多表 join」。这一轮先派三路只读审计（索引盘点、
查询路径与多表 join、查询规范反模式），再用**自建合成库量测**决定改哪些——不靠
「哪个列看起来该建索引」的直觉。

**实测（SQLite，30,000 tasks / 120,000 audit_logs / 50 projects / 50 users）**

| 查询 | 加索引前 | 加索引后 | 关键证据 |
|---|---|---|---|
| 结果中心 `project_id + 终态 + ORDER BY finished_at DESC` | 6.26 ms | **1.10 ms** | 前：`ix_tasks_project_id` + `USE TEMP B-TREE FOR ORDER BY` |
| 任务列表 `user_id + status + ORDER BY created_at DESC` | 3.83 ms | **1.03 ms** | 前：`ix_tasks_user_id` + TEMP B-TREE |
| 审计 `action + 时间范围 + ORDER BY created_at DESC LIMIT 50` | **51.07 ms** | **0.69 ms** | 前：`ix_audit_logs_action` + TEMP B-TREE |
| 审计 `count(*)`（时间范围） | 18.87 ms | 8.50 ms | 已走 covering `ix_audit_logs_created_at` |

差的是「等值列在前、排序列在后」的复合索引，不是更多单列索引。三件落地：

1. **索引层**（`20261031_01`、`20261031_02`）：新增 12 个复合/部分索引（含
   `tasks(project_id, status, finished_at)`、`tasks(user_id, status, created_at)`、
   `tasks(updated_at) WHERE status='QUEUED'`、`audit_logs(action, created_at)`、
   `task_logs(task_id, timestamp)` 等），删 12 个被更长前缀或唯一约束覆盖的单列索引，
   修 4 处「模型声明了但迁移没建 / 迁移建了但模型没有」（`datasets` 唯一约束、
   `candidates` GIN、`compounds.inchikey` 双份、`upload_sessions` 幂等单列索引）。
2. **列层**：`execution_records` 补 `task_id` 真列（FK `ON DELETE SET NULL`），
   从 `request_snapshot['task_id']` 按方言回填——原先靠 JSON 提取进 JOIN。
3. **查询层**（7 处）：`execution/records.py` 的 JSON 提取进 JOIN 改走真列；
   `services/task_views.py` 关键字搜索从 8 列 `ilike('%kw%')`（含 `Task.id`、
   两个 Text 列）收敛到「id 精确 + 5 个有索引/短列的前缀搜索」；任务列表
   `count` 包子查询、结果中心排序、产物列表、工作流列表、`/system/stats`
   改为走索引与单次聚合。

三条教训：

1. **`DESC NULLS LAST` 必须按方言建索引**。PG 的 ASC 索引反向扫描得
   `NULLS FIRST`，与 `finished_at.desc().nullslast()` 不匹配，必须显式建
   `(…, finished_at DESC NULLS LAST)`；SQLite 相反（NULL 最小，DESC 扫描天然最后），
   建普通 ASC 即可。这是全仓**唯一需要方言分叉**的索引。
2. **JSON 提取不能进 JOIN**。`ON tasks.id = execution_records.request_snapshot->>'task_id'`
   让 PG 放弃 `tasks.id` 索引走哈希连接——写起来一行、慢起来一条查询一份全表扫描。
   热字段该升真列。
3. **迁移要能跑在「精简 legacy 库」上**。两条 `test_alembic_*` 用例会在中途 revision
   建库后直接 `upgrade head`，那条路径上 `audit_logs` / `tasks` 并不存在，反射与
   子查询都会抛 `NoSuchTableError` / `no such table`。凡是「补索引 / 回填」类迁移，
   开头就该判表是否存在——缺表是这条路径的正常形态，不是错误。

规范沉淀成 `docs/20-数据库索引与查询规范.md`（DRP-DB-IDX-001 v1.0）：12 条查询硬规则
（每条带仓库真实反例）、索引基线清单与 11 条「不建索引」理由、模型/迁移一致性根因
（基线 `create_all` 造成双来源）、生产执行注意事项（`CONCURRENTLY`、分批发布顺序、
24 小时后看 `pg_stat_user_indexes.idx_scan`）。

验证：后端全量 **1971 passed / 5 failed**（5 个均既有 Windows 差异）、flake8 零告警、
`alembic heads` 单头 `20261031_02`、SQLite 双向迁移 rc=0。

| `job_ttl_seconds` 默认 86400，且**没有任何环境变量入口** | `backend/app/execution/adapters/kubernetes.py:47` |
| 写进 Job 规格 | `backend/app/execution/adapters/kubernetes_manifest.py:99` |
| 平台侧无任何主动删除 | `grep delete_namespaced_job` → 0 处 |
| 唯一的主动删除是取消任务 | `backend/app/execution/transports/kubernetes_http.py:123`（`propagationPolicy=Background`） |
| 卡死的 Job 不会永久泄漏 | `timeout_sec` 默认 3600 → `activeDeadlineSeconds`（`kubernetes_job.py:251`） |

**24h 的真正代价不是 Pod 数量，而是日志会消失**。查日志链路发现：

- `ExecutionService.logs()`（`backend/app/execution/service.py:67`）**全仓无调用方**；
- `GET /tasks/{id}/logs` 只读 `task_logs` 表，而那张表里**只有平台自己写的状态行**；
- 于是 `ttlSecondsAfterFinished` 一到、Pod 一删，容器日志永久 404，追溯包里的日志段也就断了。

对一个要求「结果可回放」的制药平台，这比 Pod 堆积严重得多。所以顺序必须是
**先把日志落库 → 再缩短 TTL → 才清历史 Job**，不能反过来。

**改动**：

1. 新增 `backend/app/services/runtime_logs.py`：
   - `harvest_task_runtime_logs(db, *, task, execution_service=None, max_bytes=None) -> int`：
     读 `task_external_execution_id(task)` → 按游标把日志拉完 → 切块写 `TaskLog`
     （`log_data.source = "runtime"`，带 `sequence` / `adapter_type` / `external_id` / `truncated`）。
   - 三条契约：**尽力而为**（任何异常只记 warning，绝不影响任务终态写入）、
     **幂等**（以 `log_data.source == "runtime"` 为标记，重复调用返回 0）、
     **有上限**（`TASK_LOG_MAX_BYTES` 默认 2MB，按 UTF-8 字节截断且不切断多字节字符）。
   - `split_log_content()` 优先在换行处切、无换行时硬切，单行上限 8192 字符——
     模型刷屏式输出（超长 JSON / 进度条）不会把一行撑成几百 KB。
2. `backend/app/worker/tasks.py`：成功与失败/超时两条终态路径各插一次
   `await harvest_task_runtime_logs(db, task=task)`，都在写 `task_logs` 终态行的同一个事务里。
3. 新增配置：`TASK_LOG_HARVEST_ENABLED`（默认 true）、`TASK_LOG_MAX_BYTES`（默认 2_000_000）、
   `K8S_ADAPTER_JOB_TTL_SECONDS`（默认 **1800**，原硬编码 86400）。
4. `backend/app/execution/transports/kubernetes_runtime.py`：把 `K8S_ADAPTER_JOB_TTL_SECONDS`
   传给 `KubernetesJobExecutionConfig(job_ttl_seconds=...)`——此前该字段从未被赋值，只能吃默认值。

**为什么 TTL 取 1800 秒**：日志已落库，Pod 只在「刚结束、运维还在看现场」这段时间有意义。
24h 会让「每天任务数」直接等于「常驻 Pod 数」（按当前节奏约 54 个/天，虚拟筛选批量跑起来是几百上千）；
30 分钟足够排障，也不至于让节点 `kubectl get pods -A` 变成噪音。

**没做的事**（明确记下）：没有加平台侧的 Job 清理循环。`ttlSecondsAfterFinished` 由 k8s
控制器负责，加一层自研巡检属重复实现；真发现 TTL 控制器不工作（老集群 / 被禁用）再补。

验证：新增 `test/test_runtime_logs.py` 9 条用例（分块、游标翻完、幂等、无外部队列跳过、
截断标记、抓取失败不上抛、开关关闭、空输出）全绿；后端全量 **2097 passed / 6 failed**，
6 个全部是环境差异而非缺陷——3 个点名过的 Windows 差异（`database_url_resolution` /
`model_package_template` / `tool_example_paths`），另 3 个（`test_config_security` 与
`test_kubernetes_runtime` ×2）由本机 `backend/.env` 指向 4090 k3s 引起：把 `.env` 临时移开后
这 3 个连同相关用例 **147 passed**。flake8 零告警、迁移数不变（本次无 schema 变更）。

### 5.39 步骤 43：结果页产物可见性（版本级溯源）

**症状**：MolP-PC 真机任务 `succeeded`、`task_outputs.result.standard_artifacts`
里两个产物 ID 都在、`artifact_versions.source_task_id` 也写对了，但结果详情页
`artifacts` 为空，导出报告「结论」段与追溯包 `outputs` 同样为空。

**根因**：`Artifact` 是**跨任务共享的逻辑实体**（同项目内同一 `artifact_type` +
同一标识只保留一条，后来者追加版本），`Artifact.source_task_id` 记的是**首建者**。
`app/api/v1/results.py::_artifact_outputs`、报告段、`app/services/traceability.py`
三处都按 `Artifact.source_task_id == task_id` 过滤，于是**非首建任务一条产物都查不到**
——产物在库里，只是查询问错了列。

**改法**：新增 `app/services/artifact_outputs.py`（唯一真源）

| 项 | 内容 |
|---|---|
| `ArtifactOutput` | 冻结 dataclass：artifact 展示元数据 + 版本号/文件名/大小/sha256 + `metrics_json`/`summary_json`（顺带消掉报告段的 N+1 回查） |
| `artifact_outputs_for_task(db, *, task_id)` | `Artifact JOIN ArtifactVersion ON artifact_id`，`WHERE ArtifactVersion.source_task_id = task_id`，按 `(created_at, version)` 升序；**同任务多版本全部返回**，由调用方决定取哪条 |
| 三处调用方 | `results.py::_artifact_outputs`（结果详情）、`results.py` 报告段（结论摘要）、`traceability.py::build_traceability_package`（追溯包 outputs） |

**验证**：新增 `test/test_artifact_outputs.py` 3 例（非首建任务只见自己的版本、
同任务多版本全返回、结果 API 跟随版本级来源）；真实 MolP-PC 任务复跑
`_artifact_outputs` 由 0 条变 **2 条**（`molecule_table v2` / `run_report v20`）。

**这条的一般化教训**：「逻辑实体共享 + 版本级溯源」的模型里，任何按
`<实体>.source_xxx` 过滤的地方都要问一句——**这条边记的是首建还是本次**。

### 5.40 步骤 44：领域表任务回写——把「计算完成」接到「领域数据可见」（2026-11-10）

**症状**（`../../docs/26-甲方需求V3.0符合性对照报告.md` H-16）：Boltz-2 结构预测、
结构准备、LVpocket 口袋预测跑完都是 `succeeded`、也有产物，但
`protein_structures` / `pockets` / `pocket_residues` 三个领域表一行都没多。
表现到界面上是三件事：

1. `GuidedWorkflow` 第 1 步靠「`listStructures` 里出现新行」判定结构已就绪，
   恒不完成 → 结构 → 口袋两步硬断；
2. 口袋预测读的是**原始结构**而不是准备后可对接结构，与 TGT-04-1 相反；
3. 口袋列表、评分排序、残基分析只对手工导入和种子数据生效——真实任务跑完看不到东西。

**根因**：执行链路的终点停在 `ArtifactVersion`。`app/services/standard_artifacts.py`
把 result.v2 声明的东西落成 `Artifact` / `ArtifactVersion` / `File`，这是一条**通用**的
产物管道，不认识「这个产物在领域模型里代表什么」。领域语义只存在于提交侧
（`app/services/domain_targets.py` 把 `{"kind": ...}` 写进 `task.extra_data["domain"]`），
成功侧从来没有人读它。

**改法**：

| 项 | 内容 |
|---|---|
| 新增 `app/services/domain_results.py` | `write_back_domain_results(db, *, task, persistence_result, tool, tool_version)`：按 `task.extra_data["domain"]["kind"]` 分发到结构预测 / 结构准备 / 口袋预测三条分支 |
| `app/services/standard_artifacts.py` | `StandardArtifactPersistenceResult` 增 `file_ids_by_artifact_role`（产物 ref → 角色 → file_id）与 `parsed_artifacts_by_ref`（产物 ref → `ParsedStandardArtifact`，含 `metadata` / `metrics`）；`_persist_artifact` 由 4 元组扩为 5 元组 |
| 接线（两处，成对） | `app/worker/tasks.py`：`harvest_task_runtime_logs` 之后、`TaskStateMachine.complete` 之前；`app/tasks/direct_recovery.py`：`remote_success` 分支的 `finish_task_execution_record_best_effort` 之后（`app/tasks/recovery.py` 的 `prepare_recovered_task_output` 因此多返回一个 `StandardArtifactPersistenceResult \| None`） |
| 下游输入 | `app/services/domain_targets.py` 新增 `structure_input_file_record()`：优先 `prepared_urn`，无则回退 `structure_urn`；`submit_pocket_prediction` 改用它 |
| 幂等 | 结构预测按 `(protein_id, task_id)` upsert；口袋预测按 `task_id` 先删旧行再建（显式删 `pocket_residues` 再删 `pockets`）；`rank` 接在结构内 `max(rank) + 1` 之后 |

**三个刻意的设计选择**：

1. **不新增列，只用约定字段**：领域写回不解析 result.v2，而是读同一事务里
   `standard_artifacts` 已经算出来的 `ParsedStandardArtifact`。新增的两个字段不进
   `TaskOutput.result`（`standard_artifact_result_summary()` 未动），纯粹是「把已知的东西
   传给下一个消费者」，避免下游重解析 JSON 或反查 `ArtifactVersionFile`。
2. **SAVEPOINT 隔离，失败不降级任务**：回写在 `async with db.begin_nested()` 里跑，异常只写

   `db.rollback()`**。同一事务里已经有产物、`TaskOutput` 和状态变更，一次领域映射失败
   不该把任务判成失败——但也不能静默，标记会跟着 `commit_current_attempt` 落库。
3. **几何缺失写 NULL 而不是 0**：`volume` 只在 bbox 三维都有效时相乘。写 0 会让排序把

清理 / rank 固定为 1 / 取消 pLDDT 归一化 / 取结构不优先 prepared）分别只让对应用例变红。

`F821,E9` 零输出。

**为什么做**：V3.0 每条需求用例表的业务规则都写着「预测与计算结果仅作为研发辅助参考」，而全站零命中。这类缺口最容易被忽略——它不是功能，是一句必须出现的话。

**做法**：共享组件 `ResultDisclaimer.vue` + i18n 键，挂到 20 个结果页；3 条守护测试锁住覆盖、措辞与 i18n 走位。

**两个刻意选择**：

* **判据是「页面显示模型算出来的数」，不是「页面名字带结果」**：候选物详情页展示预测属性，也必须挂。
* **文案必须走 i18n 键**：硬编码进 20 个模板，下次改措辞要全库搜，漏一个就是口径不一致。

**验证**：前端全量 273 文件 / 1175 用例通过、`vue-tsc` 零错、`npm run build` 33.30s。

### 5.45 步骤 49：导出留痕（P0-8）

**为什么做**：`AuditAction.EXPORT` 从建模之初就在枚举里，全仓零调用。审计表能回答「谁登录了」「谁下载了哪个文件」，回答不了「谁导出了什么、按什么范围导出」——而 V3.0 §6.2 把「导出下载留痕」写成了需求。

**为什么不能靠下载留痕补**：下载是取一个已存在的文件；导出是**按条件生成一份新内容**。一次导出对应「范围 + 格式 + 内容摘要」三件事，只在下载那一刻记一句 `FILE_DOWNLOAD`，事后无法回答「他导出的是哪一批候选物、哪个版本的结构」。

**改法（5 项）**：

| 位置 | 内容 |
| --- | --- |
| `backend/app/common/enums.py` | `RESOURCE_TYPE` 增 `CANDIDATE_SET` / `STRUCTURE`（列是 `String(64)`，**不需要迁移**） |
| `backend/app/common/request_meta.py`（新增） | `client_meta(request)`；`api/v1/auth.py` 去重复用；**不解析 `X-Forwarded-For``——由网关决定是否信任 |
| `backend/app/logging/audit.py` | `AuditLogger.log_export_operation(...)`，`action` 固定 `EXPORT` |
| `backend/app/services/audit_exports.py`（新增） | `record_export(...)`，**吞异常只打 warning** |
| 四个 `:export` 端点 | 追溯包 / PDF 报告 / 候选集 CSV / 结构包，各自带 `kind`、`format` 与内容摘要 |

**三个刻意选择**：

* **资源类型不复用 `file`**：审计员按资源维度排查「这个候选集被谁导出过」时，记成 `file` 就永远找不到。
* **留痕失败不阻断导出**：审计是旁路。写失败抛出会把一次已经生成好的导出变成 500，用户重试就产生第二份文件——错误被放大而不是被记录。
* **内容摘要进 detail，内容本体不入库**：追溯包可由任务重新生成，PDF/CSV 有 `file_id` 可回溯；把字节存进审计表既撑大只追加表，也违反「审计表只记事实」。

**验证**：8 条新测试（4 条端到端 + 3 条单元 + 1 条 `ast` 结构守护，后者要求每个 `:export` 路由的函数体里真的出现 `record_export(`）；守护测试做过变异验证（把 `targets.py` 的那一行换成 `pass`，用例退出码 1）；相关 8 个测试文件合跑 114 passed；`flake8` rc=0。

**未覆盖**：`AuditAction.IMPORT` 同样是零调用的枚举值——批量导入化合物/数据集目前没有留痕，不在 P0 范围。

**一般化教训**：**「枚举里有、但没人调用」是最难发现的一类缺口**——它不报错、不警告、类型检查也过，只在被追问「查一下上个月谁导出过数据」时才暴露。判断一个动作「有没有留痕」不能看枚举定义，只能 `grep` 调用方；而防止它再次退化，靠的是**遍历路由表**的守护测试，不是逐个手写断言。

### 5.46 步骤 50：候选物相关结果（P0-9 / `26` H-14）

**症状**：`GET /candidates/{id}/results` 一直返回空列表，候选物详情页只有一个「关联任务」链接。

**根因**：端点按 `Task.extra_data["domain"]["candidate_id"]` 过滤，而这个键的写入方只有
`domain_targets.py` 三张**提交函数**（结构预测/结构准备/口袋预测）——候选物既不是它们提交的对象，
也没人替它写这个键。而「这个候选物是哪次任务产出的」这条关系一直存在：`Candidate.task_id`。

**改法**：

| 位置 | 改动 |
|---|---|
| `backend/app/services/candidate_results.py`（新增） | `attach_candidate_domain()` 在提交侧写域上下文；`candidate_result_conditions()` 生成「产出侧 ∪ 消费侧 ∪ 输入快照」的 SQL 条件 |
| `backend/app/schemas/tasks.py` | `TaskCreate` 加可选 `candidate_id` |
| `backend/app/tasks/service.py` | 在 `create_and_schedule_tool_task`（全平台唯一建任务入口）里调用 `attach_candidate_domain` |
| `backend/app/api/v1/results.py` | `list_candidate_results` 改用 `candidate_result_conditions` |
| `frontend/src/api/results.ts` + `views/compounds/CandidateDetail.vue` | 新增 `listCandidateResults` 与「相关计算结果」表（独立加载） |

**三个刻意选择**：

1. **读取侧取并集而不是只认声明**：只做消费侧时，用户第一次点开一个刚设计出来的候选物，
   列表必然是空的——那恰好是最需要看到结果的时刻。
2. **写入侧不做「文件 → 分子」反推**：候选物是逻辑对象、任务输入是文件，反推需要分子级匹配；
   **误判比缺失更糟**，错的结果挂到别的候选物上比查不到更难发现。
3. **校验放在服务层、跨项目一律拒绝**：挂在 HTTP 层的话，工作流与领域分析这两条提交路径会绕过它；
   不校验项目的话，一次提交就能把 A 项目的结果挂到 B 项目的候选物下。

**验证**：`test/test_candidate_results.py` 9 例（产出侧/消费侧/快照侧/跨项目/无项目/404 + 双键名），
三处变异均被捕获；前端 `compounds-pages-surface.test.ts` 加 1 条守护。

**一般化教训**：判断一个「列表接口」有没有实现，不能看它返回 200 和空数组——要看**它过滤的那一列
是谁写的**。过滤条件里的键若全仓只有读、没有写，这个接口从上线那天起就是装饰。

### 5.47 步骤 51：镜像 1.0.1 重建与 digest 回写（P0-5/P0-6 的落地条件）

**为什么单列一步**：前面两步（§5.42 自由能逐帧契约与 MD 两图）改的是 `deploy/model-images/k8s/gromacs/`
下的两个 Python 脚本，而交付形态是「镜像 + 权重分离、镜像以 `@sha256:` 钉死」。脚本进了仓库、
镜像没重建，线上跑的还是旧脚本——**「代码已修」与「行为已修」之间隔一次 `docker build` 和一次 digest 回写**。

| 动作 | 位置 | 结果 |
|---|---|---|
| 重建 GROMACS 镜像 | 4090 `/data/zhouyc/k8s-model-build/gromacs` | `compute-gromacs:1.0.1` / `sha256:cee36ec427a4665f2e9aecf0cd7cf96bc313968e0798fa1c0c9282aa28149855` |
| 重建 MMPBSA 薄层 | 4090 `/data/zhouyc/k8s-model-build/gmx-mmpbsa` | `compute-gmx-mmpbsa:1.0.1` / `sha256:9122a4773ed3c2674ec1cc9a4e50ee71e4d76df3c4e1ef787ca0a500c38306ee`（FROM 指向新 gromacs digest） |
| 写回工具清单 | `backend/alembic/versions/20261110_01_gromacs_image_refresh.py` | config 里 4 处 digest + `version` + `changelog` 一起换 |
| seeding 折叠 | `backend/app/services/platform_tool_seeding.py` | 启动期重建 config 时用同一份 `NEW_DIGESTS` |
| 守护测试 | `test/test_gromacs_image_digest.py` | 任何一处漏改即红 |

**三个刻意选择**：

1. **迁移里做「文本替换」而不是「按 slug 重写整个 config」**：工具 config 是 ToolPackage v2 的完整清单
   （inputs/outputs/artifacts/variants），重写会把后续手工调过的槽位与角色偏好一起抹掉；替换 digest 只动该动的字符。
2. **`_as_json_text()` 兼容 asyncpg 把 json 列解成 dict**：直接 `str(dict)` 得到单引号 Python repr，
   PG 会报 `invalid input syntax for type json`；SQLite 侧则不能写 `CAST(:config AS json)`（没有 json 亲和性）。
   同一个迁移必须在两种方言下都能跑，这是 `docs/20` §5.6 那条「方言分支先问失败后事务还能不能用」的延伸。
3. **seeding 与迁移共用常量**：seeding 用 `_load_migration_module()` 读迁移模块的 `NEW_DIGESTS`，
   不复制一份映射表——两份映射表迟早会不一致，而不一致的表现是「新装环境对、升级环境错」。

**验证**：dev 库 `alembic upgrade head` 到 `20261110_01`，两工具 `version=1.0.1` 且
`image` 与 `artifacts.primary.image_digest` 一致；4090 上真跑 `compute-gromacs:1.0.1`（`nsteps=200`），
日志出现 `__DRP_PROGRESS__` 进度行，产物含 `rmsf.csv` 与带 `rg_nm` 的 `analysis.csv`。

**教训**：「以 digest 钉镜像」的交付形态里，**镜像版本号属于工具清单的一部分**，
模型代码、镜像、工具清单三者必须同一次变更一起改；只改前两个，第三个会让前两个白改。

### 5.48 领域回写的坑都在「模型真的跑完」之后

* **同一份数据有两个来源，先确认哪一个非空**：Boltz-2 的结构产物 `metrics` 是空字典，
  pLDDT 实际在 `run_report@1` 的 `report.json`（`confidence.complex_plddt`）；LVpocket 的
  `prediction.json` 只给口袋残基 PDB，中心、包围盒与体积要自己从坐标反算。回写代码按
  「字段一定存在」写，就会写进 0 或 NULL，页面上表现为「跑成功了但没数据」。
* **输入形态由工具类型决定，不是由槽名决定**：tool-package v2 工具（LVpocket / GROMACS /
  MolP-C）要求 `input_bindings` 指向已落盘的 `ArtifactVersion`，内置工具要
  `standard_input_uploads`。混用时报的是「Kubernetes 输入需要已落盘的标准 ArtifactVersion」，
  与输入内容本身无关。
* **下游格式契约要在一个地方收口**：无表头 `SMILES.txt` 这类产物，若指望每个消费方镜像
  各自容错，最终有几个镜像就有几种容错。放在 `standard_artifacts._persist_artifact` 落库处
  规范化一次（旧文件保留、`file_meta.normalized_from_file_id` 指回），是唯一不会漏的位置。
* **「环境缺件」是最容易下的错误结论**：MolP-C 报错时第一判断是「这台机器没有权重」，
  实际 9 个 `.pth` 一直在镜像 `/opt/sciminer/MolP-PC/predict/model/` 里，真正原因是表头大小写
  （镜像内嵌 runner 只认大写 `SMILES`）。**先读日志里的原始异常，再怀疑环境。**
* **一次性回填脚本先干跑再 `--apply`**：回填会改 `ArtifactVersionFile` 指向，干跑应输出
  `scanned/changed` 与逐条 `fix/ok` 清单，确认只有该改的那条被改。
* **Windows 侧两个固定坑**：pwsh 无 heredoc，提交信息与长文档一律写文件再用 `-F` / 脚本；
  `Set-Content -Encoding UTF8` 会写 BOM，Python 写文件不要带 BOM。

### 5.49 用户输入的字符串不能直接当对象键或路径段

预测页补上「从项目候选集选择」后，第一次真跑就炸在 10 秒：

```
Kubernetes 输入暂存失败：unsafe Kubernetes input path segment: Pocket2Mol 生成集.csv
```

候选集导出接口按候选集名生成文件名（`Pocket2Mol 生成集.csv`），而
`stage_kubernetes_inputs` 要把每个输入拼成 `inputs/<task>/<attempt>/<slot>/<文件名>`
的对象键——这个键同时是 Job 内的路径段，于是一段 ASCII 白名单把整个任务挡在门外。

两个判断：

1. **这是我自己引入的新路径的真实边界，不是环境问题。** 同一份数据走
   `input_bindings`（demo_build 那条路）能跑通，因为那条路用的是 ArtifactVersion
   的文件，文件名是产物名（ASCII）；只有「用户给候选集起名」这条路才会带中文。
2. **不能靠「让用户改名」解决。** 名称是业务数据，任务的可运行性不该由它决定；
   而拒绝整个任务并给一句 `unsafe path segment`，是把内部约束泄漏成了用户错误。

修法：`_input_filename(filename, file_id)` 保留扩展名、把其余字符归一化成
`[A-Za-z0-9_.-]`，并拼上文件 id 前 8 位——清洗会抹掉区分度，同一个 slot 目录里
两个不同文件可能撞名。已经是安全名的文件原样不动（现存行为零变化）。
输出侧不受影响：`safe_output_relative_path` 只拦绝对路径与 `..`，模型产出中文名照收。

一般化结论：**凡是把「用户可输入/可命名的字符串」拼进对象键、挂载路径、容器内文件名的地方，
都要显式定义归一化规则**；并且在写功能时就该想到「如果这个名字是中文会怎样」。

### 5.50 页面全白与「同一句话出现三遍」是两个性质完全不同的问题

用户在真机点出两件事：结果页上「预测与计算结果仅作为研发辅助参考」出现了三遍；
从结果页点「返回任务中心」后主区全白，URL 变了但内容不渲染，点别的导航也白，必须 F5。

**第二个是框架级的，第一个只是组件归属没想清楚。**

页面全白的根因在路由过渡：

```html
<transition :name="transitionName" mode="out-in">
  <component :is="Component" :key="route.path" />
</transition>
```

结果页普遍有多个根节点（页头 + 内容 + 免责声明），也就是 Fragment 根；Vue 对
Fragment 根算不出离场动画，`out-in` 模式下旧页被移除后新页的进场钩子永远等不到。
开发态那句 `Component inside <Transition> renders non-element root node` 就是预警，
但它只是 `warn`，控制台里早就有，没人看见。改法是让过渡的子树固定是单个元素：

```html
<transition :name="transitionName" mode="out-in">
  <div :key="route.path" class="shell-route"><component :is="Component" /></div>
</transition>
```

免责声明那件事没有玄机：`Result` → `PropertyPredictResult` →
`MoleculePredictDetail` → `AffinityPredictDetail` 四层里三层各挂了一条，没人从
「用户一页看到几条」的角度看过。我先试的是 provide/inject 去重，写下去才发现
**兄弟节点之间不共享 provide**——最外层那条声明并不是内层的祖先，四层各挂一条时
谁都拦不住谁。最终改用归属规则：页面级组件渲染一次，嵌套面板一律不渲染，
并加一个扫导入图的守护测试（渲染声明的组件不得再引用另一个渲染声明的组件）。

三条结论：

1. **过渡/动画的子树必须是单个元素。** 任何「页面组件直接当 `<transition>` 子节点」
   的写法，都会在第一个多根页面上变成「点了没反应」——而这种故障只发生在运行时，
   类型检查和单测都看不见。
2. **合规声明这类「整页只需要一句」的东西，要按归属分配，不要按组件就近放置。**
   就近放置的代价是嵌套一层就多一句，而作者当时只看得见自己那一层。
3. **「点一下看看」是这类问题的唯一有效验证手段。** 这两条缺陷都能读出来，但读
   代码时它们看起来都「正确」；我最终是用 Playwright 登录后走真实路由复现、并在
   修复后重新截图对比才敢说修好（修复前 `.shell-content` 子节点 0、innerHTML 7 字节；
   修复后 42689 字节、0 pageerror）。

### 5.51 「刷新闪烁」不是性能问题，是加载态与内容的关系没定义

用户的原话是「刷新有明显的闪烁感，不应该是丝滑转圈、无感刷新吗」。先把三种闪法拆开：

| 现象 | 真实机制 |
|---|---|
| 任务中心每 10 秒白闪一下 | `SkeletonList v-if="loading"`：自动刷新置 `loading=true` → 整张表格被卸载、骨架屏挂上、请求回来再挂回 |
| 任务详情一刷新整页闪 | `fetchTaskDetail` 与列表共用同一个 `loading` 标志，详情页骨架屏也是裸 `v-if="loading"` |
| 首次打开白屏一拍 | `index.html` 只有空的 `<div id="app">`，JS 解析执行完之前没有可看的东西 |

**结论：骨架屏的语义是「这里还没有内容」，不是「正在请求」。** 一旦把两者混为一谈，
每次后台刷新都会真的把内容拆掉——用户看到的「闪烁」就是这个拆卸-重挂过程，
它是真事，不是渲染性能问题。判据写成 `loading && !hasContent`，有内容时只叠加
一条顶部进度条（`LoadingBar`，2px，不改变布局、不卸载内容）。

两条可复用的规矩：

1. **列表态与详情态必须是两个标志。** 共用 `loading` 的后果不是「多闪一下」，
   而是一个页面的刷新会把另一个页面拆掉——跨页面的耦合缺陷，极难从单页测试里看出来。
2. **首屏不能等 JS。** 主题色也要在解析期就落（内联脚本读 `cpumodel_theme` 设置
   `data-theme`），否则暗色用户会先看到一眼亮色骨架——比没有骨架更糟。

验证这类问题只有一种可信办法：**制造「请求在途」的窗口**（Playwright 里给列表接口
注入 900ms 延迟），然后断言「内容节点是否还在 DOM 里」，而不是截图看有没有转圈。

### 5.52 快照只写 URN 不写文件 id，下游渲染就会静默降级

口袋预测结果页「完整蛋白 + 口袋残基 + 体素格」三层叠加，用户看到的是「完整蛋白不见了，
只剩一团灰色结构」。查真数据才发现不是渲染问题：

```text
{"inputRole":"RECEPTOR","entityType":"artifact_version",
 "urn":"artifact:3b558093-...","fileId":null,"detail":{...}}
{"inputRole":"RECEPTOR","entityType":"protein_structure",
 "urn":"file:479f3ae8-...","fileId":null,"detail":{...}}
```

`traceability.py` 写输入快照时只把标识塞进 `urn`（binding 是 `artifact:<versionId>`、
领域结构是 `file:<id>`），`file_id` 一直是 NULL。前端 `PocketComplexViewer` 只认
`fileId` / `detail.derived_from_file`，于是取不到受体 → 走「只有残基」的降级分支，
把口袋残基文件当受体画。**视图没有报错，它只是少画了一层**——这类缺陷只能靠
「用真数据核对每个应有的图层是否都在」发现，不能靠读代码。

三条结论：

1. **快照是给下游消费的，不是给审计看的。** 只写「能追溯」而写不了「能取回」的字段，
   等于把解码责任推给每一个消费方。落地时 `file_id` 与 `urn` 必须同时写。
2. **URN 要有反向解析规则。** `file:` 前缀取 id、`artifact:` 前缀按 version 下载，
   这两条规则写在一个函数里（前端 `snapshotFileUrl`），任何页面都不再各自猜。
   顺带暴露了一个 API 缺口：历史快照只有 version id，于是新增
   `GET /artifacts/versions/{version_id}/download`——**没有 artifact_id 也必须能取到文件**。
3. **等异步附属数据齐了再挂 viewer。** `MoleculeViewer` 对 `[entries, voxelGrid]` 是
   deep watch，体素格晚到会触发整份结构重新下载重渲染（同一文件下载两次、画面闪一下）。
   加一个 `voxelReady` 门（成功失败都算就绪）后再挂载：真机复测得三个文件各下载一次。

图例颜色也必须等于看到的颜色：图例写「灰色卡通」而实际用主题强调色渲染，用户第一反应
是「图例坏了」。颜色常量与渲染调用放同一处（`0x9ca3af`）比写两遍 CSS 更可靠。

### 5.53 「有分数」比「分数准」更重要，前提是必须说明它不是能量

甲方问「口袋的关键残基能不能排序」。查真数据：99 个残基全部 `is_key=true`、
`contribution=NULL`——LVpocket 只给「距口袋点 8 Å 内的残基清单」，压根没有逐残基分数；
Vina 的 `docked_poses.sdf` 是 0 字节（姿态没存），接触频率热点分析没有输入；
MD 的 `rmsf.csv` 来自 mock 工具包，是合成值不能当证据。

于是选了「几何 + 理化启发式」先上线：贴近口袋中心 0.45 + 4.5 Å 接触面 0.30 +
8 Å 埋深 0.15 + Kyte–Doolittle 疏水 0.10，按 ≥0.70 核心 / ≥0.55 关键 / 其余外围分级，
99 个残基变成 8 核心 + 11 关键。三条裁决：

1. **能被质疑的分数要主动交代口径。** 模块 docstring、接口返回、界面说明三处都写
   「排序参考，不是结合自由能」。反过来做（悄悄排个序、不说明来源）短期好看，
   一旦甲方拿去写进报告，就是平台在替模型背书。
2. **分级由分数派生，不另存列。** `score_tier` 是 `tier_for(contribution)` 算出来的：
   阈值改了不需要迁移历史数据，也不会出现「分数 0.72 却标着外围」的自相矛盾状态。
3. **打分不可用时要退回旧口径，不能把全部残基降级。** `_score_pocket_residues` 在缺受体
   或缺点云时返回 `{}`，写入口据此保留「清单即关键残基」——模型说过这些是口袋残基，
   平台没算出分数不等于它们都是外围。

历史数据用一次性脚本回填（只更新 `contribution`/`is_key`，不动任务与产物），
回填后重跑 `updated=0` 验证幂等。真机核对：表格首行 `A15 LEU 核心残基 0.863`，
成果页 chip 顺序与分数一致、三类配色可区分。

### 5.54 「画面拖不动」多半不是交互没接上，是相机被写成了 NaN

口袋结果页的 3D 视图滚轮不缩放、拖拽不旋转，第一反应会怀疑 canvas 的 pointer-events、
事件没绑、或者 Mol\* 根本没初始化。逐条查下来这些全都正常：wheel / mousedown / pointerdown /
mousemove 事件确实到达 canvas，`elementFromPoint` 命中的就是 `CANVAS`，屏幕上也没有覆盖层，
结构也确实加载了（`structureCount 1`、`components 3`）。

真正的凭据在相机上：`canvas3d.camera.view` 在滚轮后、拖拽后、合成事件后、甚至显式
`managers.camera.reset()` 之后**都是同一串数字**，而 `String(camera.position)` 是 `NaN,NaN,NaN`。
也就是说不是「没响应」，是「在 NaN 上运算」——NaN 参与任何运算仍然是 NaN，画面于是彻底卡死。

根因是一行看起来无害的调用。Mol\* 的 `focusSphere` 要的是 `Sphere3D`：

```ts
// 错：普通对象里也有 center 与 radius，看上去一样，Mol* 取到的却是 undefined
plugin.managers.camera.focusSphere({ center, radius }, { durationMs: 0 })

// 对
plugin.managers.camera.focusSphere(Sphere3D.create(center, radius), { durationMs: 0 })
```

三条可复用的规矩：

1. **数值状态要被断言，不能靠肉眼判断「能不能动」。** 相机位置出现 `NaN` 是硬证据，
   而「拖了没反应」只是症状——症状能对上很多原因，断言只能对上一种。
   验收手段也就固定下来了：对 canvas 截图取 sha256，滚轮前后、拖拽前后必须不同。
2. **高亮变化不该触发全量重建。** 原来 `[pdbUrl, resIds, selectedResId]` 一个 watch，
   点一下残基就 `plugin.clear()` 重建并重新对焦，镜头每次都跳回。拆成两个 watch，
   重建路径先存 `camera.state`、重建后 `camera.setState(snapshot, 0)`，视角才留得住。
3. **结论要排在明细前面。** 99 个残基连着分数一起铺开，和「没有分数」在使用者眼里是同一个问题。
   关键残基（核心 + 关键）单列在上，全部残基放下面分页备查且不显示分数——
   顺序本身就是结论，明细只是免责。
4. **表现形态比颜色更能说明身份，但不要替用户预置结论。** 关键残基原来只换一种颜色，在 460px 高的视图里和周围的口袋残基几乎分不开；改成球棍后「这几簇原子和别人不同」不用读图例就看出来。第一版把 19 个关键残基全部自动画成球棍，结果视图里同时有 19 簇球棍和一层橙色卡通，用户点选任何一个反而看不出差别——**预置的高亮会稀释用户自己的选择**。最终规则是「只有选中的残基画球棍」，选 0 个就一个都没有。
   同一个道理也适用于文案：界面上那段「0.45 + 0.30 + 0.15 + 0.10，不是结合自由能，疏水指数为 Kyte–Doolittle 标度」是写给评审看的，不是写给用的人看的——口径留在模块 docstring 与验收文档里，面板上只保留「按评分从高到低」这种方向性提示。

### 5.55 「能力存在」与「入口存在」是两件事

用户问的是「我新建靶点之后为什么不能删除？」。查下来的事实是：`DELETE /api/v1/targets/{id}`
在 `backend/app/api/v1/targets.py` 里躺着，`deleteTarget` 在 `frontend/src/api/targets.ts` 里
也躺着，级联删除服务、测试、审计一条不缺——**唯一缺的是列表页操作列上的那颗按钮**。
于是这个功能对用户完全不存在。

这类缺口有几个共同点，值得当成一类缺陷来防：

1. **类型检查、接口测试、构建都抓不到它。** `deleteTarget` 被导出却零调用，ESLint 不会报
   （它是模块导出，不是未使用局部变量），前端测试也不会报（没人测「页面有没有这个入口」）。
   唯一能抓到的方式是**在页面上点一次**，或者写一条断言源码里存在该入口的守护测试。
2. **答案不能说「后端支持，前端没做」就完事。** 用户判断平台能力的依据只有屏幕。
   既然端点与客户端都已经就位，这次修复的成本在两颗按钮上，做掉比解释便宜。
3. **入口补上时，三件配套必须一起补。** 删除是不可逆动作：
   - 二次确认里写清**连带范围**（蛋白、结构、口袋、残基一起没，产物与任务结果保留）；
   - 删除在途时置 `deletingId` 拦住第二次点击——否则第二次请求拿到 404，
     用户看到的不是「删掉了」而是「删除失败」；
   - 翻页边界：删掉当页最后一条要回退一页，否则留下「空表格 + 还有总数」。
4. **破坏性操作要有可回答的留痕。** 原来 `delete_target_cascade` 返回 `None`，
   审计里连一行都没有。现在它返回 `{proteins, structures, pockets, pocketResidues}`，
   端点记 `AuditAction.DELETE` + `ResourceType.TARGET`，并把名字写进 `resource_name` 列——
   **靶点行删完就 join 不到了**，名字放 `detail` 里等于让审计员拿 UUID 去猜。
   顺带把 `TARGET` 加进 `RESOURCE_TYPE` 枚举并重新生成前端 `enums.generated.ts`
   （`test/test_frontend_enum_parity.py` 会守住三方一致）。

### 5.56 「可逆动作」如果没有回程入口，就等于不可逆

用户的原话是「已经归档项目我无法查看，也无法撤销归档」。查下来的事实很干净：
归档只改了一个字段（`projects.status = "archived"`），详情接口 200，数据一行没少；
但列表接口默认 `include_archived=false`，前端也从不传 `true`，于是项目从工作台消失；
后端只实现了 `POST /archive`，没有 `unarchive`。**用户看到的「数据没了」与「找不回来」
其实是同一个缺口的两个面**：列表过滤拿走了入口，缺少反接口拿走了回程。

三条值得记住的判断：

1. **先问「这个动作能不能撤销」，再决定列表怎么过滤。** 归档、冻结、暂停、隐藏
   都是可逆状态，过滤掉它们之前必须同时回答「用户从哪儿把它们找回来」。
   删除不需要回程（真的没了），归档必须有。
2. **反接口要和正接口同批交付。** 这次的正接口与反接口之间隔了好几个迭代，
   中间任何一天用户点归档都是单向操作。评审「有没有归档功能」时，
   问句应该是「归档之后怎么办」，而不是「有没有归档按钮」。
3. **空状态文案要跟着数据状态走。** 全部项目都被归档时，列表为空并不等于
   「还没有研究项目」——项目就在下面的归档段里。空状态写错会让人以为数据丢了，
   这比少一个按钮更伤信任。所以这里加了一句「当前没有进行中的项目」区分两种空。

配套的两件事顺手做完了，理由都不是「顺手」：撤销归档要能回答「恢复成什么状态」
（`projects` 不记归档前状态，只能落 `active`，并写进 docstring 说明这个取舍），
而归档与撤销都要进审计（`ResourceType.PROJECT` + `previous_status`）——
否则「谁把演示项目归档了」事后查不出来，而这恰恰是最容易被误触的动作。

### 5.57 「默认最新」不等于「只能看最新」，成果的归属键是结构 id

用户的原话是「当我有了两个结构的时候，我发现不能选择看哪个结构，默认的好像是最新的，
我无法查看第一个结构的相关成果内容了」。查数据发现这不是显示问题，而是**归属键选错了层级**：

- 蛋白 `81760381…`（EGFR，327 aa）下有两个结构：`a863cd7c`（12:12，pLDDT 83.04，没跑过口袋）、
  `7965989e`（02:35，pLDDT 83.04，已准备，口袋 `dc83dd63` 挂在它上面）。
- 后端 `listStructures` 按 `created_at` 倒序，前端 `structureId = structures[0].id`，
  于是默认展示最新那个**没有口袋**的结构；口袋表读的是「当前结构的口袋」，自然永远为空。
- 旧结构的口袋、残基、3D 坐标全都还在库里，界面上却没有任何一个控件能把它们调出来。

三条裁决：

1. **「取第一条」这种默认值必须能被用户覆盖。** 只要列表长度可能 >1，第一项就不能是唯一入口。
   排序策略（最新优先）可以保留，但排序 ≠ 过滤，排序之后仍然要提供切换控件。
2. **成果挂在哪个实体上，控件就要跟着那一层走。** 口袋与残基是「结构的属性」，
   不是「蛋白的属性」，也不是「项目的属性」。放在蛋白层做选择器，就会出现
   「换了蛋白但结构没变」的错配；放在项目层更是连语义都没有。
3. **空状态要说清「为什么空」和「下一步做什么」。** 「暂无数据」在这里会把人引向
   「是不是结果丢了」；实际原因是「口袋是另一个结构上跑的」，所以文案直接写
   「口袋是按结构预测的，如果是在另一个结构上跑请切换结构查看；否则可以发起一次口袋预测」。

顺带记一个信号：**同一份数据在 UI 上「看不见」时，先查过滤条件与默认选择，再查权限。**
本例详情接口一直是 200，权限没有任何问题，消失在两个地方——列表的默认过滤与前端的下标取第一。

### 5.58 统计口径要覆盖全部子实体；同一能力在两个入口的形态要一致

设计流程页同时暴露了三个问题，根因各不相同，但都不是「代码写错了」，而是**口径**定得太窄：

1. **「已识别口袋」只数了最新那个结构。** 一个蛋白有两个结构、只有一个结构跑过口袋，
   而统计代码写的是 `structures[0]` 上的口袋数。用户看到「已识别口袋 0」，
   实际数据里明明有 1 个——**统计口径漏掉子实体，界面就会说与事实相反的话**。
   聚合类指标必须显式回答「统计范围是什么、范围外的东西去哪了」，
   逐个子实体查询并把失败降级成 0（而不是让整块报错）都是这个设计的组成部分。
2. **同一件事在两个入口必须长得一样。** ADMET 能就地在流程里填参数提交，
   亲和力却只能跳去另一个页面——同样的能力、两种形态，用户的第一反应是「这里坏了」。
   复用组件（`PropertyPredictSubmit` + `initial-type`）比再写一个精简表单更划算：
   校验、模型选择、候选集来源只有一份实现。**跳转不是对齐，复用才是。**
3. **异步加载不能覆盖用户的显式选择。** 首屏 `load()` 里有多个 `await`，
   用户在下拉里选了结构、而首次加载的后续请求回来后又把 `selectedStructureId` 写回第一条，
   表现是「点了没反应」。用自增令牌（`let loadToken = 0`，每个 `await` 后 `if (token !== loadToken) return`）
   让晚到的响应自行退出；用户动手时 `loadToken += 1`，等于宣布「后续在飞的结果作废」。

验证方式：真机上把「已识别口袋 0 → 1」当成缺陷修复的硬证据，
再把切换结构后 0.4s 内的表格行数变化当作渲染联动的证据；
单测用源码守卫锁住聚合写法与令牌检查的处数（`load()` 体内 `if (token !== loadToken) return` 至少 4 处），
红→绿的做法是把聚合改回 `selectedPocketCount`，确认守护测试会失败。

### 5.59 环境缺件是可降级的；「主文件」不能靠字典序猜

两个看着不相干的问题，根子是同一句话：**不要把「一个环节没做到」当成「整件事失败」，也不要让顺序巧合决定语义**。

1. **缺 obabel 不该让结构准备整体失败。** 制备引擎先算出 `prepared.pdb`，再调 obabel 转 `receptor.pdbqt`；
   第二步的依赖不在时，原实现直接抛错，于是已经算出来的产物跟着一起被丢掉，用户看到「任务失败 + 未知错误」。
   正确做法是把产出与依赖拆开：产物照出，缺的那一项写进 `missing_tools` / `warnings` / `status=degraded`，
   任务判成功。**「降级」是一个可交付的状态，「失败」不是**——尤其当失败方本来已经交付了 90% 的价值时。
   配套还要修报错文案：内置工具的校验异常被统一包成「未知错误：…」，把用户能自己解决的问题
   （装个 openbabel）说成看不懂的故障。校验类异常要原样带出原因，只有真意外才配叫「未知」。
2. **主文件的选择顺序必须有语义，不能是字典序。** `protein_structure@1` 版本的 role 有 `structure_file`
   和 `metadata_json`，按 role 排序时 `metadata_json`（m < s）恰好排前面，快照就记成了那个 268 字节的侧车文件。
   下游拿它当 PDB 解析 → 没有原子 → 渲染静默降级，用户看到的是「完整蛋白不见了」。
   正确顺序是 `is_primary desc → sort_order → role`：库里本来就有 `is_primary` 与 `sort_order`
   这两列表达「哪个是主文件、版本内什么顺序」，用字典序等于把已有的语义丢掉了。
   另一层保险放在消费端：**不要相信「第一条就是对的」**，逐个候选按内容探测（有 ATOM/HETATM 才算坐标文件），
   这样历史数据（只追加表，改不了）也能正常显示。
3. 验证方式：这一条必须用真机数据验——单测里造 `metadata_json` + `structure_file` 两个文件能复现写入侧，
   但「渲染退化成橙色蛋白」只有真页面看得出来；反过来，真机上也要确认「元数据被请求过但被拒」，
   否则你不知道探测逻辑是真在跑还是恰好第一条就对。
4. **纠正要发生在读路径，不要用「下载再看内容」去猜。** 第一版把容错放在前端：逐个候选下载、
   看里面有没有 `ATOM` 再决定用哪个。功能上对，代价是错：每条候选一次往返，PDB 动辄几百 KB，
   而正确的那条还要被 Mol* 再下一次——首屏慢一倍，服务端也多扛一倍的下载量。
   正确做法是把排序规则放在服务端的序列化里：一次 `WHERE artifact_version_id IN (...)` 的批量查询
   拿到主文件 id，前端只下载一个文件。历史坏行因此不需要改写（快照是只追加表，本来也改不了），
   读时纠正即可，同时把原值放进 `snapshotFileId`，记录里「原本写了什么」仍然查得到。
   前端只保留零成本判断（按文件名后缀优先挑坐标文件），**永远不要为了知道一个文件是什么而把它下载下来**。

### 5.60 同一份资产不该在平台里绕一圈：能引用就引用

虚拟筛选页最初只有「上传受体 PDB」和「上传配体库」两个入口，而平台里明明已经有
「从项目选择」的成熟做法（性质预测页就是这么做的）。结果是用户想把项目里那 21 个候选物拿去
对接，必须先导出 CSV、再上传回来；想用已准备的结构，先下载 PDB 再上传——**数据在对象存储里
来回搬了两趟，而真正需要的那两个 file id 一直都在**。

三条规矩：

1. **凡是「选已有资产」，一律按实体链选择，不要退回文件上传。** 受体是
   `靶点 → 蛋白 → 结构`，配体是 `候选集`；能选到实体就说明平台知道它是什么，
   上传文件则只剩一个文件名。同一能力出现在两个页面时，输入形态要一致，
   否则用户会以为「这个页面不支持」。
2. **提交时传 id，不要传内容。** `standard_input_uploads` 接受的就是 file id，
   候选集走 `:export` 拿导出文件 id —— 既避免一次下载 + 一次上传，
   也让输入快照里留下的是「用了哪个版本」，而不是「传了一个同名文件」。
3. **两种来源共存时要互相清空。** 切到「从项目选择」就该丢掉本地已选文件，
   否则提交时两个值都在，行为取决于代码里先判断哪一支——
   这种缺陷不会报错，只会让结果是错的。

### 5.61 「这个节点没什么可配的」通常不是节点简单，是面板认错了节点类型

画布上的四种节点（输入 / 工具 / 结果 / 控制流）长得像，但可配置的东西完全不同。`WorkflowNodeInspector` 当初只服务工具节点，
配置页签直接渲染 `NodeToolPanel`，非工具节点就落到 `NodeToolPanel` 内部那句 `当前节点无需工具`（`v-if="node.type !== 'tool'"`）。
于是「蛋白结构输入」这个节点看起来是坏的：它有标题、有描述、有状态徽标，唯独没有控件。而真正能选文件的控件在侧栏
另一个页签（运行配置）里，两者用的是同一份 `workflowRunInputSelections`，只是没人把这个关系告诉用户。

三条规矩：

1. **面板按节点类型分派，不要用一条兜底分支盖住所有类型。** 兜底文案（「当前节点无需工具」）在工具节点上是对的，
   在输入节点上就是错误信息：它把「还没实现」说成了「不需要」。凡看到「无需 X」的提示，先问一句「这个节点真的不需要 X，
   还是我们没给它做入口」。
2. **同一个值出现在两处时，先说清它们是一个值。** 输入节点的选择与运行配置页签的选择写的是同一个 map，
   所以界面上必须直说（面板里那句「与『运行配置』里的同名输入是同一个」），否则用户会在两个地方各选一次，然后怀疑哪个生效。
3. **空下拉要么给空态，要么不要渲染。** 项目里没有兼容产物时，一个空的选择框和「不能选」在视觉上没有区别；
   写明「还没有兼容产物，可以上传，或先在项目里产出该类型产物」，用户才知道下一步做什么。
   同理，未翻译的占位文案（`Select a project file`）会让人以为这是个没做完的功能。

一般化结论：**功能「存在」不等于「可达」，可达也不等于「可理解」**。这次两处都不是能力缺失——选项来自真实项目产物，
上传按钮一直都在——缺的是把入口放在用户会点的地方，以及把「这里能做什么」写在控件旁边。

### 5.62 时限过短会把「慢」变成「失败」；上游没有 batch 时，批只能是并行进程

任务 `ce0c2242-35c4-45ab-8906-0b176bddb91f`（分子生成，100 个分子）跑了 3603 秒，
`error_message` 只有一句 `Kubernetes Job 执行超时（3600 秒）`。模型没报错、日志没异常、
产物一个没有——用户看到的就是「莫名其妙失败」。查下去是两层时限：

1. 工具版本的 `resource_profile.timeout_minutes` 是 60。这不是平台常量，而是种进每个
   模型工具的**运行契约**，而十个 GPU 工具全是匀速的 60 分钟，说明当初是机械填的，不是按
   「结构预测 / 口袋 / MD / 自由能」各自的真实耗时定的。
2. Celery 的 `CELERY_TASK_SOFT_TIME_LIMIT=3600` / `TIME_LIMIT=7200`。就算 K8s 侧放宽，
   worker 也会在 3600 秒先把任务掐掉——两层时限里更小的那个才是真时限，而它藏在另一个
   配置文件里。

四条规矩：

1. **时限是运行契约的一部分，要按任务性质分档，不能一把梭。** 现在按工具分：
   结构/亲和力 6h、口袋 4h、性质/多肽/对接 4h、分子生成 12h、自由能 24h、MD 72h
   （`platform_tool_seeding.TOOL_TIMEOUT_MINUTES`）。
2. **上层时限必须大于下层的最大时限。** Celery 的 soft/hard limit 从固定的 3600/7200
   改成 `TASK_TIMEOUT_MAX_SECONDS + 余量`。否则表现为「任务莫名失败、日志里看不到模型错误」，
   排查成本极高——因为杀死发生在业务代码之外。
3. **平台必须有一个总上限，并且超限要告警截断。** `TASK_TIMEOUT_MAX_SECONDS = 7 天`，
   由 `build_resource_request` 截断并 `logger.warning`。没有上限的话，一个写错的工具配置
   就能把 worker 与卡位占死一周。
4. **迁移与 seeding 必须是同一个真源。** 时限与镜像 digest 都同时被「迁移（存量库）」和
   「seeding（启动期幂等同步）」写，两处一旦漂移，重启一次就把迁移刚写的新值覆盖回去。
   做法：常量放模块级（`TOOL_TIMEOUT_MINUTES` / `NEW_DIGEST`），seeding 直接 import 迁移模块，
   测试断言两边完全相等。

关于 `batch_size`：用户问的是「生成数量」和「一批生成多少」，但 Pocket2Mol 的上游采样阶段
根本没有批——`models/sample.py` 里每个分子都是 `Batch.from_data_list([data])`，一个分子一次
前向。所以这里能做的是**并行起几路采样进程**：`batch_size` 拆成 N 份 `num_samples`、各给一个
种子差、各写一份 config、各自输出到 `sample_output/batchN`，最后由 `finalize()` 合并 SMILES 表与
SDF。参数名沿用 `batch_size`，但面板文案写「并行采样批数」——**不要把训练侧的概念直接搬到推理
参数上**，先读上游代码确认「批」在推理阶段存不存在，再决定这个名字对用户意味着什么。

执行侧还有一个容易误判的点：`torch.load(..., map_location='cuda')` 会在反序列化阶段
为每个 storage 做一次 GPU 分配，在共享卡上直接抛 `CUDA error: out of memory`，堆栈落在
`_cuda_deserialize` 里，看起来像「模型太大」。改成先反序列化到 CPU 再 `.to(device)` 之后，
在同一张只剩约 2GB 余量的卡上依然 OOM（模型本来就要显存），但在余量约 8.6GB 的卡上
89 秒跑完 4 个分子、`SMILES.txt` 4 行——**同一个报错，根因可以在加载方式，也可以是真的没显存，
两者要靠实验区分**（`--gpus '"device=N"'` 指到不同的卡上各跑一次即可）。

顺带补了两条迁移健壮性：空库从零升级（`20260820_01` 还在种已被交付线删除的内置工具）、
以及「`alembic_version` 已前进但基线 `create_all` 没跑过」的续跑（`20261110_01` 无表守卫）。
这两条都不是本轮功能的一部分，但都是「新环境第一次装」时会撞上的坑。

### 5.63 「看起来取消了」比「没取消」更危险：网关只在 worker 里注册

取消运行中任务，接口返回 `500 服务器内部错误`，任务列表里状态还是「运行中」。两个缺陷叠在一起，
而它们单独看都不致命：

1. `tasks/cancellation.py` 在「远端取消失败」的 except 分支里读
   `settings.REMOTE_CANCEL_RETRY_INTERVAL_SECONDS`。这个配置项在远程 API 执行器下线时被删掉了，
   于是分支自己抛 `AttributeError`。更糟的是顺序：`TaskStateMachine.cancel(task)` 在前（只改内存
   里的 task），`commit` 在路由返回时才发生，异常一抛，**内存里的取消状态也跟着丢了**——用户看到
   500，任务继续跑。
2. 执行网关 `ExecutionService` 只在 Celery worker 的 `worker_process_init` / `worker_ready` 信号里
   注册（`app/worker/celery_app.py`）。**API 进程没有这些信号，从来没配过网关**，
   `get_execution_service()` 永远返回空表。于是任何从 API 发起的适配器调用都报
   「不支持的执行器类型: k8s_job」——取消、运行期日志同步都走这条路径。

三条规矩：

1. **凡是「失败后要记一笔」的 except 分支，里面的每一行都要能被执行到。** 这次的分支引用了不存在的
   配置项，平时永远不触发，一旦远端出错就先炸自己。写这类分支时先问：「这行代码上次被执行是什么
   时候？」如果答案是「从没有」，那它大概率是错的。
2. **每个会用到执行网关的进程都要配置它，不能只配 worker。** 判据不是「谁提交任务」，而是「谁调用
   适配器」。API 进程有取消、日志同步、状态查询三条链路。做法：注册表支持按 `settings` 惰性构建一次，
   构建失败就保持空表并告警一次（不要让取用方连读都读不出来）。
3. **「取消」这个动作必须验证到集群。** 只看接口 200 和数据库状态不够——`kubectl get jobs` 里那个
   Job 还在，就等于没取消。验证顺序固定成：接口状态码 → 任务状态 → 集群里 Job 是否消失。

一般化结论：**状态机的状态、数据库的事务、外部系统的资源，是三个不同的东西**。取消要做的是让三者
一致；任何一个环节「看起来对」都不算完成。
