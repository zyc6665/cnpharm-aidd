## 0. 本文档要解决的六个问题

1. **现场到底要装什么** —— 甲方内网里，哪些是甲方提供的、哪些是我们交付的、哪些是厂商随服务器带的，必须有一张不会被争论的清单（§2、§5）。
2. **业务跑在 K8s、算力跑在物理机，这两边怎么缝起来** —— `09` 已决策 DCU 走 SSH + `drp-node-agent`，那么 K8s 侧的 Pod 如何认证、如何发现节点、如何拿回产物，需要一份确定的网络与凭据设计（§4）。
3. **16 张卡如何做到"装完就能用"** —— 常驻容器不是启动一次就完事，驱动升级、镜像升级、机器重启、断电恢复后都要能自动回到指定状态（§6）。
4. **"上线"这一步的动作序列是什么** —— 不是 `helm install` 一句话，而是一次带检查点、带回退点的受控变更，需要逐步骤的验收判据与失败处理（§7）。
5. **出问题怎么退回去** —— 应用回滚、模型回滚、数据回滚三者机制不同，必须分开定义（§8）。
6. **上线前后各方的动作与签字** —— 甲方要做什么、我方要做什么、谁在什么时候签什么字（§9、§10）。

**不在本文档范围**：流水线定义（见 `11`）、日常监控与告警规则（见 `14`）、备份与恢复策略（见 `15`）、功能验收用例（见 `12`）。

## 3. 集群与 namespace 规划

### 3.1 Namespace（沿用 `03` §4.2）

| Namespace | 内容 | 资源配额（建议） | 网络策略 |
|---|---|---|---|
| `drp-system` | 网关、Ingress Controller | requests 2C/4G，limits 4C/8G | 允许全站入向 |
| `drp-app` | 业务服务 Pod | 总计 requests 16C/32G | 仅允许 `drp-system` 与内部互调 |
| `drp-middleware` | Redis / MinIO / RabbitMQ | 按中间件规格 | 仅允许 `drp-app`、`drp-compute` |
| `drp-data` | PostgreSQL（若容器化） | 按规格独占 | 仅允许 `drp-app`、`drp-scheduler`、备份 Job |
| `drp-compute` | CPU 型 Job（Vina、构象、导入导出） | 可超卖，`limits` 由节点决定 | 出向允许 MinIO、`drp-data` |
| `drp-observability` | Prometheus / Grafana / Loki | 8C/16G | 允许拉取各 namespace 指标 |

### 3.2 节点与污点（沿用 `03` §4.3）

| 节点池 | Label | Taint | 用途 |
|---|---|---|---|
| `general` | `node-role=general` | 无 | 控制面、业务、中间件 |
| `cpu-compute` | `node-role=cpu-compute` | `workload=cpu-compute:NoSchedule` | CPU 型计算 |

> **v1.1 修订**：原表第三行 `dcu-compute` 已删除。DCU 机器是**裸机、不进 K8s**，不存在节点池概念，自然也没有 label/taint（`03` v1.1 §4.1 拓扑图已重画，§4.3 已同步减为 2 个池）。
>
> 算力侧由 `drp-node-agent` 独立管理：`install-agent.sh` 安装 systemd 单元 + `/etc/drp/slots.yaml` 声明卡位 + `docker run` 拉起常驻容器（见 §6）。**仅当启用 `03` §4.4.2 演进路径（device plugin）时**，才需要重新增加 `dcu-compute` 池并打 `dcu=hygon-k100:NoSchedule` 污点。

### 3.3 服务副本数与探针基线

> **v1.1 修订**：下表按 `03` §3.2.1 的 **8 个部署单元**组织，不再是 12 个逻辑模块各一份副本。目录仍按逻辑模块划分，但镜像与进程合并。

| 部署单元 | 含逻辑模块 | 副本 | 探针类型 | 关键参数 |
|---|---|---|---|---|
| `drp-gateway`（Nginx Ingress） | — | ≥ 2 | readiness | `/healthz`，initialDelay 10s |
| `drp-api` | gateway(应用侧) + auth + project + asset + target + design | 2~3 | readiness + liveness | `/healthz`，失败 3 次重启 |
| `drp-task-api` | task + workflow + result | 2 | readiness + liveness | 依赖 DB 与 RabbitMQ；**必须与 `drp-scheduler` 共用库连接与事务边界** |
| `drp-scheduler` | scheduler | **1（单活）** | liveness | 通过 DB advisory lock 或 K8s leader-election 保证唯一 |
| `drp-mol-index` | mol-index | 1~2 | readiness | 需预热指纹缓存；RDKit 重、CPU 密集，必须独立 |
| `drp-model-registry` | model-registry | 1 | readiness | — |
| `drp-worker-cpu` | 无独立目录，复用 task/ 的 consumer 入口 | 2~4 | liveness | 消费 RabbitMQ，做导入导出/指纹预计算。**调度目标 = CPU 计算池（128 核），不得落在平台部署机（32 核）上**，见下方说明 |
| `drp-compute-*` | 模型镜像，**不是服务** | 由卡位/Job 决定 | — | DCU 侧由 `drp-node-agent` 拉起；CPU 侧为 K8s Job |
| 前端静态资源 | 2 | — | Nginx 镜像，带 `Cache-Control: max-age=31536000` 指纹 ||

> **`drp-scheduler` 单活的正确做法**：不是靠副本数=1，而是靠 PostgreSQL `pg_try_advisory_lock(hashtext('drp-scheduler'))` 抢锁；抢不到副本进入待命（读态），锁释放后自动接管。这样滚动更新与故障时不会出现"双调度器同时派卡"。

> **v1.2 新增：两类 CPU 的分工必须写死在 YAML 里（`D-03-11` 已确认）**。甲方确认 **计算节点 128 核 / 平台部署机 32 核**（`03` §5.1、§5.6）。
> - **平台部署机（32 核）只跑业务侧**：8 个部署单元 + PG / Redis / MinIO / RabbitMQ。**禁止**在此调度任何计算任务，理由见 `03` §5.6.4（长尾突发会打满 API P95、数据不在本机、故障会连带平台）。
> - **`drp-worker-cpu` 与所有 CPU 型计算 Job（Vina 分片、ETKDG 构象、gmx_MMPBSA、导入解析、指纹预计算）必须用 nodeSelector 钉到计算池**：
>   ```yaml
>   spec:
>     nodeSelector:
>       node-role: cpu-compute   # 计算节点（128 核）；平台部署机为 node-role: general
>     containers:
>       - name: worker
>         resources:
>           requests: { cpu: "2", memory: 4Gi }
>           limits:   { cpu: "4", memory: 8Gi }   # 单分片不要超过 8 核，留出并发度
>   ```
> - **计数口径**：`03` §5.6.1 的「90 有效核」= 128 × 0.7，**已包含给部署机的跨节点网络/对象存储开销**，不要在这 128 里再扣出 32 核给业务侧——32 核本来就是另一台机器。

## 4. 业务侧与算力侧的接缝（关键设计）

### 4.1 两条通道，不要混用

`09` §4.2 推荐了 `drp-node-agent`，但同时提到"SSH 端口转发或直接内网 HTTP"。这两者在运维上差异巨大，**必须选一个并写进部署规范**：

| 通道 | 适用 | 结论 |
|---|---|---|
| **A. 平台 Pod → Agent HTTP（内网）** | 常规调度、状态查询、进度回调 | ✅ **主通道**。延迟低、可复用连接池、便于限流与审计 |
| B. 平台 Pod → SSH → Agent | 通道 A 不可达时的应急、Agent 自身重启 | ⚠️ **仅作应急**。需专用密钥、禁 root 登录、操作全量审计（`09` CR-05） |
| C. Agent → 平台（反向注册/上报） | 心跳、事件推送 | ✅ **辅通道**。Agent 主动上报健康与进度，避免平台轮询 |

**结论：主通道 A + 辅通道 C，B 只保留给应急运维，不进入调度主路径。** 本文档据此规定网络与凭据（§4.2~§4.4）。

### 4.2 网络与端口清单

| 源 | 目的 | 端口 | 用途 | 方向 |
|---|---|---|---|---|
| 用户浏览器 | Ingress | 443 | 平台访问 | 入 |
| `drp-scheduler` Pod（**唯一调用方**） | `drp-node-agent` | 8780/TCP | 提交、取消、查状态 | 出 |
| `drp-node-agent` | `drp-gateway`（Nginx Ingress） | 443 | 心跳、进度、事件上报（反向，Agent 主动发起） | 出 |
| `drp-node-agent` | MinIO | 9000/TCP | 下载输入、上传产物 | 出 |
| `drp-node-agent` | Docker socket | unix | 容器管理 | 本地 |
| `drp-node-agent` | `hy-smi` | 本地命令 | DCU 健康采集 | 本地 |
| 运维跳板 | `drp-node-agent` | 22/TCP | 应急处置（通道 B） | 入 |

> 端口 8780 为约定值，落在 `values-node.yaml` 中；若甲方端口规范冲突，仅改该值。

### 4.3 认证与凭据

| 凭据 | 存放位置 | 轮换 |
|---|---|---|
| Agent 服务端证书（mTLS） | DCU 机 `/etc/drp/agent/{cert,key}.pem` | 年度，或证书泄露后立即 |
| 平台侧客户端证书 | K8s Secret `drp-agent-client-tls` | 同左 |
| Agent 调用平台上报的 API Token | DCU 机 `/etc/drp/agent/report.token`（600 权限） | 90 天 |
| Agent 访问 MinIO 的 Service Account | DCU 机 `/etc/drp/agent/minio.env`（600 权限） | 180 天，最小权限（仅 `drp-results` 写、`drp-assets` 读） |
| 应急 SSH 密钥 | 运维保险柜，不入代码库 | 90 天，用后销毁会话 |

> **禁止**：Agent 使用 root 运行 Docker。使用 `docker` 组成员身份（或 rootless Docker），且该账号仅能操作 **名称前缀为 `drp-` 的容器**（通过 `docker` CLI 包装脚本强制校验，见 §4.5）。

### 4.4 Agent 与平台的责任边界

| 事项 | Agent 负责 | 平台负责 |
|---|---|---|
| 卡位状态（FREE/BUSY/FAULT/BORROWED） | ✅ 维护与上报 | 消费并展示、参与调度决策 |
| 容器生命周期 | ✅ 执行（启停、重试） | ❌ 不直接操作 Docker |
| 排队与优先级 | ❌ | ✅ `drp-scheduler` 唯一决策者 |
| 超时判定 | 上报 `maxMinutes` 已超时的告警 | ✅ 最终判定并置 `TIMEOUT` |
| 产物哈希与入库 | ✅ 上传 + 计算 SHA-256 | ✅ 写 `artifact` 表、校验一致性 |
| 追溯元数据 | 提供设备与镜像事实 | ✅ 写入 `task`/`trace`（`03` §7） |

**关键纪律**：Agent **不做调度决策**，只执行"在 A3 卡位启动 boltz2 任务 tsk_xxx"这一条指令。调度逻辑唯一存在于平台侧 —— 这是 `09` §1 强调的"调度必须留在平台里"的落地方式。

### 4.5 Agent 安全包装（防止越权）

```bash
# /usr/local/bin/drp-docker  （Agent 仅被授权调用此包装脚本）
#!/usr/bin/env bash
set -euo pipefail
case "$1" in
  run|create|start|stop|rm|exec|inspect|logs|ps) ;;
  *) echo "drp-docker: 不允许的子命令 $1" >&2; exit 2 ;;
esac
# 强制容器名前缀，阻止影响非 drp 容器
if [[ "$*" != *"drp-"* ]]; then echo "drp-docker: 容器名必须含 drp- 前缀" >&2; exit 2; fi
exec /usr/bin/docker "$@"
```

> 该脚本配合 sudoers 白名单下发：`drpagent ALL=(root) NOPASSWD: /usr/local/bin/drp-docker *`，**不授予裸 docker**。

## 6. 算力节点安装与卡位编排

### 6.1 单台 DCU 机的安装顺序（不可乱序）

| 步骤 | 动作 | 验收判据 | 失败处理 |
|---|---|---|---|
| 1 | 预检：OS 版本、内核、磁盘 `/var/drp` ≥ 2TB、`/dev/kfd` 与 `/dev/dri/*` 存在、8 张卡全部 `hy-smi` 可见 | 8/8 卡可见，显存 64GB | 缺卡 → 停止，报厂商 |
| 2 | 确认 DCU 驱动与 DTK 版本 | `dtk` 版本 = **26.04**，`/opt/hyhal/lib` 存在 | 版本不符 → 停止，禁止跳过 |
| 3 | 安装 Docker Engine（指定版本） | `docker run hello-world` 通过 | 若甲方禁用 Docker → 切换 Podman 需重新验证（高风险，见 §11 R-02） |
| 4 | 创建运行账号 `drpagent`，加入 `docker` 组，下发 `drp-docker` 包装脚本与 sudoers | `sudo -u drpagent drp-docker ps` 通过 | — |
| 5 | 创建目录 `/var/drp/{work,model-cache,logs}` 与权限 | 属主 `drpagent`，`work` 预留 ≥ 1TB | 空间不足 → 调整值并记录 |
| 6 | 解压 `drp-node-agent`，写入配置与证书，安装 systemd 单元 | `systemctl status drp-node-agent` = active | 见 §14 日志排查 |
| 7 | Agent 自检：扫描 8 个卡位，探活 `hy-smi` | 平台侧看到 8 个卡位，状态 `FREE` | 部分卡 FAULT → 记录并剔除 |
| 8 | 预拉取 L2 模型镜像并校验 digest | 9 个镜像 `docker images` 齐全 | 缺镜像 → 从包补导 |
| 9 | 灌入权重到 `/var/drp/model-cache/<model>/<version>` | `manifest.json` 中 SHA-256 与本地一致 | 不匹配 → 重新拷贝 |
| 10 | 按 `09` §5.2 卡位表启动常驻容器 | 8 个容器 Up，`hy-smi` 显存占用符合预期 | 启动失败 → `docker logs` 定位 |

> **顺序纪律**：第 2 步（DTK 26.04）未通过时，后续全部无效。这是实测中最容易踩的坑（原项目曾因驱动/DTK 不匹配导致容器内设备不可见）。

| 卡位 | 机 A | 机 B | 承载 | 形态 |
|---|---|---|---|---|
| 0,1 | A0/A1 | B0/B1 | Boltz-2 | 常驻整卡 |
| 2,3 | A2/A3 | B2/B3 | STD-Diff | 常驻整卡 |

### 6.3 常驻容器的"期望状态"管理

`docker run` 是一次性动作，**不足以**保证长期一致。规定：

| 机制 | 说明 |
|---|---|
| systemd 托管 | 每个卡位一个 systemd unit（`drp-slot-A0.service`），`Restart=always`，`ExecStart` 为 `docker run ...`，`ExecStop` 为 `docker stop` |
| 期望状态声明 | `/etc/drp/slots.yaml` 描述 8 个卡位应跑什么（镜像 tag、模型版本、卡号）；Agent 启动时对比实际状态并按声明收敛 |
| 漂移检测 | Agent 每 60s 比对 `/etc/drp/slots.yaml` 与 `docker ps`，不一致则记录事件并（按策略）重建 |
| 升级路径 | 改 `slots.yaml` → Agent 滚动重建（先停旧、拉新、起新、校验健康），**单卡位粒度**，不影响其他卡位 |

> 这条机制解决的是 `09` 未覆盖的问题：**机器重启后常驻容器是否自动回来**、**镜像升级后旧容器是否残留**。回答：靠 systemd + 声明式 `slots.yaml`，不靠人。

### 6.4 断电与重启后的自愈顺序

| 顺序 | 动作 | 依赖 |
|---|---|---|
| 1 | 内核与 DCU 驱动加载完成（`/dev/kfd` 出现） | 驱动随内核启动 |
| 2 | `docker.service` 启动 | — |
| 3 | `drp-node-agent.service` 启动，进入 `INITIALIZING` | Docker |
| 4 | Agent 执行卡位自检（8 卡可见性） | 驱动 |
| 5 | 按 `slots.yaml` 拉起常驻容器（并行，最多同时起 4 个避免显存争抢） | 镜像与权重已就位 |
| 6 | Agent 健康后向平台上报 `READY` + 8 个卡位状态 | 平台可达 |
| 7 | 平台侧：将重启期间被打断的任务置为 `FAILED` 并允许一键重试（若任务类型支持断点续跑，则置 `QUEUED` 续跑） | 平台逻辑 |

**判定标准**：单台机器从断电到 `READY`，无人工介入，**≤ 15 分钟**（权重已在本地盘）。这是 `12` TC-NFR 高可用专项的验收项之一。

### 6.5 先行验证环境（NVIDIA 8×4090 + k3s）的安装差异（v1.3 新增）

> 背景：`D-08`（DCU 环境）到位前，用现成的 **8×4090** 先搭（`D-33`）。本节只讲「和 §6.1~§6.4 比，哪里不一样」，**其余步骤原样照做**——这正是卡位方案硬件无关的意义（`09` §5.6）。

| 项 | DCU 生产环境（§6.1） | NVIDIA 4090 先行验证环境 | 说明 |
|---|---|---|---|
| 宿主 OS | 信创 Linux + DTK 26.04 驱动 | **Linux + NVIDIA 驱动 + nvidia-container-toolkit** | 版本记入 `08A`（对应 `08` §7.4 P4-1） |
| 容器运行时 | Docker Engine（指定版本） | **Docker + `--gpus` 可用**（`docker run --gpus all nvidia/cuda:12.1-base nvidia-smi` 通过） | 判据换成 `nvidia-smi` 能进容器 |
| 卡探测 | `hy-smi` 8/8 | `nvidia-smi -L` 8/8，显存 **24GB**（不是 64GB） | **显存是硬差异**：`manifest.resources.gpuMemGB` 超 24 的模型在准入阶段就会被拒，这是预期行为，不是 bug |
| 卡位 `env{}` | `ROCR_VISIBLE_DEVICES=6` / `HIP_VISIBLE_DEVICES=0` | **`NVIDIA_VISIBLE_DEVICES=6` / `CUDA_VISIBLE_DEVICES=0`** ⚠️ | 只改 `slots.yaml`，**Agent 二进制不变**（用 `--config` 指向另一份文件）。**`CUDA_VISIBLE_DEVICES` 必须是 `0`**，填宿主卡号会导致 `device_count()==0`（见下） |
| 卡位 `dockerArgs[]` | `--device=/dev/kfd --device=/dev/dri --group-add video` | `--gpus '"device=6"' --ipc=host` | 同上 |
| 镜像基座 | `*-dtk26.04-py3.10` | **`*-cu121-py3.10`**，tag 带 **`-dev4090`**，存独立 Harbor 项目 | `11` §1.2 禁止原地覆写的红线同样适用 |
| 编排层 | 甲方 K8s（`drp-app`/`drp-compute`） | **k3s**（单机或 3 节点） | 业务侧 8 个部署单元照常；只有「存储类」「NodePort 段」两处小改，记入 `08A` |
| 权重目录 | `/var/drp/model-cache` | 同路径（**刻意保持一致**，避免两套路径习惯） | — |

> ### ⚠️ 卡位验收必须断言 GPU 真的可见（v1.4，2026-10-25 实测修正）
>
> **`NVIDIA_VISIBLE_DEVICES` 填宿主卡号，`CUDA_VISIBLE_DEVICES` 填容器内序号（恒为 0）**。两者串联过滤：`NVIDIA_VISIBLE_DEVICES=6` 已把可见范围缩到 1 张、它在容器内是第 0 个；再写 `CUDA_VISIBLE_DEVICES=6` 就是从一个只有 1 个元素的列表里取下标 6 → 空集。
>
> 后果：**容器正常启动、`nvidia-smi` 能看到卡、退出码 0，但 `torch.cuda.device_count()` 返回 0**，模型静默跑在 CPU 上。实测见 `08A` §4.2（6 组矩阵，其中两组为 0）。
>
> **因此现场验收判据从「容器 `Up`」升级为：容器内执行 `python -c "import torch; assert torch.cuda.device_count()==1"` 通过**，并核对 `torch.cuda.get_device_properties(0).uuid` 与 `slots.yaml` 声明的宿主卡一致。

**三条纪律（写死，不允许现场发挥）**

1. **不允许为 4090 改任何平台代码**。若发现「非要加个 if 才能跑」，说明是架构漏了抽象点，应该改 `slots.yaml`/manifest 的 schema，而不是加分支（`08` §7.2 硬约束 ①）。
2. **4090 上测出来的耗时、显存、复现等级一律标 `环境=dev4090`**，不得写进 `03` §5.2.1 的单件成本基线，也不得作为 `D-03-12` 容差签字依据（`08` §7.3）。
3. **验证环境不进生产清单**。`12` 的测试报告里，`环境=dev4090` 的结论只能证明「平台实现正确」，不能证明「模型在目标硬件上达标」；两者在报告模板里分成两个字段，不允许合并成一句「测试通过」。
4. **环境不可用时必须写「阻塞」而不是「跳过」**（v1.4 新增）。2026-10-25 首次实测时，该节点因 `/data` 使用率 95% 被 kubelet 打上 `node.kubernetes.io/disk-pressure:NoSchedule` 污点，**所有 Pod 无法调度**（加 toleration 强上则被 `Evicted`），k3s 侧验证因此中断。记录时必须写「阻塞 + 根因 + 解除条件」，写「跳过」等于把未知当已知（该环境项已登记为 `03B` 的 `D-34`）。

**与 `18-项目验收报告` 的关系**：验收必须在 DCU 生产环境重跑一遍 `12` 的 P1 用例，4090 的结果只能作为「提前发现问题的证据」，不能替代验收数据——这也是 `18` 至今未写的原因之一。

|---|---|
| 新模型版本上线 | 按 `07` §7 上线流程；注册中心 `model_registry` 新增版本，旧版本保留 |
| 能力默认指向 | 修改 `capabilities[].priority` 指向新版本；新建任务用新版本 |
| 历史任务 | 绑定 `model_version` 不变，重跑需显式指定版本 |
| 回退 | 改回 priority 指向旧版本，**无需重建镜像** —— 这就是版本并存的价值 |
| 镜像清理 | 旧版本镜像保留 ≥ 180 天（覆盖最长回溯需求），之后按 `15` 归档 |

### 8.3 数据回滚（最难，必须提前演练）

| 层 | 回滚方式 | RTO 目标 | 数据损失 |
|---|---|---|---|
| 结构化元数据 | PITR（WAL 归档）+ `pg_basebackup`，恢复到故障前时点（`15` §3） | ≤ 4h | 取决于归档间隔，目标 ≤ 5min |
| 对象存储 | MinIO 版本化 + 每日增量；误删走版本恢复 | ≤ 2h | 0（版本化保住） |
| 卡位与容器 | 回退 `slots.yaml` 到上一版本，Agent 收敛 | ≤ 15min | 0 |
| 权重 | 权重包分版本并存，回切软链/目录 | ≤ 30min | 0 |

> **纪律**：数据回滚**不与应用回滚合并**做。先回应用（分钟级、可逆），再评估是否需要回数据。合并操作是二次事故的常见来源。

### 8.4 上线失败的判定与回退决策

| 失败情形 | 判定 | 决策 |
|---|---|---|
| 业务服务无法就绪 | G1 未过 | **全量回退**：卸载新 release，保留数据库（迁移向后兼容时不需回数据） |
| 卡位起不来但业务正常 | G2 未过 | **降级上线**：能力标"维护中"，其余上线；48h 内修复 |
| ★ 条款失败且短期无法定位 | G3 未过 | **暂停上线**，回退到彩排通过的版本或保持旧环境；写《失败分析记录》 |
| 数据面异常（如 PITR 备份不可用） | G4 未过 | **不上线**，先修备份链路 |
| 上线后 72h 内错误率 > 5% | 运行期门 | 触发回退流程（负责人 1 人决策，无需会议） |

**回退权归属**：技术负责人（架构师）单点决策，PM 通知甲方。**不采用"多数表决"** —— 事故处置需要一个人说了算。

### 12.1 关于 Argo Workflows 的处置（已决策：不引入）

`03` 旧版 §11.3 把 Argo 列为工作流引擎，但 `09` 已决策 DCU 走 SSH + Docker。两者共存会带来"两套编排体系"的运维负担。三方案对比：

| 方案 | 结论 |
|---|---|
| A. 完全引入 Argo（业务 + CPU + DCU） | ❌ 与 `09` 冲突，DCU 上无法用 Argo |
| B. Argo 仅管 CPU 侧 Job，DCU 由平台调度 | ⚠️ 可行但需维护两套状态机 |
| **C. v1.0 不引入 Argo，`drp-workflow` 用自研轻量 DAG（DB 表 + 调度循环）** | ✅ **已采纳**。工作流本质是任务序依赖，规模 ≤ 10 节点，自研成本远低于 Argo 的运维与学习成本；保留 `WorkflowEngine` 接口，未来可换 |

> **决策状态**：已落入 `03` v1.1（§5.4、§11.3、§12 时序图、§13 风险表 AR-04 已关闭）。`07` §6.1/§6.4.1 与 `10` 目录树的 Argo 表述已同步清除。仅当甲方明确要求"使用 K8s 原生工作流引擎"时（D-13-04）才回退方案 B，并在 `11` 中补 Argo 的离线安装与 Chart 依赖。
