## 0. 一句话结论

**交付线独立成仓 `cnpharm-aidd`，从产品线 `develop@ce9a521` 分叉，此后单主干 `main` 开发，与产品线只保留单向、按需的 cherry-pick 关系。**

v1.0 设想的是「同一仓库里开 `cnpharm/*` 分支」，被本版取代的原因有两条：

1. **多人协作需要独立的权限与保护规则**。交付仓库要拉入甲方之外的实施、测试、前端多人，产品线仓库不该为交付人员开写权限。
2. **交付线要做的是减法，不是增量**。要在产品线里删掉约 8,900 行专属代码、改 38 个测试文件；留在同一仓库就等于每次产品线演进都要在交付分支上重新解一遍删除冲突，而交付期只有 3 个月。

## 2. 仓库关系

```
zyc6665/CPUmodel_V2  (产品线，私有)
  develop ──●──●──●──▶  持续演进，节奏放缓、慢慢完善
             │
             │ ce9a521  (标签 cnpharm-base-ce9a521，只存在于本仓库)
             ▼
zyc6665/cnpharm-aidd  (交付线，私有，独立仓库)
  main ──●──●──●──▶  单主干，3 个月冲刺交付
```

| 方向 | 是否允许 | 方式 |
|---|---|---|
| 产品线 → 交付线 | ✅ 允许，按需 | `git fetch upstream` + `git cherry-pick -x <sha>`，**必须带 `-x`** 记录来源 |
| 交付线 → 产品线 | ⚠️ 仅通用能力，逐条评估 | 从交付线摘独立 commit，用 PR 合回产品线 `develop`；**禁止整分支合并** |
| 双向自动同步 | ❌ 禁止 | 节奏差一个数量级，同步机制会在冲刺期变成负担 |

**交付线 → 产品线回收的三个准入条件**（同时满足才评估）：

1. 不含任何中国医药专属内容（靶点/口袋/候选物领域模型、甲方参数、LDAP 配置、离线路径）；
2. 不依赖交付线新增的领域表；
3. 有独立测试覆盖，脱离交付线上下文也能跑。

典型可回收项：`audit_log` 表、`upload_session` 分片上传、任务 SSE、`TaskStatus` 的 `QUEUED`/`TIMEOUT` 补充。

### 2.1 分叉点锚点

标签 `cnpharm-base-ce9a521` 打在 `ce9a521` 上，由仓库 ruleset `protect-base-tags` 保护（禁止删除、禁止移动）。

用途：任何时候都能精确回答「我们相对产品线改了什么」——

```bash
git log --oneline cnpharm-base-ce9a521..main      # 交付线相对产品线的全部改动
git diff --stat cnpharm-base-ce9a521..main        # 改了多少
```

这是验收和交接时最常被问的问题，别让这个标签丢掉。

## 3. 分支模型（交付仓库内部）

```
main ──●──●──●──●──▶        交付主干，受保护，随时可出包
        ╲   ╲
         ╲   ●── feature/target-entity-crud      功能
         ●────── fix/task-cancel-race            缺陷
```

| 分支 | 用途 | 从哪切 | 合到哪 | 保护 | 生命周期 |
|---|---|---|---|---|---|
| `main` | 交付主干 | — | — | 禁直推 + PR + CI 绿 | 全程 |
| `feature/<模块>-<主题>` | 新功能 | `main` | `main` | 无 | ≤ 5 工作日 |
| `fix/<模块>-<主题>` | 缺陷 | `main` | `main` | 无 | ≤ 2 工作日 |
| `refactor/<模块>-<主题>` | 不改行为的重构 | `main` | `main` | 无 | ≤ 5 工作日 |
| `docs/<主题>` | 文档 | `main` | `main` | 无 | ≤ 2 工作日 |
| `release/v1.x.y` | 交付候选 | `main` | `main` + tag | 禁直推 | 交付周期 |
| `spike/<主题>` | 技术验证 | `main` | **不合** | 无 | ≤ 3 工作日 |

**为什么主干叫 `main` 而不是 `develop`**：`docs/11-CICD与制品管理方案.md` 的 GitLab 流水线按 `main` 为主干设计（`feat/fix ──MR──▶ main`），交付线要能直接对应这份验收文档。产品线那套 `develop + beta` 双长期分支模型是为持续演进的产品节奏设计的，3 个月交付用不上——多一层集成分支只会让回滚变麻烦。

详细流程与提交规范见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 4. 提交规范

沿用产品线既有 commit 规范，但**每条提交必须带交付上下文**：

```
<type>(<scope>): <subject>

<body>

Refs: <PRD 编号 / 决策编号>
```

`type` 取 `feat|fix|refactor|docs|test|chore|perf|ci`；`Refs` 填中国医药需求编号（`M2-FR-06`）或决策编号（`D-25`）。

验收时按需求条款反查实现：

```bash
git log --grep="M2-FR-06" --oneline     # 该条款的全部实现提交
git log --grep="D-25" --oneline         # 该决策涉及的全部改动
```

三条设计决策：

1. **`pocket.selected` 用分区唯一索引**（`uq_pockets_selected_structure`，`sqlite_where=selected = 1` / `postgresql_where=selected = true`）而不是应用层判断——同一个结构只可能有一个选定口袋，这条不变式必须在数据库层成立，否则并发选定会同时成功（docs/04 §5.6）。`select_pocket` 先置旧选中为 false 再写新值，避免撞索引。
2. **`task_id` 只存字符串不建外键**——任务有独立归档与清理策略，领域表跟任务表做外键会让归档被外键卡住；追溯靠 `extra_data.domain` 里的 `target_id`/`protein_id`/`structure_id` 反查。
3. **结构文件只存 URN + sha256**（`file:{file_id}`），不复制文件内容到领域表——docs/04 §1 要求元数据入库、文件入对象存储；下载走 `/api/v1/files/{id}/download?token=...` 预签名 URL，导出接口返回的是文件清单而非文件本身。

另有一处反向改动：项目总览 `GET /projects/{id}/overview` 的 `counts` 新增 `targets`/`structures`/`pockets`（对应 docs/06 P-04 的统计卡），项目删除 `DELETE /projects/{id}` 增加领域表级联清理（`delete_project_domain_rows`），否则 `targets.project_id` 外键会阻断删除。

步骤 5 的实测结果（2026-10-25）：后端 `flake8 --select F401,F821,E9` 零告警；`alembic upgrade head` 43 张表 / `downgrade base` 通过；`pytest test/` 1339 passed / 6 failed（余下 6 个全是 Windows 环境差异）。

### 5.3 步骤 6 的加法结果（2026-10-25）

| 交付物 | 位置 | 说明 |
|---|---|---|
| 五张领域表 | `backend/app/models/compounds.py` | `compounds` / `candidates` / `candidate_sets` / `candidate_set_items` / `molecule_fingerprints`，字段口径见 docs/04 §7.1~§7.3、§5.7 |
| 迁移 | `backend/alembic/versions/20261026_02_compounds_and_candidates.py` | 幂等 upgrade/downgrade；`upgrade head` 后 48 张表 |
| RDKit 化学层 | `backend/app/chemistry/molecule_properties.py` | 一次解析出 InChIKey、分子式、分子量与 logP/TPSA/HBD/HBA/RotB/QED；ECFP4（2048 bit，打包 256 字节）/ MACCS（167 bit，21 字节）位向量与应用内 Tanimoto |
| 请求 schema | `backend/app/schemas/compounds.py` | 全部 `extra="forbid"`；`candidateIds`/`expectedVersion` 同时接受 camelCase 与 snake_case（docs/05 §5） |
| 领域服务 | `backend/app/services/domain_compounds.py` | 化合物去重、批量导入、配额、候选集乐观锁、相似性检索、比较矩阵、项目级计数与删除级联 |
| REST 路由 | `backend/app/api/v1/compounds.py` | docs/05 §4、§5 的 15 个端点，项目内集合挂在 `project_router` |
| 测试 | `test/test_compounds_api.py` | 26 个用例：去重、异常清单、SDF 解析、描述符、相似性、多肽、比较上限、指纹缓存、配额、乐观锁、导出、级联删除 |

四条设计决策：

1. **`compounds` 没有 `project_id`**——化合物是全平台去重主数据（`inchikey` 唯一），项目视图 `GET /projects/{id}/compounds` 只列被本项目候选物引用的分子。若把 `project_id` 写进化合物表，同一个分子在 A/B 两个项目就会各存一行，跨项目去重与相似性检索立刻失效（docs/04 §7.1 的 InChIKey 唯一约束正是为此）。
2. **指纹在化合物写入时就算好，不留待查询时补**——相似性检索是全表扫描 + `WHERE fp_ecfp4 IS NOT NULL`，缺指纹的分子会直接从结果里消失。`upsert_compound` 里直接调 `ensure_fingerprint`，`backfill_fingerprints` 只作为「升级 RDKit 后刷新历史数据」的运维入口。
3. **`candidates` 的形态约束写进数据库**——`ck_candidates_payload_matches_type` 要求 `SMALL_MOLECULE → compound_id NOT NULL`、`PEPTIDE → peptide_sequence NOT NULL`；否则「有多肽类型但既无序列也无分子」的脏行会一路传到生成与预测任务里，报错点会离现场很远。
4. **`candidate_set.version` 做乐观锁，冲突返 409 并带 `currentVersion`**——候选集是多人在同一项目里并发改的对象（docs/04 §5.6）。实现上注意 `UPDATE ... WHERE id=? AND version=?` 的 `rowcount == 0` 分支必须先 `rollback()` 再重查；**重查要用提前取出的主键字符串，不能用 ORM 实例的属性**，否则 rollback 使实例过期，取属性会触发隐式 IO 并抛 `MissingGreenlet`。

### 5.8 步骤 11 的时区口径统一（2026-10-25）

一个跨全仓的隐性缺陷：后端所有时间列都是**不带时区的 UTC**（`backend/app/common/time.py` 的 `utcnow()` 会 `replace(tzinfo=None)`），序列化时用裸 `isoformat()`，得到 `2026-10-25T13:00:00` 这种没有 `Z` 的字符串。前端 `new Date('2026-10-25T13:00:00')` 会**按本地时区解释**它——东八区用户看到的每个时间都晚 8 小时。这不是显示格式问题，是错误的时间。

| 层 | 改动 |
|---|---|
| 后端工具 | `backend/app/common/time.py` 新增 `isoformat_utc(value)`：naive 值补 `Z`，aware 值先归一到 UTC 再补 `Z` |
| 后端序列化 | `domain_targets.py`、`domain_compounds.py`、`traceability.py`、`api/v1/admin_audit.py` 四处 `_iso` 全部改为调用它；追溯包的 `exportedAt` 同步 |
| 后端筛选 | `api/v1/admin_audit.py` 新增 `_to_naive_utc(value)`，审计日志的时间范围筛选在比较前归一化——FastAPI 会把带 `Z`/`+08:00` 的入参解析成 aware datetime，直接比 naive 列在 PostgreSQL 下会按会话时区隐式转换，筛选窗口偏 8 小时 |
| 前端工具 | 新增 `frontend/src/utils/datetime.ts`：`parseServerDate`（无时区补 `Z`、纯日期补 `T00:00:00Z`、非法返回 `null`）、`formatServerDateTime` |
| 前端收敛 | `domain/admin/system-health.ts` 的 `formatAdminDateTime` 改为委托 `formatServerDateTime`，消除重复实现 |
| 测试 | 后端 3 条（时间戳带 `Z`、aware 筛选入参命中、`_to_naive_utc` 归一化）、前端 8 条（naive/空格/带 Z/带偏移/纯日期/空值/非法/格式化一致性） |

口径选择：**接受并显示 UTC**。全仓没有用户级时区字段，也没有 `timezone` 表；引入「按用户时区展示」需要先决定时区从哪里来（浏览器探测会在出差时改变历史记录的含义），这是产品决策而不是技术修补。当前做法是「时间在 API 上永远带 `Z`，前端按浏览器本地时区展示」，与 `docs/04` §3 的时间存储口径一致。

### 5.9 步骤 12 的分片上传收口（2026-10-26）

PR2（分片上传）合入时带着四条 reviewer 阻塞，登记为「已知未做」。这四条都不是风格问题，而是**会在生产规模下必然暴露的错误**，因此在步骤 10 收尾后单独立项收口。

| 阻塞 | 原实现的问题 | 收口方式 |
|---|---|---|
| **B1** 并发上报丢片索引 | `upload_sessions.parts` 是 JSON 列，只能整列读写：三个并发 `PUT /parts` 各自读到同一份旧列表，最后提交者覆盖前两个，DB 里只剩 `[3]`——**字节都在暂存里，索引却丢了**，断点续传直接失效 | 分片索引搬进 `upload_parts`（`(session_id, part_number)` 复合主键），写入走 `ON CONFLICT DO UPDATE`。行锁替代方案被否：SQLite 没有行锁，会让测试环境与生产行为不同 |
| **B2** 幂等键无唯一约束 | 服务层「先查后插」在并发下两个请求都看到空结果，落两行、返回两个 uploadId，客户端分片分叉到两个会话 | 加 `uq_upload_sessions_project_idem (project_id, idempotency_key)`；插入捕获 `IntegrityError` 后回滚重查，返回先落库的会话。PG 与 SQLite 下 NULL 都不参与唯一性，历史行不受影响 |
| **B3** 分片直写本地盘 | `parts_directory()` 写 `STORAGE_PATH/_uploads/{id}/`，完全绕过 `StorageBackend`；生产强制 `STORAGE_BACKEND=minio` 且 backend 容器不挂卷、多副本在不同节点 → 重启丢分片、换副本找不到片；`minio_upload_id` 恒 `None` | 新增 `backend/app/files/part_staging.py` 抽象：`LocalPartStaging`（本地目录）与 `ObjectPartStaging`（对象存储，每片一个独立对象）按 `STORAGE_BACKEND` 选择。**刻意不用 S3 原生 Multipart**——它只有 SDK 私有方法，且合并上限本来就要求服务端读一遍全部片 |
| **B4** 24h 过期从未生效 | `expires_at` 只在创建时写入，`PUT`/`complete`/`GET`/`DELETE` 四个入口都不校验；`EXPIRED` 全仓只有枚举定义，无清理任务 | 新增 `is_expired` / `expire_upload_session`，三个业务入口统一 `_require_active` 拦截（过期 → 置 EXPIRED + 清单 + 409）；新增 `backend/app/services/upload_maintenance.py` 的 `UploadSessionSweepLoop` 挂 lifespan 兜底（用户创建完就关页面时没有任何入口会再碰到该记录） |

顺带收的建议项：`S2` 合并改流式（原 `bytearray` 拼装 2GB 要常驻 2GB 内存，两个并发就 OOM；现在先统计字节数做校验、再逐片读 + 写临时文件 + 增量哈希，峰值内存只有一片）；`S3` 校验总字节数 == `declared_size`；`S4` 声明了 `sha256` 就落库并在合并后校验（新增 `declared_sha256` 列，对应 `docs/05` §4.2 的 42205）；`S7` 三张表 `updated_at` 从 `nullable=True` 纠正为 `nullable=False`；`S1` 合并上限从 256MB 放宽到 2GB（流式后不再受进程内存约束）。

**未做**：`S5` 分片 ETag 与 MinIO 口径统一的完整校验、`S6` 幂等 scope 改成 `{user_id}:{METHOD}:{path}`、`S8` `data_version` 表、`S9` `DataFile` 写入路径、`S11` 同名数据集并发去重。这些都不阻塞上传主链路，登记为后续项。

迁移 `20261028_01` 除了建表与加约束，还**搬数据**：`upload_sessions.parts` 里的 `[{partNumber, etag, size}]` 逐条迁进 `upload_parts`（`reported_at` 用会话的 `updated_at` 兜底），搬完才删列，因此可重复执行且不丢已收到的分片索引；加唯一约束前先查重复，有冲突则报中文错误而不是让数据库抛原生异常。实测：56 张表、`upgrade head` / `downgrade 20261027_03` / `downgrade base` 三步全通，legacy JSON 三条（含一条重复片号）迁成两行。

### 7.1 `main` 分支保护

不手敲 JSON——规则是交付纪律的一部分，必须可复核、可重放：

```bash
python scripts/setup_branch_protection.py            # 查看当前设置
python scripts/setup_branch_protection.py --apply    # 应用（管理员也不可绕过）
python scripts/setup_branch_protection.py --apply --approvals 1   # 成员到位后收紧
```

脚本里的 7 个必需检查（`后端规范检查`、`后端测试`、`前端构建`、`前端单元测试`、`离线合规扫描`、`部署配置校验`、`文档链接检查`）**必须与 `.github/workflows/ci.yml` 的 `job.name` 逐字一致**——写错一个字符，保护规则就在等一个永不出现的检查，PR 永远变不绿。`test_backend_lint_ci.py::test_every_ci_job_has_a_chinese_display_name` 守着这条。

`前端 E2E` 故意**不**纳入门槛：它只在 push 或 `base_ref == main` 时运行，PR 上根本不会产生该检查，纳入即死锁。

> **为什么默认 `enforce_admins: true`**：第一版脚本默认 `false`，结果验证时我直推 main 成功了——规则提示了「必须走 PR」和「缺少 7 项检查」，然后照样放行。管理员能绕过，保护就是装饰品，而管理员恰恰最容易顺手 `git push`。所以现在是默认禁止绕过，想允许得显式加 `--allow-admin-bypass`。
>
> **为什么单人期 `required_approving_review_count=0`**：唯一开发者无法 approve 自己的 PR，设 1 会把交付线锁死。成员到位后立刻改 `1`，并在仓库设置里勾选 *Require review from Code Owners* 让 CODEOWNERS 真正生效。

### 7.3 合入流程

squash merge（仓库只允许这一种），合完自动删分支。**注意 squash 会让工作分支与 main 失去祖先关系**，下一次开分支前必须 `git switch main && git pull`，否则 PR 会显示 `CONFLICTING`／`DIRTY` 并且不触发 CI。rebase 修法：

```bash
git fetch origin
git rebase --onto origin/main <原分支的旧基点> <工作分支>
git push --force-with-lease origin <工作分支>
```
