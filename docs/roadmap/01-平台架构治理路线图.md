# 平台架构治理路线图

## 1. 治理目标

当前平台已经积累了工具注册、任务执行、项目、Artifact、外部数据库、工作流、智能体、可视化等能力，但模块边界正在变得混乱。治理目标不是暂停产品建设，而是先把主线拉直，避免后续每新增一个模型或工具都要在前端、后端、工作流和智能体各改一遍。

治理目标：

- 统一工具和工作流的输入输出模型。
- 统一 Artifact 作为数据资产主线。
- 统一任务执行作为所有运行入口。
- 统一 Run Context 处理项目和默认工作空间。
- 统一重计算工具的执行器和资源画像。
- 统一预测、评分、实验实测和科学证据的语义边界。
- 统一候选决策、实验摘要回写和 DMTA 复盘的产品边界。
- 让新工具接入后自动进入工具库、工作流和智能体上下文。
- 稳定 Artifact Registry、Tool Contract、Result Manifest、Run Preparation、Task Command、Executor Gateway、Workflow Orchestration 等平台功能地基。

## 2. 当前主要问题

### 2.1 工具运行入口不一致

工具详情页、工作流节点独立运行、工作流全流程运行、智能体计划运行都在不同位置处理参数、文件、Artifact 和项目上下文。

影响：

- 同一个工具在不同入口表现不一致。
- 标准 Artifact 输入被部分 UI 误判为必须项目。
- 未来新增工具需要多处适配。

### 2.2 Artifact 输入输出边界不清

当前存在普通文件、Artifact、ArtifactVersion、semantic_type、artifact_type、标准 Artifact ref 等多套表达。

影响：

- 工作流连线容易出现语义不一致。
- 节点加载后可能丢失产物槽位。
- 可视化和下载难以按类型稳定复用。

### 2.3 工作流过度承担适配职责

工作流本应表达节点和边，但现在还承担工具字段匹配、结果绑定、节点任务恢复、预检错误解释等大量职责。

影响：

- 画布逻辑复杂。
- 新工具进入工作流需要额外修补。
- 用户看到的错误难以理解。

### 2.4 重计算部署抽象不足

分子对接、MD、深度学习模型等重任务需要 Docker、SSH、K8s、Slurm 等执行环境，但目前还没有统一资源画像和集群作业接口。

影响：

- 工具部署方式不稳定。
- 任务取消、日志、状态同步和结果回收难统一。
- 运维无法做容量规划。

### 2.5 文档体系碎片化

现有 `docs/design`、`docs/plans`、`docs/guides` 中有大量有价值内容，但缺少当前版本的统一需求、功能、架构和部署基线。

影响：

- 设计讨论容易回到局部实现。
- 新人难理解平台整体。
- 后续需求难判断归属模块。

## 3. 治理原则

1. **先主线后细节**：先理清 Project、Artifact、Tool、Task、Workflow、Agent，再改页面细节。
2. **先契约后 UI**：新工具先过 Tool Contract，再进入工具库和工作流。
3. **先标准 Artifact 后文件字段**：工作流和智能体优先使用标准 Artifact 类型，不直接依赖私有文件字段。
4. **先统一入口后新增功能**：工具详情页、节点独立运行、工作流运行应共享 Task 创建和 Artifact Binding 模型。
5. **先轻量实现后集群化**：RDKit 等轻量工具可内置，重计算工具统一走执行器和资源画像。
6. **不做大爆炸重写**：保留 legacy 兼容路径，逐步把新能力迁到标准契约。
7. **先地基后扩展**：新模型和新工具扩展前，先保证功能地基的 Interface 可复用、可预检、可验收。

## 4. 阶段路线

### 阶段 0：文档基线

目标：先形成统一语言和模块地图。

交付：

- 平台需求说明书。
- 平台功能模块说明书。
- 平台总体架构。
- 核心领域设计。
- 部署与计算资源架构。
- 平台功能地基设计。

验收：

- 后续需求能明确归属模块。
- 工具、任务、Artifact、工作流、Agent 的边界可解释。
- 团队不再只围绕单个 bug 推动架构变化。

### 阶段 1：Artifact / Tool / Task 主线统一

目标：让工具独立运行、项目运行、工作流运行使用同一套输入输出模型。

工作项：

- 收敛 Tool Contract。
- 建立 Run Preparation Module，并将 Artifact Binding Resolver 收敛为内部决策能力。
- 标准化 Run Context。
- 移除前端对标准 Artifact 输入的硬编码阻断。
- 后端任务准备逻辑成为权威。

验收：

- 工具无项目可运行。
- 项目内可选择 Artifact 或上传。
- 标准输出自动有归属项目或默认工作空间。
- 新工具声明 Artifact 输入输出后可被工作流发现。

### 阶段 2：工作流傻瓜化

目标：用户只拖节点、连线、补必要输入，平台自动处理上下游绑定。

工作项：

- 工作流节点从 Tool Contract 派生输入输出槽位。
- 连线基于标准 Artifact 类型校验。
- 预检错误按研发语言解释。
- 保存工作流恢复节点任务和 Artifact 绑定。
- 节点内可视化和结果中心统一使用 Artifact Renderer。

验收：

- Fetch PDB -> 蛋白处理 -> LVpocket -> 分子生成 -> ADMET 等流程可连续运行。
- 用户不需要手动填写上游文件路径。
- 错误提示能指出缺文件、缺准备、格式不匹配或上游未完成。

### 阶段 3：药物研发工具体系补全

目标：把药物研发常用工具按标准 Artifact 接入。

工具范围：

- 外部数据库：PDB、PubChem。
- 蛋白处理：去水、加氢、质子化、格式转换。
- 配体处理：2D/3D、构象生成、格式转换。
- 口袋预测：LVpocket。
- 分子生成。
- ADMET。
- 毒性。
- 合成可及性。
- 分子对接。
- MD。
- 打分重排。

验收：

- 每类工具都有标准输入输出。
- 每类工具能单独运行，也能进入工作流。
- 结果可视化和下载稳定。

### 阶段 3.5：科学结果和候选反馈治理

目标：让平台结果能被研发人员用于候选复核，而不是只停留在文件下载和任务成功。

工作项：

- 固定分子身份、结构状态、endpoint、单位、方向和失败状态语义。
- 为预测、生成、打分和筛选工具补模型卡、验证记录和适用域说明。
- 建立 CandidateSet、CandidateDecision、AssayResult、PredictionMeasurementLink 和 DesignCycle 的领域边界。
- 引入候选决策快照、实验摘要导入预览和预测-实测比较。
- 明确平台不替代 ELN/LIMS，不自动触发实验或再训练。

验收：

- 候选表能区分预测、评分、实测、证据等级、适用域和不可比状态。
- 基础 ADMET 至少有一个登记 endpoint、模型版本和证据附件。
- 实验导入能保留拒绝行、删失值、重复测量和单位转换记录。
- 预测-实测比较只在通过身份、endpoint、单位和 protocol 规则时计算误差。

### 阶段 4：部署和资源调度统一

目标：重计算工具可通过 Docker、SSH、Remote API、K8s、Slurm 统一部署和调度。

工作项：

- 统一 ResourceProfile。
- 统一 Executor Adapter 接口。
- SSH Job 完善取消、日志、状态同步、输出回收。
- Docker 工具标准输入输出目录。
- 设计 K8s Job Adapter。
- 设计 Slurm Adapter。

验收：

- 工具注册时能选择执行器和资源画像。
- 工作流预检能展示资源需求。
- 长时任务能取消、重试、查看日志和收集输出。

### 阶段 5：智能体与自动化增强

目标：智能体基于稳定平台契约做规划，而不是绕过平台。

工作项：

- Agent 使用 Tool Contract 和 Artifact registry 作为工具知识源。
- Agent 生成工作流草稿。
- Agent 根据预检问题建议补输入、加处理节点或转换节点。
- Agent 解释结果和下一步实验建议。

验收：

- Agent 推荐的工具可执行。
- Agent 生成的工作流可保存和运行。
- Agent 不产生无法被平台验证的虚假节点。

## 5. 暂缓事项

以下事项不应在主线收敛前优先展开：

- 大规模重写工作流前端。
- 未定义标准 Artifact 的新药研工具批量接入。
- 直接上 K8s/Slurm 而不统一 Executor Adapter。
- 给每个工具写前端专属适配。
- 过早做复杂自动编排循环。
- 重做权限系统或计费系统。

## 6. 决策记录

| 决策 | 结论 |
| --- | --- |
| 工具是否必须项目内运行 | 否，工具可独立运行；项目是运行上下文，不是工具契约 |
| 标准输出是否必须有归属 | 是，必须归属项目或默认工作空间 |
| 工作流是否手动映射字段 | 默认不手动，基于 Artifact Slot 自动绑定 |
| 新工具是否需要工作流适配 | 不应需要，只要 Tool Contract 标准 |
| RDKit 轻量工具是否必须远端部署 | 不必须，可作为平台内置工具节点 |
| 对接/MD 是否平台内置 | 不建议，应通过执行器和资源调度部署 |
| 运行成功是否等于科学验证 | 否，运行验证和科学证据等级必须分开展示 |
| 实验反馈是否替代 ELN/LIMS | 否，平台只保存受控摘要、外部引用和研发决策链路 |

## 8. 近期推荐工作顺序

1. 冻结当前文档基线，作为后续需求评审依据。
2. 清点现有功能与文档模块映射，标记重复、错位和缺口。
3. 按平台功能地基设计冻结 Artifact Registry、Tool Contract、Result Manifest 和 Run Preparation 的 Interface。
4. 设计并实现 Run Preparation Module。
5. 修正工具详情页、节点独立运行和工作流运行的输入模型。
6. 以 Fetch PDB -> Protein Preparation -> LVpocket 作为第一条标准验收链路。
7. 再扩展 ADMET、毒性、对接、MD 等工具模板。
8. 将 K8s / Slurm Adapter 作为重计算工具生产化的独立阶段，不和 UI 优化混在一起。
9. 冻结 Architecture Kernel Interface，再逐步替换 workflow、tool detail、agent 中的重复逻辑。
10. 先固化标准 Artifact 驱动的 BindingDecision 状态机，再进入 Run Preparation 代码施工。
11. 先补基础 ADMET 的真实 endpoint、模型卡和证据附件，再扩展多模型比较和质量看板。
12. 候选决策和实验回写先按 V1.1 做受控导入与快照，DesignCycle 多轮复盘放入 V2。
