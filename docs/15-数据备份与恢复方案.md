## 0. 本文档要解决的六个问题

1. **"备份什么"** —— 不是只备份数据库。平台的资产分为**结构化元数据、对象文件、配置与代码、模型权重**四层，各有不同生命周期，混着备份是最常见的错误（§2）。
2. **"多久备一次、留多久"** —— DRP-NFR-09 只要求"定期备份"，本文必须给出可验收的具体频率与保留期（§3）。
3. **"怎么恢复"** —— 恢复比备份难十倍。必须给出四种真实场景的逐步操作，而不是一句"用 pg_restore"（§4）。
4. **"备份备份本身"** —— 备份介质单点、备份文件未验证、备份脚本静默失败，是数据事故的三大来源（§5、§6）。
5. **"怎么证明能恢复"** —— 必须有定期恢复演练机制与判据，否则备份形同虚设（§7）。
6. **"删了的数据算谁的"** —— 软删除 90 天（`01` BR-3）、审计不可删、项目归档只读，这些规则要落到备份与恢复语义上（§8）。

**不在本文档范围**：集群层面高可用与故障转移（见 `03` §8.1、`14` §7）、应用回滚（见 `13` §8.1）、日常监控告警（见 `14`）。

## 1. 备份原则

| 编号 | 原则 | 落地要求 |
|---|---|---|
| BK-01 | **分层备份，不混装** | 四类资产独立备份通道与独立保留策略，禁止把 DB dump 和对象文件打进同一个包 |
| BK-02 | **备份必须可验证** | 每个备份产物带 SHA-256 清单，备份流程自带校验步骤；校验失败视为备份失败 |
| BK-03 | **3-2-1 原则（离线内网变体）** | ≥ 3 份副本、≥ 2 种介质、≥ 1 份异地/异机存放（甲方内网内） |
| BK-04 | **恢复优先于备份** | 备份方案的设计以"能不能在 4 小时内恢复业务"为验收标准，而不是以"备份了多少 TB" |
| BK-05 | **备份失败即告警** | 任何一次备份失败必须触发 P2 告警（`14` AL-17），不允许静默 |
| BK-06 | **恢复可审计** | 每次恢复操作记录发起人、原因、范围、源备份、结果，进入审计日志 |
| BK-07 | **脱敏后离场** | 任何导出到内网之外的介质（如送检、演练带回）必须脱敏并审批 |

## 2. 备份对象清单（四层资产）

### 2.1 全景表

| 层 | 对象 | 载体 | 变更频率 | 关键性 | 备份方式 |
|---|---|---|---|---|---|
| **L1 结构化元数据** | `project` / `target` / `protein` / `compound` / `candidate` / `task` / `task_input_snapshot` / `artifact` / `workflow_*` / **`decision_record` / `decision_item`** / `model_registry` / `*_result` / `audit_log` | PostgreSQL 15 | 高（每分钟） | **最高** | `pg_basebackup` 全备 + WAL 连续归档（PITR） |
| **L2 对象文件** | 分子/蛋白结构文件、计算结果（PDB/SDF/CSV）、报告、MD 轨迹、2D 渲染 SVG | MinIO（`drp-assets`/`drp-results`/`drp-bulk`/`drp-logs`） | 中（小时级） | 高 | 版本化 + 每日增量 + 每周全量 |
| **L3 配置与代码** | Helm values、K8s Secret（加密后）、`slots.yaml`、Agent 配置、CI 流水线、源码 | Git + 现场配置目录 | 低（按变更） | 高（否则无法重建环境） | Git 版本化 + 每次变更快照导出 |
| **L4 模型资产** | 模型权重包、`manifest.yaml`、L0/L1/L2 镜像 | `/var/drp/model-cache`、Harbor | **极低（仅升级时）** | 高（重新获取代价极大） | 永久归档 + SHA-256 清单 + 镜像 digest 记录 |
| （补充）中间件状态 | Redis 中的非持久缓存 / RabbitMQ 队列 | Redis / RabbitMQ | 高 | 低 | **不备份**（设计为可重建，见 §2.3） |

### 2.2 为什么 L1 和 L2 必须分开

| 理由 | 说明 |
|---|---|
| 恢复粒度不同 | 误删单个项目 → 只回滚部分 L1 记录 + 对应 L2 前缀；不需要整库回滚 |
| 体型差异巨大 | L1 首年 ≤ 200GB（`04` §14），L2 可达 5TB。混备会导致每次全备都是 TB 级 |
| 保留期不同 | L1 需要按 PITR 天级保留；L2 中 MD 轨迹按 180 天生命周期（`03` §4.5），不应与 DB 同策略 |
| 一致性耦合 | 两者的关联靠 `artifact.urn` + `sha256`。**恢复时必须保证"DB 记录指向的对象存在"**，见 §4.4 |

### 2.3 明确不备份的对象

| 对象 | 理由 | 重建方式 |
|---|---|---|
| Redis 缓存（权限、元信息、热点列表） | 全部为可重算的派生数据 | 清空后服务自动预热 |
| RabbitMQ 队列消息 | 任务真相在 `task` 表，队列可重放 | 从 `task` 表按状态重建待消费消息（见 §4.5） |
| 任务工作目录 `/var/drp/work` | 中间过程，产物已上传 MinIO | 不重建；重跑任务 |
| Prometheus TSDB、Loki 日志索引 | 运维数据，非业务数据（日志原文件在 `drp-logs` 桶） | 不重建 |
| K8s etcd | 由甲方集群自身备份机制负责 | 甲方职责（需书面确认，见 D-15-02） |

## 3. 备份策略

### 3.1 L1 结构化数据（PostgreSQL）

| 类型 | 频率 | 保留 | 存储位置 | 说明 |
|---|---|---|---|---|
| 基础全备 `pg_basebackup` | 每日 02:00 | 30 天 | 备份盘 `/backup/pg/base/` + MinIO `drp-backup/pg/base/` | 物理备份，可配合 WAL 做 PITR |
| WAL 连续归档 | 实时（`archive_command` 推送） | **30 天** | MinIO `drp-backup/pg/wal/` | RPO 的决定因素 |
| 逻辑备份 `pg_dump -Fc` | 每周日 03:00 | 90 天 | MinIO `drp-backup/pg/logical/` | 用于单表/单项目恢复与版本跨大版本迁移 |
| 迁移前快照 | 每次 `alembic upgrade` 前 | 保留 5 个版本 | 同上 | 重大变更的专用回退点 |
| 审计表 `audit_log` 独立导出 | 每月 1 日 | **≥ 1 年**（等保） | 独立前缀 + 只读账号 | 与业务数据分离保留 |

> **RPO 计算**：WAL 归档间隔决定 RPO。`archive_timeout = 60s` 保证最坏 60 秒产生一次归档，配合异步流复制（`03` §8.1 主备）可做到 **RPO ≤ 5 分钟**（含故障发现与切换时间）。

### 3.2 L2 对象文件（MinIO）

| 桶 | 内容 | 备份方式 | 频率 | 保留 |
|---|---|---|---|---|
| `drp-assets` | 输入资产（结构、序列、数据集） | 版本化 + `mc mirror` 增量 | 每日 01:00 | 版本 ≥ 90 天，删除保护 90 天 |
| `drp-results` | 计算结果与报告 | 版本化 + 增量 | 每日 01:00 | 90 天（与 DB 同步期） |
| `drp-bulk` | MD 轨迹等大文件 | 增量；**全量仅每季** | 每日增量 | 生命周期 180 天（`03` §4.5） |
| `drp-logs` | 日志归档 | 增量 | 每日 | 180 天 |
| `drp-backup` | 备份落地点（DB 备份、清单） | 不备份自身（见 §6） | — | — |
| `drp-temp` | **分片上传临时区**（`04` §5.8 `upload_session`）、导入中间文件 | **不备份**（可重新上传） | lifecycle：未完成分片 7 天自动 `AbortIncompleteMultipartUpload`，对象 30 天 `Expiration` | — |
| `drp-models` | 模型权重与镜像导出物（`11` 制品） | **不备份**（可由 Harbor / 离线包重建，见 `11` §7） | 随版本保留，旧版本 3 个 | — |

**备份目标**：独立的 MinIO 实例或独立存储池（甲方提供），**不得与生产桶位于同一节点组**（BK-03）。

> **`drp-temp` / `drp-models` 为何不备份**（v1.2 补）：这两个桶装的是**可重建数据**——`drp-temp` 是上传中的临时分片（源文件在用户手上，备份它只会让备份窗口变长），`drp-models` 是制品（Harbor 与离线安装包才是真源，`11` §7）。把可重建数据纳入备份只会稀释 RTO 预算。**但必须配 lifecycle**：`drp-temp` 若不清理，失败的上传会长期占盘——这是运维最常漏的一条（对应 `14` C-13）。

### 3.3 L3 配置与代码

| 对象 | 方式 | 频率 |
|---|---|---|
| Helm values / K8s manifests | Git（内网 GitLab `11`）；每次变更留 tag | 每次变更 |
| K8s Secret（含凭据） | 导出为**加密包**（age/GPG 公钥加密） | 每次变更 |
| `slots.yaml` / Agent 配置 | Git + 随交付包归档 | 每次变更 |
| 现场已应用的实际状态 | `kubectl get all -o yaml` 导出快照（去除 status） | 每周 + 每次重大变更后 |
| Git 仓库本体 | 由 GitLab 自身备份 + 每周 `git bundle` 到备份盘 | 每周 |

### 3.4 L4 模型资产

| 对象 | 方式 | 保留 |
|---|---|---|
| 模型权重 | 与交付包同源，永久归档 2 份（生产机本地 + 备份盘） | **永久** |
| `manifest.yaml` + SHA-256 清单 | 随权重同目录归档；同时写入 `model_registry` 元数据 | 永久 |
| L0/L1 镜像 | Harbor 保留全部版本；关键版本额外 `docker save` 归档 | 永久（L0/L1）；L2 保留 ≥ 180 天 |
| 镜像 digest 记录 | 写入 `task.image_ref` 与发布记录 | 与任务同周期 |

> **纪律**：权重是最贵的资产（重新获取需厂商配合与安全审查）。**任何情况下不得只保留一份权重**。

### 3.5 备份日历（一张图看清什么时候在跑什么）

| 时间 | 任务 | 预计耗时 | 影响 |
|---|---|---|---|
| 每分钟 | WAL 归档 | 秒级 | 无 |
| 每日 01:00 | MinIO 增量（assets/results） | 10~90min | 无（只读源） |
| 每日 02:00 | PG 基础全备 | 20~60min | 轻微 IO 压力（在低峰） |
| 每日 03:00 | 备份产物完整性校验 | 5~15min | 无 |
| 每周日 03:00 | PG 逻辑备份 | 10~30min | 无 |
| 每周日 04:00 | K8s 状态快照 + `git bundle` | 5min | 无 |
| 每季 | MinIO 全量（bulk） | 数小时 | IO 压力显著，需公告 |
| 每月 1 日 | 审计表导出 + 月度恢复抽验 | 30~60min | 无 |
| 每季 | **恢复演练**（`14` §8.4） | 半天（在 staging） | 不影响生产 |

## 4. 恢复场景与步骤

### 4.1 恢复能力矩阵（先定义"能恢复到什么程度"）

| 场景 | 手段 | RTO | RPO |
|---|---|---|---|
| R-A 单个项目误删（软删除后的 90 天内） | 应用层回收站恢复 | ≤ 15 分钟 | 0 |
| R-B 单条/批量记录误改 | 逻辑备份 + 定向恢复 | ≤ 1 小时 | 取决于最近备份（≤ 7 天） |
| R-C 整库回滚到某时点 | PITR（base + WAL） | **≤ 4 小时（目标 2 小时）** | **≤ 5 分钟** |
| R-D 对象文件误删/损坏 | MinIO 版本恢复 / 增量回滚 | ≤ 2 小时 | 0（版本化） |
| R-E 整机/整环境重建 | 交付包 + 备份 + L3 配置 | ≤ 8 小时 | 见各层 |
| R-F 灾难（机房级） | 异地备份介质 + 完整重建 | ≤ 24 小时 | 按最近备份 |
| R-G 模型/工具版本回退 | 版本并存 + 切换 | ≤ 30 分钟 | 0 |

### 4.2 R-A：项目级恢复（最高频，必须最快）

```bash
# 前提：project 表有 deleted_at（软删除，01 BR-3 保留 90 天）
# 1) 定位项目与保留期
psql -c "select id,name,deleted_at,now()-deleted_at as age from project where deleted_at is not null order by deleted_at desc;"

# 2) 若在 90 天内：应用层恢复（推荐，走平台 API，自动恢复关联对象前缀）
curl -X POST https://<平台>/api/v1/admin/projects/{projectId}:restore -H "Authorization: Bearer <admin>"

# 3) 若已超过 90 天：需从逻辑备份做定向恢复（见 R-B）
```

> **纪律**：项目恢复**必须走平台 API**，不要直接 `UPDATE project SET deleted_at=NULL` —— 后者不会恢复成员、配额、对象存储前缀，会留下孤儿数据。

### 4.3 R-C：整库 PITR 恢复（最关键的场景）

**前置检查（恢复前必须完成）**

- [ ] 明确目标恢复时点 T（精确到秒，用业务事件时间而非模糊描述）
- [ ] 确认该时点所需的 WAL 段全部存在于归档（`pg_waldump` 或归档清单核对）
- [ ] 通知甲方：**恢复期间系统只读或停机**，需公告窗口
- [ ] 若可能，先在 `staging` 用同样备份做一次恢复验证再操作生产

**步骤**

```bash
# 1) 隔离：停写入。将业务服务副本数置 0（保留网关，返回维护页）
kubectl -n drp-app scale deploy --all --replicas=0
kubectl -n drp-app scale deploy drp-scheduler --replicas=0

# 2) 保全现场：把当前数据目录改名，不删除（事后可对比）
systemctl stop postgresql || kubectl -n drp-data scale sts <pg> --replicas=0
mv /var/lib/postgresql/15/main /var/lib/postgresql/15/main.failed.$(date +%s)

# 3) 取最近的基础全备恢复
mkdir -p /var/lib/postgresql/15/main && chown postgres:postgres /var/lib/postgresql/15/main
pg_basebackup -D /var/lib/postgresql/15/main -h <backup-host> -U replicator -Fp -Xs -P
# 或从归档 tar 解包：tar -xzf /backup/pg/base/base-YYYYMMDD.tar.gz -C /var/lib/postgresql/15/main

# 4) 写恢复目标（精确到秒，UTC）
cat > /var/lib/postgresql/15/main/postgresql.auto.conf <<'EOF'
restore_command = 'wal-g wal-fetch %f %p'
recovery_target_time = '2026-10-20 08:15:00+00'
recovery_target_action = 'promote'
EOF
touch /var/lib/postgresql/15/main/recovery.signal

# 5) 启动并等待 promote
systemctl start postgresql
psql -c "select pg_is_in_recovery(), now();"    # 应为 f（已 promote）

# 6) 一致性校验（关键，不可跳过）
psql -c "select count(*) from task;"
psql -c "select count(*) from artifact where urn is null;"          # 应为 0
psql -c "select count(*) from information_schema.tables where table_schema='public';"
psql -c "select max(created_at) from audit_log;"                     # 与目标时点吻合

# 7) 恢复业务
kubectl -n drp-app scale deploy drp-scheduler --replicas=1
kubectl -n drp-app scale deploy --all --replicas=<原值>
```

**恢复后必做**：① 与 L2 一致性核对（§4.4）；② 任务补偿（§4.5）；③ 记录恢复报告（§8.3）。

### 4.4 L1 与 L2 的一致性核对（最容易漏的一步）

PITR 只回滚了数据库，对象存储没有回滚。这会产生两类不一致：

| 不一致类型 | 现象 | 处置 |
|---|---|---|
| **孤儿对象**（存在但 DB 无记录） | 对象存储里有文件，`artifact` 表无对应行 | 暂不删除，标记为孤儿并计入报告；确认后按保留期清理 |
| **悬空引用**（DB 有记录但对象不存在） | `artifact.urn` 指向的对象在恢复时点后才写入 | **严重**：把对应任务置为 `FAILED`，产物置 `INVALID`，通知用户重跑 |

**核对脚本（必须写成工具，不靠人眼）**

```bash
# 从 DB 导出期望清单
psql -At -c "select urn, sha256 from artifact where created_at < '<T>';" > /tmp/expect.txt
# 从 MinIO 导出实际清单（限相关前缀）
mc ls --recursive --json drp-local/drp-results | jq -r '"\(.key) \(.etag)"' > /tmp/actual.txt
# 双向比对
comm -23 <(sort /tmp/expect.txt) <(sort /tmp/actual.txt)   # 悬空引用（DB 有、对象无）
comm -13 <(sort /tmp/expect.txt) <(sort /tmp/actual.txt)   # 孤儿对象（对象有、DB 无）
```

> 该脚本的产出是**恢复报告的核心附件**，也是 `12` TC-NFR 的验收证据。

### 4.5 恢复后的任务补偿

数据库回滚会把"已提交但未完成"的任务带回旧状态，需按状态机（`03` §3.4）补偿：

| 恢复后状态 | 处置 |
|---|---|
| `RUNNING`（但实际容器早已结束） | 查 Agent 侧是否还有容器；无 → 置 `FAILED` 并生成重试建议 |
| `QUEUED` | 保留，重新入队（注意幂等：同 `task.id` 不得重复派发） |
| `SUCCEEDED`（产物在 DB 有、对象缺失） | 转为 `FAILED`（`INVALID`），见 §4.4 悬空引用 |
| `CREATED` | 保留，由用户重新提交 |

**幂等要求**：重放队列时用 `task.id` + `idempotency_key` 去重；Agent 侧派发前校验卡位真实状态，避免"一卡两用"。

### 4.6 R-D：对象文件恢复

```bash
# 单对象版本恢复（版本化已开启）
mc cp --version-id <vid> drp-backup/drp-results/<key> drp-local/drp-results/<key>

# 前缀批量回滚（误删目录）
mc mirror --overwrite --remove=false drp-backup/drp-results/<prefix>/ drp-local/drp-results/<prefix>/

# 恢复后校验
mc stat drp-local/drp-results/<key>   # 比对 size 与 etag 与 DB 中 sha256
```

### 4.7 R-E：整环境重建顺序（灾难恢复）

| 顺序 | 动作 | 依赖 |
|---|---|---|
| 1 | 准备硬件与 OS、K8s 集群（甲方） | 甲方 |
| 2 | DCU 驱动 + DTK 26.04（厂商） | 甲方/厂商 |
| 3 | 导入介质（`13` §5）、建 Harbor 项目 | — |
| 4 | 恢复 L3 配置（Helm values、Secret 解密、`slots.yaml`） | 备份盘 |
| 5 | 初始化中间件（空库） | — |
| 6 | **恢复 L1 数据库**（§4.3） | 步骤 5 |
| 7 | **恢复 L2 对象**（§4.6）或先挂空桶后按需回灌 | 步骤 5 |
| 8 | 部署 Agent 与常驻容器（`13` §6） | 步骤 2/3/4 |
| 9 | 恢复 L4 权重并校验 SHA-256 | 步骤 3 |
| 10 | 一致性核对（§4.4）+ 任务补偿（§4.5） | 步骤 6/7 |
| 11 | 冒烟（`13` §7.3） | 全部 |
| 12 | 恢复审计与监控告警 | — |

> **顺序不可乱**：先 DB 后对象，可让"悬空引用"在有备份可补时被尽快发现；反之先对象后 DB 会出现大量孤儿对象且难以判断。

## 5. 备份执行与校验机制

### 5.1 备份执行的责任链

| 环节 | 责任人 | 机制 |
|---|---|---|
| 触发 | 定时（K8s CronJob / 主机 cron） | 不依赖人工 |
| 执行 | 备份 Job | 幂等，失败重试 2 次 |
| 校验 | 同 Job 内校验步骤 | SHA-256 + 可读性 + 元数据 |
| 上报 | Pushgateway → Prometheus | 成功/失败/耗时/大小 |
| 告警 | `14` AL-17 | 失败即 P2 |
| 留档 | 备份清单写入 `drp-backup/manifest/` | 每日追加 |

### 5.2 校验的三个层次

| 层次 | 内容 | 频率 |
|---|---|---|
| L1 完整性 | 备份文件 SHA-256 与记录一致、可解包 | 每次 |
| L2 可用性 | 在临时 PG 实例上 `pg_verifybackup` / 恢复到一个 scratch 库并 `select count(*)` | 每日（PG）、每周（对象抽样） |
| L3 业务可用性 | 恢复后跑冒烟关键查询（项目数、任务数、最近产物可下载） | 每月抽验 + 每季演练 |

> **反模式**："备份文件存在"不等于"备份可用"。必须至少有 L2 层校验。

### 5.3 备份窗口与业务影响控制

| 控制 | 做法 |
|---|---|
| 避开业务高峰 | 全备在 01:00~04:00 |
| IO 限速 | `pg_basebackup --max-rate=200M`；`mc mirror` 限制并发 |
| 不与计算任务抢带宽 | DCU 机产物上传与备份错峰；大文件全备只在周末 |
| 停不下的任务 | 备份**从不停止**任务；仅在 PITR 恢复时才停业务写入 |

## 6. 备份介质与防"备份本身失效"

### 6.1 介质布局（3-2-1 的内网落地）

| 副本 | 位置 | 介质 | 内容 |
|---|---|---|---|
| 副本 1（在线） | 生产 MinIO `drp-backup` 桶 | SSD/NVMe | 全部备份 |
| 副本 2（近线） | 独立备份服务器 `/backup`（不同物理机） | HDD 阵列 | DB 全备 + 逻辑备份 + 配置 |
| 副本 3（离线/异地） | 移动硬盘或甲方异机房的 NAS | 离线介质 | 每周/每月归档 + 权重 + 交付包 |

> **异地**在甲方单机房场景下，应与生产**不同楼宇/不同机柜供电域**，避免同一次事故全灭。若甲方只有单机房，则副本 3 作为离线介质由我方保管（需甲方书面同意）。

### 6.2 介质容量规划

| 项 | 估算 | 说明 |
|---|---|---|
| PG 基础全备 | 200GB × 30 份 ≈ 6TB | 开启压缩后约 2~3TB（`pg_basebackup -z`） |
| WAL 归档 | 每日 10~30GB × 30 天 ≈ 0.9TB | 与写入量相关 |
| PG 逻辑备份 | 100GB × 13 周 ≈ 1.3TB | 压缩后 0.4TB |
| MinIO 增量 | 每日 20~100GB | 与计算量相关 |
| MinIO 全量（季） | 5TB × 4 次/年，保留 2 份 | 仅 `bulk` 季备 |
| 权重与镜像 | 40~70GB | 固定 |
| **首年合计（压缩后）** | **约 12~20TB** | 需在 `13` P1 阶段向甲方确认存储供给予 |

### 6.3 防止"备份静默失败"的机制

| 机制 | 说明 |
|---|---|
| 心跳式监控 | 每日备份 Job 若未在规定时间完成 → 触发**缺失告警**（不是只有失败才告警） |
| 偶发破坏性自检 | 每月抽一份随机备份恢复到一个 scratch 环境，验证可用 |
| 备份大小趋势监控 | 备份体积异常缩小 50% 以上 → 告警（常见于备份了空库） |
| 权限双人 | 备份目录写权限与删除权限分离；删除操作需审批 |

## 7. 恢复演练制度

### 7.1 演练频次与范围

| 类型 | 频次 | 环境 | 范围 | 记录 |
|---|---|---|---|---|
| 月度抽验 | 每月 | `staging` | 随机 1 份备份 + 单项目恢复 | 抽验记录 |
| 季度演练 | 每季 | `staging` | **完整 PITR** + 一致性核对 + 任务补偿（R-C 全流程） | 演练报告（`14` §8.4/8.6 模板） |
| 上线前演练 | 1 次 | `staging` | 同季度演练 | 交付材料附件 |
| 灾难演练 | 每年（或按甲方要求） | 隔离环境 | 整环境重建（R-E） | 演练报告 |

### 7.2 判据（不通过即整改）

| 指标 | 判据 |
|---|---|
| RTO | PITR ≤ 4 小时（目标 2 小时） |
| RPO | 数据丢失 ≤ 5 分钟 |
| 一致性 | 悬空引用数 = 0；孤儿对象数有清单且已定责 |
| 完整性 | 恢复后冒烟（`13` §7.3）一次通过 |
| 可重复性 | 同一份备份连续两次恢复结果一致 |

### 7.3 演练报告必含字段

| 字段 | 说明 |
|---|---|
| 备份源（时间、路径、SHA-256） | 可复现 |
| 目标时点 T | 精确到秒 |
| 实际操作耗时分解 | 停写/取包/回放/校验/恢复业务各阶段 |
| 与 RTO/RPO 对比 | 达标与否 |
| 遇到的问题 | 脚本缺陷、文档缺失、权限问题 |
| 改进项与责任人 | 有跟进 |

## 8. 备份语义与业务规则的对应

### 8.1 软删除、归档与备份的关系

| 业务规则 | 出处 | 备份语义 |
|---|---|---|
| 项目删除为软删除，保留 90 天后物理清理 | `01` BR-3 | 90 天内走 R-A 快速恢复；超过 90 天需从备份取（DB 记录 + 对象前缀） |
| 项目归档后只读 | `01` BR-2 | 归档数据仍在备份范围内，不做特殊处理 |
| `audit_log` 只追加、不可删改 | `04` §5.4 | 独立导出，保留 ≥ 1 年；**备份不得包含"清理审计"的脚本** |
| `decision_record` / `decision_item` 只追加、不可改删 | `04` §9.5 | 与 `task` 同库同策略；恢复时**不得覆盖已有决策行**。决策记录丢失 = 追溯链断在「为什么选它」，而选哪一个往下走恰恰是研发过程最关键的一步 |
| `task_input_snapshot` 只追加 | `04` §9.2 | 与 `task` 同库同策略；恢复时不得覆盖已有快照行 |
| 模型/工具多版本并存 | `03` §8.4 | 权重与镜像永久保留，保证历史任务可重跑 |

### 8.2 违反 DRP-NFR-07 的恢复操作（明令禁止）

| 禁止 | 原因 |
|---|---|
| 恢复时改写 `task` 的 `model_version`/`params_json` 使其"看起来一致" | 伪造追溯链，等于销毁证据 |
| 删除"不一致"的 `artifact` 行而不记录 | 破坏完整性（DRP-NFR-06） |
| 用旧备份覆盖新数据且不留 `.failed` 目录 | 无法事后查明丢失范围 |

### 8.3 恢复操作记录模板（每次恢复必填，入审计）

| 字段 | 内容 |
|---|---|
| 恢复编号 / 时间 | |
| 发起人 / 执行人 / 审批人 | |
| 恢复类型 | R-A ~ R-G |
| 原因 | 事故单号 / 用户请求 / 演练 |
| 源备份（路径 + SHA-256） | |
| 目标时点 T | |
| 影响范围 | 受影响项目/用户/任务数 |
| 数据丢失评估 | 时间窗口与条数 |
| 一致性核对结果 | 悬空/孤儿 数量与处置 |
| 结果与遗留问题 | |
