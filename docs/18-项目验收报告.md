**设计决策中的三个「反直觉但正确」的点**（评审已确认，验收时可能被问到）：

1. `compounds` **没有 `project_id`**——化合物是全平台去重主数据，项目视图只列被本项目候选物引用的分子。若做成项目资产，同一分子在两个项目各存一份，InChIKey 去重就跨不了项目。
2. `protein_structures.task_id` **不建外键**——任务有独立归档策略，外键会把结构行的生命周期绑死在任务表上。
3. 分片索引**从 JSON 列搬进行级表**——JSON 列只能整列读写，三个并发 `PUT /parts` 后提交者会覆盖前者（字节还在，索引丢了）。行锁替代方案被否，因为 SQLite 没有行锁，会让开发/测试与生产行为不同。

### 3.3 可追溯（DRP-NFR-06，证据链而非口头说明）

- **六类元数据**（`01` §11.2）：输入快照 / 执行环境 / 运行参数 / 执行过程 / 输出产物 / 归属关系，由 `backend/app/services/traceability.py` 的 `build_traceability_package()` 装配成 `traceability.v1` JSON，含 `inputs[].sha256`、`environment.image/tool/model`、`params.requested`、`outputs[].sha256/sizeBytes`、`bizRef`。

|---|---|---|
| 任务完成、Job 仍在 | `succeeded` | `succeeded` ✅ |

| 取消后查状态 | `KubernetesTransportError: HTTP 404` | `ExecutionHandleGone` → worker 转 `CANCELLED` ✅ |

#### 3.9.1 这一轮暴露的四类真实缺陷

这些缺陷都不是「写错一行」，而是**只在真环境或版本差异下才现形**，值得单独记下来：

1. **PostgreSQL 的 `jsonb` 拒收 `NaN`，SQLite 静默接受**（G-3）。同一份内容在测试里存得下、在生产报错。修法不是在写入后捕获数据库异常，而是在写入**前**拒绝非法 JSON（`allow_nan=False`）。
2. **第三方 SDK 的位置参数顺序会变**（G-12）。`minio` 7.2.3 的 `Rule.__init__` 第二个参数是 `abort_incomplete_multipart_upload`，7.2.20 是 `rule_filter`。本机装的是新版、`requirements.txt` pin 的是旧版，于是**本机全绿、CI 13 条同挂**。教训：凡调 SDK 构造函数，一律用关键字传参。
3. **「能力探测」不能靠假设**（G-12）。`AbortIncompleteMultipartUpload` 是本机 MinIO 直接拒收的规则，且本仓库的分片是**对象级暂存**、根本没走 S3 原生 Multipart Upload —— 原缺口描述（`04` §5.8）照抄了一份本平台不适用的需求。实测推翻了文档假设。
4. **测试通过 ≠ 测试能杀死变异**（G-3）。把鉴权判据改成无条件返回，**70 个用例全绿、零用例杀死**；补的用例做了变异验证后才真正守住。同类的还有 G-7 的 contextvar 泄漏——原 34 条用例在变异下仍全绿，因为 `asyncio.gather` 在子 task 里跑、context 是复制的。

> **一句话**：本轮的五个 PR 里有四个是「代码按文档写完、跑测试全绿、然后被真环境或变异验证推翻」。这说明**验收报告里的 ✅ 必须挂在「在真环境跑过」或「变异能被杀死」上**，不能挂在「单元测试通过」上。

### 3.10 `REJECTED` 第 8 态落库（2026-10-27，B-2 关闭）

`§6.4 B-2` 里最后一条规格偏差：`04` §4.2 定义了八态，实现只有七态，缺 `REJECTED`（准入拒绝）。本轮补齐。

**为什么要落一行「被拒的任务」**：此前配额/准入校验直接抛 `429`，**一条记录都不留**。用户事后说「我提交过但失败了」，平台拿不出任何证据——没有任务行、没有审计、没有可统计的拒绝率。`03` §3.4 的状态机本来就画了 `CREATED --> REJECTED: 配额/参数校验失败`，缺的是实现。

| 改动 | 内容 |
|---|---|
| 状态枚举 | `models/tasks.py` 加 `REJECTED = "REJECTED"`，`common/task_status.py` 双映射（API → `rejected`、执行态 → `rejected`，**不映射成 `queued`**，否则监控面板上「被拒」与「排队中」混为一谈） |
| 状态机 | `TRANSITIONS[PENDING]` 加 `REJECTED`；`TRANSITIONS[REJECTED] = set()`（无出边）；新增 `reject(task, error_message, progress_message)`；**把「终态」与「要核销」拆成 `TERMINAL_STATES` 与 `_SETTLED_STATUSES` 两个集合**（`REJECTED` 只进前者） |
| 配额拒绝落库 | `tasks/service.py` 新增 `_record_quota_rejection`：建 `Task(status=PENDING)` → 写 `TaskInput` → `extra_data["rejection"] = {维度, 限额, message}` → `TaskStateMachine.reject()` → `commit`。**不调 `record_task_inputs` / `record_tool_usage`**——被拒的提交没真的用输入，工具也不算被使用过。记录失败只 `rollback` + 日志，不能把 429 变成 500 |
| 视图口径 | `task_views` 的「历史」加 `REJECTED`（它存在的唯一理由就是被找到）；「需关注」**刻意不加**（那是运维口径，被拒是用户侧输入问题，提交时已用 429 告知） |
| SSE | `task_event_stream.TERMINAL_STATUSES` 加 `REJECTED`，否则订阅方会等一个永不到来的状态变化，挂到 30 分钟上限才断 |
| 工作流三处 | `workflow_waiting_task` / `workflow_loop_scheduler` / `workflow_map_scheduler` 的失败判定集合各加 `REJECTED`（节点任务同样过配额，被拦时留 REJECTED 行而不执行；不算失败则工作流会一直等一个永不开始的任务直到整体超时） |
| 前端 | 第八态文案/配色（`default` 灰，不是 `error` 红——红色留给「跑失败了」，被拒是「没让你跑」）；进度条走 `normal` 而非 `exception`；归终态与历史、不进行中 |
| 迁移 | `20261028_07`：`upgrade`/`downgrade` 均为空操作（`tasks.status` 是 `String(20)`，全仓无 CHECK 约束；历史库中本来就没有可回填的拒绝记录，凭空造一批等于伪造审计证据） |

**三处非显然的取舍**：

1. **`REJECTED` 不核销算力**（`03` §7.3、`04` §6.2 明确要求）。把「终态」与「要核销」拆成两个集合，是为了不让「以后再加一个终态」自动等于「多一条白嫖算力的口子」。
2. **不可重试**。`retry_task` 这条路**不做配额准入**（配额只在 `create_and_schedule_tool_task` 里查），允许重试等于给「提交被拒 → 点重试」开一条绕过配额的路。正确做法是重新提交，走完整准入。这也是我实现到一半**自我推翻**的地方：初版让它可重试，想清楚这条路径后就回滚了。
3. **422/429 响应体不变**。用户看到的仍是「配额不足」，只是库里同时多了一行可追溯的 REJECTED。改响应体会破坏已有前端与文档契约。

**验证**：新增 `test/test_task_status_rejected.py` 16 条用例（八态集合、双映射、`PENDING→REJECTED` 唯一入边、无出边、`TERMINAL_STATES` 含而 `_SETTLED_STATUSES` 不含、`reject()` 副作用「有 `finished_at`、无 `started_at`、无 `execution_time_sec`、`progress=0」、不可 start/complete/retry、四个视图口径、SSE 终态、结果中心排除、工作流三处失败判定）；`test_project_quotas.py` 两个用例由「一条都不留」改写为「留一条 REJECTED 行且不留 PENDING 空壳」。**变异验证**：`_SETTLED_STATUSES` 加 `REJECTED` → 1 failed；工作流三处各自去掉 → 各 1 failed；`task_views` 历史去掉 → 1 failed；`service.py` 不调 `_record_quota_rejection` → 2 failed。
**一次未被杀死的变异**（如实记录）：把 `if to_status in cls._SETTLED_STATUSES` 改回 `cls.TERMINAL_STATES`，16 条用例**仍全绿**——因为 `reject()` 分支里没写 `started_at`，`cost_from_task` 算出的成本本就是 0，没有可断言的差异化结果。即该行目前靠 `test_rejected_is_terminal_but_not_settled` 守护**集合本身**，而不是靠行为差异。这类「集合正确但行为等价」的变异，只能靠读代码发现。

> **顺带说明为什么这一条值得单列一节**：它是本轮唯一一个**只改行为、不改 schema** 的规格对齐——没有新表、没有新列、迁移是空操作，但牵动了状态机、配额、视图、事件流、工作流四处判据与前端的 6 个位置。**「加一个枚举值」从来不只是加一个枚举值。**

### 3.11 `DataFile` 写入路径 + G-13 资产类型 + `retry_of` 字段（2026-10-28）

三件事一起做，因为它们都落在「数据模型里有字段、实现里没有」这一类缺口上。

**① `DataFile` 写入路径（G-11 的尾巴 / G-13 的一部分）**：`04` §8.2 的 `data_files` 表建了半年，但**没有任何代码往里写过一行**——数据集登记时 `file_urn` 只是存成字符串，`files == []` 恒成立。现在 `_materialize_data_file` 会把 `file:<file_id>` 形态的 urn 解析成 `data_files` 行，字段（文件名 / 类型 / 大小 / sha256）全部取自 `files` 行，而不是从请求体抄。

三条契约边界：

| 情形 | 行为 | 为什么 |
|---|---|---|
| 非 `file:` urn（`oss://` 等） | 不落 `DataFile`，**仍可登记** | 外部系统的 urn 不能让整个登记失败；「只登记不落 DataFile」是既有行为 |
| 文件存在但属于别的项目 | 422 | 跨项目引用必须在入口拦住，否则一个项目的资产清单能列出别人的文件 |
| 已软删除 / 已损坏 / 已过期 | 422 | **本轮复核时补的**。软删除与损坏的记录仍留在 `files` 表里（软删除等物理清理、损坏只置标记），只校验「存在」会让用户拿到一个指向已删文件的数据集，直到下载时才 404 |

可用性判定**直接复用 `app.files.file_records.is_file_usable`**——「能不能被新任务绑定」与「能不能被登记进数据集」是同一个问题，另立一套只会让两处口径慢慢分开。`_unusable_reason()` 只负责把原因说清楚，不是第二道闸门。

**② G-13 三种非结构资产类型**：`DATASET_TYPES` 补 `DOCUMENT`（`LITERATURE` / `EXPERIMENT` 原已有）。新增 `attributes` 结构化属性并入 `Dataset.summary`，**合并顺序是 `attributes` 铺底、`summary` 覆盖**——`summary` 是既有契约字段且有测试守「显式给出的 summary 键必须原样回读」，`attributes` 只是为无结构文件补键的附加面，不能反向覆盖调用方明确给出的摘要。三种类型**只登记不解析**：解析是重活且已有唯一入口（`POST /projects/{id}/compounds:import`），数据集登记再解析一遍会让同一份文件被解析两次、产生两套行数口径。

**③ G-4 `retry_of` 字段**：`04` §9.1 的字段落了（`tasks.retry_of` + 索引 + 详情/列表/追溯包 `process.retryOf`）。**但要如实说清语义差距**——本仓库的重提是**就地重试**：`TaskStateMachine.retry()` 只改同一行的 `status` 与 `retry_count`，不新建任务行。因此 `retry_of` 记的是「这条重试链的起点任务 id」，首次重试时链起点就是本行自身，之后永不覆盖；**非 NULL 等价于「这一行被重提过」**，不存在「新行的 retry_of 指向旧行」。

`12` 的 TC-M6-06 写的是「重提生成**新任务**（`retry_of` 指向原任务）；…；新任务不重复占用配额两次」——那是另一种重提模型。改成新建任务行会牵动配额核销（同一行还要求「不重复占用两次」）、工作流节点绑定、取消与列表口径，属独立的模型层改造，本轮不动。**所以 TC-M6-06 保持 ⚠️，不标 ✅，G-4 在 §6.3 里只划「部分」。**

**顺带修掉的一个迁移缺陷**：`20261028_08` 首版的 `_column_names()` 直接 `sa.inspect(bind).get_columns("tasks")`，在**没有 `tasks` 表**的库上抛 `NoSuchTableError`；`test_alembic_migration_dry_run.py` 里那个「stamp 在 `20260730_02`、无 tasks 表」的 legacy 库正好命中，新增失败 1 个。已按同目录 `20261028_06` 的既有模式补表存在性护栏。这类「迁移在正常库上通过、在残缺库上炸」的问题，只有那条 legacy 用例能发现。

**验证**：`test/test_task_retry_of.py` 6 例、`test/test_dataset_assets.py` 13 例（含 2 例不可用文件）；全量 **5 failed / 1 780 passed / 4 skipped**（5 个均为既有 Windows 差异，无新增）；flake8 零告警；迁移 `upgrade head` → 41 版 59 表、`downgrade` 通过。**变异验证**：`retry_of` 写成 `tool_id` → 2 failed；删 `TaskListResponse.retry_of` → 1 failed；删迁移的 `create_index` → 1 failed；去掉 `_materialize_data_file` 调用 → 7 failed；去掉跨项目校验 → 1 failed；去掉 `is_file_usable` 闸门 → 2 failed（新增的不可用文件用例）。

### 3.13 第一个真模型包走通平台全链路（LVpocket，2026-10-29）

**结果**：`POST /api/v1/tasks` → `queued → running → success(100%)`，`artifacts` 落库 **3 条**——`binding_pocket`（`residue_pocket_pdb` / `atom_pocket_pdb` / `pocket_metadata_json` 三 role 齐）、`run_report`、`protein_structure`（输入回填）。单次推理 17.35 s（8×RTX 4090，`--gpus device=2` 单卡）。

**踩出的五个真实缺陷**（每一个都只在「真模型 + 真集群」下才暴露，mock 包因为写得全、跑得简而全部绕过）：

| # | 缺陷 | 现象 | 根因与修法 |
|---|---|---|---|
| 1 | 迁移注册工具时缺 `tool_package_manifest` | k8s 执行器抛「Kubernetes inputs require a materialized standard ArtifactVersion」；退化成 `docker_image` 能起 Pod，但标准输入被静默忽略 | `tool_accepts_materialized_standard_uploads()` 只认 `tool-package.v2` 清单。**清单是标准输入物化的唯一开关**，缺它 `standard_input_uploads` 会被整个丢掉且不报错。修法：注册时把 v2 清单（`api_version`/`kind`/`metadata`/`artifacts`/`runtime`）一并写进 `tool_versions.config` |
| 2 | 模型入口对输入目录布局的假设与平台注入的不一致 | `missing input_files.protein_pdb` | 平台按 `SCIMINER_INPUT_MANIFEST` 把文件放成 `input/<slot>/<file>`，而模型入口按 `input_files.protein_pdb` 的相对路径找。修法：在 `platform_run.sh` 里做**输入自动发现**（按清单顺序回填首个命中文件），不改模型代码 |
| 3 | `result.v2` 里 `cardinality: one` 的产物必须写成对象而非数组 | `Output artifact pocket must be a single artifact` | 我按「多产物」的直觉写成 `[{...}]`；schema 对 `cardinality: one` 要求单对象。修法：单产物写 `{...}`，只有 `many` 才写数组 |
| 4 | 产物 role 必须与 `artifact_standards` 严格对齐，且不得混入中间产物 | `Unexpected output artifact: input.fasta` | `binding_pocket@1` 只接受 `residue_pocket_pdb`/`atom_pocket_pdb`/`pocket_metadata_json` 三个 role；LVpocket 输出的 `classification/{input.fasta,input.horiz,selected_model.txt}` 是流程中间物。修法：在 `platform_run.sh` 的产物映射里**白名单式**列举三个 role，中间产物只留在 output 目录不入 `artifacts` |
| 5 | `POST /api/v1/projects` 不传 `model_policy` / `data_policy` 会 500 | `NotNullViolation`（`projects.model_policy`） | API schema 把两项设成可选，DB 列却是 `nullable=False`（`04` §5.1 要求非空 JSON）。修法（暂未改代码）：调用方显式传 `{}`；**建议后续在 schema 层给默认值 `{}`**，否则任何自动化脚本建项目都会踩 |

**另发现一条不算缺陷但需知会的语义**：`files.sha256` 是**全局去重**的，两个内容相同的上传会指向同一个 `File` 行，因此 `file_ids` 里选两个同内容文件只会得到一个 id（报 `mismatched_file_ids`）。这是去重的正确行为，但前端/脚本要按「选文件 ≠ 得文件」来理解它。

**一般化结论（记进 `17` §5.27）**：**「能起 Pod」和「能被平台当作工具调用」是两件事**。前者只要镜像和 manifest，后者还需要 `tool_package_manifest` 这个把标准输入物化、把产物按 role 归位的契约层。mock 包一开始就写全了清单，所以六个包全绿；真实包从旧 SSH 形态迁过来时，最容易漏的恰恰是这一层——而它漏了**不报错，只是静默降级**。

### 3.14 契约收敛与项目聚合根（Task 1 / Task 2，2026-10-29）

两轮改造共用一份计划（`superpowers/plans/2026-10-29-contract-rbac-artifact-hardening.md`），目标不是加功能，而是**把已经在跑的代码里三处「同一事实多个真值源」收掉**。

**Task 2：项目聚合根与 RBAC**

| 项 | 改前 | 改后 |
|---|---|---|
| 任务的项目归属 | `extra_data["project_id"]` 这个 JSON 字段，无外键、无索引，只能走 JSON 表达式过滤；全仓仅 2 个入口会写 | `tasks.project_id` 真列 + 索引 `ix_tasks_project_id` + 外键 `fk_tasks_project_id → projects.id ON DELETE SET NULL`；新任务双写，旧行按方言回填（PG `extra_data::jsonb->>'project_id'`、SQLite `json_extract`） |
| 项目权限判定 | 三个路由文件各写一份角色判断，口径不完全一致 | `app/services/rbac.py` 单一入口 `require_project_access(db, *, project, user, need, allow_admin)`；admin 可读可写，非成员一律 404（不泄露存在性） |
| 项目列表对 admin | admin 看不到自己不是成员的项目 | admin 放行全部项目；`_serialize` 的 `role` 恒为字符串（admin 非成员为 `"admin"`），`membership` 可 `null`，前端据此判定归档/删改/成员管理 |

外键用 `SET NULL` 而非 `CASCADE` 是刻意的：删项目不该连带删掉任务历史，也不该留下指向已删项目的悬空引用。

**Task 1：契约收敛**

- **枚举单一源** `backend/app/common/enums.py`：项目状态、任务状态、优先级、项目角色、审计三组集中定义，每组给 `Enum`（带 `values()`）与 `Literal` 两个形态；字符串值冻结，仅项目状态补 `paused`。`scripts/gen_frontend_enums.py` 生成 `frontend/src/types/enums.generated.ts`，`test/test_frontend_enum_parity.py` 守护三方一致——这是为了防「后端加了枚举值、前端漏加」这类只在运行时才炸的问题。
- **统一响应与异常信封**：业务端点全部改 `success_response` / `page_response`；`HTTPException` 与校验错误也纳入同一错误信封。处理器挂的是 **`StarletteHTTPException`** 而不是 `fastapi.HTTPException`——后者是前者的子类，挂父类才能把框架自身抛的 404/405 一并覆盖，否则会出现「业务 403 有信封、框架 404 裸 `detail`」的割裂。
- **9 个直接返回 pydantic 模型的端点**（`/system/health`、`GET|PATCH /users/me`、`/users/admin/{id}`、`/gpu/info|stats/{i}|summary|health|allocate`）此前根本没包信封。这类最隐蔽：调用方对同一个 API 的两种形状混用，写 `res.data` 的代码在信封端点上正常、在这 9 个上是 `undefined`。改前先 grep 确认 `/system/health` 的 body 消费方——compose 三份、`backend/Dockerfile` 两处、`scripts/start-dev.sh` 全部是 `curl -f` 只判状态码，没有解析 `status`/`services` 的脚本，改信封不会让探针误判重启。
- **审计补录**：登录/登出/登录失败、项目归档/删除/成员变更、工具发布、权限变更等此前只写文件日志的动作补进 `audit_logs`。顺带修掉一个真 bug——多处调用把 `reason`/`user_email` 塞进 `**extra`，而 `AuditLogger` 只读具名参数，等于静默丢弃。
- **死信表删除**：`POST /workflows/{id}/runs` 补挂 `@idempotent_route` 时发现，`functools.wraps` 让 FastAPI 用 `inspect.unwrap` 取到原函数签名，而注解求值用的是中间件模块的 `__globals__`；`workflows.py` 有 `from __future__ import annotations` 时类型名在中间件里不存在，求值失败后 FastAPI **静默降级**成 query 参数（表现是 422 `Field required`）。修法是装饰期 `inspect.signature(func, eval_str=True)` 并把解析后的签名写回 `wrapper.__signature__`。这个缺陷可怕之处在于静默：端点能注册、OpenAPI 能出文档，只是参数位置错。

### 3.22 游标（keyset）分页与真 PostgreSQL 复核（2026-10-30）

`20` §8 里挂着的「offset 深分页换游标」在这一步落地。`LIMIT 20 OFFSET 100000` 不是
「跳过 10 万行」，而是让数据库**逐行产出再丢掉** 10 万行：20 万行表实测
`OFFSET 1000` 3.0 ms、`OFFSET 100000` 3.0 ms、`OFFSET 199000` **9.4 ms**，随页深线性增长；
游标恒定 0.14~0.18 ms。

| 条件写法 | 执行计划 | 页深 10 万 | 页深 19.9 万 |
|---|---|---|---|
| `ts < ? OR (ts = ? AND id < ?)` | `SCAN tasks USING COVERING INDEX` | 10.2 ms | 21.2 ms |
| `(ts, id) < (?, ?)` | `SEARCH tasks USING COVERING INDEX ((ts,id)<(?,?))` | **0.16 ms** | **0.14 ms** |

**同一份数据、同一个索引，写法差 60 倍。** `OR` 形式让 SQLite 与 PostgreSQL 都用不上
索引区间，退化成整段索引全扫——这条比「要不要上游标」更值得记：先上了游标但把条件
展开写，性能可能还不如原来的 offset。已加守护测试断言编译 SQL 里不得出现 ` OR `。

落地范围：`backend/app/common/keyset.py`（编解码 + `apply_desc_keyset` + `next_cursor`）、
`services/task_views.query_task_page(...)`、`GET /api/v1/tasks`、`GET /api/v1/admin/audit-logs`。
契约：不传 `cursor` 时 `page`/`page_size`/`total` 完全不变；传了不算 total，用
`nextCursor`/`hasMore` 翻页（`total` 为 `null`、`totalKnown` 为 `false`）；偏移模式也返回
`nextCursor`，客户端可从第 N 页平滑切到游标。

**为什么游标里要带主键**：只按时间戳翻页时，同一毫秒的多行会漏行或重复。守护用例
刻意造了「25 行里 4 行同毫秒」的数据逐页翻完，断言 25 条不重不漏。

**后续（2026-10-30 同日收口）**：结果中心、产物、工作流三个列表**已全部补上 `cursor`**
（见新增 §3.2x「三列表游标分页」），不再是 offset-only。结果中心另补部分索引
`ix_tasks_project_terminal_finished_id`，产物/工作流补 `(project_id, created_at, id)` 索引
（迁移 `20261031_04` / `20261031_05`）。

**验证**：`test/test_keyset_pagination.py` 9 passed；后端全量 **1980 passed / 5 failed /
4 skipped**（5 个均既有 Windows 差异）；`flake8 F401,F821,E9` 零输出。

**真 PostgreSQL 复核（同日补充）**：游标分页在 SQLite 上做好后，本机起 PostgreSQL 16
灌 20 万任务复核，结果**否定了两个已经写进文档的结论**，并在这一步一并收口（迁移
`backend/alembic/versions/20261031_03_keyset_and_nulls_last_index.py`）：

| 问题 | 证据 | 处置 |
|---|---|---|
| `ix_tasks_project_status_finished` 的 `DESC NULLS LAST` **在空库上从未生效** | 基线 `20260624_01` 用 `create_all()` 先按模型（普通升序）建了同名索引，`20261031_01` 见索引存在即跳过；`EXPLAIN` 仍是 `Bitmap Index Scan` + `top-N heapsort`，4.52 ms | PG 上 `DROP/CREATE INDEX CONCURRENTLY` 重建为 `(project_id, status, finished_at DESC NULLS LAST, created_at DESC)`，降到 **2.53 ms** |
| 游标翻页**缺 `(created_at, id)` 索引** | 无筛选的游标翻页走 `Parallel Seq Scan`，**21.15 ms**，与 `OR` 展开式 23.00 ms 一样慢 | 补 `ix_tasks_created_at_id`，降到 **0.079 ms**（`Index Only Scan Backward`，**267×**） |
| `candidates.attrs` 用 `sa.JSON` 却建 GIN | 空库迁移直接失败：`data type json has no default operator class for access method "gin"` | 模型与建表迁移改 `JSON().with_variant(JSONB, "postgresql")` |
| `request_snapshot ? 'task_id'` 回填 | 空库迁移直接失败：`operator does not exist: json ? unknown` | 改 `(request_snapshot::jsonb) ? 'task_id'` |

修完后空库 `alembic upgrade head`（51 个迁移）全通过、`alembic downgrade base` rc=0；
后端全量仍是 **1980 passed / 5 failed**（5 个均既有 Windows 差异）。
**这说明前一版的「SQLite 实测基线」只能当量级示意，不能当作 PostgreSQL 上的性能结论**——
两个引擎的优化器与索引语法都不是一一对应。已把这条写进 `20` §1.1 与 §6 的新增规则。

**基线（相对分叉点 `cnpharm-base-ce9a521`）**：106 个提交、1153 个文件
`+100725/−31781`、后端 `backend/app` 72,851 行、迁移 **51** 个（单 head `20261031_03`）、
测试文件 260 个、前端页面 61 个 `.vue`。

### 3.15 产物写入单点化与来源血缘（Task 3a，2026-10-29）

产物系统此前的实际能力是「资产完整、追溯半个」：`ArtifactVersion` 没有来源列，`link_artifact_lineage()` 全仓零调用，因此**非工作流单任务的「输入版本 → 输出版本」血缘完全缺失**；追溯包虽然靠 `task_input_snapshots` 钉住了输入，谱系图却画不出这条边。

| 项 | 改前 | 改后 | 证据 |
|---|---|---|---|
| 版本来源 | 仅 `Artifact.source_task_id` 单值 | `artifact_versions` 增 `source_task_id` / `source_attempt_id` / `source_tool_version_id` / `storage_tier` | 迁移 `20261030_05`；`test_artifact_version_source.py` |
| 版本取号 | 应用层 `max()+1`，并发撞唯一约束返 500 | `artifact_writer._create_version_with_retry` 持锁取号 + 重试 | `test_upsert_version_retries_when_version_number_collides` |
| 输入→产出血缘 | 不存在 | 由 `task_input_snapshots` 派生 `ArtifactLineage`，`ON CONFLICT DO NOTHING` | `test_artifact_lineage_from_snapshot.py` |
| 写入入口 | 三处各写一套（`artifacts.py` / `standard_artifacts.py` / `standard_input_uploads.py`） | `ArtifactWriter` 独占三表；角色文件统一走 `attach_version_files` | `test_attach_version_files_skips_roles_that_already_exist` |

**本步骤推翻的一项计划判断**：计划书 §5.1 原写「保留 `(artifact_id, sha256)` 内容唯一索引，靠复用避免重复存储」。实施中确认这两件事互斥——对只追加的生产记录表，**「每一次生产都留痕」优先**；而它想省的存储本来就不存在（同内容的不同版本指向同一个 `File` 行，只多一行元数据）。故删除该索引，保留 `(artifact_id, version)`。

**两个在复用路径上被抓出来的真实缺陷**（都不是设计问题，是「写入侧没收干净」）：

1. 同一任务重放时，`standard_artifacts._persist_artifact` 会把同一批角色文件再写一遍 → 撞 `uq_artifact_version_files_version_role` → 500。而重放正是幂等存在的理由，执行硬化后会成为常态路径。
2. 上传同内容两次时，`artifacts._attach_uploaded_file` 会复用版本却仍存第二份 `File` 并挂同 role 的 link → 同样 500（线上可触发）。

修法统一为「角色文件写入必须幂等」：`attach_version_files` 按 `(artifact_version_id, role)` 跳过已存在者，成为唯一入口。

**验证（`main@23ac83b`，本机）**：flake8 `F401,F821,E9` 零输出；`pytest test/` **1866 passed / 5 failed（5 个均为已知 Windows 环境差异）/ 4 skipped**；迁移单 head `20261030_05`，空库 `upgrade head` + `downgrade base` 双向 rc=0。**两次变异验证**均为先红后绿（去掉跳过判断 → 幂等用例红；`if not created:` 改 `if False:` → 上传复用用例红）。

**仍未落地（明确登记，不用「设计上支持」代替）**：`standard_input_uploads` 仍是裸构造 `Artifact`/`ArtifactVersion`（现能跑只因每次新建 artifact，同槽重复物化即撞 `uq_artifact_versions_artifact_version`），收编属 Task 3b；上传/下载改预签名 URL、产物列表分页属 Task 3c；`storage_tier` / `reference_count` 目前只是字段，未参与生命周期决策。

### 3.18 执行链路硬化（Task 4，2026-10-29）

五项问题共同点：**都不报错，但会把「卡住」伪装成「通过」或把「内存爆掉」拖到并发时才暴露。**

| 问题 | 为什么危险 | 改法 |
|---|---|---|
| `blocked` 不在 run 收口集合 | 含 blocked 节点的 run 永远「运行中」，看板上像是还在算 | 补进 `workflow_scheduler` 收口集合，收敛为 `failure` + `error_message` |
| `workflow_skip` 会把 blocked 覆盖成 skipped | **run 反而被判成功**——把「卡住」伪装成「通过」，这是本节最重要的一条 | `_NON_SKIPPABLE_STATUSES` 补 `blocked` |
| run 无超时 | 一个卡死的 run 永久占用并发名额 | 新增 `WORKFLOW_RUN_TIMEOUT_SECONDS`（默认 12h），`reconcile` 把超时非终结 run 置 failure |
| K8s 大产物整块读进内存 | 2GB 轨迹就是 2GB 常驻，几个并发即 OOM | `open_stream` 分块 → 增量 sha256 → 同盘 `.part` → `os.replace` 原子改名，峰值 1MB |

| 节点调度取实时 `tool_version_id` | 工具发版后，同一 run 前后节点用不同版本，产物契约可能不兼容，追溯无法解释 | 统一走 `workflow_tool_version.resolve_tool_version`：优先建 run 时快照，无快照才回退；并为 loop body 的 tool 节点补记快照（此前只遍历顶层节点，loop body 根本没快照） |

**两处最容易做错的细节**：

1. **迁移回填必须优先保住非终态行**。lookup 带 `status IN (PENDING,QUEUED,RUNNING,SUCCESS)` 过滤；若把唯一键回填给一条已 FAILURE/TIMEOUT 的更早行，则 lookup 查不到 → 调度器建新任务 → 撞唯一索引 → 回查到那条终结行 → **节点以为任务存在，永远等不到结果**。所以回填顺序是「非终态中最早 → 全部中最早 → 其余留 NULL」。
2. **留 NULL 的历史行要能自愈认领**。同组 ≥2 条非终态重复行时，落选者三列留 NULL；`find_existing_workflow_node_task` 增加回退：精确查询落空时按 `TaskInput.params` 的 run/node（兼容驼峰）在同状态集合里找回并写回三列，用 `UPDATE ... WHERE workflow_run_id IS NULL` 保证只有一个写入者生效。没有这条，它们是「查不到但仍会继续跑」的僵尸任务——重复占算力、重复写产物。

### 3.20 三路只读审计与两批缺陷收口（2026-10-30）

Task 1~5 完成后，按「找漏洞，但不要过度设计」的要求，派出三路只读审计
（任务/执行/状态机、API 契约/前端一致性、产物/资产/存储），共报出 20 余项。
按「同一病根合并成一个最小修复」的原则收敛为两批、13 项改动，不做重构。

**判据（为什么这样归并）**：不按审计报告的分路归并，而按**病根**归并——
同一个「集合在多处各写一份」的病根，无论在哪个文件里表现，都算一处缺陷。

| 批次 | 病根 | 项数 | 提交 |
|---|---|---|---|
| 产物与文件完整性 | 产物身份的判据不一致 / 删除与引用的顺序不清 | 5 | `0fde8b9` |
| 任务状态八态扩散 | 八态引入后「哪些算已提交/失败/终态」散落十余处 | 10 | `7ac5588` |

两批里最值得记录的三条：

1. **互相制衡的两个缺陷**：项目删除原先把「对象泄漏」（只删行不删 MinIO 对象）
   与「跨项目引用」（`artifact_version_files.file_id` 外键无 ondelete，而文件
   去重是按 sha256 全局的，一个 File 可能被别的项目产物引用）分开看都成立，
   但只修前者会把项目删除事务打挂。最终按「共享引用必须跳过、从属记录陪着删」
   两种性质分别处理。
2. **写回超时要用 CAS**：排队超时写回原先是无条件 `UPDATE`，会把已被 worker
   启动成 RUNNING 的任务覆盖回 TIMEOUT。改成「状态机先算字段 → expunge 掉
   ORM 脏实例 → `WHERE status='QUEUED'` 条件更新 → rowcount 不为 1 只告警」，
   且资源租约**只在 CAS 命中后归还**（先归还会提前释放 RUNNING 任务的配额）。
3. **计数器不能混用**：资源不足重排原先用 `retry_count`，会把用户的重试额度
   吃光；拆出 `resource_retry_count`，并把它从 `RESOURCE_WAIT_METADATA_KEYS`
   移除，否则 `start()` 每轮都清空、资源重排永不封顶。

### 3.21 数据库索引与查询硬化（2026-10-30）

按要求「预留复合索引、注意查询规范、规避多表 join」，先派三路只读审计（索引盘点、

判据只有一条——看执行计划里还有没有 `USE TEMP B-TREE FOR ORDER BY` 与全表扫描。

| 查询 | 改前 | 改后 | 证据 |

改动面：12 个新索引、删 12 个冗余单列索引、`execution_records.task_id` 真列化、
7 处查询改写。规范写成 `20-数据库索引与查询规范.md`。

三条值得记录：

1. **`DESC NULLS LAST` 是唯一需要方言分叉的索引**。PG 的 ASC 索引反向扫描得
   `NULLS FIRST`，与「未结束的任务排最后」的意图相反，必须显式建
   `(…, finished_at DESC NULLS LAST)`；SQLite 的 NULL 最小，DESC 扫描天然把
   NULL 放最后，建普通 ASC 即可。同一句 SQL 两个库要两套索引。
2. **JSON 提取进 JOIN 是一行代码换一次全表扫描**。
   `ON tasks.id = execution_records.request_snapshot->>'task_id'` 让 PG 放弃主键索引
   走哈希连接；热字段必须升真列。
3. **「迁移跑在精简 legacy 库上」不是边角场景**。本轮两条迁移在
   `test_alembic_migration_dry_run` / `test_task_project_aggregate` 的路径上直接炸
   （那条路径从旧 revision 起库，没有 `audit_logs` 与 `tasks`）。凡是补索引、回填
   数据的迁移，开头都要判表存在——**这与我方在 v1.12 记的
   `20261028_08` 首版 `_column_names()` 是同一个坑，第二次踩**。
