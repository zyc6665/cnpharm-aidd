# 仓库清理与分支初始化清单

## 1. 目标

本清单用于把当前工作区整理成符合团队协作规范的开发基线。清理目标不是删除所有脏文件，而是把文件分成四类：

1. 应纳入版本的代码、文档和协作配置。
2. 应忽略的本地运行数据、模型打包产物和测试产物。
3. 应归档或退场的历史文档。
4. 需要负责人确认后才能提交、删除、推送或改分支的高风险项。

## 2. 当前状态摘要

当前工作区存在以下情况：

- 当前工作分支：`v1.0-7.28`。
- 当前分支相对 `origin/v1.0-7.28` 明显领先，不能直接视作远端已同步。
- 当前 `main` 与 `v1.0-7.28` 不是简单快进关系，不能直接强推覆盖。
- 已跟踪文件存在大量修改和删除。
- 新增了一批架构、交付、开发规范文档。
- 本地存在大量运行数据、日志、SQLite 数据库、Node 依赖、模型打包产物和二进制报告，需要通过 `.gitignore` 排除。

## 4. 应忽略的内容

以下内容不应进入 Git：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 本地数据库 | `backend/app.db`、`backend/storage/*.db`、`storage/*.db` | `.gitignore` 排除 |
| 运行日志 | `logs/*.log`、`backend/*.log` | `.gitignore` 排除 |

| 测试产物 | `frontend/test-results/`、`frontend/playwright-report/`、`coverage/` | `.gitignore` 排除 |

| 模型打包产物 | `model/kaiwu-venv-model-bundles/`、`model/**/*.tar.zst` | `.gitignore` 排除 |

| 临时目录 | `tmp/`、`temp/` | `.gitignore` 排除 |

## 5. 历史文档退场策略

当前平台已经形成新的文档基线。旧 `docs/design`、`docs/frontend`、`docs/guides`、`docs/archive` 和根目录零散历史报告如果继续保留，会让团队不知道哪份文档才是权威。

推荐策略：

1. 当前版本只保留 `docs/README.md` 索引中的基线文档。
2. 历史文档通过 Git 历史、归档 tag 或单独归档分支追溯。
3. 未来如果某份历史文档仍有价值，应迁移内容到当前基线文档，而不是继续保留多个入口。
4. 删除历史文档必须作为单独提交，提交信息建议为 `docs: retire obsolete legacy documentation`。

需要单独确认的文件：

- `AGENTS.md`：如果团队还需要仓库级 AI/协作代理指令，应保留或重写；如果已经迁移到团队规范，可删除。
- `START_SCRIPT_USAGE.md`：如果启动流程仍有效，应迁移到 `README.md` 或 `docs/development/`；如果过期，可删除。
- `docs/API_DOCUMENTATION.md`：如果接口文档仍有效，应迁移到企业交付设计文档；如果过期，可删除。

## 7. 分支初始化策略

### 7.1 不推荐的做法

当前不推荐：

- 直接强推当前 `v1.0-7.28` 覆盖 `main`。
- 在脏工作区直接创建并推送 `main`、`beta`、`develop`。
- 把历史分支全部删除。
- 把所有文档清理和分支初始化混在一个提交里。

### 7.2 推荐的过渡做法

推荐流程：

1. 在当前 `v1.0-7.28` 上完成仓库清理提交。
2. 将清理后的 `v1.0-7.28` 作为新的平台改造基线候选。
3. 从该基线创建 `develop`。
4. 从同一基线创建 `beta`，用于预发布验收。
5. `main` 暂时不强推；等 beta 验收通过后，通过 release PR 或负责人确认的方式更新。

本地命令示例：

```bash
git switch v1.0-7.28
git status --short

# 清理提交完成后再创建长期分支
git branch develop
git branch beta
```

远端推送示例：

```bash
git push -u origin v1.0-7.28
git push -u origin develop
git push -u origin beta
```

注意：推送前必须确认远端分支策略和保护规则。`main` 不允许 force push。

## 8. 分支保护建议

在 Git 平台设置：

| 分支 | 保护规则 |
| --- | --- |
| `main` | 禁止直接 push；必须 PR；必须 CI 通过；必须 reviewer；必须 tag 发布 |
| `beta` | 禁止直接 push；必须 PR；必须核心测试通过；必须验收记录 |
| `develop` | 禁止 force push；建议 PR；至少基础 CI 通过 |

## 9. 清理完成判据

清理完成后应满足：

- `git status --short` 只显示本轮计划内变更，或完全干净。
- `git status --ignored --short` 中本地数据库、日志、模型打包产物均为 ignored。
- 新增文档能从 `docs/README.md` 找到入口。
- 根 `README.md` 不再鼓励直接在历史版本分支开发。
- `.github/pull_request_template.md` 存在。
- `main`、`beta`、`develop` 分支角色明确。
- 不存在未经确认的 `git reset --hard`、force push 或大规模删除提交。

## 10. 本轮需要负责人确认的事项

在真正提交和推送前，需要确认：

1. 是否提交 49 个已跟踪文件的删除。
2. `AGENTS.md` 是恢复、重写，还是删除。
3. `START_SCRIPT_USAGE.md` 是迁移到 README，还是删除。
4. `docs/API_DOCUMENTATION.md` 是迁移到交付设计文档，还是删除。
5. 是否允许创建并推送 `develop` 和 `beta`。
6. 是否允许将本地领先远端的 `v1.0-7.28` 推送到远端。
7. `main` 是否暂时保持不动，等 beta 验收后再更新。
