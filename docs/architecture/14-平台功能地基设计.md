# 平台功能地基设计

## 1. 目标

平台当前已经具备工具注册、任务执行、标准 Artifact、外部数据库、工作流、智能体和可视化能力。下一阶段最重要的不是继续堆单点功能，而是把所有功能共同依赖的“地基”稳定下来。

本设计回答三个问题：

1. 哪些能力是平台功能地基，必须先稳定。
2. 新模型、新工具、新 Artifact 类型接入时，应修改哪里，不应修改哪里。
3. 工作流和智能体如何在新工具扩展后继续自动发现、预检、绑定和运行。

核心原则：**新工具扩展不应要求修改工作流专属适配逻辑；应只补 Tool Contract、Artifact Registry、Result Manifest、必要 Renderer 和执行器配置。**

## 2. 地基定义

平台功能地基不是单个页面，也不是某个工具集合，而是所有运行入口共同依赖的领域能力和契约。

地基能力必须满足：

- 可被工具详情页、工作流节点、整条工作流和智能体共同调用。
- 有稳定 Interface，调用方不需要理解工具私有文件名、目录结构或 executor 细节。
- 有明确输入、输出、错误状态和验收方式。
- 新增工具时默认复用，而不是在每个入口再写一次适配。

非地基能力包括：

- 单个工具页面的展示细节。
- 某个开源工具的私有参数布局。
- 某个前端组件的局部交互。
- 某个 executor 的内部命令拼接。

这些能力可以重要，但不能成为平台扩展性的源头规则。

## 3. 功能地基总览

推荐的地基顺序如下：

```text
Artifact Registry + Standard Artifact Boundary
  -> Tool Contract
  -> Run Preparation
  -> Task Command
  -> Executor Gateway
  -> Standard Result Manifest
  -> Artifact Persistence + Lineage
  -> Workflow Orchestration
  -> Renderer Registry + Artifact Presentation
  -> Agent Plan + Approval
  -> Admin Governance + Validation
```

依赖方向必须保持单向：上层入口调用下层地基，下层地基不反向依赖页面、工作流画布或智能体话术。

## 4. 地基模块

### 4.1 Artifact Registry + Standard Artifact Boundary

定位：定义平台认可的科学数据对象。

它包括：

- Standard Artifact type ref，例如 `protein_structure@1`、`ligand_structure@1`、`binding_pocket@1`。
- file roles，例如 `structure_file`、`prepared_pdb`、`receptor_pdbqt`、`sdf_3d`。
- metadata schema，例如 pH、链 ID、加氢状态、构象来源、表格列定义。
- validation rules，例如 required roles、必填 metadata、允许的 lifecycle state。
- compatibility rules，例如版本兼容、role 兼容、转换建议。

如果这一层不稳定，会导致：

- 工作流只能按文件名和扩展名猜测上下游。
- 新工具的输出无法被旧工具可靠识别。
- 可视化、下载和智能体解释无法复用。

设计要求：

- 新科学数据类型必须先进入 Artifact Registry。
- 新 role 优先扩展已有 type，只有语义对象变化时才新增 type。
- ArtifactVersion 不可变；处理、转换、筛选、打分都应产生新版本或新 Artifact。

### 4.2 Tool Contract

定位：定义平台如何理解一个工具。

它包括：

- 工具身份、版本、分类和标签。
- 普通参数 schema。
- Artifact input slots 和 output slots。
- executor 类型和 resource profile。
- run surfaces，例如 tool detail、workflow node、agent plan。
- example inputs 和 smoke test。

如果这一层不稳定，会导致：

- 工具库、工作流、智能体分别维护自己的工具知识。
- 新工具注册后还要额外写 workflow 适配。
- “一键填入示例”“节点独立运行”“Agent 推荐工具”出现不一致。

设计要求：

- Tool Contract 是工具进入平台的唯一标准入口。
- Remote API、Docker、SSH、内置工具、Tool Package 都必须归一化为 Tool Contract。
- 工作流和智能体只读取 Tool Contract，不读取 executor 私有配置。

### 4.3 Run Preparation

定位：把一次运行请求准备成可执行 Task 输入。

它包括：

- 解析 Run Context。
- 解析用户参数、上传文件、已有 ArtifactVersion、workflow input、上游节点输出。
- 计算 Binding Decision。
- 校验权限、Artifact readiness、role、metadata、cardinality 和版本兼容。
- 把标准 Artifact 输入投影为工具 legacy 参数或 executor 输入文件。
- 生成 Readiness Report 和 PreparedRun。

如果这一层不稳定，会导致：

- 工具详情页可运行，工作流节点不可运行。
- 节点独立运行和整条工作流运行表现不一致。
- 前端误判“必须项目上下文”或“缺少有效工作流契约”。

设计要求：

- Run Preparation 是所有 run surfaces 的唯一权威。
- 前端只能展示 Readiness Preview，不能构造最终 Task 内部字段。
- Workflow Binding Resolver 只是 Run Preparation 内部的 Artifact slot/source/role 决策能力。

### 4.4 Task Command

定位：统一任务生命周期命令。

它包括：

- create task。
- start task。
- cancel task。
- retry task。
- attach outputs。
- sync status。

如果这一层不稳定，会导致：

- 不同页面自己拼 TaskCreate payload。
- 取消、重试、日志和输出回收逻辑分散。
- 保存工作流加载后无法稳定恢复节点任务。

设计要求：

- Task Command 只接受 PreparedRun 或明确的 Task command input。
- 不允许页面、工作流或 Agent 绕过 Task Command 直接创建执行记录。
- 重试应创建新的 Execution Record，但不改变 Task 作为用户可见运行实例的语义。

### 4.5 Executor Gateway

定位：统一计算资源和执行环境。

它包括：

- builtin。
- python。
- docker。
- ssh。
- remote_api。
- k8s。
- slurm。

标准 Interface：

```text
submit(request) -> execution_handle
inspect(handle) -> execution_status
cancel(handle) -> cancel_result
logs(handle, cursor?) -> execution_logs
collect(handle) -> collected_outputs
```

如果这一层不稳定，会导致：

- 分子对接、MD、深度学习模型无法统一调度。
- 长任务取消、日志、状态同步和结果回收各做各的。
- 工具部署方式和工作流语义耦合。

设计要求：

- executor 只处理执行，不决定 Artifact 语义。
- Tool Package 是交付格式，不是 executor 类型。
- K8s/Slurm 是 Executor Adapter，不应改变 Tool Contract 和 Workflow Contract。

### 4.6 Standard Result Manifest

定位：定义工具运行结果如何回到平台。

它包括：

- output slot name。
- artifact type ref。
- file roles。
- files path、size、checksum、mime。
- metadata。
- validation hints。
- lineage relations。
- preview hints。

如果这一层不稳定，会导致：

- 平台只能扫描目录猜测结果。
- 输出文件能下载但不能进入下游工作流。
- 同一个工具不同执行器返回结果后语义不一致。

设计要求：

- 标准 Artifact 输出必须通过 Result Manifest 声明。
- 平台侧复算 checksum，并按 Artifact Registry 校验 role 和 metadata。
- Result Manifest 不能临时定义平台未知的 Artifact type；未知类型必须先注册。

### 4.7 Artifact Persistence + Lineage

定位：把运行结果持久化成可追溯的数据资产。

它包括：

- Artifact。
- ArtifactVersion。
- ArtifactFile。
- file role。
- lifecycle state。
- derived_from、contains、describes、ranked_by、validated_by 等谱系关系。

如果这一层不稳定，会导致：

- 用户能看到文件，但无法知道从哪个任务、参数、上游数据产生。
- 保存工作流恢复时只能恢复空节点，无法恢复节点任务和产物绑定。
- Agent 不能基于可信产物继续建议下一步。

设计要求：

- ArtifactVersion 不可变。
- 跨项目复用必须显式导入或复制，不能直接跨项目绑定。
- Node Task Binding 应引用 Task 和 ArtifactVersion，而不是临时文件路径。

### 4.8 Workflow Orchestration

定位：表达节点、边、运行状态和节点任务绑定。

它包括：

- WorkflowDefinition。
- WorkflowRun。
- node、edge、workflow input。
- Node Task Binding。
- slot-to-slot edge。
- 节点级 readiness 和运行状态。

如果这一层不稳定，会导致：

- 连线后仍要用户手动绑定上下游文件。
- 保存工作流加载后节点任务丢失。
- 新工具加入后工作流不能自动发现输入输出。

设计要求：

- 工作流边连接 `source_node.output_slot -> target_node.input_slot`，不连接文件路径。
- 工作流不做工具私有字段映射，不解析结果目录。
- 工作流可调用 Run Preparation 预检并创建节点任务。

### 4.9 Renderer Registry + Artifact Presentation

定位：统一科学结果展示和下载。

它包括：

- artifact type 到 renderer 的映射。
- 预览 payload。
- 下载选项。
- 节点面板、任务详情、Artifact 详情、结果中心的展示规则。

如果这一层不稳定，会导致：

- 每个工具都写自己的可视化。
- 同一个 ligand/protein/pocket 在不同页面展示不一致。
- 新 Artifact 类型进入平台后只能下载，不能自然展示。

设计要求：

- 可视化按 Artifact type 和 role 选择，不按工具名选择。
- Renderer 可以复用，但 renderer registry 必须可配置。
- 工具只声明输出类型和 preview hints，不直接控制前端组件细节。

### 4.10 Permission + Run Context

定位：定义一次运行和一次产物访问的上下文。

它包括：

- standalone tool run。
- project tool run。
- workflow run。
- agent-approved run。
- 默认工作空间。
- project scope。
- file-only run。

如果这一层不稳定，会导致：

- 标准 Artifact 输出报 `project_id is required`。
- 工具明明可以独立用，却被项目上下文阻断。
- 跨项目数据被误绑定。

设计要求：

- 工具可独立使用，project 是可选运行上下文，不是工具契约必填项。
- 标准输出必须归属 project 或默认工作空间。
- 所有 ArtifactVersion 绑定都必须重新校验权限。

### 4.11 Agent Plan + Approval

定位：让智能体基于平台契约做可验证规划。

它包括：

- Plan Version。
- tool capability summary。
- artifact readiness。
- workflow draft。
- user approval。
- execution audit。

如果这一层不稳定，会导致：

- Agent 生成无法运行的工具调用。
- Agent 绕过平台契约直接拼文件路径。
- 用户无法审计计划为什么可执行。

设计要求：

- Agent 只能基于 Tool Contract、Artifact Registry 和 Run Preparation 生成计划。
- 未通过预检的计划不能直接执行。
- Agent approval 记录应引用 Plan Version，而不是临时 prompt 文本。

### 4.12 Admin Governance + Validation

定位：控制新工具、新类型、新 renderer 和新 executor 的发布质量。

它包括：

- Tool Contract validation。
- Artifact Registry validation。
- Result Manifest validation。
- smoke test。
- example input/output。
- renderer availability check。
- executor resource profile check。

如果这一层不稳定，会导致：

- 新工具虽然注册成功，但工作流不可用。
- 标签、分类、筛选硬编码。
- 远端 API 返回非标准结果后平台才在运行期暴露错误。

设计要求：

- 新工具发布前必须通过 contract validation 和 smoke test。
- 工具标签、分类、能力标签必须来自可维护的 registry，不应硬编码在前端。
- 管理员可以新增标签、分类、Artifact type、role 和 renderer 映射，但发布前必须校验引用完整性。

## 5. 新工具接入标准路径

新增一个模型或药物研发工具时，推荐路径如下：

1. 若产生新科学数据对象，先注册或扩展 Standard Artifact type、role 和 metadata schema。
2. 编写 Tool Contract，声明参数、Artifact slots、executor、resource profile、run surfaces 和示例。
3. 若是 Remote API，自注册 manifest 必须能返回 Tool Contract、example input 和 smoke test 信息。
4. 提供或复用 Result Manifest 输出规则，确保平台能持久化标准输出。
5. 选择 executor：builtin、python、docker、ssh、remote_api、k8s 或 slurm。
6. 如果输出需要可视化，注册或复用 Artifact Renderer。
7. 通过 Admin Validation，包括 contract validation、artifact validation、example run 和 renderer check。
8. 发布后工具自动进入工具库、工作流候选节点和 Agent capability summary。

不应做的事情：

- 在 workflow scheduler 里写工具名特判。
- 在前端节点面板里写私有字段映射。
- 让 executor 返回平台未知语义并要求下游工具猜测。
- 为一个新模型复制一套任务创建逻辑。

## 6. 边界规则

| 场景 | 正确归属 | 禁止做法 |
| --- | --- | --- |
| 判断上游输出能否进入下游 | Run Preparation + Artifact Registry | 工作流按文件名或扩展名猜测 |
| 新工具声明输入输出 | Tool Contract | 前端工具库硬编码字段 |
| 输出文件转标准 Artifact | Result Manifest + Artifact Persistence | executor 直接写 Artifact 记录 |
| 任务启动、取消、重试 | Task Command + Executor Gateway | 各页面自己调用不同执行器 |
| 节点任务恢复 | Workflow Orchestration + Node Task Binding | 只保存画布节点不保存任务绑定 |
| 可视化选择 | Renderer Registry | 按工具 slug 选择组件 |
| Agent 生成计划 | Agent Plan + Run Preparation | Agent 直接拼 executor payload |
| 标签和筛选 | Admin Governance registry | 前端硬编码标签集合 |

## 7. 第一阶段冻结顺序

为了避免继续走一步改一步，第一阶段应按以下顺序冻结 Interface：

1. Artifact Registry：type、role、metadata、validation、lifecycle。
2. Tool Contract：input/output slots、resource profile、run surfaces、examples。
3. Result Manifest：output slot、roles、metadata、checksum、lineage。
4. Run Preparation：Readiness Report、Binding Decision、PreparedRun。
5. Task Command：create/start/cancel/retry/sync。
6. Workflow Orchestration：slot-to-slot edge、Node Task Binding、saved workflow hydration。
7. Renderer Registry：artifact type 到 renderer 的可配置映射。
8. Admin Validation：发布前校验和 smoke test。

建议验收链路：

- `Fetch PDB -> Protein Preparation -> LVpocket`。
- `Fetch PubChem Ligand -> Ligand Preparation -> RDKit Properties -> ADMET`。

这两条链路覆盖外部数据库、准备工具、内置工具、模型工具、标准 Artifact、Result Manifest、Renderer、工作流自动绑定和节点任务恢复，是第一阶段最小但足够严格的架构验收面。
