# 软件工程架构治理规范

## 1. 背景

平台已经从原型阶段进入模块基本定型阶段。原型期快速堆功能是合理的，但继续沿用“页面发现问题、局部补逻辑、工作流再适配一次”的方式，会导致新增工具、标准 Artifact、执行器和工作流能力时不断扩散复杂度。

本规范的目标是把平台从功能堆积改造成工程化架构：核心规则集中在少数深模块，页面、工作流、智能体和执行器只通过稳定接口使用这些能力。

## 2. 推荐架构方案

### 2.1 方案 A：模块化单体 + 深模块接口

这是推荐方案。

特点：

- 继续保持一个后端应用和一个前端应用，避免过早拆微服务。
- 按领域模块收敛代码：Project、Artifact、Tool、Task、Workflow、Agent、Executor。
- 把跨入口复用逻辑沉到 Architecture Kernel。
- 外部计算环境通过 Executor Adapter 接入。
- 测试围绕深模块 Interface 编写，而不是围绕散落的工具函数编写。

适用原因：平台仍在快速演进，模块间数据关系强，拆服务会放大事务、权限、测试和部署成本。

### 2.2 方案 B：维持现状，小步补丁

特点：

- 每个页面或功能点继续就地修复。
- 短期改动快。
- 长期新增工具仍需多处适配。

不推荐原因：它不能解决原型堆积的根因，只会继续扩大 `workflow_scheduler`、前端 composables 和工具详情页的复杂度。

### 2.3 方案 C：拆成多个微服务

特点：

- Tool、Task、Artifact、Workflow、Agent 独立服务。
- 服务边界清晰。
- 部署和治理复杂度高。

暂不推荐原因：当前主要矛盾不是进程边界，而是领域 Interface 不稳定。过早拆服务会把混乱边界固化成网络边界。

## 3. 架构原则

### 3.1 模块化单体优先

平台应先在代码层形成清晰模块，而不是先拆进程。模块清晰后，未来需要独立扩缩容的部分可以自然拆出。

### 3.2 领域能力下沉

页面、API 路由、工作流画布和 Agent 都不能各自理解工具私有输入输出。它们只能调用 Architecture Kernel 的 Interface。

### 3.3 深模块优先

一个好的模块应该暴露小 Interface，内部隐藏复杂实现。判断标准：删除这个模块后，复杂度会不会散回多个调用方。

### 3.4 单向依赖

依赖方向必须从入口流向领域，再流向执行和基础设施：

```text
Run Surface / API / UI
  -> Application Facade
  -> Domain Kernel
  -> Executor Adapter / Storage Adapter
```

禁止反向依赖：执行器不应调用工作流；Artifact 持久化不应知道页面；Tool Contract 不应知道项目上下文。

### 3.5 后端权威，前端预测

前端可以做预检、解释和自动填充，但最终绑定、权限、文件角色、Run Context 和输出归属必须以后端为准。

### 3.6 契约先行

新工具、新执行器、新标准 Artifact、新工作流能力必须先有契约，再做 UI 和调度。契约包括输入输出、错误、权限、资源和验收。

## 4. Architecture Kernel

Architecture Kernel 是平台最核心的深模块集合。它不等于一个目录，而是一组必须保持清晰 Interface 的模块。

架构术语：

- **Architecture Kernel**：拥有平台核心决策的一组深模块，包括工具契约、运行准备、任务命令、Artifact 持久化、工作流编排、执行器网关和 Artifact 展示。
- **Executor Adapter**：满足 Executor Gateway Interface 的具体适配器，用于提交、观察、取消、读取日志并收集某一种执行环境中的任务。
- **Application Facade**：面向一个用户用例的应用层入口，负责协调多个深模块，但不复制深模块内部规则。

```text
Architecture Kernel
  ├─ Tool Contract Module
  ├─ Run Preparation Module
  ├─ Task Command Module
  ├─ Standard Artifact Module
  ├─ Workflow Orchestration Module
  ├─ Executor Gateway Module
  └─ Artifact Presentation Module
```

### 4.1 Tool Contract Module

Interface：

```text
get_contract(tool_slug, version?) -> ToolContract
validate_contract(contract) -> ValidationResult
summarize_contract(contract) -> ToolCapabilitySummary
```

职责：

- 从 legacy config、Tool Package、Remote API manifest 构建 Tool Contract。
- 校验 Artifact Slot、参数 schema、资源画像和 exposure。
- 为工具库、工作流和 Agent 提供同一份能力摘要。

不应承担：

- 项目权限。
- 任务创建。
- 工作流节点状态。

### 4.2 Run Preparation Module

Interface：

```text
prepare_run(tool_contract, run_context, input_sources) -> PreparedRun
explain_missing_inputs(tool_contract, run_context, input_sources) -> ReadinessReport
```

职责：

- 解析 Run Context。
- 解析 Artifact Binding。
- 校验 ArtifactVersion 权限和角色。
- 把标准输入投影为 executor 可消费的文件和参数。
- 生成 binding decisions、warnings、preparation suggestions。

这是当前最需要优先落地的深模块，因为工具详情页、节点独立运行、工作流调度和 Agent 都需要它。

### 4.3 Task Command Module

Interface：

```text
create_task(prepared_run) -> Task
start_task(task_id) -> Task
cancel_task(task_id) -> Task
retry_task(task_id) -> Task
```

职责：

- 统一创建、启动、取消、重试任务。
- 写入任务输入、资源画像、执行 handle 和初始状态。
- 不再让不同 Run Surface 自己拼 TaskCreate payload。

### 4.4 Standard Artifact Module

Interface：

```text
persist_outputs(task, result_manifest) -> PersistedArtifacts
validate_artifact_version(artifact_version_id, required_roles) -> ArtifactReadiness
resolve_primary_file(artifact_version_id, slot_policy) -> FileSelection
```

职责：

- 按标准 schema 持久化输出。
- 管理文件角色、元数据、谱系和版本不可变性。
- 提供 Artifact 读取和可视化所需摘要。

### 4.5 Workflow Orchestration Module

Interface：

```text
materialize_definition(definition_id) -> WorkflowPlan
preflight(plan, run_context, workflow_inputs) -> WorkflowReadiness
start_ready_nodes(workflow_run_id) -> WorkflowRunState
sync_node_task(task_event) -> WorkflowRunState
```

职责：

- 只处理节点、边、Run Surface、Workflow Input 和 Node Task Binding。
- 调用 Run Preparation Module 判断节点是否可运行。
- 调用 Task Command Module 创建任务。
- 保存并恢复节点任务和 Artifact 绑定。

不应承担：

- 工具私有字段映射。
- 文件角色猜测。
- 结果文件解析。

### 4.6 Executor Gateway Module

Interface：

```text
submit(task_execution_request) -> ExecutionHandle
inspect(handle) -> ExecutionStatus
cancel(handle) -> CancelResult
logs(handle, cursor?) -> ExecutionLogs
collect(handle) -> CollectedOutputs
```

职责：

- 对 Docker、SSH、Remote API、K8s、Slurm 提供统一 Adapter Interface。
- 隐藏底层 JobId、Pod、命令、路径和状态细节。
- 将执行结果交给 Standard Artifact Module 持久化。

### 4.7 Artifact Presentation Module

Interface：

```text
renderer_for(artifact_type) -> ArtifactRendererDescriptor
preview_payload(artifact_version_id) -> PreviewPayload
download_options(artifact_version_id) -> DownloadOption[]
```

职责：

- 按 Artifact 类型选择渲染器。
- 统一任务详情、Artifact 详情、工作流节点和结果中心的展示策略。
- 避免按工具名硬编码可视化。

## 5. 后端分层规范

### 5.1 目录职责建议

```text
backend/app/api/v1/          请求入口、权限、序列化
backend/app/domain/          领域模型、策略、纯逻辑
backend/app/application/     用例编排和 Application Facade
backend/app/execution/       Executor Gateway 与 Adapter
backend/app/infrastructure/  DB、存储、外部客户端适配
backend/app/schemas/         请求响应 DTO
backend/app/models/          ORM 模型
```

现阶段不要求一次性搬目录。可以先在现有 `services/` 下按 Interface 收敛，再逐步迁移到上述结构。

### 5.2 API 层规则

API 层只能做：

- 解析请求。
- 调用权限检查。
- 调用 Application Facade。
- 返回响应。

API 层禁止做：

- Artifact role 选择。
- Tool Contract 修补。
- 工作流节点调度判断。
- executor 命令拼接。

### 5.3 Application Facade 规则

每个用户用例应有清晰 Facade：

- `ToolRunFacade`：工具详情页和节点独立运行。
- `WorkflowRunFacade`：工作流预检、启动、同步。
- `ToolRegistrationFacade`：工具注册、自注册、样例验证。
- `ArtifactFacade`：Artifact 查询、导入、下载、可视化摘要。
- `AgentFacade`：Agent 计划生成、审批和落地。

Facade 可以协调多个深模块，但不应把深模块内部规则复制出来。

## 6. 前端分层规范

### 6.1 页面层

`views/*` 只负责路由级布局、页面状态组合和用户动作分发。页面不能直接实现 Artifact Binding、Tool Contract 归一化或任务输入投影。

### 6.2 组件层

`components/*` 负责可复用 UI。组件接收已整理的数据，不直接请求多个领域 API 做业务决策。

### 6.3 Domain 层

`domain/*` 承载可测试的前端领域逻辑，例如：

- 工具表单 schema 解释。
- Run Surface 输入模型。
- Artifact Renderer 选择。
- 任务状态展示策略。

### 6.4 Workflow 层

`workflow/*` 只处理工作流定义、节点、边、预检、运行状态和画布领域逻辑。它可以调用 Tool Contract 和 Readiness Preview，但不能复制后端 Run Preparation 的权威规则。

### 6.5 Composable 层

`composables/*` 应只负责 Vue 状态编排、事件监听和副作用管理。超过 300 行且包含大量业务判断的 composable，应拆出 domain/workflow 纯函数。

## 7. 测试规范

### 7.1 深模块接口测试

优先测试 Interface 的可观察行为：

- Tool Contract Builder 输入不同工具配置，输出标准契约。
- Run Preparation 输入不同 Run Surface，输出 PreparedRun。
- Workflow Orchestration 输入 WorkflowPlan，输出可运行节点和预检信息。
- Executor Gateway 使用 fake adapter 验证 submit/inspect/cancel/collect。

### 7.2 入口集成测试

每个 Run Surface 至少有一条集成测试：

- 工具详情页运行。
- 节点独立运行。
- 工作流全流程运行。
- Agent 计划审批后运行。

### 7.3 回归测试

每次修复工作流绑定、节点任务恢复、标准 Artifact 输出归属，都要补回归测试，避免同类问题在另一个入口复发。

## 8. 设计评审准入

新增模块或大改前必须回答：

1. 归属哪个领域对象？
2. 是否已有深模块 Interface 可以承载？
3. 是否在两个以上 Run Surface 复用？
4. 是否引入新的 Artifact type、Tool Contract 字段或 Executor Adapter？
5. 后端权威规则在哪里？
6. 前端只是预测，还是错误地成为权威？
7. 测试是否覆盖 Interface，而不是内部实现？

## 9. 禁止事项

- 禁止在页面组件里硬编码工具 slug 的业务规则。
- 禁止在工作流 scheduler 里猜测工具私有参数字段。
- 禁止 executor 直接读取或写入平台业务状态。
- 禁止 Agent 绕过 Tool Contract 直接生成不可验证任务。
- 禁止新工具接入时同时修改工具库、工作流、任务详情和智能体四处适配。
- 禁止以“先临时补一下”为理由绕过 Run Preparation Module。
