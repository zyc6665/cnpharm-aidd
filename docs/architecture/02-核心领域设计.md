# 核心领域设计

> 修订日期：2026-09-05。本次补充药研决策和实验反馈领域语言；CandidateSet、CandidateDecision、AssayResult、PredictionMeasurementLink、DesignCycle、CompoundBatch 是 V1.1/V2 拟议对象，不表示当前数据库、API 或运行时已经实现。

## 1. 领域模型总览

平台核心领域对象如下：

```text
User ── ProjectMember ── Project
                         │
                         ├─ Artifact ── ArtifactVersion ── FileRole ── File
                         ├─ Task ── TaskInput / TaskOutput / TaskLog
                         ├─ WorkflowDefinition ── WorkflowRun ── NodeState
                         ├─ Conversation / AgentRun
                         └─ ResearchBoard

Tool ── ToolVersion ── ToolContract
  │
  └─ ExecutorConfig / ResourceProfile / Examples / Tags / Groups

Project ── DesignCycle ── CandidateSet / CandidateDecision
                         ├─ CompoundBatch
                         ├─ AssayResult
                         └─ PredictionMeasurementLink
```

药研决策扩展对象只保存与研发选择、实验摘要和复盘相关的可审查事实。完整 ELN/LIMS、样品库存、仪器采集和自动实验调度不属于平台核心领域。

### 1.1 建模原则

核心领域模型必须稳定，因为它决定平台后续接入新工具、新 Artifact 类型、新执行器、新工作流和新 Agent 能力时是否需要到处改代码。

建模原则：

1. **Project 是资产归属和权限聚合，不是执行器，也不是工具配置容器。**
2. **Tool 是能力定义，Task 是运行实例，ExecutionRecord 是底层执行记录。**
3. **Artifact 是科研数据资产，File 是存储对象，两者不能混用。**
4. **Workflow 是编排定义和运行状态，不是工具适配层。**
5. **Agent 是建议和计划入口，不能绕过 Tool Contract、Run Preparation 和 Task。**
6. **Executor Adapter 是执行环境适配，不表达药物研发语义。**
7. **所有跨聚合关系优先保存 ID 引用和快照，不直接共享可变对象。**

### 1.2 聚合根

| 聚合根 | 负责 | 不负责 |
| --- | --- | --- |
| Organization | 多项目组织归属 | 工具执行、Artifact 语义 |
| Project | 研发上下文、权限、资产归属 | 工具契约、执行细节 |
| Tool | 能力身份、版本、契约、发布状态 | 运行状态、项目状态 |
| Task | 一次工具运行的状态、输入、输出、日志 | 长期资产语义、流程编排 |
| Artifact | 标准科研资产、版本、文件角色、谱系 | 执行调度、工具参数 |
| WorkflowDefinition | 可保存流程定义 | 具体任务执行状态 |
| WorkflowRun | 一次流程运行、节点状态、节点任务绑定 | 工具私有输入投影 |
| AgentRun / Conversation | 交互、计划、解释、审批 | 绕过平台执行任务 |
| ExecutionRecord | 底层执行句柄、幂等、外部状态 | 科研语义和权限决策 |

### 1.3 引用规则

跨聚合只能通过 ID、不可变版本或快照引用：

- WorkflowDefinition 引用 `tool_slug` 和 contract snapshot，不直接引用可变 Tool 对象。
- WorkflowRun 引用 Task ID 和 ArtifactVersion ID，不复制 Artifact 文件内容。
- Task 引用 ToolVersion ID 和 PreparedRun snapshot，不重新解释工作流节点。
- ArtifactLineage 引用 ArtifactVersion ID，不引用 TaskOutput 内部 JSON 路径。
- Agent 计划引用 Tool Contract 摘要和 ArtifactVersion ID，不直接生成 executor 命令。

### 1.4 生命周期边界

| 生命周期 | 对象 |
| --- | --- |
| 长期稳定 | Project、Tool、Artifact、WorkflowDefinition、ToolPackage |
| 版本不可变 | ToolVersion、ArtifactVersion、ToolPackageVersion、PlanVersion |
| 运行实例 | Task、WorkflowRun、AgentRun、ExecutionRecord |
| 展示/组织 | Tag、ToolCategory、ToolWorkbenchGroup、ResearchBoard |

设计要求：运行实例可以失败、取消、重试；版本对象不可原地修改；展示/组织对象不能成为领域规则的唯一来源。

### 1.5 药研决策扩展对象（V1.1/V2 拟议）

以下对象用于把计算结果推进到候选复核和 DMTA 反馈闭环。它们应优先引用现有 ArtifactVersion、ToolVersion、Task、Project 和外部实验系统摘要，不复制完整原始实验记录。

| 对象 | 定义 | 生命周期 | 不负责 |
| --- | --- | --- | --- |
| CandidateSet | 一次生成、筛选或重排形成的候选集合快照 | 不可变版本，可被复核和导出 | 重新计算分数、替代原始 molecule_table |
| CandidateDecision | 对候选的入选、排除、待复核及理由记录 | 审批后不可原地覆盖，更正生成新版本 | 自动决定实验、覆盖科学负责人判断 |
| CompoundBatch | 外部制备或采购批次在平台内的受控引用 | 可新增状态和外部引用，不替代库存系统 | 样品库存、采购、称量和全量批记录 |
| AssayResult | 可用于研发复盘的实验结果摘要 Artifact | ArtifactVersion 不可变，更正通过 supersedes 表达 | 原始 ELN/LIMS、仪器原始数据管理 |
| PredictionMeasurementLink | 预测/评分与实测的可比配对记录 | 由固定配对规则生成，可随新实测版本重算 | 默认按行号匹配、跨 protocol 强行比较 |
| DesignCycle | 一轮 Design-Make-Test-Analyze 复盘 | 项目内可关闭、重开并保留历史 | 自动再训练、自动实验执行 |

引用规则：

- CandidateSet 引用 `molecule_table@1` 或后续候选 ArtifactVersion，并保存筛选规则、排序协议和输入版本摘要。
- CandidateDecision 引用 CandidateSet version、分子/结构状态 ID、参与判断的预测/评分/实测 ArtifactVersion、操作者、时间和理由。
- CompoundBatch 引用 molecule/state，不反向修改分子身份；外部批号、供应商或 ELN/LIMS 链接只保存受控摘要。
- AssayResult 通过 `assay_result@1` ArtifactVersion 表达，每条测量保留 endpoint、单位、qualifier、protocol、批次和来源摘要。
- PredictionMeasurementLink 必须记录配对规则版本、排除原因、单位转换和 protocol 可比性结论。
- DesignCycle 聚合候选、批次、实验摘要、比较报告和下一轮输入，不直接拥有 Task 或 Tool。

边界要求：V1 可通过候选导出、模型卡和报告附件承载上述信息；V1.1 才引入结构化候选决策和实验摘要导入；V2 再形成多轮 DesignCycle。任何页面或 Agent 解释不得把 E1/E2 预测结果表述为已实验验证结论。

## 2. Project

### 2.1 定义

Project 是研发上下文和权限边界。项目聚合任务、Artifact、工作流、白板和智能体会话。

### 2.2 不变量

- 项目内 Artifact 不能被其他项目直接绑定。
- 项目成员权限决定能否查看、运行、编辑和管理。
- 项目归档后不应继续创建新的运行记录。

### 2.3 设计边界

- Project 不描述工具能力。
- Project 不保存工具参数 schema。
- Project 只提供上下文、权限和资产归属。

## 3. Standard Artifact

### 3.1 定义

Standard Artifact 是平台理解的科研数据对象。它由平台 registry 定义类型、版本、文件角色和元数据要求。

### 3.2 对象关系

```text
Artifact
 ├─ standard_type
 ├─ standard_version
 ├─ latest_version_id
 ├─ source_task_id
 └─ project_id

ArtifactVersion
 ├─ manifest_json
 ├─ summary_json
 ├─ metrics_json
 ├─ validation_status
 └─ files[]

ArtifactVersionFile
 ├─ role
 ├─ file_id
 └─ is_primary
```

### 3.3 不变量

- Artifact 必须归属某个项目或默认工作空间项目。
- ArtifactVersion 不可变。
- 标准类型和版本不可随意修改。
- 文件角色必须满足 registry 要求。
- 谱系关系不能跨项目建立。

### 3.4 设计边界

- File 是存储对象，Artifact 是科研语义对象。
- TaskOutput 可以包含普通文件，但只有标准结果会沉淀为 Artifact。
- 可视化应按 Artifact 类型渲染，而不是按工具名称渲染。

## 4. Tool

### 4.1 定义

Tool 是可执行能力的声明。ToolVersion 是某个版本的具体契约和执行配置。

### 4.2 Tool Contract

Tool Contract 是工具对平台的稳定接口：

```text
ToolContract
 ├─ identity
 ├─ executor
 ├─ parameters_schema
 ├─ artifacts.inputs
 ├─ artifacts.outputs
 ├─ resource_profile
 ├─ validation
 └─ examples
```

### 4.3 不变量

- 新工具必须声明确定的 Artifact 输入输出。
- 标准输出类型由平台 registry 限定。
- 参数 schema 不应承载标准 Artifact 文件输入。
- 工具不保存项目上下文。

### 4.4 设计边界

- Tool 是能力定义，Task 是运行实例。
- Tool 不直接知道工作流节点。
- Tool 不直接知道 Agent 计划。
- Tool 不直接存储集群凭据。

## 5. Task

### 5.1 定义

Task 是一次工具运行实例。所有运行入口最终都创建 Task。

### 5.2 输入模型

```text
TaskInput
 ├─ params
 ├─ file_ids
 ├─ input_bindings
 └─ standard_input_uploads
```

解释：

- `params`：普通参数。
- `file_ids`：legacy 文件输入和直接上传文件。
- `input_bindings`：已有 ArtifactVersion 绑定。
- `standard_input_uploads`：标准 Artifact slot 的直接上传文件绑定。

### 5.3 输出模型

```text
TaskOutput
 ├─ result
 ├─ file_ids
 └─ standard_artifacts
```

### 5.4 不变量

- 有已有 ArtifactVersion 绑定时必须有项目上下文。
- 有标准 Artifact 输出时必须解析出输出归属项目。
- 任务执行器不应自行决定项目归属。
- 任务日志应能解释失败原因。

### 5.5 与 ExecutionRecord 的关系

Task 是用户可见的运行实例，ExecutionRecord 是底层执行环境记录。

```text
Task
 ├─ status / progress / user-visible logs
 ├─ TaskInput / TaskOutput
 └─ execution_record_id or execution handle snapshot

ExecutionRecord
 ├─ adapter_type
 ├─ external_id
 ├─ idempotency_key
 ├─ request_snapshot
 └─ adapter status
```

规则：

- 一个 Task 可以有一个当前 ExecutionRecord。
- 重试应生成新的 ExecutionRecord，但保留 Task 的用户可见历史。
- ExecutionRecord 不决定项目权限，不解释 Artifact 语义。
- Task 状态是用户视角，ExecutionRecord 状态是执行环境视角。

## 6. Run Context

### 6.1 定义

Run Context 是一次运行的上下文，不属于 Tool Contract。

### 6.2 类型

| 类型 | 场景 | 输出归属 |
| --- | --- | --- |
| Project Context | 从项目进入工具或工作流 | 当前项目 |
| Default Workspace Context | 独立工具运行但产出标准 Artifact | 用户默认工作空间项目 |
| File-only Context | 普通文件/JSON 输出工具 | 无需 Artifact 归属 |

### 6.3 不变量

- Run Context 由调用入口和后端权限共同决定。
- Tool Contract 不包含 Run Context。
- 输出归属必须在任务派发前确定。

## 7. Artifact Binding

### 7.1 定义

Artifact Binding 是满足工具 Artifact Slot 的决策。

### 7.2 输入来源

- Existing ArtifactVersion。
- Direct Upload。
- Workflow Input。
- Upstream Node Output。

### 7.3 输出

Run Preparation Module 应输出：

- `params`。
- `file_ids`。
- `input_bindings`。
- `standard_input_uploads`。
- `binding_decisions`。
- `missing_inputs`。
- `preparation_suggestions`。

### 7.4 不变量

- Run Preparation 是运行准备唯一权威入口；Artifact Binding 是其中的 slot/source/role 决策。
- 前端可以预测和展示，后端必须最终校验。
- 角色不满足时不应静默降级。

## 8. Workflow

### 8.1 定义

WorkflowDefinition 是流程模板，WorkflowRun 是一次运行。

### 8.2 节点模型

```text
WorkflowNode
 ├─ id
 ├─ kind
 ├─ tool_slug
 ├─ params
 ├─ artifact_input_slots
 ├─ artifact_outputs
 ├─ artifact_inputs
 └─ semantic_inputs / semantic_outputs legacy
```

### 8.3 边模型

```text
WorkflowEdge
 ├─ source
 ├─ target
 ├─ source_output
 └─ target_input
```

### 8.4 不变量

- 边连接的是标准 Artifact 类型或 slot，不是文件路径。
- 下游输入优先从上游 ArtifactVersion 自动绑定。
- 工作流外部输入只出现在流程边界。
- 保存的工作流加载时需要用当前 Tool Contract 补齐旧节点槽位。

### 8.5 WorkflowDefinition 与 WorkflowRun

WorkflowDefinition 是可编辑模板，WorkflowRun 是运行快照。

规则：

- WorkflowDefinition 保存用户画布、节点、边、默认参数和 contract snapshot。
- WorkflowRun 启动时 materialize 当前 definition，运行期间不受后续模板编辑影响。
- WorkflowRun 的 node state 保存 Node Task Binding、Artifact Binding 和错误解释。
- WorkflowRun 不保存工具私有适配逻辑，只保存可恢复的运行事实。

### 8.6 Node Task Binding

Node Task Binding 是工作流节点与实际 Task 的绑定记录。

```text
NodeTaskBinding
 ├─ node_id
 ├─ task_id
 ├─ tool_slug
 ├─ tool_version_id
 ├─ artifact_version_ids_by_output
 ├─ binding_decisions
 └─ status_snapshot
```

不变量：

- 保存工作流后重新加载，节点必须能恢复最近一次 Task 和输出 Artifact。
- 同一节点重跑会产生新的 Task，并更新当前 Node Task Binding。
- 历史 Task 不应被删除，除非用户显式清理运行历史。

## 9. Agent

### 9.1 定义

Agent 是辅助规划模块。它可以生成建议和草稿，但不能绕过平台领域规则。

### 9.2 输入

- 用户自然语言。
- 项目上下文。
- 工具契约。
- Artifact 列表。
- 工作流运行状态。

### 9.3 输出

- 解释。
- 工具推荐。
- 工作流草稿。
- 缺失输入提示。
- 结果总结。

### 9.4 不变量

- Agent 输出必须经过工具契约和权限校验。
- Agent 不直接写入不可审计执行状态。
- Agent 生成的流程必须落入 WorkflowDefinition 或 Task。

### 9.5 PlanVersion 与 AgentRun

AgentRun 是一次智能体运行，PlanVersion 是可审批、可追踪的计划快照。

规则：

- AgentRun 可以产生多个 PlanVersion。
- 被批准的 PlanVersion 才能落成 WorkflowDefinition 或 Task。
- PlanVersion 应引用 Tool Contract 摘要和 ArtifactVersion ID，不保存 executor 私有命令。
- PlanDecision 是审批结果，不应被后续消息覆盖。

## 10. 外部数据库

### 10.1 定义

外部数据库模块负责从公共数据库查询并导入数据。

### 10.2 不变量

- 外部记录导入后必须转成标准 Artifact。
- 必须保留来源和时间。
- 导入动作应记录到项目或默认工作空间。

## 11. Tool Package

### 11.1 定义

Tool Package 是工具交付包，不是运行实例，也不是执行器类型。

### 11.2 对象关系

```text
ToolPackage
 └─ ToolPackageVersion
     ├─ manifest
     ├─ manifest_digest
     ├─ signature
     └─ validation_status
```

### 11.3 不变量

- ToolPackageVersion 不可变。
- manifest_digest 必须稳定，后续用于校验交付包是否被篡改。
- Tool Package 导入后应转换为 ToolVersion + Tool Contract。
- 真正运行时必须落到具体 executor，例如 Docker、SSH、Remote API、K8s 或 Slurm。

## 12. Research Board

### 12.1 定义

Research Board 是用户组织研发资产和思路的展示/探索空间。

### 12.2 不变量

- Research Board 不直接执行任务。
- 白板节点可以引用 Artifact、Task、Workflow、Note，但引用对象仍由原聚合管理。
- 白板内容保存为用户视角的布局和注释，不应成为领域事实的唯一来源。

## 13. 领域模型扩展规则

新增模型前必须判断它属于哪类：

| 新需求 | 首选模型 |
| --- | --- |
| 新科学数据类型 | Standard Artifact schema + ArtifactVersion roles |
| 新工具或模型 | ToolVersion + Tool Contract |
| 新预测、评分或实验语义 | Scientific Result Profile + ModelCard / VerificationRecord |
| 新候选筛选或入选记录 | CandidateSet + CandidateDecision |
| 新实验摘要回写 | assay_result@1 ArtifactVersion + AssayResult 导入记录 |
| 新预测-实测比较 | PredictionMeasurementLink + 固定配对规则版本 |
| 新 DMTA 轮次复盘 | DesignCycle + 不可变引用快照 |
| 新运行入口 | Run Surface + Run Preparation，不新增 Task 分支 |
| 新计算环境 | Executor Adapter + ExecutionRecord |
| 新流程能力 | WorkflowDefinition / WorkflowRun / Node Task Binding |
| 新智能体能力 | AgentRun / PlanVersion / PlanDecision |
| 新展示方式 | Artifact Renderer 或 ResearchBoard 引用 |

如果一个新对象同时想承担“能力定义、运行状态、资产语义、展示布局”，必须拆分。

## 14. 需要统一的领域语言

| 当前混乱表达 | 推荐表达 |
| --- | --- |
| 文件输入、Artifact 输入、标准输入混用 | Artifact Slot |
| 工具需要项目 | 运行需要 Run Context |
| 工作流自动处理参数 | Run Preparation 处理运行准备，Artifact Binding 决定 slot/source/role |
| 节点结果 | Task Output + Standard Artifact |
| 模型工具部署方式 | Executor Adapter |
| 工作流任务内容 | Node Task Binding |
| 候选清单、筛选表、入选列表混用 | CandidateSet 表示固定候选集合，CandidateDecision 表示人工决策 |
| 实验结果、预测结果、对接分数混用 | AssayResult、Prediction/Score Column、ScoreDefinition 分开表达 |
| 实验批次等同分子 | CompoundBatch 是外部实物批次引用，molecule/state 是结构身份 |
| 预测误差自动按行计算 | PredictionMeasurementLink 基于 endpoint、单位、protocol 和身份规则生成 |
| 研发闭环等于自动实验或自动训练 | DesignCycle 是可审查复盘对象，不触发无人审查的实验或训练 |

## 15. 领域治理规则

1. 新功能必须说明它归属哪个领域对象。
2. 新工具必须先声明 Tool Contract。
3. 新数据资产必须先判断是否应成为 Standard Artifact。
4. 新工作流能力必须依赖 Artifact Slot，不依赖工具私有字段。
5. 新执行方式必须作为 Executor Adapter，不进入业务页面逻辑。
6. 新运行入口必须复用 Run Preparation 和 Task Command Module。
7. 新智能体能力必须先生成可验证计划，再落入 Workflow 或 Task。
