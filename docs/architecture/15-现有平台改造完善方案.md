# 现有平台改造完善方案

## 1. 结论

现有平台已经可以进入原型改造阶段，但不应开始大规模重写。

推荐策略是：**以 V1 可验收链路为牵引，采用接口冻结、垂直链路迁移、双轨兼容和可回滚发布的受控改造方式**。

这意味着下一阶段的重点不是继续堆新页面或新工具，也不是推倒重来，而是把平台已经形成的能力收敛到稳定的功能地基：Standard Artifact、Tool Contract、Run Preparation、Task Command、Executor Gateway、Result Manifest、Workflow Orchestration、Renderer Registry、Task View 和 Governance Registry。

## 2. 当前平台判断

### 2.1 已具备的改造基础

现有代码和文档已经具备改造基础：

- 后端已经存在工具、任务、外部数据库、蛋白处理、执行器、远端工具、工具包、工具模板、标准 Artifact 等模块雏形。
- 前端已经存在工具中心、任务中心、工作流、Artifact 可视化、领域层和部分 workflow 纯函数。
- 文档已经形成需求、功能、架构、Artifact、Tool Contract、Run Preparation、部署和治理路线的基线。
- 两条药物研发验收链路已经明确，可作为重构过程中的保护网。

因此现阶段适合做“原型工程化改造”，不适合重建一个新系统。

### 2.2 当前主要风险

| 风险 | 表现 | 对平台的影响 |
| --- | --- | --- |
| 入口不统一 | 工具详情页、节点独立运行、工作流运行各自拼参数 | 新工具接入后仍需要多处适配 |
| Artifact 边界不稳定 | 文件、Artifact、ArtifactVersion、semantic type 混用 | 连线、可视化、下载和下游运行不可靠 |
| 工作流承担过多职责 | scheduler、preflight、persistence 都在猜测工具契约 | 工作流复杂，保存加载容易丢任务和产物 |
| 任务生命周期分散 | 创建、启动、取消、重试、日志、输出回收分布在不同路径 | 长任务和重计算工具难治理 |
| 前端页面吸收领域逻辑 | 页面和 composable 中存在绑定、预检、可视化策略 | UI 改动容易破坏运行语义 |
| 管理后台治理不足 | 标签、分类、renderer、executor profile、发布检查不完整 | 新工具越多，管理成本越高 |

## 3. 改造目标

### 3.1 产品目标

- 科研用户只需要拖节点、连线、填写必要参数或上传文件，即可运行工作流。
- 工具既能独立运行，也能在项目内运行，也能作为工作流节点运行。
- 保存的工作流重新加载后，应恢复节点任务、产物绑定、契约快照和可视化状态。
- 新模型或新工具接入后，不需要为工作流单独写适配逻辑。
- 管理员能治理工具、标签、Artifact 标准、renderer、executor、发布检查和审计。

### 3.2 架构目标

- Run Preparation 成为所有运行入口的唯一权威。
- Workflow Orchestration 只负责节点、边、运行状态和 Node Task Binding。
- Artifact Binding Resolver 降级为 Run Preparation 内部的 slot/source/role 决策能力。
- Task Command 统一 create、start、cancel、retry、attach outputs、sync status。
- Executor Gateway 统一 builtin、python、docker、ssh、remote_api、k8s、slurm。
- Result Manifest 统一工具输出回收、Artifact 持久化和 lineage。
- Renderer Registry 统一节点、任务详情、结果中心和 Artifact 详情页的可视化策略。

## 4. 改造原则

1. **不做大爆炸重写**：先包住旧实现，再沿验收链路替换。
2. **先接口后实现**：冻结 Architecture Kernel Interface，新代码只依赖稳定接口。
3. **先主链路后边缘功能**：优先保障 Fetch PDB 到 LVpocket、PubChem 到 ADMET 两条链路。
4. **先后端权威后前端体验**：前端可以做 preview，但最终可运行性以后端 Run Preparation 为准。
5. **先标准 Artifact 后工具私有字段**：工作流连线基于 slot-to-slot 和 Artifact type，不基于文件名。
6. **先兼容后清理**：保留 legacy adapter，验证通过后再删除重复逻辑。
7. **先可回滚后扩展**：每阶段必须有验收、回滚和风险隔离策略。

## 5. 改造范围

### 5.1 纳入本轮改造

- Tool Contract Builder 和契约校验。
- Standard Artifact Registry、file role、metadata schema、readiness policy。
- Run Preparation、Readiness Report、PreparedRun、BindingDecision。
- Result Manifest、Artifact Persistence、Artifact Lineage。
- Task Command、Execution Record 和 Task 可见状态。
- Workflow Orchestration、Node Task Binding、saved workflow hydration。
- Executor Gateway 的 Docker、SSH、Remote API 基础统一。
- Renderer Registry 和工作流节点可视化复用。
- Task View 和任务中心工作台基础能力。
- Governance Registry、Tool Release、标签、分类、renderer、executor profile 管理。

### 5.2 暂不纳入本轮改造

- 全量微服务拆分。
- 全局 UI 重做。
- K8s / Slurm 生产化落地作为 V1 阻断项。
- MD 完整生产链路。
- 复杂 Agent 自动闭环编排。
- 多租户计费、复杂审批流和企业级权限重构。

## 6. 目标模块与改造动作

### 6.1 Tool Contract Module

定位：平台理解工具的唯一入口。

改造动作：

- 稳定 Tool Contract DTO，覆盖工具身份、版本、参数、Artifact slots、executor、resource profile、example inputs 和 smoke test。
- 将 Remote API、Docker、SSH、内置工具和 Tool Package 统一归一化为 Tool Contract。
- 将 legacy contract 修补集中到后端 builder，前端不再承担契约修补。

重点文件：

- `backend/app/services/tool_contracts.py`
- `backend/app/tool_packages/`
- `backend/app/remote_tools/`
- `backend/app/tool_templates/`
- `frontend/src/domain/tools/`
- `frontend/src/workflow/contract-bindings.ts`

验收：

- 新工具只要声明标准 slots，即可出现在工具库和工作流工具库。
- 一键填入示例、节点独立运行、工作流运行读取同一契约。

### 6.2 Run Preparation Module

定位：所有运行入口的唯一准备层。

改造动作：

- 新增或收敛 `RunPreparationInput`、`ReadinessReport`、`PreparedRun`、`PreparationError`。
- 统一处理 standalone run、project run、workflow node run、workflow run、agent planned run。
- 统一处理上传文件、已有 ArtifactVersion、workflow input、上游节点输出和用户普通参数。
- 将 standard input upload、project_id、role policy、metadata 校验、cardinality 校验收敛到该模块。

重点文件：

- `backend/app/services/artifact_binding_resolver.py`
- `backend/app/tasks/service.py`
- `backend/app/services/workflow_scheduler.py`
- `frontend/src/domain/tools/standard-artifact-run-context.ts`
- `frontend/src/composables/useStandaloneNodeRun.ts`
- `frontend/src/workflow/preflight.ts`

验收：

- 无项目上下文时，工具可使用用户上传文件独立运行。
- 有项目上下文时，工具可选择已有 ArtifactVersion 或上传新文件运行。
- 工作流节点连线后，上游 Artifact 自动绑定到下游 slot。
- 所有不可运行原因都返回标准 BindingDecision。

### 6.3 Result Manifest 与 Artifact Persistence

定位：工具输出进入平台数据资产的统一入口。

改造动作：

- 要求标准工具输出 Result Manifest。
- 平台侧校验 output slot、artifact type、file role、metadata、checksum、size、mime 和 lineage。
- 将输出持久化为 ArtifactVersion，禁止下游直接依赖临时文件路径。

重点文件：

- `backend/app/artifact_standards/`
- `backend/app/files/`
- `backend/app/models/`
- `backend/app/tasks/service.py`
- `backend/app/worker/tools/`

验收：

- Fetch PDB 输出可作为 protein_structure ArtifactVersion 进入 Protein Preparation。
- PubChem ligand 输出可作为 ligand_structure ArtifactVersion 进入 RDKit 和 ADMET。
- 保存工作流时 Node Task Binding 能引用 Task 和 ArtifactVersion。

### 6.4 Workflow Orchestration Module

定位：表达节点、边、工作流运行和节点任务绑定，不承担工具私有适配。

改造动作：

- 将 scheduler 内部拆为 plan materialization、readiness、dispatch、state sync、hydration。
- 工作流边从文件路径绑定改为 `source_node.output_slot -> target_node.input_slot`。
- 保存工作流时保留 contract snapshot、Node Task Binding 和 ArtifactVersion binding。
- 加载工作流时优先当前 contract，兼容则 hydrate，不兼容则保留 snapshot 并提示预检。

重点文件：

- `backend/app/services/workflow_scheduler.py`
- `backend/app/services/workflow_validation.py`
- `backend/app/services/workflow_reconciliation.py`
- `backend/app/services/workflow_runs.py`
- `frontend/src/workflow/`
- `frontend/src/composables/useWorkflow*.ts`
- `frontend/src/views/workflow/index.vue`

验收：

- 保存的工作流加载后不再出现空节点任务。
- Fetch PDB -> Protein Preparation -> LVpocket 不需要手动选择上游文件路径。
- 上游未完成、类型不匹配、缺 role、缺 metadata、权限不足能被明确区分。

### 6.5 Task Command 与 Executor Gateway

定位：统一任务生命周期和底层计算执行。

改造动作：

- Task Command 统一 create、start、cancel、retry、attach outputs、sync status。
- Execution Record 记录底层执行尝试，Task 保持用户可见运行实例语义。
- Executor Gateway 统一 `submit`、`inspect`、`cancel`、`logs`、`collect`。
- V1 先统一 builtin、python、docker、ssh、remote_api；K8s 和 Slurm 作为 V2 adapter。

重点文件：

- `backend/app/tasks/service.py`
- `backend/app/tasks/executors/`
- `backend/app/execution/`
- `backend/app/execution/adapters/`
- `backend/app/remote_tools/`

验收：

- SSH、Docker、Remote API 任务状态、日志、取消和输出回收表现一致。
- 节点独立运行和整条工作流运行最终落到同一 Task Command。
- 长任务取消不会留下错误的 ArtifactVersion。

### 6.6 前端工作台与 Renderer Registry

定位：让用户体验傻瓜化，同时让前端领域逻辑可测试。

改造动作：

- 工作流页面拆为 shell、canvas、tool library、node inspector、result center。
- 可视化按 Standard Artifact type 走 Renderer Registry，不按工具 slug 特判。
- 工具库筛选来自 Governance Registry 和 Tool Contract，不硬编码分类。
- 任务中心从流水表升级为 Task View 工作台。

重点文件：

- `frontend/src/components/artifacts/`
- `frontend/src/components/tasks/`
- `frontend/src/components/tools/`
- `frontend/src/components/workflow/`
- `frontend/src/domain/tasks/`
- `frontend/src/domain/tools/`
- `frontend/src/workflow/`
- `frontend/src/views/tasks/`
- `frontend/src/views/workflow/`

验收：

- 节点可独立运行、可查看预检、可查看输入输出和可视化。
- 节点内预览、放大查看、任务详情、结果中心使用同一 renderer。
- 任务中心支持系统视图、筛选、分组、保存视图和详情侧栏。

### 6.7 Governance Registry

定位：让管理员管理平台扩展能力，而不是让开发者改硬编码。

改造动作：

- 治理标签、工具分类、研发阶段、Artifact roles、renderer mapping、executor profiles 和 validation policies。
- 工具发布必须经过 contract validation、smoke test 和治理检查。
- 管理操作写入审计日志。

重点文件：

- `backend/app/api/v1/`
- `backend/app/models/`
- `frontend/src/domain/admin/`
- `frontend/src/views/tools/`

验收：

- 管理员可调整工具标签和筛选项。
- 新工具发布失败能看到明确失败原因。
- 工具启用、禁用、发布、回滚、标签调整都有审计记录。

## 7. 阶段计划

| 阶段 | 周期建议 | 目标 | 主要产出 | 验收口径 |
| --- | --- | --- | --- | --- |
| M0 基线冻结 | 1-2 天 | 建立保护网，冻结接口草案 | 回归脚本、现状清单、接口草案 | 两条验收链路当前状态可复现 |
| M1 Run Preparation MVP | 3-5 天 | 统一工具详情、节点独立运行、工作流节点运行 | PreparedRun、ReadinessReport、BindingDecision | 同一工具多入口表现一致 |
| M2 Result Manifest 收敛 | 3-5 天 | 输出标准化进入 Artifact | Manifest 校验、ArtifactVersion 持久化、lineage | 下游不依赖临时文件路径 |
| M3 工作流瘦身 | 4-7 天 | 工作流只做编排和任务绑定 | slot-to-slot edge、hydration、Node Task Binding | 保存加载恢复任务和产物 |
| M4 Task / Executor 统一 | 3-5 天 | 任务生命周期和执行器状态统一 | Task Command、ExecutionHandle、基础 adapter | SSH/Docker/Remote API 可统一取消和回收 |
| M5 前端工作台收敛 | 3-5 天 | 用户操作傻瓜化 | 工作流面板、Renderer Registry、Task View | 用户无需手动绑定上下游文件 |
| M6 管理治理闭环 | 3-5 天 | 管理员可治理工具扩展 | Governance Registry、Tool Release、审计 | 新工具上线不改 workflow |
| M7 验收与清理 | 2-3 天 | 清理重复逻辑和文档同步 | 回归报告、迁移记录、遗留清单 | P0 验收场景全部通过 |

## 8. 回归保护网

### 8.1 后端单元测试

- Tool Contract validation。
- Artifact readiness 和 role compatibility。
- Run Preparation binding decisions。
- Result Manifest validation。
- Task Command create/start/cancel/retry。
- Executor Gateway fake adapter。
- Saved workflow hydration。

### 8.2 前端单元测试

- `contract-bindings` 归一化。
- workflow preflight 展示。
- `useWorkflowPersistence` 保存加载恢复。
- `useWorkflowCanvas` 节点、边和状态同步。
- Task View query state。
- Artifact Renderer Registry 选择策略。

### 8.3 端到端验收

- Fetch PDB -> Protein Preparation -> LVpocket。
- Fetch PubChem Ligand -> Ligand Preparation -> RDKit Properties -> ADMET。
- 保存工作流、刷新页面、重新加载、恢复节点任务和产物。
- Remote API 自注册、smoke test、运行、取消、输出回收。
- SSH 长任务运行、日志读取、取消和失败恢复。
- 大量任务下任务中心筛选、分组、保存视图和详情侧栏可用。

## 9. 回滚策略

| 改造点 | 回滚方式 | 保留数据 |
| --- | --- | --- |
| Run Preparation | 保留旧 TaskCreate 路径，按开关切回 | 用户输入、ArtifactVersion、Task |
| Result Manifest | 保留旧输出扫描路径，仅新工具强制 manifest | 原始输出文件和任务日志 |
| Workflow Hydration | 保留 contract snapshot，无法兼容时展示只读节点 | WorkflowDefinition、Node Task Binding |
| Executor Gateway | adapter 失败时切回原 executor 实现 | ExecutionRecord、日志、输出目录 |
| Renderer Registry | 无 renderer 时降级到文件列表和下载 | ArtifactFile、metadata |
| Governance Registry | 注册项发布失败不影响已发布工具 | 已发布 Tool Contract 和历史标签 |

## 10. 不做清单

本轮改造明确不做以下事项：

- 不重做所有页面视觉风格。
- 不迁移到全量微服务。
- 不让 K8s / Slurm 阻塞 V1 验收。
- 不给每个药研工具写 workflow 专属适配。
- 不让前端页面决定最终 Artifact role 和执行 payload。
- 不直接删除 legacy 实现，除非已有测试覆盖并完成链路验收。
- 不把 Agent 自动编排作为当前平台地基的前置条件。

## 11. 成功判据

平台改造完成第一阶段后，应满足以下条件：

1. 新工具只要提供标准 Tool Contract、Result Manifest 和 executor 配置，即可进入工具库、工作流和 Agent 上下文。
2. 工具详情页、节点独立运行、整条工作流运行使用同一 Run Preparation 结果。
3. Fetch PDB -> Protein Preparation -> LVpocket 链路不需要手动绑定中间文件。
4. PubChem -> Ligand Preparation -> RDKit Properties -> ADMET 链路不需要页面特判。
5. 保存工作流加载后能恢复节点任务、产物、契约快照和预检状态。
6. Task、ExecutionRecord、ArtifactVersion 和 WorkflowRun 能形成可追踪 lineage。
7. 管理员能治理工具标签、分类、renderer、executor profile、发布检查和审计。
8. 旧入口没有明显退化，失败原因能被 BindingDecision 或标准任务错误解释。

## 12. 实施优先级

### P0：必须先做

- 冻结 Tool Contract、Artifact Slot、BindingDecision、Result Manifest、PreparedRun。
- Run Preparation 后端权威化。
- 两条药研验收链路回归保护。
- 保存工作流恢复 Node Task Binding。
- 工具独立运行和工作流节点独立运行统一。

### P1：随后推进

- Task Command 和 Executor Gateway 统一。
- Renderer Registry 收敛。
- Task View 工作台。
- Governance Registry 基础治理。

### P2：稳定后扩展

- K8s / Slurm adapter。
- MD 长任务生产链路。
- Agent 可执行计划审批。
- 大规模 Artifact 生命周期治理。

## 13. 建议下一步

建议下一步不直接进入大范围代码施工，而是按以下顺序启动改造：

1. 做一次现有功能到 Architecture Kernel 的映射审计。
2. 建立 M0 回归脚本，固定当前两条验收链路和保存加载场景。
3. 冻结 `RunPreparationInput`、`PreparedRun`、`ReadinessReport`、`BindingDecision`、`ResultManifest` 五个核心 Interface。
4. 先实现 Run Preparation MVP，并让工具详情页、节点独立运行、工作流节点运行接入。
5. 再做 Result Manifest 和 Workflow Orchestration 瘦身。

只有 M0 和 M1 通过后，才建议进入更大范围的前端工作台和管理治理改造。这样能避免继续走一步改一步，也能避免一次性重构把现有可用功能打散。

## 14. 全生命周期改造蓝图

本方案从启动到最终收口分为 5 个大阶段、8 个里程碑和 4 次正式切换。

```text
准备期
  -> 地基接口冻结
  -> 双轨运行
  -> 主链路切换
  -> 治理闭环
  -> legacy 退场
```

| 大阶段 | 目标 | 对应里程碑 | 允许上线范围 |
| --- | --- | --- | --- |
| 准备期 | 建立保护网，锁定改造边界 | M0 | 仅测试、文档、feature flag |
| 地基接口冻结 | 定义所有入口共享的稳定 Interface | M1-M2 | 可上线后端兼容层 |
| 双轨运行 | 新旧路径并行，用户入口逐步迁移 | M2-M4 | 可上线部分工具和工作流链路 |
| 主链路切换 | V1 主链路全部使用新地基 | M4-M6 | 可作为默认路径 |
| legacy 退场 | 删除重复逻辑，进入长期治理 | M7 | 可关闭旧路径 |

改造期间不能只按文件或页面推进，必须按用户可见链路推进。每次切换都必须回答：用户入口是否可用、Artifact 是否可追溯、任务是否可取消、工作流是否可恢复、管理员是否可治理。

## 15. 终态架构

### 15.1 终态依赖方向

终态依赖方向固定如下：

```text
Frontend Run Surfaces
  -> Backend Run Preparation
  -> Task Command
  -> Executor Gateway
  -> Result Manifest Collector
  -> Artifact Persistence + Lineage
  -> Renderer Registry

Workflow Orchestration
  -> Backend Run Preparation
  -> Task Command

Agent Plan
  -> Tool Contract + Artifact Registry
  -> Backend Run Preparation
```

禁止反向依赖：

- Run Preparation 不依赖前端页面状态。
- Task Command 不依赖 workflow canvas。
- Executor Gateway 不理解 Artifact 业务语义。
- Workflow Orchestration 不拼 executor payload。
- Renderer Registry 不按工具执行逻辑决定产物语义。

### 15.2 终态用户链路

科研用户视角：

1. 进入项目或直接打开工具。
2. 选择工具、拖入工作流或使用模板。
3. 上传文件、选择已有 Artifact 或填写必要参数。
4. 平台预检输入是否满足工具 slot。
5. 平台自动补齐上游绑定、格式转换建议和处理建议。
6. 用户点击运行。
7. 任务进入统一任务中心。
8. 输出自动成为 ArtifactVersion，并可直接可视化、下载和进入下游。
9. 工作流保存后再次加载，节点任务和产物仍可恢复。

管理员视角：

1. 注册或导入工具。
2. 校验 Tool Contract、Artifact slots、Result Manifest 和 example inputs。
3. 配置标签、分类、研发阶段、renderer、executor profile 和发布范围。
4. 运行 smoke test。
5. 发布到工具库、工作流工具库和 Agent 工具上下文。
6. 通过质量看板查看失败率、平均耗时、资源使用和用户使用情况。

## 16. 接口冻结清单

以下 Interface 是改造的硬地基。M0 结束前必须冻结字段草案；M1-M2 可允许小范围补字段，但不能改变语义。

| Interface | 所属模块 | 调用方 | 必须稳定的内容 |
| --- | --- | --- | --- |
| `ToolContract` | Tool Contract | 工具库、工作流、Agent、Run Preparation | 工具身份、版本、参数 schema、input slots、output slots、executor、examples |
| `ArtifactTypeSpec` | Artifact Registry | Run Preparation、Result Manifest、Renderer Registry | type ref、版本、file roles、metadata schema、readiness policy |
| `RunPreparationInput` | Run Preparation | 工具详情页、节点独立运行、工作流、Agent | run surface、context、user params、uploads、artifact refs、workflow sources |
| `ReadinessReport` | Run Preparation | 前端预检、工作流预检、Agent | 每个 input slot 的状态、原因、建议动作 |
| `BindingDecision` | Run Preparation | 前端、工作流、日志、Agent | ready、missing、needs_selection、needs_preparation、invalid_type 等状态 |
| `PreparedRun` | Run Preparation | Task Command | 规范化参数、输入文件映射、Artifact 输入、执行约束、输出预期 |
| `TaskCommand` | Task Command | API、Workflow、Agent | create、start、cancel、retry、attach outputs、sync status |
| `ExecutionRequest` | Executor Gateway | Task Command | command、env、input mount、output directory、resource profile、timeout |
| `ExecutionHandle` | Executor Gateway | Task Command、Worker | executor type、external id、status cursor、log cursor、cancel token |
| `ResultManifest` | Result Collector | Worker、Artifact Persistence | output slot、artifact type、file roles、metadata、checksum、lineage |
| `WorkflowDefinition` | Workflow Orchestration | 前端、后端工作流 | nodes、edges、workflow inputs、contract snapshot、version |
| `NodeTaskBinding` | Workflow Orchestration | 工作流保存加载、结果中心 | node id、task id、artifact version bindings、contract version |
| `ArtifactRendererDescriptor` | Renderer Registry | 节点、任务详情、结果中心 | artifact type、role、viewer kind、download policy、preview policy |
| `GovernanceRegistryEntry` | Governance Registry | 管理后台、工具库筛选 | taxonomy、tags、renderer mapping、executor profile、validation policy |

冻结规则：

- 任何新工具接入不得绕过 `ToolContract`。
- 任何运行入口不得绕过 `RunPreparationInput -> PreparedRun`。
- 任何标准输出不得绕过 `ResultManifest -> ArtifactVersion`。
- 任何工作流持久化不得只保存临时文件路径。

## 17. 阶段门设计

### 17.1 G0：现状基线门

进入条件：

- 当前前后端可启动。
- 当前工具详情页、工作流页、任务中心可进入。
- 当前两条主链路的失败点和可用点已记录。

退出条件：

- 有一键回归脚本或明确手工验收脚本。
- 有当前 contract、Artifact、Task、Workflow 的现状清单。
- 所有后续改造项能映射到本方案模块。

失败处理：

- 若当前主链路无法复现，先修复阻断性 bug，不进入接口迁移。

### 17.2 G1：接口冻结门

进入条件：

- G0 通过。
- 现有 Tool Contract、Artifact type、Task payload、Workflow save payload 已抽样。

退出条件：

- `ToolContract`、`RunPreparationInput`、`PreparedRun`、`ResultManifest`、`NodeTaskBinding` 草案固定。
- 新代码依赖新 Interface，旧代码通过 adapter 接入。
- 文档和测试 fixture 使用同一字段名。

失败处理：

- 若字段争议影响运行语义，暂停施工，先补充 Artifact 边界或 Tool Contract 文档。

### 17.3 G2：Run Preparation 切换门

进入条件：

- G1 通过。
- 至少 Fetch PDB、Fetch PubChem、Protein Preparation、LVpocket、RDKit、ADMET 有 contract fixture。

退出条件：

- 工具详情页、节点独立运行、工作流节点运行都能调用同一个后端准备逻辑。
- 前端预检展示来自 `ReadinessReport`，不再自己生成最终执行 payload。
- BindingDecision 覆盖常见错误：缺输入、类型不匹配、缺 role、缺 metadata、上游未完成、权限不足。

失败处理：

- 使用 feature flag 切回旧 TaskCreate 路径，并保留准备失败样本用于测试。

### 17.4 G3：Result Manifest 切换门

进入条件：

- G2 通过。
- 标准 Artifact type 和 file role 已覆盖两条主链路。

退出条件：

- 新工具输出必须产出 Result Manifest。
- 平台按 manifest 创建 ArtifactVersion。
- 下游节点不再读取上游临时输出目录。

失败处理：

- 保留旧目录扫描作为 legacy collector，但仅对旧工具生效。

### 17.5 G4：Workflow 主链路切换门

进入条件：

- G3 通过。
- 工作流保存格式支持 contract snapshot 和 Node Task Binding。

退出条件：

- Fetch PDB -> Protein Preparation -> LVpocket 连续运行通过。
- PubChem -> Ligand Preparation -> RDKit -> ADMET 连续运行通过。
- 保存、刷新、加载后节点任务和 ArtifactVersion 绑定可恢复。

失败处理：

- 新 workflow run 走新路径；历史 workflow 保留只读或 legacy hydration。

### 17.6 G5：Executor 统一门

进入条件：

- G4 通过。
- SSH、Docker、Remote API 至少各有一个测试工具。

退出条件：

- 三类 executor 均支持 submit、inspect、cancel、logs、collect。
- Task 状态和 ExecutionRecord 状态不再混用。
- 取消任务不会产生成功状态 ArtifactVersion。

失败处理：

- adapter 按 executor type 单独回滚，不影响已切换的 Run Preparation。

### 17.7 G6：前端工作台切换门

进入条件：

- G4 通过。
- Renderer Registry 能覆盖 protein、ligand、pocket、table、report。

退出条件：

- 工作流页面仅负责交互，不决定后端运行语义。
- 节点面板、任务详情、结果中心共享 renderer。
- 工具库筛选来自治理配置和 contract metadata。

失败处理：

- 前端按页面级开关切回旧布局，但不切回旧后端运行路径。

### 17.8 G7：治理和 legacy 退场门

进入条件：

- G5、G6 通过。
- P0 验收场景连续通过。

退出条件：

- 新工具发布走 Governance Registry 和 Tool Release。
- legacy contract 修补、workflow 专属特判、目录扫描输出等旧路径有删除清单。
- 删除旧路径后回归测试通过。

失败处理：

- 未删除的 legacy 路径必须标注 owner、删除条件和最后期限。

## 18. 迁移矩阵

### 18.1 后端迁移顺序

| 顺序 | 模块 | 迁移动作 | 完成信号 |
| --- | --- | --- | --- |
| 1 | Tool Contract | builder 归一化，legacy 修补后移 | 前端消费统一 contract |
| 2 | Artifact Registry | 固定 type、role、metadata、readiness | 两条主链路无需文件名猜测 |
| 3 | Run Preparation | 汇总所有运行入口准备逻辑 | 多入口同一 PreparedRun |
| 4 | Task Command | PreparedRun 转 Task 生命周期命令 | create/start/cancel/retry 一致 |
| 5 | Result Collector | manifest 校验和 ArtifactVersion 创建 | 输出可追溯、可下游复用 |
| 6 | Workflow Orchestration | scheduler 瘦身，保存恢复绑定 | 工作流不再承担工具适配 |
| 7 | Executor Gateway | adapter 统一提交、日志、取消、回收 | executor 差异不泄漏到工作流 |
| 8 | Governance Registry | 标签、分类、renderer、executor profile 治理 | 新工具发布不改代码筛选项 |

### 18.2 前端迁移顺序

| 顺序 | 区域 | 迁移动作 | 完成信号 |
| --- | --- | --- | --- |
| 1 | domain tools | 消费后端 Tool Contract，去除 legacy 修补 | 工具详情和工作流工具库一致 |
| 2 | workflow pure functions | 保留展示级 binding preview | 纯函数测试覆盖关键状态 |
| 3 | node run | 节点独立运行调用 Run Preparation | 不再提示选择 real tool 的假错误 |
| 4 | workflow canvas | slot-to-slot edge 和 readiness 展示 | 用户连线后自动绑定 |
| 5 | renderer | ArtifactRendererRegistry 统一预览 | 两个节点可同时可视化 |
| 6 | task center | Task View 工作台 | 大量任务可筛选、分组、保存视图 |
| 7 | admin | Governance Registry 配置页 | 标签和分类不再硬编码 |

### 18.3 数据迁移顺序

| 顺序 | 数据对象 | 迁移动作 | 兼容策略 |
| --- | --- | --- | --- |
| 1 | Tool | 增加 contract version 和 release status | 旧工具通过 builder 生成 snapshot |
| 2 | Artifact | 补 type ref、version、role metadata | 缺失值按 legacy inference 标记为待校验 |
| 3 | Task | 区分 Task 与 ExecutionRecord | 历史任务保留原状态映射 |
| 4 | WorkflowDefinition | 增加 schema version、contract snapshot | 历史工作流加载时执行 hydrate |
| 5 | NodeTaskBinding | 保存 node-task-artifact 关系 | 历史缺失时展示未绑定，不伪造成功 |
| 6 | GovernanceRegistry | 初始化标签、分类、renderer mapping | 先导入默认配置，管理员后续修改 |

## 19. Feature Flag 与切换策略

改造必须支持渐进切换。推荐最少保留以下开关：

| Flag | 默认阶段 | 作用 |
| --- | --- | --- |
| `RUN_PREPARATION_V2_ENABLED` | G2 | 控制运行入口是否走新准备层 |
| `RESULT_MANIFEST_REQUIRED_FOR_NEW_TOOLS` | G3 | 新工具是否强制 manifest |
| `WORKFLOW_SLOT_EDGE_ENABLED` | G4 | 工作流是否使用 slot-to-slot edge |
| `NODE_TASK_BINDING_HYDRATION_ENABLED` | G4 | 保存工作流加载是否恢复任务绑定 |
| `EXECUTOR_GATEWAY_ENABLED` | G5 | 任务是否走统一 executor gateway |
| `ARTIFACT_RENDERER_REGISTRY_ENABLED` | G6 | 前端是否走 renderer registry |
| `GOVERNANCE_REGISTRY_ENABLED` | G7 | 工具标签和分类是否走治理配置 |

切换规则：

- 单个 flag 只能控制一个明确能力，不能混合控制多个模块。
- 每个 flag 必须有默认值、回滚路径、删除条件。
- G7 通过后，P0 flag 应进入删除计划，不能长期保留双轨复杂度。

## 20. 数据一致性和历史兼容

### 20.1 Artifact 一致性

- 新 ArtifactVersion 必须不可变。
- 输出文件必须有 file role。
- 缺 metadata 的历史 Artifact 不自动伪造成 ready，只能标记为 `needs_validation` 或 `legacy_unverified`。
- 跨项目使用 Artifact 必须显式导入、复制或授权，不能直接绑定临时路径。

### 20.2 Task 一致性

- Task 是用户可见运行实例。
- ExecutionRecord 是底层执行尝试。
- retry 创建新的 ExecutionRecord，不覆盖旧日志。
- cancel 只能让 Task 进入 canceled、cancel_requested 或 failed，不允许进入 success。

### 20.3 Workflow 一致性

- WorkflowDefinition 保存意图和结构。
- WorkflowRun 保存一次运行过程。
- NodeTaskBinding 保存节点和任务关系。
- ArtifactVersion binding 保存节点输出和下游输入关系。
- 历史工作流无法 hydrate 时，必须展示原因，而不是渲染成空节点。

## 21. 新工具接入终态流程

新模型或新工具上线时，最终流程固定为：

1. 注册或选择 Standard Artifact type。
2. 编写 Tool Contract。
3. 声明 input slots、output slots、参数 schema 和 resource profile。
4. 准备 example inputs 和 smoke test。
5. 根据执行方式选择 builtin、python、docker、ssh、remote_api、k8s 或 slurm。
6. 工具输出 Result Manifest。
7. 配置 renderer mapping 和下载策略。
8. 管理员配置标签、分类、研发阶段和可见范围。
9. 平台执行 contract validation 和 smoke test。
10. 发布到工具库、工作流工具库和 Agent 上下文。

接入完成标准：

- 工具详情页可一键填入示例并运行。
- 工作流中可拖拽为节点并独立运行。
- 与兼容 Artifact type 的上游节点连线后可自动绑定。
- 输出可进入结果中心、Artifact 详情和下游节点。
- 不需要改 workflow 专属代码。

## 22. 研发执行方式

### 22.1 分支和变更粒度

- 每个里程碑独立分支或独立变更组。
- 每个变更组只允许触碰一个主模块和必要调用方。
- 不把 UI 美化、契约迁移、执行器改造混在同一变更中。
- 每个变更必须带测试或验收记录。

### 22.2 代码组织要求

- API 层只做请求解析、鉴权和调用 application 层。
- application 层承载 Run Preparation、Task Command、Workflow Orchestration 等用例。
- domain 层承载 Artifact、Tool、Task、Workflow、BindingDecision 等领域对象。
- execution 层承载 executor Interface 和 adapter。
- infrastructure 层承载数据库、文件系统、远端请求等具体实现。
- frontend views 只做页面组合；领域决策进入 domain 或 workflow 纯函数。

### 22.3 测试组织要求

- Interface 测试优先于 implementation 测试。
- 每个核心 Interface 至少有 happy path、missing input、invalid type、permission denied、legacy fallback 测试。
- 每个切换门必须有一条端到端验收记录。

## 24. 最终验收矩阵

| 能力域 | 最终验收问题 | 通过标准 |
| --- | --- | --- |
| 工具扩展 | 新工具是否需要改 workflow 代码 | 不需要 |
| 运行入口 | 同一工具多入口表现是否一致 | 工具详情、节点、工作流使用同一 PreparedRun |
| Artifact | 输出是否可追踪、可下载、可下游复用 | ArtifactVersion、file role、metadata、lineage 完整 |
| 工作流 | 保存加载是否恢复任务和产物 | NodeTaskBinding 和 ArtifactVersion binding 可恢复 |
| 执行器 | SSH/Docker/Remote API 状态是否一致 | submit、inspect、cancel、logs、collect 统一 |
| 可视化 | 节点和结果中心是否复用 renderer | 同 type 使用同一 renderer descriptor |
| 任务中心 | 大量任务是否可管理 | 系统视图、筛选、分组、保存视图、详情侧栏可用 |
| 管理后台 | 标签、分类、renderer、executor 是否可治理 | 管理员可配置且有审计 |
| 兼容性 | 历史工作流是否可解释 | 能 hydrate 或明确提示不可运行原因 |
| 可回滚 | 每个切换点是否可回退 | 有 feature flag 或 legacy fallback |

## 25. 完成后的平台状态

改造完成后，平台应从“原型功能堆积”进入“标准 Artifact 驱动的平台内核”状态：

- 新工具扩展靠 Tool Contract、Artifact Registry、Result Manifest 和 executor adapter。
- 新 workflow 能力靠 slot-to-slot、Run Preparation 和 NodeTaskBinding。
- 新可视化能力靠 Renderer Registry。
- 新任务治理靠 Task View 和 ExecutionRecord。
- 新管理能力靠 Governance Registry 和 Tool Release。
- 前端页面不再散落运行语义。
- 后端服务不再为单个页面写特殊运行路径。
- 重计算扩展不再改变工作流语义。

这就是本轮改造的终点。到这个状态后，平台后续才适合继续推进 K8s / Slurm 生产化、MD 长任务、分子对接大规模筛选、Agent 可执行计划审批和更复杂的企业治理能力。
