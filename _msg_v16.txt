## §5.14.5 记的三条失效（评审抓出、我逐条复核）

- B-1 准入只挂 POST /api/v1/tasks 一个入口，而
  create_and_schedule_tool_task 有 8 处调用方（k8s smoke、结构预测/
  结构准备/口袋预测、工作流 5 处、direct 兜底）→ 工作流与领域分析
  可白嫖配额，G-9 核心失效
- A-1 settle_finished_tasks 的 SQL 无 cost 条件，过滤靠 Python continue，
  最早 batch（默认 800）条核销完后每轮取回同一批、全部 continue、返回 0
  → 永不推进，存量超 800 条时后续漏核销永久不入账
- A-2 _dcu_count 只认 gpu_count 或 gpu_index，而 gpu_index 在释放时被清空
  → 事后补核销把 DCU 分钟（权重 1.0）按 CPU 的 1/64 记账，少扣一个数量级

共同点：三条都能通过单元测试，因为测试只走一条路径、只造「cost 为空且
总数小于批量」的数据、只在 gpu_index 还在时断言。

## 两条教训

1. 缺陷不在函数里，在「谁来调它」和「数据已经变了之后还读不读得到」。
   评审该问的是「这个机制有哪些调用方」「这个字段在什么时机会被清空」。
2. 验收报告的「已落地」必须对应已合入的 commit，不能用「已开 PR」代替。
